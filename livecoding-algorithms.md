## Подход к решению и оценка сложности

### 15. Как вести себя на лайвкодинге

Лайвкодинг проверяет не столько готовый ответ, сколько процесс: как кандидат думает, общается и проверяет себя. Человек, молча выдавший идеальное решение за минуту, часто выглядит хуже того, кто рассуждал вслух и сам нашёл у себя баг.

Что делать по шагам:

1. **Уточнить условие до написания кода.** Всегда спросить про ограничения: какие размеры входных данных, может ли вход быть пустым или null, есть ли дубликаты, гарантирован ли ответ, что делать при его отсутствии. Половина «подводных камней» задачи кроется именно в уточнениях, и интервьюер ждёт этих вопросов.
2. **Проговорить идею словами.** Прежде чем писать, изложить план: «сначала решу в лоб за O(n²), потом оптимизирую через HashMap до O(n)». Это даёт интервьюеру шанс поправить курс до того, как потрачено время.
3. **Начать с наивного решения.** Рабочее медленное решение лучше красивого, но недописанного. Наивный вариант фиксирует понимание задачи и становится точкой отсчёта для оптимизации.
4. **Думать вслух, пока пишешь.** Называть, что делает каждый кусок: «здесь сохраняю ссылку на next, иначе потеряю хвост списка». Молчание заставляет интервьюера гадать, застрял кандидат или думает.
5. **Проверить код руками на примерах.** Прогнать на входе из условия, потом на краевых случаях: пустой вход, один элемент, все элементы одинаковые, n равно длине. Ошибки на границах ловятся именно так, а не перечитыванием кода.
6. **Назвать сложность и варианты улучшения.** После рабочего решения: время, память, что можно улучшить и чем за это придётся заплатить (обычно памятью).

Типовые ошибки: сразу бросаться писать код, игнорировать подсказки интервьюера (он не зря задаёт наводящие вопросы), называть переменные `a`, `b`, `tmp` и защищать баг, который уже показали. Если застрял — честно сказать «застрял, рассматриваю такой-то вариант», это нормальный рабочий сигнал, а не провал.

### 1. Big O: как оценивать сложность алгоритма

Big O задаёт асимптотическую верхнюю границу роста времени или памяти при увеличении входа `n`. Само обозначение не означает «худший случай»: отдельно называют, какую функцию оценивают — худшее, ожидаемое или амортизированное время. Константы и младшие члены отбрасываются: линейная функция `2n + 10` принадлежит O(n).

Типовые классы в порядке роста:

| Сложность | Название | Пример |
| :--- | :--- | :--- |
| O(1) | константная | доступ к элементу массива по индексу; `HashMap.get` при хороших хешах |
| O(log n) | логарифмическая | бинарный поиск в отсортированном массиве |
| O(n) | линейная | один проход по массиву |
| O(n log n) | линейно-логарифмическая | `Arrays.sort()` для объектов (TimSort), сортировка слиянием |
| O(n²) | квадратичная | пузырьковая сортировка, вложенный цикл по массиву |
| O(2ⁿ) | экспоненциальная | наивная рекурсия Фибоначчи |

Как оценивать на практике:

- Один цикл по `n` элементам — O(n). Два вложенных цикла по тому же массиву — O(n²).
- Если на каждом шаге задача делится пополам — появляется log n.
- Вызов метода внутри цикла считается со своей сложностью: `list.contains()` в цикле по `n` элементам — это O(n²), а не O(n).
- Память считается отдельно: рекурсия глубиной `n` — это O(n) памяти на стек вызовов, даже если алгоритм не создаёт объектов.
- Бывает амортизированная сложность: `ArrayList.add` в хвост — O(1) амортизированно, потому что геометрическое расширение иногда копирует O(n) элементов, но суммарная работа для n добавлений остаётся O(n). Точный коэффициент роста — деталь реализации. Вставка в начало требует O(n) сдвигов; в позицию i — O(n − i).
- Не переносите оценку учебного QuickSort на все версии JDK. В документации Java 17–21 для `Arrays.sort(int[])` указана реализация Dual-Pivot Quicksort с O(n log n) на всех наборах данных. Сортировка объектов стабильна; конкретный алгоритм — деталь реализации. При анализе памяти сортировки учитывайте стек и временные буферы, а не только новый массив.

Частое уточнение интервьюера: «а в лучшем случае?». Например, у пузырьковой сортировки с флагом «обменов не было» лучший случай O(n), у поиска в HashMap — O(1) в среднем и O(n) в худшем при плохих хэш-кодах (деревья бакетов в современных JDK помогают при коллизиях, но обещать O(log n) для любых пользовательских ключей нельзя: поиск среди несравнимых ключей с одинаковым хешем может обходить несколько ветвей).

### 12. FizzBuzz и что он на самом деле проверяет

**Условие:** вывести числа от 1 до 100. Вместо чисел, кратных 3, — `Fizz`, кратных 5 — `Buzz`, кратных и 3, и 5 — `FizzBuzz`.

**Идея:** задача-фильтр на базовую внимательность. Проверку деления на 15 надо поставить первой — иначе кратные 15 попадут в ветку `Fizz`. Либо проверять оба условия независимо и собирать строку.

```java
for (int i = 1; i <= 100; i++) {
    if (i % 15 == 0) {
        System.out.println("FizzBuzz");
    } else if (i % 3 == 0) {
        System.out.println("Fizz");
    } else if (i % 5 == 0) {
        System.out.println("Buzz");
    } else {
        System.out.println(i);
    }
}
```

**Сложность:** O(n) по времени, O(1) по памяти — здесь сложность спрашивают редко, важен сам код.

**Что на самом деле проверяет интервьюер:**

- Порядок условий: частая ошибка — начать с `i % 3`, тогда `FizzBuzz` никогда не выведется.
- Границы: цикл от 1 до 100 включительно, а не до 99 и не с 0.
- Как кандидат реагирует на развитие задачи: «а теперь добавьте правило для 7 — `Woof`». Ветвление быстро разрастается, и хороший ответ — вынести правила в список пар «делитель → слово» и идти по нему циклом, собирая строку. Это показывает умение обобщать, а не копипастить `else if`.

## Массивы, строки и стандартные коллекции

### 2. Развернуть строку и проверить палиндром

**Условие:** дано слово, например `"шалаш"`. Нужно определить, читается ли оно одинаково в обе стороны, и написать метод разворота строки.

**Идея:** палиндром проверяется двумя указателями с краёв к середине — разворачивать строку для этого не обязательно. Для разворота проще всего `StringBuilder.reverse()`, но на собеседовании часто просят руками: идём с конца и собираем новую строку.

```java
boolean isPalindrome(String s) {
    int left = 0, right = s.length() - 1;
    while (left < right) {
        if (s.charAt(left) != s.charAt(right)) {
            return false;
        }
        left++;
        right--;
    }
    return true;
}

String reverse(String s) {
    StringBuilder sb = new StringBuilder(s.length());
    for (int i = s.length() - 1; i >= 0; i--) {
        sb.append(s.charAt(i));
    }
    return sb.toString();
}
```

**Сложность:** оба метода O(n) по времени. Палиндром — O(1) по памяти, разворот — O(n) под результат. Здесь единица сравнения — `char`, то есть UTF-16 code unit: это подходит для условия с BMP-символами без составных графем. Ручной разворот ломает surrogate pair у emoji. `new StringBuilder(s).reverse().toString()` сохраняет пары; для проверки по Unicode code point можно получить `s.codePoints().toArray()` и сравнивать с краёв, потратив O(n) памяти. Даже code point не равен пользовательскому символу: нормализацию и составные графемы обсуждают отдельно.

**Частые уточнения:**

- А если нужно игнорировать регистр и знаки препинания? («А роза упала на лапу Азора») — тогда указатели пропускают не-буквы через `Character.isLetterOrDigit` и сравнивают `Character.toLowerCase`.
- Почему нельзя собирать строку через `result += c`? Потому что `String` иммутабельна, каждая конкатенация создаёт новый объект — получается O(n²) по времени. Поэтому `StringBuilder`.
- Пустая строка и строка из одного символа — палиндромы, код это обрабатывает корректно.

### 3. Two Sum: найти пару чисел с заданной суммой

**Условие:** дан массив целых чисел и число `target`. Вернуть индексы двух элементов, которые в сумме дают `target`. Пара гарантированно существует (или нужно вернуть признак отсутствия — уточнить).

**Идея:** наивное решение — два вложенных цикла, O(n²). Быстрое решение: идём по массиву один раз и для каждого числа `x` проверяем, встречали ли уже `target - x`. Встреченные числа храним в HashMap «значение → индекс».

```java
int[] twoSum(int[] nums, int target) {
    Map<Long, Integer> seen = new HashMap<>();
    for (int i = 0; i < nums.length; i++) {
        long complement = (long) target - nums[i];
        Integer j = seen.get(complement);
        if (j != null) {
            return new int[]{j, i};
        }
        seen.put((long) nums[i], i);
    }
    throw new IllegalArgumentException("Пары нет");
}
```

**Сложность:** O(n) по времени, O(n) по памяти. Наивный перебор — O(n²) по времени, O(1) по памяти.

**Частые уточнения:**

- Почему `put` идёт после проверки? Чтобы элемент не «подошёл сам себе»: для `nums = [3, 2, 4]`, `target = 6` число 3 не должно складываться само с собой.
- А если массив отсортирован? Тогда можно без дополнительной памяти: два указателя с краёв, сдвигаем тот, который нужно увеличить/уменьшить, — O(n) по времени, O(1) по памяти.
- Если нужны все пары индексов, храните список предыдущих индексов каждого значения. Время O(n + P) ожидаемо, где P — размер ответа, который может быть O(n²). Не путайте пары значений с парами индексов.
- Разность вычислена в `long`: например, `target = -2`, два `Integer.MAX_VALUE` не образуют пару, хотя их `int`-сумма переполнится в −2. Для двух указателей сумму тоже считают в `long`.

### 4. Проверить сбалансированность скобок в строке

**Условие:** строка содержит скобки `()`, `{}`, `[]`. Проверить, что каждая открывающая скобка закрыта подходящей парой и в правильном порядке. `"()[]{}"` — да, `"(]"` — нет, `"([)]"` — нет.

**Идея:** классическая задача на стек. Открывающую скобку кладём в стек. На закрывающей смотрим вершину стека: если там пара — снимаем, иначе строка невалидна. В конце стек должен быть пуст.

```java
boolean isBalanced(String s) {
    Deque<Character> stack = new ArrayDeque<>();
    for (char c : s.toCharArray()) {
        if (c == '(' || c == '{' || c == '[') {
            stack.push(c);
        } else if (c == ')' || c == '}' || c == ']') {
            if (stack.isEmpty()) {
                return false;
            }
            char open = stack.pop();
            if (c == ')' && open != '(' || c == '}' && open != '{' || c == ']' && open != '[') {
                return false;
            }
        }
    }
    return stack.isEmpty();
}
```

**Сложность:** O(n) по времени, O(n) по памяти в худшем случае (строка из одних открывающих скобок).

**Частые уточнения:**

- Какую реализацию стека взять? `ArrayDeque` — он быстрее и не синхронизирован, в отличие от устаревшего `Stack`, где основные операции синхронизированы.
- Закрывающая скобка на пустом стеке — сразу `false` (защита от `pop()` по пустому стеку).
- А если в строке есть другие символы? Их просто пропускаем, как в коде выше — надо проговорить это интервьюеру.
- Пустая строка валидна.

### 5. Найти дубликаты в массиве

**Условие:** дан массив чисел, нужно вернуть элементы, которые встречаются больше одного раза.

**Идея:** два рабочих подхода. Через `HashSet`: добавляем элементы, если `add` вернул `false` — элемент уже был, это дубликат. Через сортировку: сортируем копию массива, дубликаты оказываются рядом. Сет даёт ожидаемое линейное время; сортировка позволяет обойтись без дополнительного множества, если можно менять вход.

```java
Set<Integer> findDuplicates(int[] nums) {
    Set<Integer> seen = new HashSet<>();
    Set<Integer> duplicates = new HashSet<>();
    for (int n : nums) {
        if (!seen.add(n)) {
            duplicates.add(n);
        }
    }
    return duplicates;
}
```

**Сложность:** через Set — O(n) по времени, O(n) по памяти. Через сортировку — O(n log n) по времени плюс память конкретной реализации сортировки; сам проход по соседним элементам требует O(1). Копия для сохранения входа требует O(n), а коллекция результата учитывается отдельно.

**Частые уточнения:**

- Нужны дубликаты по одному разу или со счётчиком вхождений? Со счётчиком — `Map<Integer, Integer>` и `merge(n, 1, Integer::sum)`.
- Можно ли менять входной массив? Если да — сортировка на месте без лишней памяти.
- А если числа лежат в диапазоне от 1 до n? Тогда есть трюк с отметкой через знак элемента по индексу — O(n) по времени и O(1) по памяти, но массив портится.

### 24. Найти первый неповторяющийся элемент с сохранением порядка

Дан `int[]`: для `[4, 2, 4, 7, 2, 9]` вернуть `7`; при отсутствии ответа — `OptionalInt.empty()`. «Первый» означает самый ранний во входе, а не минимальный по значению. Уточните это до выбора структуры.

Сначала посчитаем частоты, затем пройдём исходный массив ещё раз. `HashMap` не обязана сохранять порядок, но нам это и не нужно: порядок задаёт второй проход. Одного `Set` недостаточно, поскольку повторение должно исключить значение из кандидатов, а не просто скрыть повторную запись.

```java
OptionalInt firstUnique(int[] values) {
    Map<Integer, Integer> counts = new HashMap<>();
    for (int value : values) counts.merge(value, 1, Integer::sum);
    for (int value : values) {
        if (counts.get(value) == 1) return OptionalInt.of(value);
    }
    return OptionalInt.empty();
}
```

Ожидаемое время O(n), дополнительная память O(k) для k различных значений. Сортировка за O(n log n) потеряет исходный порядок, если не сохранять индексы. Два прохода не означают O(n²): это O(n) + O(n).

Проверьте пустой массив, один элемент, все одинаковые, уникальный элемент только в конце и отрицательные числа. Не возвращайте `-1` как признак отсутствия: `-1` может быть корректным ответом. Если данные приходят потоком и повторное чтение невозможно, сохраняйте порядок первых появлений, например через `LinkedHashMap`, и после завершения потока ищите частоту 1. До конца произвольного потока окончательный ответ вообще не гарантирован: будущий элемент может повторить текущего кандидата.

### 25. Удалить дубликаты из отсортированного массива на месте

Дан отсортированный `int[]`. Нужно записать уникальные значения в начало того же массива и вернуть их количество. Например, `[1, 1, 2, 2, 4]` превращается в префикс `[1, 2, 4]`, ответ — 3. Содержимое оставшегося хвоста не определено контрактом; длина самого массива не меняется.

Указатель `read` читает вход, `write` указывает следующую свободную позицию результата. После каждой итерации префикс `[0, write)` содержит уникальные значения уже просмотренной части в исходном порядке. Важно сравнивать с последним записанным значением, а не перемещать весь хвост при каждом дубле.

```java
int uniquePrefix(int[] sorted) {
    int write = 0;
    for (int read = 0; read < sorted.length; read++) {
        if (write == 0 || sorted[read] != sorted[write - 1]) {
            sorted[write++] = sorted[read];
        }
    }
    return write;
}
```

Время O(n), дополнительная память O(1). Пустой массив возвращает 0, все одинаковые — 1. Условие сортировки существенно: на `[1, 2, 1]` алгоритм оставит оба значения 1, потому что одинаковые элементы не соседствуют.

Для `ArrayList` с удалением внутри цикла стоимость может стать O(n²) из-за сдвигов, хотя сравнений всего O(n). Можно сначала уплотнить значения через `set`, затем одним `subList(write, size).clear()` удалить хвост. Для собственного связного списка пропускайте повторные узлы переназначением `next`, сохраняя O(n) времени. Выбор представления меняет цену операций, но не сам инвариант алгоритма.

### 26. Циклически сдвинуть массив на k позиций

Нужно сдвинуть массив вправо: `[1, 2, 3, 4, 5]`, k = 2 → `[4, 5, 1, 2, 3]`. Допустим отрицательный k: он означает сдвиг влево. Требуются O(n) времени и O(1) дополнительной памяти, вход можно изменять.

Нормализуем k по длине массива и применим три разворота. Если вход представить как `A B`, где B — последние k элементов, полный разворот даст `reverse(B) reverse(A)`. Разворот каждой из этих частей отдельно даст требуемое `B A`.

```java
void rotateRight(int[] values, int k) {
    if (values.length == 0) return;
    int shift = Math.floorMod(k, values.length);
    reverseRange(values, 0, values.length - 1);
    reverseRange(values, 0, shift - 1);
    reverseRange(values, shift, values.length - 1);
}

void reverseRange(int[] values, int left, int right) {
    while (left < right) {
        int tmp = values[left];
        values[left++] = values[right];
        values[right--] = tmp;
    }
}
```

Три линейных прохода остаются O(n); временная переменная даёт O(1) памяти. Пустой массив обрабатывается до вычисления остатка: деление по модулю нуля ошибочно. `Math.floorMod` в отличие от `%` даёт подходящий неотрицательный сдвиг и для отрицательного k, включая `Integer.MIN_VALUE`.

Проверьте k = 0, k = n, k > n, k = −1 и массив из одного элемента. Частая ошибка — переносить каждый элемент k раз за O(nk) или записывать элемент на новое место, не сохранив вытесненный. Ещё один допустимый вариант — новый массив и запись по круговым индексам: проще доказать, но требует O(n) памяти.

### 27. Слить два отсортированных массива без повторной сортировки

Даны два отсортированных `int[]`, нужно вернуть новый отсортированный массив со всеми элементами, включая повторы. Для `[1, 3, 3]` и `[2, 3]` ответ `[1, 2, 3, 3, 3]`. Объединить и снова отсортировать можно, но это лишняя работа: порядок входов уже известен.

Держим указатель в каждом входе. Следующим в результат идёт меньший из двух ещё не использованных элементов. Если один вход закончился, переносим остаток другого. Инвариант: записанный префикс отсортирован и содержит ровно самые маленькие уже выбранные элементы.

```java
int[] mergeSorted(int[] left, int[] right) {
    int[] result = new int[Math.addExact(left.length, right.length)];
    int i = 0, j = 0, out = 0;
    while (i < left.length && j < right.length) {
        result[out++] = left[i] <= right[j] ? left[i++] : right[j++];
    }
    while (i < left.length) result[out++] = left[i++];
    while (j < right.length) result[out++] = right[j++];
    return result;
}
```

Время O(n + m), память O(n + m) под результат и O(1) сверх результата. Суммарная длина проверяется на переполнение; даже корректная длина не обещает, что массив поместится в heap. Выбор левого элемента при равенстве сохраняет стабильность, если обобщить алгоритм на записи с ключами.

Проверьте два пустых входа, один пустой, одинаковые значения и случай, когда все элементы одного входа меньше другого. Если первый массив заранее содержит свободный хвост нужного размера, можно писать с конца и получить O(1) дополнительной памяти: запись с начала затрёт ещё не прочитанные значения.

### 6. Бинарный поиск: итеративно и рекурсивно

**Условие:** в отсортированном массиве найти индекс элемента `key` или вернуть -1.

**Идея:** сравниваем `key` со средним элементом и отбрасываем половину массива, где `key` быть не может. Главная ловушка — вычисление середины: `(low + high) / 2` переполняется на больших индексах (сумма двух int может вылететь за `Integer.MAX_VALUE`). Правильно: `low + (high - low) / 2`.

```java
int binarySearch(int[] a, int key) {
    int low = 0, high = a.length - 1;
    while (low <= high) {
        int mid = low + (high - low) / 2; // не (low + high) / 2
        if (a[mid] == key) {
            return mid;
        } else if (key > a[mid]) {
            low = mid + 1;
        } else {
            high = mid - 1;
        }
    }
    return -1;
}

int binarySearchRec(int[] a, int key, int low, int high) {
    if (low > high) {
        return -1;
    }
    int mid = low + (high - low) / 2;
    if (a[mid] == key) {
        return mid;
    }
    return key > a[mid]
            ? binarySearchRec(a, key, mid + 1, high)
            : binarySearchRec(a, key, low, mid - 1);
}
```

**Сложность:** O(log n) по времени. Итеративная версия — O(1) по памяти, рекурсивная — O(log n) на стек вызовов.

**Частые уточнения:**

- Границы: цикл `while (low <= high)`, сдвиги `mid + 1` / `mid - 1`. Если сдвинуть на `mid` — получите бесконечный цикл.
- Что вернуть, если элементов несколько (дубликаты)? Стандартный ответ — любой; если нужен первый, после находки продолжаем поиск в левой половине.
- На практике вместо рукописного поиска используют `Arrays.binarySearch` / `Collections.binarySearch`. Частый follow-up: что они возвращают, если элемента нет? Не -1, а `-(insertion point) - 1` — позицию, куда элемент встал бы без нарушения порядка, закодированную отрицательным числом. И ещё: массив обязан быть отсортирован, иначе результат не определён — исключения не будет, просто мусор.

### 9. Частотный анализ: посчитать слова и вывести топ-N

**Условие:** дан текст. Посчитать, сколько раз встречается каждое слово, и вывести N самых частых.

**Идея:** сначала `HashMap` «слово → счётчик» через `Map.merge`. Потом сортировка записей по убыванию счётчика — удобно стримом.

```java
Map<String, Integer> countWords(String text) {
    Map<String, Integer> counts = new HashMap<>();
    for (String word : text.toLowerCase(Locale.ROOT).split("[^\\p{L}\\p{N}]+")) {
        if (!word.isEmpty()) counts.merge(word, 1, Integer::sum);
    }
    return counts;
}

List<Map.Entry<String, Integer>> topN(Map<String, Integer> counts, int n) {
    if (n < 0) throw new IllegalArgumentException("n < 0");
    return counts.entrySet().stream()
            .sorted(Map.Entry.<String, Integer>comparingByValue().reversed()
                    .thenComparing(Map.Entry.comparingByKey()))
            .limit(n)
            .toList();
}
```

Без стримов топ-N делается через `PriorityQueue` размером N — тогда не нужно сортировать всю мапу. Куча хранит N самых частых слов, наверху — наименее частое из них:

```java
List<String> topNHeap(Map<String, Integer> counts, int n) {
    if (n < 0) throw new IllegalArgumentException("n < 0");
    if (n == 0) return List.of();
    Comparator<Map.Entry<String, Integer>> bestFirst =
            Map.Entry.<String, Integer>comparingByValue().reversed()
                    .thenComparing(Map.Entry.comparingByKey());
    // наверху худший кандидат: редкий, при равенстве — позже по алфавиту
    PriorityQueue<Map.Entry<String, Integer>> heap =
            new PriorityQueue<>(bestFirst.reversed());
    for (Map.Entry<String, Integer> e : counts.entrySet()) {
        heap.offer(e);
        if (heap.size() > n) {
            heap.poll(); // вытесняем самое редкое
        }
    }
    List<String> result = new ArrayList<>();
    while (!heap.isEmpty()) {
        result.add(heap.poll().getKey());
    }
    Collections.reverse(result); // из кучи слова выходят по возрастанию частоты
    return result;
}
```

**Сложность:** подсчёт — O(m) по времени и O(k) по памяти, где m — число слов, k — число уникальных слов. Топ-N через сортировку — O(k log k), через кучу фиксированного размера — O(k log(N + 1) + N log(N + 1)) с извлечением результата, где N = min(n, k); дополнительная память O(N). Оценки не учитывают длину сравниваемых слов. При равной частоте обе версии теперь возвращают слова по алфавиту; n = 0 даёт пустой список.

**Частые уточнения:**

- `merge` выражает обновление счётчика без отдельного `containsKey`. Боксинг `Integer` при этом остаётся; атомарность зависит от реализации мапы: у обычной `HashMap` её нет. При огромном потоке слов нужен `long` или проверка переполнения счётчика.
- Как при равном счётчике сортировать по алфавиту? Добавить `.thenComparing(Map.Entry.comparingByKey())`.
- Слова разделены не только пробелами? Регулярку расширить: `split("[^\\p{L}\\p{N}]+")`.
- Ловушка в `split`: `" текст".split("\\s+")` вернёт `["", "текст"]` — ведущий пробел порождает пустую первую строку, которая попадёт в мапу как отдельное «слово». Поэтому перед split делают `strip()` или проверяют `word.isEmpty()`.

### 10. Типовые задачи на Stream API

На лайвкодинге по Stream API просят не алгоритм, а уверенное владение цепочкой «отфильтровать — преобразовать — собрать». Типовые просьбы и их решения на примере списка сотрудников:

```java
record Employee(String name, String department, int salary) {}

List<Employee> employees = List.of(
        new Employee("Иван", "IT", 200_000),
        new Employee("Мария", "HR", 150_000),
        new Employee("Пётр", "IT", 250_000),
        new Employee("Анна", "HR", 180_000));

// Отфильтровать и собрать: имена сотрудников IT с зарплатой выше порога
List<String> names = employees.stream()
        .filter(e -> e.department().equals("IT"))
        .filter(e -> e.salary() > 210_000)
        .map(Employee::name)
        .toList();

// Сгруппировать: средняя зарплата по отделам
Map<String, Double> avgByDept = employees.stream()
        .collect(Collectors.groupingBy(
                Employee::department,
                Collectors.averagingInt(Employee::salary)));

// Посчитать: количество сотрудников по отделам
Map<String, Long> countByDept = employees.stream()
        .collect(Collectors.groupingBy(
                Employee::department,
                Collectors.counting()));

// flatMap: собрать все навыки из списков в один плоский список без дубликатов
List<List<String>> skills = List.of(
        List.of("Java", "SQL"),
        List.of("Java", "Kafka"));
List<String> allSkills = skills.stream()
        .flatMap(Collection::stream)
        .distinct()
        .toList();

// Найти максимум
Optional<Employee> richest = employees.stream()
        .max(Comparator.comparingInt(Employee::salary));
```

**Частые уточнения:**

- Чем `map` отличается от `flatMap`? `map` превращает один элемент в один элемент, `flatMap` разворачивает каждый элемент в поток и склеивает потоки в один.
- Что вернёт `max` на пустом списке? Пустой `Optional` — NPE не будет, если не вызывать `get()` без проверки.
- `forEach` против `peek`: `peek` — промежуточная операция для отладки, `forEach` — терминальная. Если на стриме нет терминальной операции, промежуточные вообще не выполнятся (ленивость).
- Когда стрим медленнее цикла? На простых переборах примитивов разница есть, но незаметна; `parallelStream` на собеседовании лучше не предлагать первым — у него общий ForkJoinPool и неочевидная потокобезопасность.
- Частый follow-up — собрать мапу «отдел → сотрудник» через `Collectors.toMap`: если ключи дублируются, `toMap` бросит `IllegalStateException`, потому что по умолчанию он не знает, как слить два значения. Нужна merge-функция: `toMap(Employee::department, e -> e, (a, b) -> a)` — но чаще правильный ответ вообще `groupingBy`.
- `.toList()` (Java 16+) возвращает немодифицируемый список; это не делает его элементы immutable. `Collectors.toList()` не гарантирует тип и изменяемость результата. Если нужен изменяемый список, пишите `collect(Collectors.toCollection(ArrayList::new))`.

### 20. Анаграммы и пропавшее число в массиве

**Условие:** две строки — проверить, являются ли они анаграммами (одна получается из другой перестановкой букв: `"listen"` и `"silent"`). Затем: дан список слов, сгруппировать анаграммы вместе. Бонусная задача: массив содержит все числа от 1 до N кроме одного — найти пропавшее.

**Идея проверки анаграмм:** два слова — анаграммы, если у них совпадают частоты всех букв. Для латиницы достаточно массива из 26 счётчиков: идём по обеим строкам одновременно, для первой инкрементируем, для второй декрементируем — в конце все счётчики должны быть нулевыми. Это O(n) и один проход. Наивный вариант — отсортировать обе строки и сравнить — O(n log n), его называют первым и сразу улучшают.

```java
boolean isAnagram(String a, String b) {
    if (a.length() != b.length()) return false;
    int[] counts = new int[26]; // только строчные a-z — ограничение проговорить
    for (int i = 0; i < a.length(); i++) {
        counts[a.charAt(i) - 'a']++;
        counts[b.charAt(i) - 'a']--;
    }
    for (int c : counts) {
        if (c != 0) return false;
    }
    return true;
}
```

Если алфавит не ограничен, считайте Unicode code point через `codePoints()` и `Map<Integer, Integer>`. `Map<Character, Integer>` работает с UTF-16 code unit и разделяет supplementary-символы на половины. Правила регистра и нормализации задают до подсчёта.

**Идея группировки:** у всех анаграмм одинаковый «канонический вид». Кладём слова в HashMap «канонический ключ → список». Ключ — либо отсортированные буквы слова, либо сигнатура из счётчиков.

```java
List<List<String>> groupAnagrams(String[] words) {
    Map<String, List<String>> groups = new HashMap<>();
    for (String w : words) {
        char[] chars = w.toCharArray();
        Arrays.sort(chars);
        String key = new String(chars); // "eat", "tea", "ate" -> "aet"
        groups.computeIfAbsent(key, k -> new ArrayList<>()).add(w);
    }
    return new ArrayList<>(groups.values());
}
```

Ключ через сортировку стоит O(k log k) на слово, где k — длина слова. Ключ через счёт букв — O(k): собираем строку вида `"1#0#2#..."` из 26 счётчиков. На коротких словах разницы нет, и сортировка читается проще; вариант со счётом показывают, когда интервьюер спрашивает «а быстрее можно?».

**Идея пропавшего числа:** сумма `1..N` известна — `N * (N + 1) / 2`; вычитаем фактическую сумму массива, разница — пропавшее число. Альтернатива без арифметики — XOR всех чисел от 1 до N и всех элементов массива: парные значения взаимоуничтожаются (`x ^ x == 0`), остаётся пропавшее.

```java
int missingBySum(int[] nums, int n) {
    long expected = (long) n * (n + 1L) / 2; // оба множителя вычисляем в long до умножения
    long actual = 0;
    for (int x : nums) {
        actual += x;
    }
    return (int) (expected - actual);
}

int missingByXor(int[] nums, int n) {
    int xor = 0;
    for (int i = 0; i < n; i++) {
        xor ^= i + 1;
    }
    for (int x : nums) {
        xor ^= x;
    }
    return xor;
}
```

**Сложность:** проверка анаграмм — O(n) по времени, O(1) по памяти для фиксированного алфавита. Группировка — O(w · k log k) с ключом-сортировкой, O(w · k) с ключом-счётом, где w — число слов; память O(w · k) под ключи в худшем случае и O(w) ссылок на слова. Пропавшее число — O(n) по времени, O(1) по памяти.

**Частые уточнения и edge cases:**

- Строки разной длины — сразу `false`, проверка стоит первой строкой.
- Регистр и пробелы: по умолчанию `"Listen"` и `"Silent"` — не анаграммы; если нужно игнорировать, приводим к нижнему регистру до подсчёта. Это уточнение ждут от кандидата.
- XOR-вариант не переполняется никогда — операция побитовая. Суммой пользуются чаще, но про `long` забывать нельзя: `(long) n * (n + 1L)` — приведение до умножения, и прибавление единицы тоже в `long`; иначе промежуточное вычисление может переполниться ещё в `int`.
- Пропавшее число может быть равно N (тогда массив — это `1..N-1`, разница даст N) и равно 1 — оба случая обрабатываются без отдельного кода.
- Развитие: пропавших чисел два — XOR даст их объединённый xor, дальше массив делится по любому установленному биту этого xor на две группы, в каждой пропавшее находится отдельно. А задача «найти дублирующееся число» при числах `1..N-1` при ровно одном лишнем повторении и наличии всех остальных значений — XOR диапазона и массива; при иной модели повторений нужны другие методы. XOR не проверяет корректность входа.

## Окно, префиксные суммы и интервалы

### 28. Самая длинная подстрока без повторяющихся символов

Нужно вернуть длину самой длинной непрерывной подстроки без повторов: для `"abba"` ответ 2. Это подстрока, а не подпоследовательность: нельзя произвольно пропускать символы. Здесь символом считаем UTF-16 `char`; для emoji контракт следует изменить на Unicode code point.

Окно `[left, right]` содержит только разные символы. Запоминаем последний индекс каждого символа. Когда он встретился снова внутри окна, переносим левую границу сразу после предыдущего вхождения. Обязателен `max`: прежнее вхождение могло находиться уже вне окна, и сдвигать границу назад нельзя.

```java
int longestDistinctSubstring(String text) {
    Map<Character, Integer> lastIndex = new HashMap<>();
    int left = 0, best = 0;
    for (int right = 0; right < text.length(); right++) {
        char current = text.charAt(right);
        Integer previous = lastIndex.put(current, right);
        if (previous != null) left = Math.max(left, previous + 1);
        best = Math.max(best, right - left + 1);
    }
    return best;
}
```

Ожидаемое время O(n), память O(min(n, размер алфавита)). Левая граница только растёт, поэтому окна не перебираются заново. Для `"abba"` при последней `a` прежний индекс 0 уже вне окна; присваивание `left = previous + 1` без `max` вернуло бы границу назад и ошибочно разрешило повтор `b`.

Проверьте пустую строку (0), один символ (1), все одинаковые (1), все разные и повтор на границе окна. Чтобы вернуть саму подстроку, запоминайте начало лучшего окна при обновлении `best`. Если сначала материализовать `codePoints().toArray()`, индексы будут относиться к этому массиву, а не напрямую к `String.substring`.

### 29. Максимальная сумма непрерывного подмассива

Дан непустой массив целых чисел. Нужно найти максимальную сумму непустого непрерывного подмассива. Для `[-2, 1, -3, 4, -1, 2, 1, -5, 4]` ответ 6: `[4, -1, 2, 1]`. Для `[-5, -2]` ответ −2, а не 0: пустой подмассив запрещён.

Алгоритм Кадане хранит лучший ответ среди подмассивов, заканчивающихся текущей позицией. Такой подмассив либо начинается здесь, либо продолжает лучший подмассив с предыдущей позиции. Более плохой вариант продолжать бессмысленно: прибавление одного и того же следующего числа не изменит их порядок.

```java
long maxSubarraySum(int[] values) {
    if (values.length == 0) throw new IllegalArgumentException("Пустой массив");
    long endingHere = values[0];
    long best = endingHere;
    for (int i = 1; i < values.length; i++) {
        endingHere = Math.max((long) values[i], endingHere + values[i]);
        best = Math.max(best, endingHere);
    }
    return best;
}
```

Время O(n), дополнительная память O(1). Используем `long`, потому что сумма нескольких корректных `int` может выйти за диапазон `int`. Инициализация первым элементом обеспечивает правильный ответ для полностью отрицательного массива. Инициализация нулём подменяет условие задачей с разрешённым пустым ответом.

Для восстановления границ храните начало текущего кандидата; когда выгоднее начать заново, меняйте его на i. При улучшении глобального ответа копируйте обе границы. Отдельно определите правило при равных суммах: первый, самый короткий или любой. Проверьте единственный отрицательный элемент, все нули, максимум в начале и в конце. Сортировка здесь разрушает требование непрерывности.

### 30. Посчитать подмассивы с заданной суммой через префиксы

Дан `int[]`, в котором могут быть отрицательные числа и нули. Нужно посчитать число непрерывных непустых подмассивов с суммой k. Для `[1, -1, 0]`, k = 0 ответ 3: `[1, -1]`, `[0]`, `[1, -1, 0]`.

Пусть `prefix[r]` — сумма элементов до текущего правого края включительно. Сумма участка равна k, когда ранее встречался префикс `prefix[r] − k`. Поэтому хранить нужно число появлений каждого префикса, а не только факт наличия или последний индекс. Нулевой префикс до начала массива регистрируем один раз: это позволяет учитывать участки, начинающиеся с индекса 0.

```java
long countSubarrays(int[] values, int k) {
    Map<Long, Long> frequencies = new HashMap<>();
    frequencies.put(0L, 1L);
    long prefix = 0, answer = 0;
    for (int value : values) {
        prefix += value;
        answer += frequencies.getOrDefault(prefix - k, 0L);
        frequencies.merge(prefix, 1L, Long::sum);
    }
    return answer;
}
```

Время O(n) ожидаемо, память O(n). Ответ и суммы — `long`: для n нулей ответ n(n + 1)/2, что быстро превышает `int`. Сначала считаем совпадения, потом регистрируем текущий префикс, иначе при k = 0 посчитаем ещё и пустой участок.

Пустой вход даёт 0. Проверьте один ноль, несколько нулей, отсутствие совпадений и отрицательный k. Обычное окно с правилом «сумма слишком велика — сдвинь левую границу» здесь не работает: отрицательное число способно уменьшить сумму при расширении. Метод префиксов не требует монотонности элементов.

### 31. Объединить пересекающиеся интервалы

Дан список замкнутых интервалов `[start, end]`, где start ≤ end. Нужно вернуть объединение: `[1, 3], [2, 6], [8, 10]` → `[1, 6], [8, 10]`. Соприкосновение в одной точке считается пересечением: `[1, 2]` и `[2, 3]` объединяются. Для полуоткрытых интервалов правило границы будет другим.

Сортируем копию по началу. После этого новый интервал либо пересекает последний накопленный и расширяет его конец, либо начинает следующую независимую группу. С более ранними группами сравнивать не нужно: они уже закончились до начала текущей.

```java
record Interval(int start, int end) {
    Interval {
        if (start > end) throw new IllegalArgumentException("start > end");
    }
}

List<Interval> mergeIntervals(List<Interval> intervals) {
    List<Interval> sorted = new ArrayList<>(intervals);
    sorted.sort(Comparator.comparingInt(Interval::start));
    List<Interval> result = new ArrayList<>();
    for (Interval current : sorted) {
        if (result.isEmpty() || result.get(result.size() - 1).end() < current.start()) {
            result.add(current);
        } else {
            Interval previous = result.remove(result.size() - 1);
            result.add(new Interval(previous.start(), Math.max(previous.end(), current.end())));
        }
    }
    return result;
}
```

Время O(n log n), память O(n) для копии, результата и сортировки. Входной список не меняется, элементы immutable. Сравнение через `comparingInt` не переполняется, в отличие от `a.start() - b.start()`.

Проверьте пустой список, вложенные интервалы, одинаковые начала, точечный `[2, 2]` и полностью раздельные интервалы. Частая ошибка — заменить конец текущим `end`, сократив большой интервал при вложенном маленьком. Здесь нужен `max`. Для расписаний полезно отдельно спросить, конфликтуют ли встречи, одна из которых заканчивается ровно в момент начала другой.

## Связные списки, деревья и графы

### 7. Развернуть односвязный список

**Условие:** дан head односвязного списка `1 -> 2 -> 3 -> null`, развернуть его в `3 -> 2 -> 1 -> null` и вернуть новый head.

**Идея:** итеративно идём по списку с тремя указателями: `prev`, `curr`, `next`. На каждом шаге разворачиваем ссылку `curr.next` на `prev` и сдвигаемся вперёд. Рекурсивный вариант короче, но тратит стек.

```java
class Node {
    int value;
    Node next;

    Node(int value) {
        this.value = value;
    }
}

Node reverse(Node head) {
    Node prev = null;
    Node curr = head;
    while (curr != null) {
        Node next = curr.next; // запомнили, иначе потеряем хвост
        curr.next = prev;
        prev = curr;
        curr = next;
    }
    return prev;
}

Node reverseRec(Node head) {
    if (head == null || head.next == null) {
        return head;
    }
    Node newHead = reverseRec(head.next);
    head.next.next = head;
    head.next = null;
    return newHead;
}
```

**Сложность:** обе версии O(n) по времени. Итеративная — O(1) по памяти, рекурсивная — O(n) на стек, на длинном списке получите `StackOverflowError`.

**Частые уточнения:**

- Что вернётся для пустого списка и списка из одного элемента? Итеративный код вернёт `null` и тот же узел — корректно.
- Частая ошибка — потерять ссылку на хвост до разворота `curr.next`. Поэтому `next` сохраняется первой строкой цикла.
- Как проверить? Прогнать руками на списке из 2–3 элементов, вслух.

### 8. Найти N-й элемент с конца односвязного списка

**Условие:** дан head односвязного списка и число `n`. Вернуть n-й элемент с конца за один проход, длину списка заранее не считать.

**Идея:** два указателя с зазором в `n` шагов. Сначала `fast` уходит на `n` позиций вперёд, потом оба идут вместе, пока `fast` не упрётся в конец. В этот момент `slow` стоит ровно на n-м элементе с конца.

```java
Node nthFromEnd(Node head, int n) {
    if (n <= 0) throw new IllegalArgumentException("n должно быть положительным");
    Node fast = head;
    Node slow = head;
    for (int i = 0; i < n; i++) {
        if (fast == null) {
            throw new IllegalArgumentException("n больше длины списка");
        }
        fast = fast.next;
    }
    while (fast != null) {
        fast = fast.next;
        slow = slow.next;
    }
    return slow;
}
```

**Сложность:** O(L) по времени, где L — длина списка, и O(1) по памяти. Наивное решение «посчитать длину, потом пройти до L - n» — два прохода, тот же O(L), но интервьюер ждёт именно два указателя.

**Частые уточнения:**

- n равно длине списка — должен вернуться head. Проверьте: `fast` дойдёт до `null`, цикл `while` не выполнится, вернётся `slow == head`.
- n больше длины или n <= 0 — спросить, что делать: бросить исключение или вернуть null.
- Тот же приём решает задачи «найти середину списка» (fast шагает по два узла) и «найти цикл в списке» (алгоритм Флойда).

### 16. Проверить цикл в односвязном списке: алгоритм Флойда

**Условие:** дан односвязный список, в котором `next` последнего узла может указывать на один из предыдущих узлов (цикл). Определить, есть ли цикл. Классическое развитие — найти узел, где цикл начинается.

**Наивное решение** — складывать посещённые узлы в `HashSet`: O(N) времени и O(N) памяти. Его предложить стоит, но интервьюер сразу спросит «а за O(1) по памяти?».

**Алгоритм Флойда («черепаха и заяц»):** два указателя, медленный делает шаг, быстрый — два. Если цикла нет, быстрый дойдёт до конца. Если цикл есть, указатели обязательно встретятся внутри него: как только оба оказались в цикле, быстрый сокращает отставание на один узел за шаг — «догнать» он не может промахнуться.

```java
boolean hasCycle(Node head) {
    Node slow = head, fast = head;
    while (fast != null && fast.next != null) {
        slow = slow.next;
        fast = fast.next.next;
        if (slow == fast) return true;   // встретились — цикл есть
    }
    return false;                        // быстрый дошёл до конца
}
```

Сложность O(N) по времени, O(1) по памяти.

**Найти начало цикла (вторая фаза):** после встречи один указатель ставится на `head`, дальше оба идут по одному шагу — встретятся ровно в узле начала цикла.

```java
Node findCycleStart(Node head) {
    Node slow = head, fast = head;
    while (fast != null && fast.next != null) {
        slow = slow.next;
        fast = fast.next.next;
        if (slow == fast) {
            slow = head;
            while (slow != fast) { slow = slow.next; fast = fast.next; }
            return slow;
        }
    }
    return null;
}
```

Почему это работает, объясняется арифметикой длин: если до цикла `a` узлов, а точка встречи отстоит от начала цикла на `b`, то из равенства пройденных путей следует, что путь от точки встречи до начала цикла кратен его длине минус `a` — поэтому синхронный проход от `head` и от точки встречи сходится в начале цикла.

Edge cases для проговаривания: пустой список, один узел без цикла, узел со ссылкой сам на себя, цикл на весь список. Эта же пара техник решает задачу «найти середину списка» (быстрый дошёл до конца — медленный в середине).

### 17. Бинарное дерево: обходы и проверка на BST

**Условие:** дано бинарное дерево. Вывести значения узлов в порядках inorder, preorder, postorder и проверить, является ли дерево бинарным деревом поиска (BST).

**Идея:** три обхода отличаются только местом, где обрабатывается сам узел: preorder — до потомков (корень, лево, право), inorder — между ними (лево, корень, право), postorder — после (лево, право, корень). Удобный мнемонический факт: inorder по BST выдаёт значения в отсортированном порядке. Для проверки BST недостаточно сравнить узел с родителем — это главная ловушка задачи, ниже разобрано почему.

```java
class TreeNode {
    int value;
    TreeNode left;
    TreeNode right;

    TreeNode(int value) {
        this.value = value;
    }
}

// Рекурсивные обходы
void inorder(TreeNode node) {   // лево - корень - право
    if (node == null) return;
    inorder(node.left);
    System.out.println(node.value);
    inorder(node.right);
}

void preorder(TreeNode node) {  // корень - лево - право
    if (node == null) return;
    System.out.println(node.value);
    preorder(node.left);
    preorder(node.right);
}

void postorder(TreeNode node) { // лево - право - корень
    if (node == null) return;
    postorder(node.left);
    postorder(node.right);
    System.out.println(node.value);
}

// Итеративный inorder через стек
void inorderIterative(TreeNode root) {
    Deque<TreeNode> stack = new ArrayDeque<>();
    TreeNode curr = root;
    while (curr != null || !stack.isEmpty()) {
        while (curr != null) {   // спускаемся влево до упора, всё кладём в стек
            stack.push(curr);
            curr = curr.left;
        }
        curr = stack.pop();      // крайний левый необработанный узел
        System.out.println(curr.value);
        curr = curr.right;       // переходим в правое поддерево
    }
}
```

Итеративная версия имитирует рекурсию руками: стек заменяет стек вызовов. Сначала весь левый «хребет» кладётся в стек, затем узлы достаются и обрабатываются, после каждого — шаг вправо, и цикл повторяется.

Проверка на BST. Определение: для каждого узла все значения в левом поддереве меньше него, все в правом — больше. Ключевое слово — «все», а не «непосредственные потомки». Поэтому сравнение узла только с родителем не работает: в левом поддереве корня может сидеть узел, больше самого корня — с родителем он согласован, а инвариант нарушен. Правильное решение — тащить вниз по рекурсии допустимый диапазон (min, max), который сужается на каждом шаге:

```java
boolean isValidBst(TreeNode root) {
    return checkRange(root, Long.MIN_VALUE, Long.MAX_VALUE);
}

private boolean checkRange(TreeNode node, long min, long max) {
    if (node == null) return true;
    if (node.value <= min || node.value >= max) return false;
    return checkRange(node.left, min, node.value)
            && checkRange(node.right, node.value, max);
}
```

Границы — `long`, а не `int`: иначе дерево из одного узла со значением `Integer.MIN_VALUE` или `Integer.MAX_VALUE` даст ложный отрицательный ответ. Неравенства строгие, потому что в классическом условии дубликаты в BST запрещены — но это стоит уточнить у интервьюера.

**Сложность:** обходы и проверка — O(n) по времени, каждый узел посещается один раз. По памяти — O(h), где h — высота дерева: для сбалансированного это O(log n), для вырожденного в список — O(n), и рекурсивная версия на таком дереве упадёт со `StackOverflowError` (ещё один аргумент в пользу итеративного обхода).

**Частые уточнения и edge cases:**

- Пустое дерево (`root == null`) — считается валидным BST, обход просто ничего не печатает.
- Альтернативная проверка BST: сделать inorder-обход и убедиться, что последовательность строго возрастает. Тот же O(n), но нужна память под результат (или одна переменная «предыдущее значение»).
- preorder нужен для копирования/сериализации дерева (корень записан до потомков), postorder — для удаления и подсчёта размера поддеревьев (потомки обработаны до родителя).
- Частый follow-up — обход в ширину (level order): он делается не стеком, а очередью (`ArrayDeque` как `Queue`): кладём корень, в цикле достаём узел, печатаем, кладём его детей.

### 18. LCA: наименьший общий предок и сумма пути

**Условие:** дано бинарное дерево (не обязательно BST) и два узла `p` и `q`, которые гарантированно есть в дереве. Найти их наименьшего общего предка (LCA) — самый глубокий узел, у которого оба находятся в поддеревьях (сам узел считается предком самого себя). Вторая задача: проверить, есть ли в дереве путь от корня до листа, сумма значений которого равна `targetSum`.

**Идея LCA:** рекурсивно ищем `p` и `q` в поддеревьях. Если оба нашлись в разных поддеревьях текущего узла — текущий узел и есть LCA. Если оба в одном поддереве — ответ придёт из рекурсии в это поддерево. Если текущий узел сам равен `p` или `q` — он кандидат: второй узел либо в его поддереве (тогда он ответ), либо найдётся выше.

```java
TreeNode lowestCommonAncestor(TreeNode root, TreeNode p, TreeNode q) {
    if (root == null || root == p || root == q) {
        return root;
    }
    TreeNode left = lowestCommonAncestor(root.left, p, q);
    TreeNode right = lowestCommonAncestor(root.right, p, q);
    if (left != null && right != null) {
        return root; // p и q в разных поддеревьях — развилка здесь
    }
    return left != null ? left : right; // пробрасываем наверх то, что нашли
}
```

Код короткий, но семантику возврата надо проговорить: метод возвращает либо найденный LCA, либо `p`/`q` (как сигнал «один из искомых — в этом поддереве»), либо `null`. Узлы сравниваются по ссылке (`==`), а не по значению — в дереве могут быть одинаковые значения.

**Идея path sum:** идём вниз, вычитая из остатка суммы значение узла. Ответ «да» — только если остаток обнулился ровно на листе (узел без детей). Промежуточное совпадение в середине пути не считается.

```java
boolean hasPathSum(TreeNode root, long targetSum) {
    if (root == null) return false;
    if (root.left == null && root.right == null) {
        return root.value == targetSum; // лист: сверяем остаток
    }
    long rest = targetSum - root.value;
    return hasPathSum(root.left, rest) || hasPathSum(root.right, rest);
}
```

**Сложность:** обе задачи — O(n) по времени (LCA в худшем случае обходит всё дерево, path sum может выйти раньше за счёт `||`), O(h) по памяти на стек рекурсии.

**Частые уточнения и edge cases:**

- Частый follow-up к LCA: а если дерево — BST? Тогда рекурсия не нужна: идём от корня, если оба значения меньше текущего — влево, оба больше — вправо, иначе текущий узел и есть LCA. Это O(h) по времени и O(1) по памяти.
- LCA при отсутствии одного из узлов в дереве: код выше молча вернёт найденный узел как ответ — некорректно. Если гарантии нет, нужен второй проход-проверка или возврат пары «найден p / найден q».
- Path sum: пустое дерево — `false`, даже если `targetSum == 0`. Путь обязан заканчиваться листом, «пустой путь» не считается.
- Значения в дереве могут быть отрицательными — поэтому нельзя прекращать поиск, когда остаток стал меньше нуля. Это любимая ловушка: с неотрицательными числами отсечение работало бы, с отрицательными — ломается.
- Развитие задачи — вернуть все такие пути (path sum II): рекурсия с текущим списком пути, на листе список копируется в ответ. Или path sum III — путь может начинаться и заканчиваться где угодно: тогда префиксные суммы от корня и HashMap «сумма → сколько раз встречалась».

### 32. Кратчайший путь в невзвешенном графе и восстановление маршрута

Дан граф списками смежности: вершины — индексы 0..V−1, все рёбра имеют одинаковую цену. Верните путь от start до goal либо пустой список, если пути нет. Для корректного start = goal путь содержит одну вершину. Входные списки не-null и содержат только допустимые индексы.

BFS обходит вершины по расстоянию от старта: сначала расстояние 0, затем 1, 2 и далее. Первый обнаруженный путь до вершины имеет минимальное число рёбер. Запомним родителя при постановке в очередь, чтобы не добавлять вершину повторно и восстановить маршрут назад.

```java
List<Integer> shortestPath(List<List<Integer>> graph, int start, int goal) {
    int size = graph.size();
    Objects.checkIndex(start, size);
    Objects.checkIndex(goal, size);
    int[] parent = new int[size];
    Arrays.fill(parent, -1);
    parent[start] = start;
    Queue<Integer> queue = new ArrayDeque<>();
    queue.add(start);
    while (!queue.isEmpty() && parent[goal] == -1) {
        int vertex = queue.remove();
        for (int next : graph.get(vertex)) {
            if (parent[next] == -1) {
                parent[next] = vertex;
                queue.add(next);
            }
        }
    }
    if (parent[goal] == -1) return List.of();
    List<Integer> path = new ArrayList<>();
    for (int v = goal; v != start; v = parent[v]) path.add(v);
    path.add(start);
    Collections.reverse(path);
    return path;
}
```

Время O(V + E), память O(V) сверх входа. Циклы, самопетли и несколько путей не ломают алгоритм: вершину отмечаем при добавлении. Если помечать только при извлечении, очередь может разрастись от повторов.

Проверьте недостижимую вершину, старт = цель и цикл. DFS может найти путь, но не гарантирует кратчайший. Для произвольных неотрицательных весов нужна Дейкстра; при отрицательных — другие алгоритмы. Важен контракт, а не слово «граф» само по себе.

## Динамическое программирование и жадный выбор

### 11. Числа Фибоначчи: рекурсия, мемоизация, итерация

**Условие:** вернуть n-е число Фибоначчи: `F(0) = 0`, `F(1) = 1`, `F(n) = F(n-1) + F(n-2)`.

**Идея:** наивная рекурсия пересчитывает одни и те же значения экспоненциальное число раз — `F(50)` будет считаться минутами. Мемоизация запоминает посчитанные значения. Итерация требует O(1) дополнительной памяти: достаточно двух последних чисел. Для всех трёх вариантов ниже допустимо 0 ≤ n ≤ 92; наивную рекурсию практически применяют только на небольших n. Мемоизация требует свежий массив размером хотя бы n + 1.

```java
// Наивная рекурсия: O(2^n) по времени — на собеседовании показать, но сразу объяснить проблему
long fibRec(int n) {
    if (n < 0 || n > 92) throw new IllegalArgumentException("0 <= n <= 92");
    if (n < 2) {
        return n;
    }
    return fibRec(n - 1) + fibRec(n - 2);
}

// Мемоизация: O(n) по времени, O(n) по памяти
long fibMemo(int n, long[] cache) {
    if (n < 0 || n > 92) throw new IllegalArgumentException("0 <= n <= 92");
    if (cache.length <= n) throw new IllegalArgumentException("Маленький cache");
    if (n < 2) {
        return n;
    }
    if (cache[n] == 0) {
        cache[n] = fibMemo(n - 1, cache) + fibMemo(n - 2, cache);
    }
    return cache[n];
}

// Итерация: O(n) по времени, O(1) по памяти
long fib(int n) {
    if (n < 0 || n > 92) throw new IllegalArgumentException("0 <= n <= 92");
    if (n == 0) return 0;
    long prev = 0, curr = 1;
    for (int i = 2; i <= n; i++) {
        long next = Math.addExact(prev, curr);
        prev = curr;
        curr = next;
    }
    return curr;
}
```

**Сложность:** см. комментарии у каждой версии. Итеративный вариант — финальный ответ.

Как вызывается `fibMemo`: `fibMemo(n, new long[n + 1])`. Ноль в кэше читается как «ещё не считали» — это безопасно, потому что `F(n) = 0` только при `n = 0`, а эта ветка обрабатывается до обращения к кэшу.

**Частые уточнения:**

- Когда ломается `long`? `F(93)` уже переполняет `long`, дальше — `BigInteger`.
- Рекурсия против итерации в целом: рекурсия читается ближе к математической формулировке, но каждый вызов — фрейм на стеке; в Java нет оптимизации хвостовой рекурсии, поэтому на больших n — `StackOverflowError`. Цикл этого лишён и быстрее.
- Мемоизация сверху вниз против динамического программирования снизу вверх: итеративная версия — это и есть DP снизу вверх с оптимизацией памяти до двух переменных.

### 33. Минимальное число монет: почему жадность требует доказательства

Даны положительные номиналы, запас каждого неограничен, и сумма amount ≥ 0. Нужно вернуть минимальное число монет либо −1, если сумму набрать нельзя. Для `[1, 3, 4]` и суммы 6 жадный выбор даёт `4 + 1 + 1`, а оптимальный — `3 + 3`. «Брать самую крупную» нельзя обосновать тем, что так обычно удобно.

Динамическое программирование: `dp[s]` — минимальное число монет для суммы s. Последней монетой может быть любой номинал coin ≤ s; тогда кандидат — `dp[s − coin] + 1`. База `dp[0] = 0`, недостижимые суммы помечены −1.

```java
int minCoins(int[] coins, int amount) {
    if (amount < 0) throw new IllegalArgumentException("amount < 0");
    for (int coin : coins) {
        if (coin <= 0) throw new IllegalArgumentException("coin <= 0");
    }
    int[] dp = new int[Math.addExact(amount, 1)];
    Arrays.fill(dp, -1);
    dp[0] = 0;
    for (int sum = 1; sum <= amount; sum++) {
        for (int coin : coins) {
            if (coin <= sum && dp[sum - coin] != -1) {
                int candidate = dp[sum - coin] + 1;
                if (dp[sum] == -1 || candidate < dp[sum]) dp[sum] = candidate;
            }
        }
    }
    return dp[amount];
}
```

Время O(amount · m), память O(amount), где m — число номиналов. Это псевдополиномиальный алгоритм: зависимость идёт от численного значения суммы, а не числа бит в её записи. Для очень больших сумм таблица не подходит; ограничения следует выяснить заранее.

Проверьте amount = 0, пустые номиналы, `[2]` для суммы 3 и дубли номиналов. Чтобы восстановить набор, храните выбранную последнюю монету. Ограниченное число купюр — другая задача: нельзя разрешать повторное использование одного и того же экземпляра через этот переход; соответствующий пример разобран в задаче про банкомат в `code-review.md`.

## Состояние, конкурентность и кэш

### 13. Потокобезопасный счётчик и producer-consumer

**Условие:** несколько потоков инкрементируют общий счётчик — написать его корректно. Затем смоделировать схему «один поток производит задачи, другой обрабатывает».

**Идея:** `count++` — это три операции (прочитать, увеличить, записать), без синхронизации потоки теряют инкременты. Проще всего взять `AtomicInteger`. Для producer-consumer в Java есть готовая `BlockingQueue` — она сама блокирует producer'а, когда очередь полна, и consumer'а, когда пуста. Руками через `wait/notify` это пишут, только если прямо попросили.

```java
class Counter {
    private final AtomicInteger count = new AtomicInteger();

    int increment() {
        return count.incrementAndGet();
    }

    int get() {
        return count.get();
    }
}
```

```java
BlockingQueue<String> queue = new ArrayBlockingQueue<>(10);

// producer
new Thread(() -> {
    try {
        for (int i = 0; i < 100; i++) {
            queue.put("task-" + i); // put блокируется, если очередь полна
        }
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
    }
}).start();

// consumer
new Thread(() -> {
    try {
        while (true) {
            String task = queue.take(); // take блокируется, если очередь пуста
            process(task);
        }
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
    }
}).start();
```

**Сложность:** у `ArrayBlockingQueue` работа с одним элементом O(1), но ожидание свободного места, данных или блокировки не ограничено этой оценкой. Аналогично нельзя обещать O(1) задержку `incrementAndGet` при конкуренции: атомарность не означает отсутствие повторов или гарантированное время завершения каждого потока. Пример consumer работает до interrupt; `process` — прикладной обработчик, который нужно определить. Для штатного окончания нужен отдельный протокол завершения.

**Частые уточнения:**

- `AtomicInteger` удобен для одного атомарного значения; `synchronized` защищает инвариант из нескольких полей. Скорость зависит от конкуренции и нагрузки, измерять нужно конкретный сценарий. Подробности — в `multithreading.md`.
- А если потоков много и все ломятся в один счётчик? Тогда CAS начинает часто проигрывать гонку и крутиться в retry-цикле. Ответ — `LongAdder`: он размазывает значение по нескольким ячейкам (потоки пишут в разные), а сумма собирается в `sum()`. Под высокой конкуренцией на запись он заметно быстрее `AtomicLong`, ценой того, что `sum()` — не мгновенный снапшот.
- Почему `InterruptedException` нельзя просто проглотить? Потому что interrupt — это просьба потоку завершиться; проглотив её, consumer никогда не остановится. Минимум — восстановить флаг через `Thread.currentThread().interrupt()`.
- Как consumer узнает, что задачи кончились? Через «poison pill» — специальный объект-маркер в очереди, при получении которого consumer выходит из цикла.
- Почему `put/take`, а не `add/remove`? `add` бросит исключение на полной очереди, `remove` — на пустой; для producer-consumer нужно именно блокирующее поведение.

### 14. LRU Cache на LinkedHashMap

**Условие:** реализовать кэш фиксированной ёмкости: при переполнении вытесняется элемент, к которому дольше всего не обращались (least recently used).

**Идея:** писать LRU с нуля — это хэш-таблица плюс двусвязный список, на собеседовании это 30+ минут аккуратного кода. Но в JDK есть `LinkedHashMap` с режимом access-order: при чтении элемент перемещается в конец, а переопределённый `removeEldestEntry` вытесняет самый старый. Если условие разрешает готовые коллекции, это компактное решение; если проверяют устройство LRU, потребуется связка map + двусвязный список.

```java
class LruCache<K, V> extends LinkedHashMap<K, V> {
    private final int capacity;

    LruCache(int capacity) {
        super(capacity, 0.75f, true); // accessOrder = true
        if (capacity < 0) throw new IllegalArgumentException("capacity < 0");
        this.capacity = capacity;
    }

    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > capacity;
    }
}
```

Третий аргумент конструктора `accessOrder = true` — ключевой: без него `LinkedHashMap` хранит порядок вставки, и вытесняться будет самый старый по вставке, а не по обращению (это FIFO, а не LRU).

**Сложность:** `get` и `put` — O(1) в среднем, как у обычной `HashMap`; память — O(capacity).

**Частые уточнения:**

- Потокобезопасен ли такой кэш? Нет, `LinkedHashMap` не синхронизирован. Минимум — обернуть вызовы в `synchronized`, для высокой конкуренции смотреть на готовые библиотеки (Caffeine).
- Неочевидный нюанс: в режиме access-order даже `get()` — структурная модификация (элемент переставляется в конец цепочки). Поэтому итерация по кэшу в одном потоке и `get()` в другом — это `ConcurrentModificationException` несмотря на то, что «мы только читаем». Обычной `HashMap` на чтении такое не грозит.
- Почему вручную это сложнее? Нужно поддерживать инвариант «мапа ссылается на узлы списка, список хранит порядок обращений» на каждом `get` и `put`; любая ошибка — утечка или вытеснение не того элемента.
- Где это встречается в жизни? Кэши в Hibernate, кэш страниц в ОС, `LinkedHashMap`-трюк исторически использовался в простых кэшах приложений.

## Практика SQL

### 19. SQL-задачи: вторая зарплата, top-N в группе, кумулятивная сумма

На Java-собеседованиях SQL почти всегда сводится к трём сценариям на одной таблице сотрудников. Дальше примеры для PostgreSQL, схема:

```sql
CREATE TABLE employees (
    id            BIGINT PRIMARY KEY,
    name          TEXT NOT NULL,
    department_id BIGINT NOT NULL,
    salary        NUMERIC NOT NULL
);
```

**Вторая по величине зарплата.** Способ первый — `LIMIT` + `OFFSET` по отсортированным значениям:

```sql
SELECT DISTINCT salary
FROM employees
ORDER BY salary DESC
LIMIT 1 OFFSET 1;
```

`DISTINCT` здесь обязателен: если двое получают максимальную зарплату, без него запрос вернёт ту же максимальную, а не вторую различную. Способ второй — подзапрос:

```sql
SELECT MAX(salary) AS second_max_salary
FROM employees
WHERE salary < (SELECT MAX(salary) FROM employees);
```

Способ третий — оконная функция:

```sql
SELECT DISTINCT salary
FROM (
    SELECT salary, DENSE_RANK() OVER (ORDER BY salary DESC) AS rnk
    FROM employees
) ranked
WHERE rnk = 2;
```

Почему вариант «MAX два раза» хрупок, спрашивают почти всегда. Он решает ровно одну формулировку — «вторая различная» — и ломается при малейшем развитии задачи: для третьей зарплаты придётся вкладывать третий подзапрос, для N-ой — N подзапросов. `DENSE_RANK` масштабируется заменой константы, а `RANK`/`ROW_NUMBER` дают выбрать семантику при ничьих. Ещё нюанс: если различных зарплат меньше двух, подзапрос с `MAX` вернёт `NULL`, а вариант с `LIMIT` не вернёт ни одной строки — разница видна, если результат дальше используется в коде.

**Top-N в каждой группе:** три самых высокооплачиваемых сотрудника в каждом отделе. Без оконных функций это мучительный самоджоин, с ними — один запрос, который может потребовать сортировку:

```sql
SELECT department_id, name, salary
FROM (
    SELECT department_id, name, salary,
           ROW_NUMBER() OVER (
               PARTITION BY department_id
               ORDER BY salary DESC, id
           ) AS rn
    FROM employees
) ranked
WHERE rn <= 3;
```

`PARTITION BY` режет строки на независимые группы, внутри каждой работает своя нумерация. Разницу трёх функций надо знать наизусть: `ROW_NUMBER` нумерует строго по порядку (при равных зарплатах порядок произвольный — в группу попадёт ровно N строк), `RANK` даёт одинаковым значениям один ранг с пропуском следующих (1, 1, 3), `DENSE_RANK` — без пропусков (1, 1, 2). «Топ-3 с учётом ничьих» — это `RANK`/`DENSE_RANK`, «ровно три строки на отдел» — `ROW_NUMBER`.

**Кумулятивная сумма:** накопительный итог зарплат по отделам в порядке роста:

```sql
SELECT
    department_id,
    name,
    salary,
    SUM(salary) OVER (
        PARTITION BY department_id
        ORDER BY salary, id
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) AS running_total
FROM employees;
```

Рамку `ROWS BETWEEN ...` стоит писать явно. По умолчанию при наличии `ORDER BY` в `OVER` PostgreSQL использует `RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW`, в которую попадают и все «равные» строки (peers): двое с одинаковой зарплатой получат одинаковый накопительный итог, а не построчный. Для кумулятивной суммы по строкам это почти всегда не то, что хотели.

**Частые уточнения:**

- Почему оконные функции нельзя использовать в `WHERE`? Они вычисляются после `WHERE`/`GROUP BY`, на этапе формирования результата — поэтому фильтрация по рангу делается через подзапрос. Отдельный оператор `QUALIFY` для этого существует, но не в PostgreSQL (он есть в Snowflake, BigQuery, Teradata) — на собеседовании безопаснее подзапрос.
- Чем `GROUP BY` отличается от `PARTITION BY`? `GROUP BY` схлопывает группу в одну строку-агрегат, `PARTITION BY` оставляет все исходные строки и добавляет к каждой вычисленное значение.
- Скользящее среднее за последние 3 строки — та же рамка: `ROWS BETWEEN 2 PRECEDING AND CURRENT ROW`.
- Вопрос на понимание плана запроса: `ORDER BY salary DESC LIMIT 1 OFFSET 1` без подходящего индекса требует чтения строк, но планировщик может применить top-N heapsort вместо полной сортировки; `DISTINCT` добавляет работу. `MAX` может читаться индексом или проходом — сравнивайте реальные планы через `EXPLAIN (ANALYZE, BUFFERS)`. На собеседовательских объёмах это неважно, но упоминание индекса — плюс.

### 21. SQL: работа с дублями и самосоединения

Схема для примеров (PostgreSQL):

```sql
CREATE TABLE users (
    id    BIGINT PRIMARY KEY,
    email TEXT NOT NULL,
    name  TEXT
);

CREATE TABLE employees (
    id         BIGINT PRIMARY KEY,
    name       TEXT NOT NULL,
    salary     NUMERIC NOT NULL,
    manager_id BIGINT REFERENCES employees (id) -- NULL у топ-менеджера
);
```

**Найти дубли email.** Классика на пару `GROUP BY` + `HAVING`:

```sql
SELECT email, COUNT(*) AS cnt
FROM users
GROUP BY email
HAVING COUNT(*) > 1;
```

`GROUP BY` схлопывает строки с одинаковым email в одну, `HAVING` фильтрует уже посчитанные группы — агрегаты в `WHERE` писать нельзя, потому что `WHERE` отрабатывает до группировки. Следом спросят: «а покажи сами строки-дубли, а не только email». Тогда либо джойн обратно на таблицу по найденным email, либо оконная функция `COUNT(*) OVER (PARTITION BY email) > 1` в подзапросе — она оставляет все исходные строки.

**Удалить дубли, оставив одну запись.** Быстрый постгресовый способ — через `ctid`, физический адрес строки:

```sql
DELETE FROM users u
USING users u2
WHERE u.email = u2.email
  AND u.ctid > u2.ctid;
```

Для каждого email остаётся строка с минимальным `ctid`. Более переносимый вариант — оконная `ROW_NUMBER` в CTE:

```sql
WITH ranked AS (
    SELECT id, ROW_NUMBER() OVER (PARTITION BY email ORDER BY id) AS rn
    FROM users
)
DELETE FROM users
WHERE id IN (SELECT id FROM ranked WHERE rn > 1);
```

`ctid` — это пара «номер страницы, номер кортежа», уникальная в таблице на текущий момент, но меняющаяся при `UPDATE` и `VACUUM FULL`. Как одноразовый приём для чистки — отлично, как замена первичного ключа — нет. Обязательный follow-up: «как не допустить дублей вообще?» — `UNIQUE (email)` на уровне БД (не проверка в коде, она проигрывает гонкам) и `INSERT ... ON CONFLICT DO NOTHING / DO UPDATE` при вставках.

**Сотрудники и менеджеры: self-join.** Таблица ссылается сама на себя через `manager_id`, поэтому джойним её дважды под разными алиасами:

```sql
SELECT e.name AS employee, m.name AS manager
FROM employees e
LEFT JOIN employees m ON m.id = e.manager_id;
```

`LEFT JOIN`, а не `JOIN`: у топ-менеджера `manager_id IS NULL`, и inner join выкинет его из результата. Следующая ступень классики — сотрудники, зарабатывающие больше своего менеджера:

```sql
SELECT e.name, e.salary, m.name AS manager, m.salary AS manager_salary
FROM employees e
JOIN employees m ON m.id = e.manager_id
WHERE e.salary > m.salary;
```

Здесь уже правильный `JOIN`: сравнивать зарплату с `NULL` бессмысленно (любое сравнение с `NULL` даёт `NULL`, то есть «не истина»), и безменеджерные сотрудники в ответ не входят по условию задачи. Один self-join показывает ровно один уровень иерархии; если попросят всю цепочку подчинённых произвольной глубины — это рекурсивный CTE `WITH RECURSIVE`, где якорный член находит корни, а рекурсивный джойнит следующий уровень.

### 22. SQL: gaps and islands и последние записи

Схема для примеров:

```sql
CREATE TABLE user_activity (
    user_id       BIGINT NOT NULL,
    activity_date DATE NOT NULL
);

CREATE TABLE customers (
    id   BIGINT PRIMARY KEY,
    name TEXT NOT NULL,
    city TEXT
);

CREATE TABLE orders (
    id          BIGINT PRIMARY KEY,
    customer_id BIGINT NOT NULL REFERENCES customers (id),
    amount      NUMERIC NOT NULL,
    status      TEXT NOT NULL, -- 'done', 'cancelled', ...
    created_at  TIMESTAMPTZ NOT NULL
);
```

**Подряд идущие дни активности (islands).** Приём: у непрерывной последовательности дат разность «дата минус порядковый номер» постоянна — пропуск дня сдвигает дату, но не номер, и константа меняется. Эта константа и есть ключ группы-«островка»:

```sql
WITH days AS (
    SELECT DISTINCT user_id, activity_date -- DISTINCT, если в день бывает несколько событий
    FROM user_activity
),
marked AS (
    SELECT user_id, activity_date,
           activity_date - (ROW_NUMBER() OVER (
               PARTITION BY user_id ORDER BY activity_date
           ))::int AS grp
    FROM days
)
SELECT user_id,
       MIN(activity_date) AS start_date,
       MAX(activity_date) AS end_date,
       COUNT(*)          AS days_in_row
FROM marked
GROUP BY user_id, grp
ORDER BY user_id, start_date;
```

В PostgreSQL дата минус целое — это дата, поэтому вычитание номера работает напрямую. Обратная задача — «gaps», найти пропуски — решается через `LEAD(activity_date) OVER (...)`: где разница между текущей и следующей датой больше дня, там дыра. Follow-up: «выведи самую длинную серию» — обернуть результат в `MAX(days_in_row)` с группировкой по пользователю; «а если в колонке timestamp, а не date» — сначала привести к `::date`.

**Последняя запись по каждой группе.** Нужен последний заказ каждого клиента. Вариант без оконных функций — джойн на агрегат:

```sql
SELECT o.*
FROM orders o
JOIN (
    SELECT customer_id, MAX(created_at) AS max_created
    FROM orders
    GROUP BY customer_id
) last ON last.customer_id = o.customer_id
      AND last.max_created  = o.created_at;
```

Вариант с оконной функцией:

```sql
SELECT id, customer_id, amount, created_at
FROM (
    SELECT o.*,
           ROW_NUMBER() OVER (PARTITION BY customer_id ORDER BY created_at DESC, id DESC) AS rn
    FROM orders o
) t
WHERE rn = 1;
```

И идиоматичный для PostgreSQL третий вариант — `SELECT DISTINCT ON (customer_id) * FROM orders ORDER BY customer_id, created_at DESC, id DESC`. Про планы: агрегация с join, окно и `DISTINCT ON` могут выбирать разные планы. Индекс `(customer_id, created_at DESC, id DESC)` может убрать сортировку, но это не гарантирует чтение только одной строки на клиента. Сравнивайте `EXPLAIN (ANALYZE, BUFFERS)`, объём данных и селективность. Функционально join на `MAX` возвращает все строки с максимальным временем, а две другие версии с дополнительным `id DESC` выбирают ровно одну детерминированно.

**Клиенты без единого заказа.** Два канонических написания:

```sql
SELECT c.id, c.name
FROM customers c
LEFT JOIN orders o ON o.customer_id = c.id
WHERE o.id IS NULL;
```

```sql
SELECT c.id, c.name
FROM customers c
WHERE NOT EXISTS (
    SELECT 1 FROM orders o
    WHERE o.customer_id = c.id
);
```

Планировщик PostgreSQL обычно сводит оба к одному и тому же узлу anti join, так что по скорости они чаще всего одинаковы — сверяйте через `EXPLAIN`, а не по памятным правилам. `NOT EXISTS` предпочтительнее по двум причинам: он читается как условие («не существует заказа»), а не как джойн с постфильтром, а его смысл не зависит от числа совпавших заказов. Не считайте, что `LEFT JOIN ... IS NULL` обязательно материализует все совпадения: планировщик может выполнить anti join. Третий вариант, `WHERE c.id NOT IN (SELECT customer_id FROM orders)`, на собеседовании приводят как ловушку: если в подзапросе окажется хоть один `NULL`, `NOT IN` не вернёт строки с несовпавшим id: для них результат станет UNKNOWN. В приведённой схеме `customer_id NOT NULL`, поэтому именно здесь такой NULL невозможен; ловушка относится к nullable подзапросам. `NOT EXISTS` от `NULL` не страдает.

### 23. SQL: условная агрегация и трансформация вывода

Схема — те же `orders` и `customers` из задачи 22: `orders(id, customer_id, amount, status, created_at)`, `customers(id, name, city)`.

**Pivot вручную: месяцы по колонкам.** Условная агрегация — это агрегат, внутри которого строки отфильтрованы условием. Через `FILTER` (стандарт SQL, в PostgreSQL работает давно):

```sql
SELECT
    SUM(amount) FILTER (WHERE created_at >= DATE '2025-01-01' AND created_at < DATE '2025-02-01') AS jan,
    SUM(amount) FILTER (WHERE created_at >= DATE '2025-02-01' AND created_at < DATE '2025-03-01') AS feb,
    SUM(amount) FILTER (WHERE created_at >= DATE '2025-03-01' AND created_at < DATE '2025-04-01') AS mar
FROM orders;
```

То же самое через `CASE` — работает в любой СУБД:

```sql
SUM(CASE WHEN created_at >= DATE '2025-01-01' AND created_at < DATE '2025-02-01'
         THEN amount END) AS jan
```

`FILTER` короче и читается лучше, `CASE` — универсальнее. Деталь, которую проверяют: в `CASE` для `SUM` можно писать `ELSE 0` или опустить `ELSE` (тогда `NULL`, и `SUM` его проигнорирует) — результат различается, если строки есть, но ни одна не удовлетворяет условию: без `ELSE` будет NULL, с `ELSE 0` — 0. На полностью пустом входе оба `SUM` возвращают NULL, поэтому для гарантированного нуля нужен `COALESCE`. Для `COUNT` пишут `THEN 1` без `ELSE`, потому что `COUNT` считает не-`NULL` значения, и `ELSE 0` завысит счётчик. Жёсткое ограничение приёма: набор колонок фиксирован в тексте запроса, SQL не умеет «колонки по данным». Для динамического pivot в PostgreSQL есть `crosstab` из расширения `tablefunc`, но обычно перекладку строк в колонки делают уже на стороне приложения или BI.

**Средний чек по городам с 10+ заказами.** Фильтр по агрегату — это `HAVING`, сортировка и ограничение — `ORDER BY` + `LIMIT`:

```sql
SELECT c.city,
       COUNT(o.id)  AS orders_cnt,
       AVG(o.amount) AS avg_check
FROM customers c
JOIN orders o ON o.customer_id = c.id
GROUP BY c.city
HAVING COUNT(o.id) >= 10
ORDER BY avg_check DESC
LIMIT 20;
```

Здесь полезно проговорить логический порядок выполнения запроса: `FROM`/`JOIN` → `WHERE` → `GROUP BY` → `HAVING` → `SELECT` → `ORDER BY` → `LIMIT`. Из него следуют оба «почему»: почему условие на количество идёт в `HAVING` (на этапе `WHERE` групп ещё нет) и почему в `ORDER BY` виден алиас `avg_check` (сортировка после `SELECT`). Follow-up: `AVG` игнорирует `NULL` в `amount` — если «нулевой» заказ записан как `NULL`, а не как 0, средний чек завысится; и `JOIN` vs `LEFT JOIN` — города без заказов в отчёт не попадают, и это надо осознанно выбрать.

**Отчёт за месяц одним запросом.** Число заказов, выручка, средний чек и доля отменённых — четыре выражения с условной агрегацией над одним сканом:

```sql
SELECT
    COUNT(*)                                             AS orders_cnt,
    SUM(amount) FILTER (WHERE status <> 'cancelled')     AS revenue,
    AVG(amount) FILTER (WHERE status <> 'cancelled')     AS avg_check,
    ROUND(COUNT(*) FILTER (WHERE status = 'cancelled') * 100.0 / NULLIF(COUNT(*), 0), 2) AS cancelled_pct
FROM orders
WHERE created_at >= DATE '2025-03-01'
  AND created_at <  DATE '2025-03-01' + INTERVAL '1 month';
```

Период задан полуоткрытым интервалом `>= начало AND < начало следующего месяца` — так не теряется последний момент месяца. Для `TIMESTAMPTZ` границы должны быть рассчитаны в бизнес-часовом поясе: литерал `DATE` преобразуется с учётом timezone сессии. Например, для московского марта задайте `TIMESTAMPTZ '2025-03-01 00:00:00 Europe/Moscow'` и такую же границу 1 апреля. Предикат по исходной колонке позволяет использовать обычный индекс, но выбор индекса остаётся за планировщиком. Написание `created_at::date = ...` или `date_trunc('month', created_at) = ...` обычно не позволяет использовать обычный индекс по колонке для этого условия (может помочь индекс по выражению), это частый вопрос следом. Второй момент — `* 100.0` перед делением: без него `bigint / bigint` даст целочисленное деление, и доля отменённых почти всегда будет 0. Умножение на число с точкой заранее приводит выражение к `NUMERIC`, и `ROUND` получает что округлять. Спорное место, которое стоит проговорить: считаем ли выручку с отменёнными — здесь решено, что нет, но на собеседовании это вопрос к постановщику задачи, а не к SQL.
