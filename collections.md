## Контракты коллекций и выбор структуры

### 4. Какова иерархия интерфейсов в Java Collections Framework?

Java Collections Framework (JCF) состоит из двух основных корней: интерфейса `java.util.Collection` и интерфейса `java.util.Map`. Схема ниже показывает базовые связи Java 17; новые интерфейсы упорядоченного обхода Java 21 разобраны в вопросе 29.

```text
                     Iterable<T>
                          |
                      Collection<T>
                   /      |        \
             List<T>   Set<T>     Queue<T>
               |          |          |  (Deque расширяет Queue)
          ArrayList    HashSet    ArrayDeque
          LinkedList   TreeSet    PriorityQueue
                       LinkedHashSet

                       Map<K, V>  (SortedMap/NavigableMap расширяют Map)
                     /     |     \
               HashMap  TreeMap  Hashtable
               LinkedHashMap    ConcurrentHashMap
```

- **`List`** — упорядоченная коллекция с доступом по индексу (допускает дубликаты). Основные реализации: `ArrayList`, `LinkedList`, `Vector`.
- **`Set`** — коллекция уникальных элементов (без дубликатов). Реализации: `HashSet` (на базе `HashMap`), `TreeSet` (на базе красно-черного дерева), `LinkedHashSet`.
- **`Queue` / `Deque`** — коллекции для работы по принципу FIFO/LIFO. Реализации: `ArrayDeque`, `LinkedList`, `PriorityQueue`.
- **`Map`** — структура «ключ-значение». Ключи уникальны. Реализации: `HashMap`, `TreeMap`, `LinkedHashMap`, `ConcurrentHashMap`.

Нюансы, о которых спрашивают:

- `Map` **не** наследуется от `Collection` — это отдельная ветка. Но представления `keySet()`, `values()`, `entrySet()` возвращают `Set`/`Collection`, и через них мапу можно обходить for-each.
- У обеих веток есть свои расширения: у `Map` — `SortedMap`/`NavigableMap` (навигация по отсортированным ключам, реализует `TreeMap`) и `ConcurrentMap` (атомарные `putIfAbsent`/`compute`/`merge`, реализует `ConcurrentHashMap`); у `Queue` — `Deque` (двусторонняя очередь) и `BlockingQueue` (блокирующая, для producer-consumer).
- Между интерфейсами и реализациями стоят абстрактные классы (`AbstractList`, `AbstractMap`...) с базовыми реализациями — на собеседовании достаточно упомянуть, что они есть.
- `Collection` сам наследуется от `Iterable` — поэтому любая коллекция работает в for-each (см. вопрос 9).

### 20. Как выбрать коллекцию под задачу: практическая шпаргалка

На собеседовании регулярно просят не знание устройства, а выбор: «что возьмёте для...». Сводка:

**Список:**
- Обычно начинают с `ArrayList`: быстрый доступ по индексу и компактное хранение.
- Для работы с двух концов без доступа по индексу — `ArrayDeque` (это `Deque`, а не `List`).
- `LinkedList` — почти никогда (см. вопрос 2).
- Чтение из многих потоков, редкие записи — `CopyOnWriteArrayList`.

**Мапа:**
- Дефолт — `HashMap`.
- Нужен порядок вставки или LRU — `LinkedHashMap`.
- Нужна сортировка по ключу или range-запросы — `TreeMap`.
- Многопоточность — `ConcurrentHashMap`.
- Ключи — enum — `EnumMap`. Метаданные по жизненному циклу ключа — `WeakHashMap`; для ограниченного по размеру или времени жизни кэша нужен отдельный механизм.

**Множество:**
- Дефолт — `HashSet`. Порядок вставки — `LinkedHashSet`. Сортировка — `TreeSet`.

**Очередь:**
- Однопоточная FIFO/стек — `ArrayDeque`. Приоритетная — `PriorityQueue`.
- Producer-consumer — `LinkedBlockingQueue` с явной ёмкостью.
- Прямая передача задач — `SynchronousQueue`. Отложенные задачи — `DelayQueue`.

Три вопроса, которыми интервьюер проверяет осмысленность выбора: «какая сложность у основных операций выбранной структуры?», «а что будет в многопоточной среде?», «а если порядок важен?». Если на каждый из них есть ответ без паузы — тема закрыта.

### 25. Как устроены equals и hashCode у List, Set и Map?

Равенство определяется контрактом интерфейса, а не конкретной реализацией. У списков важны одинаковый размер, равные элементы и одинаковый порядок. У множеств важен состав элементов, а порядок обхода не влияет на равенство. У карт сравниваются отображения ключей в значения, а порядок вставки также не учитывается.

```java
System.out.println(new ArrayList<>(List.of(1, 2))
        .equals(new LinkedList<>(List.of(1, 2)))); // true
System.out.println(Set.of(1, 2).equals(new LinkedHashSet<>(List.of(2, 1)))); // true
System.out.println(List.of(1, 2).equals(List.of(2, 1))); // false
System.out.println(List.of(1, 2).equals(Set.of(1, 2)));  // false
```

Совместимые реализации этих интерфейсов обязаны иметь согласованный hashCode, поэтому HashSet и LinkedHashSet с равным составом могут иметь одинаковый хэш независимо от порядка обхода. Но изменение элемента, влияющего на его равенство, может изменить хэш всей коллекции. Использовать изменяемый список как ключ HashMap опасно даже при неизменной ссылке на сам список.

Особые реализации требуют внимания: `IdentityHashMap` намеренно использует ссылочную идентичность, а `TreeSet` с компаратором, несогласованным с equals, может нарушить общий контракт Set и даже симметричность сравнения с HashSet. Поэтому «у обоих size равен двум» ещё не доказывает корректность равенства.

Частая ошибка — сравнивать коллекции через `toString()` или `hashCode()`: строка не является контрактом равенства, коллизии хэшей законны.

### 31. Как вычесть одну коллекцию из другой, если значения повторяются?

Для левого списка `[A, A, B]` и правого `[A]` возможны два ответа. Если правая коллекция задаёт запрещённые значения, из копии левой удаляем все `A` через `removeAll`: останется `[B]`. Если каждая правая запись отменяет ровно одну левую, ответ — `[A, B]`. Это разность мультимножеств. В таком случае надо считать доступные отмены.

```java
var remaining = new HashMap<String, Integer>();
for (String value : right) remaining.merge(value, 1, Integer::sum);
var result = new ArrayList<String>();
for (String value : left) {
    int count = remaining.getOrDefault(value, 0);
    if (count == 0) result.add(value);
    else remaining.put(value, count - 1);
}
```

Результат сохраняет порядок оставшихся элементов из `left`. Значение, присутствующее только справа, ничего не удалит. Для обычного распределения хэшей ожидаемое время — O(n + m), дополнительная память помимо результата пропорциональна числу разных значений справа. Контрольный случай для интервью — две одинаковые отмены при одной покупке.

### 12. Неизменяемые коллекции: List.of/Set.of/Map.of против Arrays.asList и Collections.unmodifiableList

Три механизма, которые регулярно путают, — у них разные гарантии.

| | Изменить элемент (`set`) | Добавить/удалить | null | Связь с источником |
| :--- | :--- | :--- | :--- | :--- |
| `Arrays.asList(...)` | можно | UnsupportedOperationException | можно | живая обёртка над массивом |
| `Collections.unmodifiableList(list)` | нельзя | нельзя | можно | живая обёртка над исходным списком |
| `List.of(...)` / `Set.of(...)` / `Map.of(...)` (Java 9+) | нельзя | нельзя | нельзя (NPE) | независимая копия |

- `Arrays.asList()` возвращает список фиксированного размера поверх переданного массива: `list.set(0, x)` работает и меняет сам массив (и наоборот), а `add()`/`remove()` падают с `UnsupportedOperationException`. Это способ «смотреть на массив как на список», а не неизменяемая коллекция.
- `Collections.unmodifiableList()` — декоратор только для чтения, но не копия: если исходный список поменять, изменения видны через обёртку. Защита работает, только если ссылку на исходный список больше никто не держит.
- `List.of()`, `Set.of()`, `Map.of()` (и `copyOf`-варианты) — неизменяемые по структуре реализации: любая модификация — `UnsupportedOperationException`, null-элементы и null-ключи запрещены (NPE ещё при создании), внутри компактное хранение. Неизменяемость поверхностная: состояние изменяемого элемента всё ещё может меняться. `copyOf` отделяет структуру от исходной коллекции, но вправе переиспользовать уже подходящий неизменяемый экземпляр. Две мелочи, которые спрашивают: дубликат в `Set.of("a", "a")` — это `IllegalArgumentException` ещё при вызове фабрики, а не молчаливое слияние; у фабрик перегрузки до 10 аргументов (у `Map.of` — до 10 пар), дальше varargs-версия и `Map.ofEntries(Map.entry(k, v), ...)` для сколько угодно пар.

Частый follow-up: «как сделать неизменяемую копию существующего списка?» — `List.copyOf(list)` (Java 10+); старый вариант — `Collections.unmodifiableList(new ArrayList<>(list))`.

### 21. Что возвращает subList и почему изменение исходного списка ломает представление?

`list.subList(from, to)` возвращает представление диапазона `[from, to)`, связанное с исходным списком. Это не самостоятельная копия: `set` через представление меняет исходный список, а разрешённые удаления через представление удаляют соответствующие элементы в оригинале.

```java
List<String> all = new ArrayList<>(List.of("a", "b", "c", "d"));
List<String> middle = all.subList(1, 3);
middle.set(0, "B");
System.out.println(all); // [a, B, c, d]
middle.clear();
System.out.println(all); // [a, d]
```

Структурное изменение исходного списка через другую ссылку делает семантику старого представления неопределённой по контракту. У `ArrayList` последующая операция с ним обычно бросит CME. Это возможно и в одном потоке: многопоточность для ошибки не нужна. Неструктурный `set` исходного элемента обычно виден через представление; изменение размера снаружи — принципиально другой случай.

Для независимого диапазона создают `new ArrayList<>(all.subList(from, to))` либо `List.copyOf(...)`, если нужны неизменяемая структура и запрет null. Это поверхностная копия: вложенные изменяемые объекты остаются общими.

Ещё одна практическая опасность — удержание большого исходного массива маленьким subList. Долгоживущее представление на несколько элементов может сохранить весь исходный список в памяти. Частая ошибка — возвращать subList из сервиса как «готовую страницу», продолжая менять оригинал.

### 22. Можно ли менять Map через keySet, values и entrySet?

Эти методы возвращают связанные с картой представления. Удаление из поддерживающего изменение view удаляет соответствующую запись карты. Добавление произвольного ключа в `keySet` обычно не поддерживается: для него неизвестно значение. Изменение записи через `Map.Entry.setValue` возможно, если конкретная карта и её entry поддерживают эту операцию.

```java
Map<String, Integer> scores = new HashMap<>();
scores.put("a", 10);
scores.put("b", 20);
scores.put("c", 10);
scores.keySet().remove("b"); // удаляет b=20 из scores
scores.values().remove(10);  // удаляет одну запись с таким значением
System.out.println(scores.size()); // 1
```

Какой именно ключ будет удалён из `HashMap` через `values().remove(10)`, полагаться нельзя: порядок обхода не гарантирован. Для удаления всех подходящих записей удобнее `entrySet().removeIf(e -> e.getValue() == 10)`. Поддержка удаления зависит от изменяемости карты: у `Map.of` такая операция недоступна.

Живое view нельзя считать снимком для передачи в другой поток. `new HashSet<>(map.keySet())` отделяет набор ключей, но для обычной карты само копирование требует отсутствия конкурентных изменений или внешней синхронизации. У `ConcurrentHashMap` обход безопасен по её контракту, однако не создаёт атомарного снимка всех записей.

Частая ошибка — сохранить `keySet` как состояние «на момент вызова» и удивиться, что оно изменилось после нового `put`.

### 26. Какие ловушки есть у Arrays.asList с примитивами и у Collection.toArray?

Generics не принимает примитивный параметр типа. Поэтому `Arrays.asList(new int[]{1, 2})` создаёт `List<int[]>` с одним элементом-массивом, а не список из двух Integer. У массива ссылочного типа varargs ведёт себя иначе: `Arrays.asList(new Integer[]{1, 2})` содержит два элемента и связан с исходным массивом.

```java
int[] raw = {1, 2};
List<int[]> one = Arrays.asList(raw);
System.out.println(one.size()); // 1
List<Integer> boxed = Arrays.stream(raw).boxed().toList(); // Java 16+, неизменяемый список

List<String> names = List.of("a", "b");
Object[] objects = names.toArray();
String[] strings = names.toArray(String[]::new); // Java 11+
```

`toArray()` возвращает `Object[]`; приведение `(String[]) names.toArray()` не меняет фактический тип массива и обычно приводит к `ClassCastException`. Типизированная перегрузка создаёт массив нужного типа. Источник с несовместимыми элементами, например `List<Object>` с числом при попытке получить String[], может дать `ArrayStoreException`.

Если в `toArray(T[])` передан массив большего размера, коллекция заполняет начало и устанавливает `null` в позицию сразу после последнего элемента. Остальной хвост не обязан очищаться. Это важно при повторном использовании буфера и наличии null в самой коллекции.

Частая ошибка — считать `.boxed()` бесплатным: объекты-обёртки и ссылочный список меняют расход памяти. Если задача числовая, часто проще остаться в `IntStream` или `int[]`.

### 29. Что добавили SequencedCollection, SequencedSet и SequencedMap в Java 21?

Стабильная возможность Java 21 вводит общий контракт коллекций с определённым порядком встречи элементов: получение первого и последнего, операции на концах и представление обратного порядка. Раньше подходящие методы были разбросаны между List, Deque и конкретными классами.

```java
SequencedMap<String, Integer> map = new LinkedHashMap<>(); // Java 21+
map.put("a", 1);
map.put("b", 2);
System.out.println(map.firstEntry()); // a=1
System.out.println(map.reversed());   // {b=2, a=1}, живое представление
map.putFirst("b", 2);                 // меняет позицию существующего ключа
```

`List` и `Deque` расширяют `SequencedCollection`, `LinkedHashSet` реализует `SequencedSet`, `LinkedHashMap` — `SequencedMap`. У `HashSet` и `HashMap` порядок по-прежнему не гарантирован: добавление интерфейсов в JDK не делает их упорядоченными.

`reversed()` возвращает связанное представление, а не независимую копию. Допустимость модификаций зависит от источника. У сортированных коллекций порядок определяется компаратором, поэтому произвольная вставка «в начало» через `addFirst`/`putFirst` не поддерживается. Даже наличие метода в интерфейсе не гарантирует, что конкретная операция разрешена: применимы optional operations и `UnsupportedOperationException`.

Если проект собирается с `--release 17`, этих API нет: нужно использовать старые способы обхода или обновить минимальную версию. Частая ошибка — увидеть метод в IDE с JDK 21 и незаметно сломать сборку или runtime на Java 17.

### 2. В чем разница между ArrayList и LinkedList и какова сложность их основных операций (Big O)?

**`ArrayList`** — обёртка над динамическим массивом `Object[] elementData`.

- Начальная ёмкость по умолчанию — 10 (массив создаётся лениво, при первом `add`).
- При переполнении новая ёмкость считается как `oldCapacity + (oldCapacity >> 1)` — рост в 1.5 раза; элементы копируются через `Arrays.copyOf()` (внутри — `System.arraycopy`, быстрое поблочное копирование памяти).
- `get(i)`/`set(i)` — прямой доступ по индексу, O(1).
- Вставка/удаление в середину — O(N): всё хвостовое содержимое сдвигается на одну позицию.
- Ссылки в массиве лежат плотно — обход обычно хорошо использует кэш. Сами объекты-элементы при этом не обязаны располагаться рядом.

**`LinkedList`** — двусвязный список из узлов `Node<E>` (поля `item`, `next`, `prev`).

- `get(i)` — O(N): обход от ближайшего конца (для `i < size/2` идёт с головы, иначе с хвоста).
- Вставка в начало/конец — O(1); вставка в середину — тоже O(N), потому что до узла ещё нужно дойти. «O(1) вставка» справедлива только если ссылка на узел уже есть (например, через `ListIterator`).
- Каждая позиция требует отдельного объекта узла со ссылками `item`, `next`, `prev`. Точный размер зависит от JVM, выравнивания и compressed oops; дополнительные переходы по ссылкам обычно хуже используют кэш процессора.

| Операция | ArrayList | LinkedList |
| :--- | :---: | :---: |
| `get(i)` | **O(1)** | O(N) |
| `add(e)` в конец | **O(1)** амортиз. | **O(1)** |
| `add(0, e)` | O(N) | **O(1)** |
| вставка/удаление в середину | O(N) | O(N) |
| `remove(Object)` | O(N) | O(N) |
| дополнительная память | ссылка в массиве и резерв ёмкости | отдельный объект узла на позицию |

Важный практический вывод: несмотря на асимптотику, **LinkedList почти никогда не быстрее**. На обходах и доступе по индексу он обычно проигрывает массиву. Но серии вставок в начало без поиска позиции действительно могут быть выгодны `LinkedList`; абсолютный победитель зависит от нагрузки и измерений. Реальная ниша LinkedList — когда нужен `Deque` и обработка с двух концов, но и там обычно лучше `ArrayDeque`.

Отдельный маркер: `ArrayList` реализует интерфейс-метку `RandomAccess`. Алгоритмы (`Collections.binarySearch` и др.) проверяют его и для RandomAccess-коллекций выбирают доступ по индексу вместо итератора.

### 24. Чем size отличается от capacity и почему new ArrayList<>(100) не содержит сто элементов?

`size` — количество логических элементов, а `capacity` — доступное место во внутреннем массиве. `new ArrayList<>(100)` резервирует ёмкость, но создаёт пустой список: `get(0)` и `set(0, value)` пока недопустимы. `set` заменяет существующий элемент, не создаёт позиции.

```java
List<String> result = new ArrayList<>(100);
System.out.println(result.size()); // 0
result.add("a");                   // теперь size == 1
result.set(0, "A");                // замена существующей позиции
```

Резервирование полезно, когда число элементов известно: оно уменьшает количество расширений и копирований массива. Но большая произвольная ёмкость может зря удерживать память. `ensureCapacity` управляет резервом без добавления элементов, `trimToSize` может уменьшить резерв до size. Вызывать trim после каждого удаления не стоит: следующий add снова потребует расширения.

Для `HashMap` начальная capacity — число бакетов, а не гарантированное количество записей до resize: участвует load factor. В Java 19+ `HashMap.newHashMap(expectedMappings)` позволяет указать ожидаемое число отображений; в Java 17 подбирают начальную ёмкость с учётом коэффициента загрузки. Это оценка ресурса, а не ограничение размера: для bounded-кеша требуется собственное вытеснение.

Частая ошибка — считать заранее выделенный список аналогом `new String[100]`. Если нужны сто логических пустых мест, нужно явно выбрать модель: массив или список, заполненный значениями.

### 23. Почему `List<Integer>.remove(1)` удаляет второй элемент, а не число 1?

У `List` есть перегрузки `remove(int index)` и `remove(Object value)`. Целочисленный литерал имеет тип `int`, поэтому компилятор выбирает удаление по индексу без boxing. Обёртка `Integer` подходит к `Object` без unboxing и выбирает удаление по значению.

```java
List<Integer> numbers = new ArrayList<>(List.of(1, 2, 1));
int removed = numbers.remove(1); // индекс 1: удалено число 2
System.out.println(numbers);   // [1, 1]

boolean changed = numbers.remove(Integer.valueOf(1)); // первое вхождение значения 1
System.out.println(numbers);   // [1]
```

Возвращаемый тип здесь тоже различается: индексная версия возвращает удалённый элемент, версия по значению — boolean. Но компилятор не выбирает перегрузку по желаемому возвращаемому типу: запись `boolean ok = numbers.remove(1)` не переключит метод, а даст ошибку типов.

Статический тип ссылки меняет доступные методы. У `Collection<Integer>` нет индексной версии; `collection.remove(1)` выполнит boxing и удаление по значению. Это дополнительная причина читать сигнатуру интерфейса, через который работает код, а не только реализацию объекта.

Индекс вне диапазона приводит к `IndexOutOfBoundsException`; отсутствующее значение — к false. `removeIf(n -> n == 1)` удаляет все совпадения, поэтому это уже другой контракт. Частая ошибка при рефакторинге — заменить переменную `int` на `Integer` и незаметно изменить смысл вызова.

### 9. Iterator и Iterable: зачем нужны, как работает remove() итератора и что скрывается под капотом for-each?

`Iterable` — это обещание «по мне можно итерироваться»: единственный абстрактный метод `iterator()`, возвращающий `Iterator`. Реализуйте `Iterable` — и объект можно использовать в цикле for-each.

`Iterator` — сам курсор. `hasNext()` проверяет наличие следующего элемента и не сдвигает позицию (его можно вызывать сколько угодно раз подряд, ничего не «проскочит»). `next()` возвращает элемент и сдвигается; вызов за границей — `NoSuchElementException`.

for-each — синтаксический сахар. Компилятор разворачивает его примерно так:

```java
for (String s : list) {
    System.out.println(s);
}

// превращается в
Iterator<String> it = list.iterator();
while (it.hasNext()) {
    String s = it.next();
    System.out.println(s);
}
```

Для массивов вместо итератора генерируется обычный цикл по индексу.

Если реализация поддерживает удаление, `Iterator.remove()` позволяет удалить элемент из обычной коллекции во время данного обхода: он удаляет последний возвращённый `next()` элемент и согласует счётчик модификаций коллекции (`modCount`), поэтому `ConcurrentModificationException` не возникает. Ограничения: `remove()` можно вызвать только один раз после каждого `next()`; второй вызов подряд или вызов до первого `next()` — `IllegalStateException`. Удаление через `list.remove(x)` прямо внутри for-each нарушает договорённость об обходе и может вызвать CME; исключение не гарантировано, например если следующего вызова `next()` уже не будет. Если нужно удалять по условию без ручного итератора, есть `collection.removeIf(predicate)`.

С Java 8 у `Iterable` появились default-методы, о которых тоже спрашивают: `forEach(Consumer)` — обход без явного итератора, и `spliterator()` — объект, умеющий разбивать источник на части для обхода; именно на сплитераторах построен Stream API и его параллельные стримы.

### 6. В чем разница между Fail-Fast и Fail-Safe итераторами?

Речь о поведении итератора, когда коллекция меняется во время обхода — другим потоком или тем же, но не через сам итератор.

**Fail-Fast** (`ArrayList`, `HashMap`, `HashSet`, большинство коллекций `java.util`):

- Коллекция ведёт счётчик структурных модификаций `modCount`: каждый `add`/`remove` его инкрементирует.
- Итератор при создании запоминает `expectedModCount` и при каждом `next()` сверяет с текущим. Не сошлось — `ConcurrentModificationException`.
- «Структурных» — потому что `list.set(i, x)` счётчик не трогает: размер и структура не изменились, итератор не упадёт.

**Snapshot и weakly consistent** (`CopyOnWriteArrayList`, `ConcurrentHashMap`):

- Термин «fail-safe» не является отдельной гарантией JCF. Эти итераторы не бросают CME из-за конкурентных изменений, но устроены по-разному. Итератор `CopyOnWriteArrayList` работает со снимком массива на момент создания — изменений он просто не увидит. Итератор `ConcurrentHashMap` обходит живую таблицу и отражает изменения «как получится»: какие-то свежие записи увидит, какие-то нет, но корректное состояние гарантировано.

Две важные оговорки, которые любят выяснять следом:

1. `ConcurrentModificationException` — **best effort, а не гарантия**. Проверка `modCount` не синхронизирована, и в многопоточном коде отсутствие исключения не означает отсутствие проблем. Это механизм раннего обнаружения багов, а не инструмент синхронизации.
2. Для обычной fail-fast коллекции согласованный способ менять структуру в ходе данного обхода — поддерживаемые методы самого итератора (`remove()`, у `ListIterator` ещё `add()`/`set()`), которые согласуют `modCount`. Подробнее в вопросе 9.
3. Обёртки `Collections.synchronizedList()` и ей подобные — **не** fail-safe: внутри у них обычный fail-fast итератор. Их обход обязан идти под ручной синхронизацией по самой обёртке (`synchronized (list) { for (...) }`), иначе ловите `ConcurrentModificationException` или гонки.

### 32. Как вставить элемент во время обхода списка и какой элемент вернёт previous()?

```java
var tasks = new ArrayList<>(List.of("A", "C"));
ListIterator<String> it = tasks.listIterator();
it.next();       // A; курсор между A и C
it.add("B");     // A, B | C
it.next();       // C
it.previous();   // тоже C
it.set("D");     // [A, B, D]
```

У `ListIterator` курсор находится между элементами. `add` вставляет непосредственно перед следующим элементом; курсор оказывается после вставки. Если только что выполнен `next`, немедленный `previous` вернёт тот же элемент и сдвинет курсор назад. Метод `set` заменяет элемент, который последним вернул `next` или `previous`.

Что будет с `set` сразу после `add("B")`? На этом месте ещё нет разрешённого для замены последнего элемента, поэтому будет `IllegalStateException`. Всё это предполагает изменяемый список с поддержкой указанных операций.

### 14. Как сортируются коллекции: Collections.sort, TimSort, стабильность и сложность сортировки?

`Collections.sort(list)` с Java 8 делегирует `list.sort(null)`. Default-реализация `List.sort` копирует элементы в массив, сортирует и записывает обратно; `ArrayList` переопределяет метод и сортирует свой внутренний массив. А дальше алгоритм зависит от того, что лежит в массиве — примитивы или объекты.

**Для объектов — TimSort** (гибрид сортировки слиянием и вставками, портирован из Python, автор Тим Петерс). Массив сканируется на уже упорядоченные участки (runs), короткие досортировываются вставками, затем runs сливаются, как в merge sort.

- Сложность: худший и средний случай — **O(N log N)**, лучший (почти отсортированные данные) — **O(N)**.
- Стабильность: TimSort **стабилен** — равные по компаратору элементы сохраняют исходный относительный порядок. Это критично для объектов: два разных объекта могут быть «равны» по компаратору, и их порядок нельзя терять (иначе сломается многоуровневая сортировка — сначала по одному полю, потом по другому).
- Цена: до N/2 дополнительной памяти под буфер слияния.

**Для примитивов — Dual-Pivot QuickSort** (`Arrays.sort(int[])`, `long[]` и т.д., разработан Владимиром Ярославским). Вместо одного опорного элемента берутся два (p1 и p2), и массив режется на три части: `< p1`, между пивотами, `> p2` — за счёт этого меньше рекурсивных проходов, чем у классического QuickSort. Конкретный алгоритм и пороги зависят от примитивного типа и версии JDK: применяются также сортировка вставками и другие ветви. Для `byte`/`short`/`char` возможна counting sort.

- Устаревшее описание «всегда худший O(N²)» нельзя переносить на все современные реализации: Javadoc Java 21 описывает O(N log N) на всех входах для соответствующих перегрузок. Конкретная реализация использует дополнительные защитные ветви; расход памяти зависит от пути выполнения и очень дружелюбен к процессорному кэшу (примитивы лежат в массиве плотно).
- **Нестабилен** — и это нормально: для примитивов стабильность бессмысленна, два равных `int` неотличимы. Именно поэтому для объектов QuickSort не используют — там стабильность нужна.

Ещё есть **`Arrays.parallelSort()`** (Java 8+): массив режется на куски, сортируется параллельно в `ForkJoinPool.commonPool`, потом куски сливаются. Выигрыш зависит от размера, типа данных, ядер и стоимости сравнения; универсального порога в элементах нет.

```java
int[] primitives = {5, 1, 4, 2};
Arrays.sort(primitives);                 // DualPivotQuicksort, нестабильная (и не нужна)

String[] objects = {"b", "a", "c"};
Arrays.sort(objects);                    // TimSort, стабильная
Arrays.sort(objects, Comparator.reverseOrder());

List<User> users = getUsers();
users.sort(Comparator.comparing(User::getLastName)
                     .thenComparingInt(User::getAge));
// благодаря стабильности внутри одинаковых фамилий порядок по возрасту сохранится
```

Порядок задаётся либо естественно — элементы реализуют `Comparable` (метод `compareTo()`), либо внешним `Comparator`. К компаратору предъявляются обычные требования отношения порядка: транзитивность, антисимметричность, `compare(x, x) == 0`. Если их нарушить, TimSort может упасть с `IllegalArgumentException: Comparison method violates its general contract!`:

```java
// сломанный компаратор: для равных элементов вернёт -1 вместо 0
Comparator<Integer> bad = (a, b) -> a > b ? 1 : -1;

// корректно
Comparator<Integer> good = Integer::compare;
```

Частый follow-up: «почему нельзя отсортировать `int[]` компаратором?» — перегрузки `Arrays.sort` с `Comparator` принимают только `T[]` (объекты). Для примитивов сначала упаковывают (`Arrays.stream(ints).boxed()`), либо используют `IntStream` с `sorted()`.

### 28. Как binarySearch кодирует отсутствие элемента и какие требования предъявляет к сортировке?

Бинарный поиск требует, чтобы вход был отсортирован в том же порядке, который используется для поиска. Отсортировать по одному компаратору, а искать по другому — нарушение предусловия; результат не обязан быть корректным. При найденном элементе возвращается неотрицательный индекс, а при отсутствии — `-(insertionPoint) - 1`.

```java
List<Integer> sorted = List.of(10, 20, 30);
int index = Collections.binarySearch(sorted, 25); // -3
int insertionPoint = -index - 1;                 // 2

List<Integer> mutable = new ArrayList<>(sorted);
mutable.add(insertionPoint, 25);                 // [10, 20, 25, 30]
```

Insertion point — позиция, куда можно вставить отсутствующий элемент, сохранив сортировку. Простое `Math.abs(index)` неверно: нулевую точку вставки тоже нужно отличать от найденного индекса 0. При нескольких равных элементах API не обещает первое или последнее вхождение; для границ диапазона нужен отдельный lower/upper bound алгоритм.

Бинарный поиск означает O(log N) сравнений, но не обязательно O(log N) времени доступа. У большого `LinkedList` без RandomAccess перемещение итератора по списку может потребовать O(N) переходов. Для частых запросов массивный список обычно уместнее; для постоянных вставок и поиска ближайшего значения можно рассмотреть TreeSet/TreeMap.

Частая ошибка — ускорять поиск вызовом `binarySearch`, забыв стоимость предварительной сортировки и её влияние на исходный порядок данных.

## Хэширование, множества и карты

### 1. Как устроена HashMap: хэширование, бакеты, коллизии, деревья и resize

`HashMap` — хэш-таблица: массив бакетов (`Node<K,V>[] table`), где каждый бакет — голова связного списка, а с Java 8 при больших коллизиях — красно-черное дерево.

**Константы по умолчанию:**

- `DEFAULT_INITIAL_CAPACITY = 16` — стартовый размер массива (сам массив создаётся лениво, при первом `put()`). Размер всегда степень двойки.
- `DEFAULT_LOAD_FACTOR = 0.75` — фактор загрузки.
- `threshold = capacity * loadFactor` — при превышении этого числа элементов массив удваивается (`resize()`). Для 16 это 12.
- `TREEIFY_THRESHOLD = 8` — внутренний порог запроса на treeify. В обычном `put` OpenJDK 21 проверка счётчика приводит к запросу при добавлении девятого узла в список из восьми; это не универсальное правило API «восемь элементов = дерево».
- `UNTREEIFY_THRESHOLD = 6` — порог для частей дерева при разделении бакета во время resize. При обычном удалении используется также проверка формы дерева; точного публичного порога «шесть» нет.
- `MIN_TREEIFY_CAPACITY = 64` — если возник запрос на treeify, но массив меньше 64, вместо дерева выполняется обычный resize: коллизия почти наверняка от плохого распределения, и дешевле расширить таблицу.

**Дополнительное хэширование.** `hashCode()` ключа не используется напрямую. Внутренний метод `hash()` перемешивает старшие биты с младшими:

```java
static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}
```

Зачем: индекс бакета вычисляется как `(n - 1) & hash`, то есть берутся только младшие `log2(n)` бит хэша (при n=16 — всего 4 бита). Если у ключей различаются только старшие биты (типично для плохих `hashCode`), без перемешивания все они попали бы в один бакет. Сдвиг `h >>> 16` «спускает» старшие биты вниз, и XOR вносит их в выбор бакета. **Null-ключ** даёт hash 0 и лежит в бакете 0 вместе с любыми другими ключами, попавшими туда по хэшу. Единственный null-ключ — следствие уникальности ключей Map, а не отдельного бакета.

**Алгоритм `put(K key, V value)`:**

1. Вычисляется `hash(key)` (см. выше).
2. Индекс бакета: `i = (n - 1) & hash`. Степень двойки как раз и нужна, чтобы заменить дорогой `hash % n` битовой маской.
3. Бакет пуст — создаётся новый `Node`.
4. Бакет занят — обход цепочки (списка или дерева): если у узла совпал хэш и ключ равен (`==` или `equals()`), значение перезаписывается; иначе новый узел добавляется в конец списка (в Java 8 — в хвост, в Java 7 добавляли в голову).
5. При достаточно длинной цепочке вызывается `treeifyBin`: при `capacity < 64` он расширяет таблицу, иначе преобразует список в дерево. Точные счётчики — детали версии реализации.
6. Если `size > threshold` — `resize()`.

**Алгоритм `get(Object key)`:** тот же `hash()` и индекс; проверяется первый узел (попадание с первого раза — самый частый случай), затем обход цепочки со сравнением сначала хэша, потом ключа. Хэш хранится в самом узле, чтобы не вызывать `hashCode()` повторно.

**Resize.** Массив удваивается (16 → 32 → 64...), `threshold` пересчитывается, элементы перераспределяются. В Java 8 пере-хэширование не нужно: для каждого узла достаточно одного бита — `e.hash & oldCap`. Если бит 0, узел остаётся на старом индексе, если 1 — переезжает на `index + oldCap`. Узлы распадаются на две цепочки (lo и hi) с сохранением относительного порядка. В старых реализациях Java 7 несинхронизированные конкурентные resize могли приводить к циклам в цепочках. Новый перенос не делает HashMap потокобезопасной: для совместных записей нужен другой контракт синхронизации.

**Красно-черные деревья (Java 8+).** При длинной цепочке и достаточной ёмкости появляется сбалансированное дерево (`TreeNode`). Для хорошо различимых хэшей или сравнимых ключей оно обеспечивает логарифмический поиск. При одинаковых хэшах и несравнимых ключах поиск равного ключа может потребовать обхода обеих ветвей и остаться линейным: дерево не даёт безусловной гарантии O(log N). Порог 8 выбран по распределению Пуассона: при идеальном хэше вероятность 8+ элементов в одном бакете около 0.00000006 — то есть дерево включается только при плохом `hashCode` или намеренной атаке (hash-flooding). Порядок в дереве — по хэшу; при равных хэшах ключи сравниваются через `Comparable`, а если класс не сравним — через `tieBreakOrder` (identity hash code).

**Обратное преобразование (untreeify).** Оно существует в обе стороны: при resize части дерева размером не больше `UNTREEIFY_THRESHOLD = 6` превращаются в списки. При удалении решение зависит и от формы дерева, поэтому заучивать один порог для всех путей не следует. Порог 6 отделён от порога 8 гистерезисом, чтобы бакет не метался туда-сюда при колебаниях размера около границы.

```java
// Узел связного списка в HashMap
static class Node<K,V> implements Map.Entry<K,V> {
    final int hash;   // кэшированный хэш ключа
    final K key;
    V value;
    Node<K,V> next;
}
```

**Почему load factor именно 0.75.** Компромисс между памятью и длиной цепочек: при 0.5 таблица реже коллидирует, но больше памяти уходит на пустые бакеты и resize случается чаще; при 1.0 память экономится, но цепочки длиннее и поиск дорожает. 0.75 — эмпирическая середина.

Частый follow-up: «какая сложность `get()` у HashMap?» Ожидаемое время `get()` — O(1) при хорошем распределении хэшей; вставка имеет амортизированную ожидаемую O(1) из-за resize. Худший случай поиска может быть O(N), в том числе с деревом при неудачных хэшах несравнимых ключей.

### 33. Почему полный обход двух HashMap одинакового размера может стоить по-разному?

Пусть в обеих картах по 50 записей, но первая создана с расчётом на сотни тысяч ключей. При обходе обычной `HashMap` итератор проходит таблицу бакетов, включая пустые. Стоимость обхода представления `entrySet()` пропорциональна сумме ёмкости таблицы и числа записей. Ожидаемая стоимость отдельного `get` не описывает стоимость подготовки полного отчёта.

Если операция выполняется ежесекундно, измерьте обход типичной и завышенной таблиц, потребляя пары ключ–значение в обоих прогонах. Сохраните число записей и их распределение, чтобы сравнение отражало изменение ёмкости. У `LinkedHashMap` обход идёт по связанным записям, его стоимость пропорциональна размеру карты; за это реализация хранит дополнительные связи. Для редкого отчёта обычно проще начать с разумной начальной ёмкости обычной карты.

### 11. Какие требования предъявляются к объектам в роли ключей HashMap?

Ключ `HashMap` должен корректно реализовывать `equals()`/`hashCode()` и не менять состояние, от которого зависит поиск, пока он используется как ключ. Полная неизменяемость объекта не обязательна: изменение поля, не влияющего на равенство и хэш, допустимо. Компилятор это не проверяет — требование продиктовано устройством хэш-таблицы.

Требования по существу:
- равенство и хэш согласованы; строго одинаковый набор полей не требуется (постоянный хэш законен, но неэффективен);
- равные по `equals()` ключи обязаны иметь одинаковый `hashCode()` (обратное не требуется — коллизии законны);
- поля, участвующие в `equals()`/`hashCode()`, не должны меняться, пока объект лежит в мапе ключом.

Что ломается при изменении ключа после `put()`:

```java
class Key {
    int id;
    Key(int id) { this.id = id; }

    @Override public int hashCode() { return id; }
    @Override public boolean equals(Object o) {
        return o instanceof Key k && k.id == id;
    }
}

Map<Key, String> map = new HashMap<>();
Key key = new Key(1);
map.put(key, "value");
key.id = 42;                       // поле участвует в hashCode
System.out.println(map.get(key));  // null — элемент «потерялся»
```

При `put()` ключ попал в бакет по старому хэшу. После изменения `get()` вычисляет новый `hashCode()` и идёт в другой бакет — записи там нет. При этом сама запись никуда не делась: она лежит в старом бакете, недостижимая ни для `get()`, ни для `remove()`. По сути это утечка. `resize()` не исправляет проблему: он переносит записи по сохранённому в узле хэшу, не пересчитывая `key.hashCode()`.

Отдельная ловушка — массивы в роли ключей: у них `equals()`/`hashCode()` унаследованы от `Object` и сравнивают ссылки. Два массива с одинаковым содержимым — разные ключи, достать значение выйдет только по той же самой ссылке.

Поэтому на практике ключами делают `String`, `Integer` и классы значений со стабильным равенством. У record ссылки компонентов final, но содержимое списка или массива внутри остаётся изменяемым; это нужно учитывать отдельно.

### 7. Как устроен HashSet и почему внутри него обычная HashMap?

`HashSet` — не самостоятельная структура данных, а тонкая обёртка над `HashMap`. Внутри лежит поле `private transient HashMap<E,Object> map`: добавляемый элемент становится ключом, а значением служит одна общая константная заглушка.

```java
// Из исходников HashSet
private static final Object PRESENT = new Object();

public boolean add(E e) {
    return map.put(e, PRESENT) == null;
}
```

- `add()`, `remove()`, `contains()` просто делегируют к `map.put()`, `map.remove()`, `map.containsKey()` — отсюда те же O(1) и те же требования к `equals()`/`hashCode()` элементов, что и у ключей `HashMap`.
- Заглушка нужна, чтобы `add()` мог вернуть `boolean`: если элемента не было, `map.put()` вернёт `null` (результат `true`), если был — вернёт `PRESENT` (результат `false`).
- Всё семейство устроено так же: `LinkedHashSet` — обёртка над `LinkedHashMap` (порядок вставки), `TreeSet` — над `TreeMap` (отсортированный порядок, O(log N)).
- Из семейства выбивается `EnumSet`: это не обёртка над мапой, а битовая маска (один `long`, если констант не больше 64). Добавление и проверка отдельной константы используют соответствующий бит. Операции над всем набором могут обрабатывать несколько машинных слов; порядок итерации соответствует объявлению констант enum. Правило простое: для enum-ключей мапы берут `EnumMap` (см. вопрос 10), для enum-множеств — `EnumSet`.

Частый follow-up: почему порядок обхода `HashSet` выглядит случайным. Потому что это порядок бакетов внутренней `HashMap` — он зависит от хэш-кодов элементов и меняется после resize.

### 34. Как вывести повторяющиеся значения по одному и в нужном порядке?

Уточните, в какой момент значение должно попасть в результат. Для входа `[A, B, B, A]` повтор у `B` обнаружился раньше, зато исходный список начинался с `A`.

```java
var seen = new HashSet<String>();
var repeats = new LinkedHashSet<String>();
for (String value : values) {
    if (!seen.add(value)) repeats.add(value);
}
```

Получится `[B, A]`. Первый набор сообщает, встречалось ли значение, второй сохраняет порядок обнаружения повторов и пропускает третье и последующие совпадения. Если нужен порядок **первого появления** повторяющихся значений, одним проходом соберите счётчики в `LinkedHashMap`, затем выведите ключи со счётчиком больше одного: получится `[A, B]`.

Оба решения требуют памяти по числу различных значений; при обычном распределении хэшей время линейно. Вызов `Collections.frequency(values, v)` для каждого элемента списка заново считает его вхождения. На большом списке это превращает один проход в квадратичную работу.

### 5. Чем HashMap отличается от TreeMap и LinkedHashMap?

Три мапы с разными гарантиями порядка и сложности.

| | HashMap | LinkedHashMap | TreeMap |
| :--- | :--- | :--- | :--- |
| Структура | хэш-таблица | хэш-таблица + двусвязный список | красно-черное дерево |
| Порядок обхода | не определён | порядок вставки или доступа | сортировка по ключу |
| get/put | O(1) амортиз. | O(1) амортиз. | O(log N) |
| null-ключ | один разрешён | один разрешён | только если Comparator допускает null (при natural ordering — NPE) |
| Требования к ключу | equals/hashCode | equals/hashCode | Comparable или Comparator |

- **`HashMap`** — выбор по умолчанию: самая быстрая, но порядок итерации не гарантирован и может измениться после resize.
- **`LinkedHashMap`** — к узлам `HashMap` добавлены ссылки `before`/`after`, связывающие все записи в двусвязный список. Порядок обхода — порядок вставки; в режиме `accessOrder=true` — порядок последнего обращения, на чём строится LRU-кэш (подробнее в вопросе 15). Цена — чуть больше памяти и работы на каждую операцию.
- **`TreeMap`** — ключи всегда отсортированы: либо по natural ordering (`Comparable`), либо по `Comparator` из конструктора. Базовые операции поиска, вставки и удаления — O(log N). Зато даёт навигацию: `firstKey()`, `lastKey()`, `floorKey()`, `ceilingKey()`, `subMap()` — то, чего у хэш-мап нет в принципе (см. вопрос 16).

Частый follow-up: «а если ключ в TreeMap не Comparable и без компаратора?» С Java 7 упадёт уже первый `put()`: вставка в пустое дерево делает контрольное сравнение `compare(key, key)` ради ранней проверки типа, так что `ClassCastException` прилетает сразу. Утверждение «первый `put()` пройдёт, второй упадёт» — верно только для Java 6, но до сих пор ходит по старым шпаргалкам.

### 35. Как описать набор разрешений через EnumSet, чтобы после обновления не появилось лишнее право?

```java
enum Action { READ, COMMENT, DELETE }
EnumSet<Action> guest = EnumSet.of(Action.READ, Action.COMMENT);
EnumSet<Action> trial = EnumSet.copyOf(guest);
trial.remove(Action.COMMENT);
```

Теперь у гостя по-прежнему два разрешения, у пробного пользователя одно. Присваивание `trial = guest` вместо копирования дало бы обеим переменным один изменяемый набор. На границе API можно вернуть `Set.copyOf(guest)`, если вызывающему коду разрешено только проверять права.

Проверка на эволюцию модели: завтра появится `EXPORT`. При явном перечислении разрешений у гостя оно останется выключенным. Выражение `EnumSet.complementOf(EnumSet.of(Action.DELETE))` сегодня строит такой же набор, но после обновления автоматически включит `EXPORT`. Для модели «доступ выдаём явно» это существенная разница.

### 15. LinkedHashMap: порядок вставки, порядок доступа и LRU-кэш из коробки

`LinkedHashMap` наследует `HashMap` и добавляет к каждой записи ссылки `before`/`after`, связывающие все элементы в двусвязный список. Хэш-таблица даёт те же O(1) на get/put, а список — предсказуемый порядок обхода.

Два режима, выбираются конструктором:

```java
// порядок вставки (по умолчанию)
Map<String, Integer> insertionOrder = new LinkedHashMap<>();

// порядок доступа: каждый get() переносит запись в «свежий» конец
Map<String, Integer> accessOrder = new LinkedHashMap<>(16, 0.75f, true);
```

- В обычном режиме обход идёт в порядке `put()` — полезно, когда нужна мапа с детерминированной итерацией (например, для вывода конфигурации).
- В режиме `accessOrder=true` любое обращение (включая `get()` и повторный `put()` существующего ключа) перемещает запись в конец списка. В начале списка оказываются самые давно не использованные записи.

На этом строится LRU-кэш без единой строчки логики — достаточно переопределить один метод:

```java
class LruCache<K, V> extends LinkedHashMap<K, V> {
    private final int maxSize;

    LruCache(int maxSize) {
        super(16, 0.75f, true);   // accessOrder = true
        this.maxSize = maxSize;
    }

    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > maxSize;  // вернуть true — и самая старая запись удалится
    }
}
```

Из коробки `removeEldestEntry` всегда возвращает `false` (никогда ничего не вытесняет). Ловушка для собеседования: `LinkedHashMap` не потокобезопасна, и в режиме accessOrder даже `get()` — структурная модификация (перелинковка списка), поэтому даже `get()` может сделать существующий итератор невалидным. CME — best effort; её отсутствие не делает доступ потокобезопасным. Для конкурентного LRU берут `ConcurrentHashMap` + ручную логику или готовый Caffeine.

### 16. TreeMap и NavigableMap: красно-черное дерево и методы навигации

`TreeMap` — сбалансированное красно-черное дерево (самобалансирующееся бинарное дерево поиска: повороты и перекраски при вставке/удалении держат высоту ~log N). Все базовые операции — `get`, `put`, `remove` — за O(log N), а обход итератором идёт в отсортированном порядке ключей.

Ключи обязаны быть взаимно сравнимыми: либо реализуют `Comparable`, либо в конструктор передан `Comparator`. Сравнение через `compareTo`/`compare` полностью заменяет `equals`: два ключа с `compareTo == 0` считаются одним и тем же ключом, даже если `equals()` вернул бы `false`. Расхождение `compareTo` с `equals` — классическая ловушка: `new BigDecimal("1.0")` и `new BigDecimal("1.00")` не равны по `equals`, но `compareTo` даёт 0, и в `TreeMap` они затрут друг друга.

Главная ценность — интерфейс `NavigableMap` с методами навигации, которых нет у хэш-мап:

```java
TreeMap<Integer, String> map = new TreeMap<>();
map.put(10, "a"); map.put(20, "b"); map.put(30, "c");

map.firstKey();          // 10
map.lastKey();           // 30
map.floorKey(25);        // 20 — наибольший ключ <= 25
map.ceilingKey(25);      // 30 — наименьший ключ >= 25
map.lowerKey(20);        // 10 — строго меньше
map.higherKey(20);       // 30 — строго больше
map.headMap(20);         // {10=a} — все ключи < 20
map.tailMap(20);         // {20=b, 30=c} — все ключи >= 20
map.subMap(10, 30);      // {10=a, 20=b} — диапазон [10, 30)
map.descendingMap();     // обратный порядок
```

Все view (`headMap`, `subMap`...) — живые представления, а не копии: изменения видны в обе стороны.

Когда `TreeMap` оправдана: нужен отсортированный порядок, range-запросы («все события за период»), поиск ближайшего значения. Если сортировка и навигация не нужны, `HashMap` обычно дешевле по времени поиска; разницу нужно оценивать на конкретных данных.

### 10. Специализированные реализации Map: WeakHashMap, EnumMap и IdentityHashMap

Три мапы для задач, где обычная `HashMap` либо не подходит, либо избыточна.

**`WeakHashMap`** — ключи хранятся через `WeakReference`. Когда на ключ не остаётся сильных ссылок, сборщик мусора удаляет объект-ключ, и запись исчезает из мапы. Классическое применение — прикрепить метаданные к объектам, чей жизненный цикл вы не контролируете (кэш «объект → доп. информация»), не создавая утечку памяти. Ловушка: `size()` может уменьшиться между двумя вызовами без всякого `remove()` — GC работает, когда захочет. Вторая ловушка тоньше: значение не должно сильно ссылаться на свой ключ (прямо или через цепочку), иначе ключ никогда не станет кандидатом на сборку и запись не удалится никогда. И ещё: записи вычищаются не мгновенно, а при ближайшем обращении к мапе, которое разгребёт `ReferenceQueue`, — «мертвые» ключи могут какое-то время висеть в таблице.

**`EnumMap`** — мапа, ключами которой могут быть только константы одного enum. Внутри — просто массив значений, индексом служит `ordinal()` константы: ни хэширования, ни бакетов, ни цепочек. Отсюда максимальная скорость и компактность, а итерация идёт в порядке объявления констант enum. null-ключ запрещён, null-значения разрешены. Если ключи — enum одного типа, `EnumMap` обычно предпочтительнее; требования к конкурентности или существующий контракт могут потребовать другой реализации.

**`IdentityHashMap`** — сравнивает ключи по ссылке (`==`) вместо `equals()` и использует `System.identityHashCode()` вместо `hashCode()`. Контракт `Map` нарушен осознанно: нужна именно идентичность объектов. Применяется в сериализации и глубоком копировании (пометить уже обработанные объекты графа, чтобы не зациклиться) и при обходах графов. Побочный плюс: не требует от ключей корректных `equals()`/`hashCode()` и не ломается при их изменении.

### 27. Чем отличаются getOrDefault, putIfAbsent, computeIfAbsent и merge при null-значениях?

Если карта допускает null, `get(k) == null` не отличает отсутствие ключа от отображения `k → null`. Для проверки наличия есть `containsKey`. При этом разные методы по-разному трактуют null: `getOrDefault` возвращает default только при отсутствии записи, а `putIfAbsent` и `computeIfAbsent` рассматривают null-значение как отсутствие полезного значения.

```java
Map<String, Integer> counts = new HashMap<>();
counts.put("a", null);
System.out.println(counts.getOrDefault("a", 7)); // null, ключ существует
counts.computeIfAbsent("a", k -> 1);           // заменяет null на 1
counts.merge("a", 2, Integer::sum);            // теперь 3
counts.merge("a", 1, (oldValue, delta) -> null); // удаляет запись
```

У `computeIfAbsent` null-результат функции не добавляет значение: при следующем вызове вычисление может повториться. Это неудобно для отрицательного кеширования; отсутствие результата представляют отдельным sentinel или Optional-значением по согласованному контракту. У `merge` переданное новое значение должно быть не-null; если старого значения нет или оно null, оно записывается без вызова remapping-функции. Null-результат remapping удаляет запись.

Эти методы у обычного `HashMap` не обеспечивают потокобезопасности. Гарантии атомарности зависят от реализации, например от `ConcurrentHashMap`, которая null вообще запрещает. Также функция вычисления не должна менять ту же карту: это может нарушить контракт или привести к исключению.

Частая ошибка — считать `getOrDefault(k, expensive())` ленивым: аргумент вычисляется ещё до входа в метод.

## Очереди и задачи с приоритетом

### 8. PriorityQueue и пары методов Queue/Deque: offer/poll/peek против add/remove/element

У интерфейса `Queue` каждая базовая операция существует в двух версиях: одна бросает исключение при неудаче, другая возвращает специальное значение.

| Действие | Бросает исключение | Возвращает false/null |
| :--- | :--- | :--- |
| Вставить | `add(e)` → IllegalStateException | `offer(e)` → false |
| Извлечь голову | `remove()` → NoSuchElementException | `poll()` → null |
| Посмотреть голову | `element()` → NoSuchElementException | `peek()` → null |

Две версии нужны потому, что очередь может быть ограниченной по ёмкости (например, `ArrayBlockingQueue`) или пустой — и это штатная ситуация, а не ошибка. На практике почти всегда используют `offer`/`poll`/`peek`. У `Deque` те же пары продублированы для обоих концов: `offerFirst`/`offerLast`, `pollFirst`/`pollLast`, `peekFirst`/`peekLast`.

`PriorityQueue` — реализация `Queue` на бинарной min-куче (обычный массив). Головой очереди всегда минимальный элемент: по natural ordering (`Comparable`) или по `Comparator`, переданному в конструктор. `null`-элементы запрещены контрактом класса, в том числе при пользовательском компараторе, умеющем сравнивать null.

| Операция | Сложность |
| :--- | :---: |
| `offer()` / `poll()` | O(log N) |
| `peek()` | O(1) |
| `contains()` / `remove(Object)` | O(N) |

Ловушка, на которой подстрекают на собеседованиях: итератор `PriorityQueue` **не** обходит элементы в порядке приоритета — он просто идёт по внутреннему массиву кучи. Порядок гарантируется только при последовательном извлечении через `poll()`.

### 18. ArrayDeque: почему для стека и очереди берут его, а не Stack и LinkedList

`ArrayDeque` — двусторонняя очередь на циклическом массиве (ring buffer): поля `head` и `tail` «бегут» по массиву, при заполнении буфер расширяется (коэффициент роста зависит от реализации). Операции на обоих концах — `offerFirst/offerLast`, `pollFirst/pollLast`, `peekFirst/peekLast` — амортизированные O(1). null-элементы запрещены, потому что `poll()` возвращает null как признак пустой очереди.

Почему он вытеснил оба «исторических» варианта:

**Как стек (вместо `Stack`):**
```java
Deque<Task> stack = new ArrayDeque<>();
stack.push(task);    // = addFirst
stack.pop();         // = removeFirst; на пустом стеке исключение
stack.peek();        // посмотреть верхушку
```
Те же операции стека, но без `synchronized` на каждом методе (наследие `Vector`) и без доступа по индексу, ломающего абстракцию стека. Javadoc класса `Stack` сам отправляет к `Deque`.

**Как очередь (вместо `LinkedList`):** те же O(1) на концах, но ссылки на элементы лежат в одном массиве вместо разбросанных по куче узлов с двумя ссылками — меньше памяти, никаких аллокаций на вставку, кэш процессора работает. Обычно это выгоднее по памяти и локальности; конкретную производительность проверяют измерениями.

Чего `ArrayDeque` не умеет: доступа по индексу (это не `List`) и блокирующего ожидания (для producer-consumer нужны `BlockingQueue`, см. следующий вопрос).

### 36. Как обработать строку с Backspace и сохранить порядок ввода?

В мини-редакторе `#` стирает последний введённый символ, а в начале строки ничего не делает. Например, ввод `"##ab#c"` должен оставить `"ac"`. Удобно хранить введённое слева направо и изменять только правый конец.

```java
static String applyKeys(String input) {
    var letters = new ArrayDeque<Integer>();
    input.codePoints().forEach(cp -> {
        if (cp == '#') letters.pollLast();
        else letters.addLast(cp);
    });
    var result = new StringBuilder();
    for (int cp : letters) result.appendCodePoint(cp);
    return result.toString();
}
```

`pollLast()` безопасно возвращает `null` на пустой очереди. Обычный обход читает оставшееся от начала к концу. Если добавлять через `push()` в голову, а затем итерироваться в том же направлении, сохранившиеся буквы окажутся в обратном порядке.

Алгоритм занимает O(n) времени и O(n) памяти. В этом условии один Backspace удаляет одну кодовую точку Unicode. Поэтому для `"A😀#"` получится `"A"`. Для настоящего редактора нужно отдельно договориться об удалении графем: буква вместе с комбинируемым знаком может содержать несколько кодовых точек.

### 30. На подумать: как найти top-K событий и почему изменение приоритета ломает PriorityQueue?

В память поступает миллион событий с целочисленным score. Сначала нужно сохранить 10 событий с наибольшим score на момент приёма: каждое событие рассматривается как неизменяемый снимок, весь миллион удерживать и сортировать нельзя. Какую структуру выбрать? Отдельно рассмотрите обычную очередь с изменяемыми приоритетами и более сложное требование — актуальный top-K при произвольных обновлениях score ранее принятых событий.

<details>
<summary>Разбор</summary>

Для потокового top-K по неизменяемым снимкам достаточно min-heap размера не больше K: голова — худший из текущих победителей. Новое событие добавляют, а при превышении K извлекают минимальное. Получается O(N log K) времени и O(K) дополнительной памяти.

```java
record Event(long id, int score) { }
PriorityQueue<Event> best = new PriorityQueue<>(
        Comparator.comparingInt(Event::score).thenComparingLong(Event::id));
for (Event event : incoming) {
    best.offer(event);
    if (best.size() > 10) best.poll();
}
List<Event> result = new ArrayList<>(best);
result.sort(best.comparator().reversed());
```

Дополнительный id задаёт детерминированный выбор при одинаковом score. Итератор очереди не сортирует результат — поэтому финальные десять элементов отдельно упорядочены. Если K может быть нулём или отрицательным, это условие проверяют на входе.

У обычной очереди с изменяемыми приоритетами другая проблема: изменение поля не восстанавливает heap-инвариант, и `peek()` может вернуть уже не минимальный объект. Удаление и повторная вставка восстанавливают порядок среди хранимых элементов (`remove(Object)` стоит O(M) при размере очереди M). Возможны также индексируемая структура или неизменяемые версионные записи с учётом актуальной версии и удалением устаревших. Версионные записи сами по себе не ограничивают память величиной O(K). Просто сделать поле volatile недостаточно: видимость не перестраивает кучу.

Для актуального top-K по произвольно обновляемым событиям одних K победителей недостаточно. При K=1 события A=100 и B=90 оставят только A; после изменения A до 1 правильный победитель — уже отброшенное B. Даже remove/reinsert не вернёт потерянного кандидата. Нужны хранение и индекс всех активных кандидатов либо внешний источник для пересчёта. Гарантия O(K) памяти относится к первой задаче с фиксированными снимками, а не к этому варианту.

Опасный ответ — «PriorityQueue сама пересортирует при следующем peek». Сравнения выполняются при структурных операциях, произвольные мутации она не отслеживает.

</details>

## Конкурентные коллекции и наследие API

### 3. Как устроена ConcurrentHashMap и почему она эффективнее Collections.synchronizedMap()?

`Collections.synchronizedMap(map)` — обёртка, где **каждый** метод синхронизирован по одному монитору. Десять потоков, читающих разные ключи, выстроятся в очередь. Плюс составные операции всё равно приходится синхронизировать снаружи: классическое `if (!map.containsKey(k)) map.put(k, v)` неатомарно и без внешней блокировки ломается.

`ConcurrentHashMap` в Java 8+ устроен так же, как `HashMap` (массив бакетов, списки, деревья), но с точечной конкурентностью:

- **`get()` — без блокировок вообще.** Поля узлов (`val`, `next`) объявлены `volatile`, а публикация таблицы и узлов использует необходимые гарантии видимости. Успешное чтение конкретного ключа связано happens-before с установкой наблюдаемого значения; это не атомарный снимок всей карты. Чтение не мешает записи.
- **`put()` в пустой бакет — через CAS** (`compareAndSwapObject` на элементе массива): поток атомарно «захватывает» пустую ячейку без всяких блокировок.
- **`put()` в занятый бакет — `synchronized` на первом узле** этого бакета. Блокируется одна цепочка, остальные бакеты свободны и для чтения, и для записи. Теоретический уровень параллелизма — число бакетов.
- **Resize кооперативный:** поток, обнаруживший перенос (`ForwardingNode`), помогает переносить бакеты, а не ждёт.
- **`size()` приблизительный:** счётчик размазан по массиву ячеек (`baseCount` + `CounterCell[]`, идея та же, что у `LongAdder`) — суммирование без глобальной блокировки. `mappingCount()` — та же оценка, но в `long`; берите его, когда число записей теоретически может переполнить `int`. При конкурентных изменениях результат не подходит для управления инвариантами. Без конкурентных записей `size()` точен; точный согласованный снимок можно получить только с дополнительным протоколом координации.

До Java 7 включительно вместо этого были **сегменты**: карта делилась на 16 независимых `Segment` (наследников `ReentrantLock`), число сегментов зависело от заданного `concurrencyLevel` (значение по умолчанию — 16). В Java 8 сегменты выбросили — CAS и блокировка на бакет дешевле и масштабируются лучше.

Два следствия, о которых спрашивают следом:

1. **null запрещён** — ни ключи, ни значения. Причина не техническая, а семантическая: в обычной мапе `get() == null` означает «нет такого ключа», в конкурентной — ещё и «значение удалили прямо сейчас». Разрешив null, нельзя было бы отличить одно от другого без блокировки. Если нужно «значение-заглушка», используют sentinel-объект.
2. **Атомарные составные операции из коробки:** `putIfAbsent`, `computeIfAbsent`, `compute`, `merge` — атомарны относительно соответствующего ключа, поэтому паттерн «проверить и добавить» безопасен без внешней синхронизации. Ловушка: функция в `computeIfAbsent` не должна модифицировать ту же мапу — получите взаимоблокировку или `IllegalStateException: Recursive update`.
3. **Массовые операции без итераторов:** `forEach`, `search`, `reduce` с параметром `parallelismThreshold` — обходят всю мапу и при достаточном размере распараллеливаются на общий ForkJoinPool. Полезность параллельного обхода зависит от стоимости обработки и порога; автоматического ускорения нет.

### 17. CopyOnWriteArrayList: устройство и когда она лучше синхронизированного списка

`CopyOnWriteArrayList` — потокобезопасный список с радикальным подходом: **изменение содержимого обычно публикует новую копию массива** (операция без фактического изменения может обойтись без копии).

- `add()`/`set()`/`remove()` при фактическом изменении обычно копируют массив (O(N) и новая аллокация), подменяют ссылку на массив (она `volatile`) и отпускают блокировку. Записи между собой сериализованы через внутренний лок.
- Чтение — совершенно свободное: никаких блокировок и CAS, просто текущий массив. Итератор фиксирует снимок массива на момент создания и спокойно обходит его, пока другие потоки пишут (fail-safe, см. вопрос 6). Изменения, сделанные после создания итератора, ему не видны.

Когда это выигрыш: **много чтений, очень мало записей** и короткий список. Классические сценарии — списки слушателей (listeners), подписчики событий, белые списки конфигурации: обход происходит на каждое событие, а подписываются/отписываются раз в жизни приложения.

Когда это провал: частые записи или большой список — копирование массива на каждый `add()` съест и процессор, и память (в момент записи живут две копии). Для такого профиля — `Collections.synchronizedList` или очереди.

Snapshot-итератор не поддерживает `remove`; `ListIterator` также не поддерживает `add`/`set` и бросает `UnsupportedOperationException`. «Не бросает CME» не означает «разрешает менять список через итератор».

Родственный класс — `CopyOnWriteArraySet`: тот же принцип для `Set` (проверка `contains` при добавлении делает запись ещё дороже — O(N) на проверку плюс O(N) на копию).

### 19. Блокирующие очереди: ArrayBlockingQueue, LinkedBlockingQueue, SynchronousQueue

`BlockingQueue` (пакет `java.util.concurrent`) — очередь, которая умеет **ждать**: потребитель блокируется, пока очередь пуста, производитель — пока она полна. Это готовый паттерн producer-consumer без ручных `wait/notify`; на них же построены пулы потоков (см. раздел по многопоточности).

Методы снова идут семействами на случай неудачи:

| Действие | Исключение | Спец. значение | Блокировка | С таймаутом |
| :--- | :--- | :--- | :--- | :--- |
| Вставить | `add(e)` | `offer(e)` → false | `put(e)` | `offer(e, t, unit)` |
| Извлечь | `remove()` | `poll()` → null | `take()` | `poll(t, unit)` |

Основные реализации:

- **`ArrayBlockingQueue`** — ограниченная, на циклическом массиве фиксированного размера. Один лок на чтение и запись. «Честная» (fair) версия обслуживает потоки в порядке прихода, но медленнее.
- **`LinkedBlockingQueue`** — на связном списке, по умолчанию фактически неограниченная (`Integer.MAX_VALUE` — легко словить OOM, ёмкость лучше задавать явно). Два раздельных лока (на голову и на хвост), что позволяет чтению и записи выполняться параллельно; превосходство по пропускной способности зависит от нагрузки.
- **`SynchronousQueue`** — очередь без ёмкости вообще: `put()` блокируется, пока другой поток не сделает `take()`, и наоборот. Прямая передача «из рук в руки». На ней построен `Executors.newCachedThreadPool()`.
- **`PriorityBlockingQueue`** — неограниченная, извлекает по приоритету (как `PriorityQueue`, но потокобезопасная).
- **`DelayQueue`** — извлекает элементы только после истечения их индивидуальной задержки (`Delayed.getDelay()`). У `ScheduledThreadPoolExecutor` есть собственная внутренняя `DelayedWorkQueue` со схожей семантикой; это не экземпляр `DelayQueue`.

Связь с пулами потоков, которую любят спрашивать: `fixedThreadPool` использует неограниченную `LinkedBlockingQueue` (задачи копятся, новые потоки не создаются), `cachedThreadPool` — `SynchronousQueue` (задача не встаёт в очередь, а сразу порождает поток).

### 13. Vector, Hashtable и Stack: почему они считаются legacy и что использовать вместо них?

Все три класса появились в Java 1.0, до Collections Framework (Java 1.2), и оставлены только ради обратной совместимости. В новом коде им места нет.

- **`Vector`** — аналог `ArrayList`, у которого каждый метод помечен `synchronized`. Это защищает отдельные вызовы, но не составные операции («проверить и добавить», обход) всё равно приходится синхронизировать снаружи, а платите вы за блокировку на каждый вызов. Плюс `Vector` удваивает массив при росте (`ArrayList` — увеличивает в 1.5 раза), то есть тратит больше памяти. Вместо: `ArrayList`; при реальной многопоточности — `CopyOnWriteArrayList` или `Collections.synchronizedList()` с внешней синхронизацией при обходе.
- **`Hashtable`** — та же история для мап: `synchronized` на каждом методе, запрет null-ключей и null-значений, перебор через старый `Enumeration`. Вместо: `HashMap`, в многопоточном коде — `ConcurrentHashMap`.
- **`Stack`** — стек, который наследует `Vector`. Из-за наследования у «стека» есть доступ к любому элементу по индексу, вставка и удаление из середины — это ломает саму идею стека. Javadoc самого класса `Stack` прямо рекомендует использовать `Deque`. Вместо: `Deque<Integer> stack = new ArrayDeque<>()` — методы `push()`/`pop()`/`peek()` на месте, работает быстрее и без лишней синхронизации.
