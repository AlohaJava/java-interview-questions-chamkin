### 1. Как устроена HashMap: хэширование, бакеты, коллизии, деревья и resize

`HashMap` — хэш-таблица: массив бакетов (`Node<K,V>[] table`), где каждый бакет — голова связного списка, а с Java 8 при больших коллизиях — красно-черное дерево.

**Константы по умолчанию:**

- `DEFAULT_INITIAL_CAPACITY = 16` — стартовый размер массива (сам массив создаётся лениво, при первом `put()`). Размер всегда степень двойки.
- `DEFAULT_LOAD_FACTOR = 0.75` — фактор загрузки.
- `threshold = capacity * loadFactor` — при превышении этого числа элементов массив удваивается (`resize()`). Для 16 это 12.
- `TREEIFY_THRESHOLD = 8` — при таком числе элементов в одном бакете список превращается в дерево.
- `UNTREEIFY_THRESHOLD = 6` — при падении числа элементов в древовидном бакете до 6 дерево превращается обратно в связный список.
- `MIN_TREEIFY_CAPACITY = 64` — если бакет дорос до 8, но массив меньше 64, вместо дерева выполняется обычный resize: коллизия почти наверняка от плохого распределения, и дешевле расширить таблицу.

**Дополнительное хэширование.** `hashCode()` ключа не используется напрямую. Внутренний метод `hash()` перемешивает старшие биты с младшими:

```java
static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}
```

Зачем: индекс бакета вычисляется как `(n - 1) & hash`, то есть берутся только младшие `log2(n)` бит хэша (при n=16 — всего 4 бита). Если у ключей различаются только старшие биты (типично для плохих `hashCode`), без перемешивания все они попали бы в один бакет. Сдвиг `h >>> 16` «спускает» старшие биты вниз, и XOR вносит их в выбор бакета. Отдельный случай: **null-ключ** даёт hash 0 и всегда лежит в бакете 0 — поэтому null-ключ ровно один.

**Алгоритм `put(K key, V value)`:**

1. Вычисляется `hash(key)` (см. выше).
2. Индекс бакета: `i = (n - 1) & hash`. Степень двойки как раз и нужна, чтобы заменить дорогой `hash % n` битовой маской.
3. Бакет пуст — создаётся новый `Node`.
4. Бакет занят — обход цепочки (списка или дерева): если у узла совпал хэш и ключ равен (`==` или `equals()`), значение перезаписывается; иначе новый узел добавляется в конец списка (в Java 8 — в хвост, в Java 7 добавляли в голову).
5. Если после вставки длина списка достигла 8 — бакет превращается в дерево (`treeifyBin`), но только если `capacity >= 64`.
6. Если `size > threshold` — `resize()`.

**Алгоритм `get(Object key)`:** тот же `hash()` и индекс; проверяется первый узел (попадание с первого раза — самый частый случай), затем обход цепочки со сравнением сначала хэша, потом ключа. Хэш хранится в самом узле, чтобы не вызывать `hashCode()` повторно.

**Resize.** Массив удваивается (16 → 32 → 64...), `threshold` пересчитывается, элементы перераспределяются. В Java 8 пере-хэширование не нужно: для каждого узла достаточно одного бита — `e.hash & oldCap`. Если бит 0, узел остаётся на старом индексе, если 1 — переезжает на `index + oldCap`. Узлы распадаются на две цепочки (lo и hi) с сохранением относительного порядка. Это исправляет старый дефект Java 7: там элементы переносились в голову списка с разворотом порядка, что при конкурентном resize могло замкнуть список в кольцо и увести `get()` в бесконечный цикл.

**Красно-черные деревья (Java 8+).** При восьми элементах в бакете список превращается в сбалансированное красно-черное дерево (`TreeNode`), и поиск в бакете деградирует с O(N) до O(log N). Порог 8 выбран по распределению Пуассона: при идеальном хэше вероятность 8+ элементов в одном бакете около 0.00000006 — то есть дерево включается только при плохом `hashCode` или намеренной атаке (hash-flooding). Порядок в дереве — по хэшу; при равных хэшах ключи сравниваются через `Comparable`, а если класс не сравним — через `tieBreakOrder` (identity hash code).

**Обратное преобразование (untreeify).** Оно существует в обе стороны: когда из древовидного бакета удаляют элементы (или он дробится при resize) и размер падает до `UNTREEIFY_THRESHOLD = 6`, дерево превращается обратно в обычный связный список. Порог 6 отделён от порога 8 гистерезисом, чтобы бакет не метался туда-сюда при колебаниях размера около границы.

```java
// Узел связного списка в HashMap
static class Node<K,V> implements Map.Entry<K,V> {
    final int hash;   // кэшированный хэш ключа
    final K key;
    V value;
    Node<K,V> next;
}
```

**Почему load factor именно 0.75.** Компромисс между памятью и длиной цепочек: при 0.5 таблица реже коллидирует, но треть массива простаивает и resize случается чаще; при 1.0 память экономится, но цепочки длиннее и поиск дорожает. 0.75 — эмпирическая середина.

Частый follow-up: «какая сложность `get()` у HashMap?» Корректный ответ — амортизированно O(1), в худшем случае (все ключи в одном бакете) O(log N) с деревом и O(N) без него.

### 2. В чем разница между ArrayList и LinkedList и какова сложность их основных операций (Big O)?

**`ArrayList`** — обёртка над динамическим массивом `Object[] elementData`.

- Начальная ёмкость по умолчанию — 10 (массив создаётся лениво, при первом `add`).
- При переполнении новая ёмкость считается как `oldCapacity + (oldCapacity >> 1)` — рост в 1.5 раза; элементы копируются через `Arrays.copyOf()` (внутри — `System.arraycopy`, быстрое поблочное копирование памяти).
- `get(i)`/`set(i)` — прямой доступ по индексу, O(1).
- Вставка/удаление в середину — O(N): всё хвостовое содержимое сдвигается на одну позицию.
- Массив лежит в памяти непрерывно — процессор эффективно подтягивает его в кэш-линии, и обход списка очень быстрый.

**`LinkedList`** — двусвязный список из узлов `Node<E>` (поля `item`, `next`, `prev`).

- `get(i)` — O(N): обход от ближайшего конца (для `i < size/2` идёт с головы, иначе с хвоста).
- Вставка в начало/конец — O(1); вставка в середину — тоже O(N), потому что до узла ещё нужно дойти. «O(1) вставка» справедлива только если ссылка на узел уже есть (например, через `ListIterator`).
- Каждый элемент — отдельный объект: само значение плюс две ссылки (24+ байта накладных расходов на узел), разбросанные по куче. Кэш процессора при обходе почти не работает.

| Операция | ArrayList | LinkedList |
| :--- | :---: | :---: |
| `get(i)` | **O(1)** | O(N) |
| `add(e)` в конец | **O(1)** амортиз. | **O(1)** |
| `add(0, e)` | O(N) | **O(1)** |
| вставка/удаление в середину | O(N) | O(N) |
| `remove(Object)` | O(N) | O(N) |
| память на элемент | ~4 байта (ссылка) | ~24+ байта (узел) |

Важный практический вывод: несмотря на асимптотику, **LinkedList почти никогда не быстрее**. Из-за кэш-промахов он проигрывает ArrayList даже на вставках в начало на больших объёмах — проверяется любым бенчмарком. Реальная ниша LinkedList — когда нужен `Deque` и обработка с двух концов, но и там обычно лучше `ArrayDeque`.

Отдельный маркер: `ArrayList` реализует интерфейс-метку `RandomAccess`. Алгоритмы (`Collections.binarySearch` и др.) проверяют его и для RandomAccess-коллекций выбирают доступ по индексу вместо итератора.

### 3. Как устроена ConcurrentHashMap и почему она эффективнее Collections.synchronizedMap()?

`Collections.synchronizedMap(map)` — обёртка, где **каждый** метод синхронизирован по одному монитору. Десять потоков, читающих разные ключи, выстроятся в очередь. Плюс составные операции всё равно приходится синхронизировать снаружи: классическое `if (!map.containsKey(k)) map.put(k, v)` неатомарно и без внешней блокировки ломается.

`ConcurrentHashMap` в Java 8+ устроен так же, как `HashMap` (массив бакетов, списки, деревья), но с точечной конкурентностью:

- **`get()` — без блокировок вообще.** Поля узлов (`val`, `next`) объявлены `volatile`, поэтому читатель всегда видит актуальное состояние. Чтение не мешает записи.
- **`put()` в пустой бакет — через CAS** (`compareAndSwapObject` на элементе массива): поток атомарно «захватывает» пустую ячейку без всяких блокировок.
- **`put()` в занятый бакет — `synchronized` на первом узле** этого бакета. Блокируется одна цепочка, остальные бакеты свободны и для чтения, и для записи. Теоретический уровень параллелизма — число бакетов.
- **Resize кооперативный:** поток, обнаруживший перенос (`ForwardingNode`), помогает переносить бакеты, а не ждёт.
- **`size()` приблизительный:** счётчик размазан по массиву ячеек (`baseCount` + `CounterCell[]`, идея та же, что у `LongAdder`) — суммирование без глобальной блокировки. `mappingCount()` — та же оценка, но в `long`; берите его, когда число записей теоретически может переполнить `int`. Точного «мгновенного» размера конкурентной мапы не существует в принципе: пока вы считаете, соседние потоки пишут.

До Java 7 включительно вместо этого были **сегменты**: карта делилась на 16 независимых `Segment` (наследников `ReentrantLock`), уровень параллелизма был зашит в константу. В Java 8 сегменты выбросили — CAS и блокировка на бакет дешевле и масштабируются лучше.

Два следствия, о которых спрашивают следом:

1. **null запрещён** — ни ключи, ни значения. Причина не техническая, а семантическая: в обычной мапе `get() == null` означает «нет такого ключа», в конкурентной — ещё и «значение удалили прямо сейчас». Разрешив null, нельзя было бы отличить одно от другого без блокировки. Если нужно «значение-заглушка», используют sentinel-объект.
2. **Атомарные составные операции из коробки:** `putIfAbsent`, `computeIfAbsent`, `compute`, `merge` — выполняются под блокировкой бакета целиком, поэтому паттерн «проверить и добавить» безопасен без внешней синхронизации. Ловушка: функция в `computeIfAbsent` не должна модифицировать ту же мапу — получите взаимоблокировку или `IllegalStateException: Recursive update`.
3. **Массовые операции без итераторов:** `forEach`, `search`, `reduce` с параметром `parallelismThreshold` — обходят всю мапу и при достаточном размере распараллеливаются на общий ForkJoinPool. На больших мапах это заметно быстрее ручного итерирования по `entrySet()`.

### 4. Какова иерархия интерфейсов в Java Collections Framework?

Java Collections Framework (JCF) состоит из двух основных корней: интерфейса `java.util.Collection` и интерфейса `java.util.Map`.

```text
                     Iterable<T>
                          |
                      Collection<T>
                   /      |        \
             List<T>   Set<T>     Queue<T>
               |          |          |  (Deque расширяет Queue)
          ArrayList    HashSet    ArrayDeque
          LinkedList   TreeSet    PriorityQueue
                       LinkedHashSet

                       Map<K, V>  (SortedMap/NavigableMap расширяют Map)
                     /     |     \
               HashMap  TreeMap  Hashtable
               LinkedHashMap    ConcurrentHashMap
```

- **`List`** — упорядоченная коллекция с доступом по индексу (допускает дубликаты). Основные реализации: `ArrayList`, `LinkedList`, `Vector`.
- **`Set`** — коллекция уникальных элементов (без дубликатов). Реализации: `HashSet` (на базе `HashMap`), `TreeSet` (на базе красно-черного дерева), `LinkedHashSet`.
- **`Queue` / `Deque`** — коллекции для работы по принципу FIFO/LIFO. Реализации: `ArrayDeque`, `LinkedList`, `PriorityQueue`.
- **`Map`** — структура «ключ-значение». Ключи уникальны. Реализации: `HashMap`, `TreeMap`, `LinkedHashMap`, `ConcurrentHashMap`.

Нюансы, о которых спрашивают:

- `Map` **не** наследуется от `Collection` — это отдельная ветка. Но представления `keySet()`, `values()`, `entrySet()` возвращают `Set`/`Collection`, и через них мапу можно обходить for-each.
- У обеих веток есть свои расширения: у `Map` — `SortedMap`/`NavigableMap` (навигация по отсортированным ключам, реализует `TreeMap`) и `ConcurrentMap` (атомарные `putIfAbsent`/`compute`/`merge`, реализует `ConcurrentHashMap`); у `Queue` — `Deque` (двусторонняя очередь) и `BlockingQueue` (блокирующая, для producer-consumer).
- Между интерфейсами и реализациями стоят абстрактные классы (`AbstractList`, `AbstractMap`...) с базовыми реализациями — на собеседовании достаточно упомянуть, что они есть.
- `Collection` сам наследуется от `Iterable` — поэтому любая коллекция работает в for-each (см. вопрос 9).

### 5. Чем HashMap отличается от TreeMap и LinkedHashMap?

Три мапы с разными гарантиями порядка и сложности.

| | HashMap | LinkedHashMap | TreeMap |
| :--- | :--- | :--- | :--- |
| Структура | хэш-таблица | хэш-таблица + двусвязный список | красно-черное дерево |
| Порядок обхода | не определён | порядок вставки или доступа | сортировка по ключу |
| get/put | O(1) амортиз. | O(1) амортиз. | O(log N) |
| null-ключ | один разрешён | один разрешён | только если Comparator допускает null (при natural ordering — NPE) |
| Требования к ключу | equals/hashCode | equals/hashCode | Comparable или Comparator |

- **`HashMap`** — выбор по умолчанию: самая быстрая, но порядок итерации не гарантирован и может измениться после resize.
- **`LinkedHashMap`** — к узлам `HashMap` добавлены ссылки `before`/`after`, связывающие все записи в двусвязный список. Порядок обхода — порядок вставки; в режиме `accessOrder=true` — порядок последнего обращения, на чём строится LRU-кэш (подробнее в вопросе 15). Цена — чуть больше памяти и работы на каждую операцию.
- **`TreeMap`** — ключи всегда отсортированы: либо по natural ordering (`Comparable`), либо по `Comparator` из конструктора. Все операции — O(log N). Зато даёт навигацию: `firstKey()`, `lastKey()`, `floorKey()`, `ceilingKey()`, `subMap()` — то, чего у хэш-мап нет в принципе (см. вопрос 16).

Частый follow-up: «а если ключ в TreeMap не Comparable и без компаратора?» С Java 7 упадёт уже первый `put()`: вставка в пустое дерево делает контрольное сравнение `compare(key, key)` ради ранней проверки типа, так что `ClassCastException` прилетает сразу. Утверждение «первый `put()` пройдёт, второй упадёт» — верно только для Java 6, но до сих пор ходит по старым шпаргалкам.

### 6. В чем разница между Fail-Fast и Fail-Safe итераторами?

Речь о поведении итератора, когда коллекция меняется во время обхода — другим потоком или тем же, но не через сам итератор.

**Fail-Fast** (`ArrayList`, `HashMap`, `HashSet`, большинство коллекций `java.util`):

- Коллекция ведёт счётчик структурных модификаций `modCount`: каждый `add`/`remove` его инкрементирует.
- Итератор при создании запоминает `expectedModCount` и при каждом `next()` сверяет с текущим. Не сошлось — `ConcurrentModificationException`.
- «Структурных» — потому что `list.set(i, x)` счётчик не трогает: размер и структура не изменились, итератор не упадёт.

**Fail-Safe / weakly consistent** (`ConcurrentHashMap`, `CopyOnWriteArrayList`):

- Исключения не бросают. Итератор `CopyOnWriteArrayList` работает со снимком массива на момент создания — изменений он просто не увидит. Итератор `ConcurrentHashMap` обходит живую таблицу и отражает изменения «как получится»: какие-то свежие записи увидит, какие-то нет, но корректное состояние гарантировано.

Две важные оговорки, которые любят выяснять следом:

1. `ConcurrentModificationException` — **best effort, а не гарантия**. Проверка `modCount` не синхронизирована, и в многопоточном коде отсутствие исключения не означает отсутствие проблем. Это механизм раннего обнаружения багов, а не инструмент синхронизации.
2. Единственный легальный способ изменить коллекцию во время обхода — методы самого итератора (`remove()`, у `ListIterator` ещё `add()`/`set()`), которые согласуют `modCount`. Подробнее в вопросе 9.
3. Обёртки `Collections.synchronizedList()` и ей подобные — **не** fail-safe: внутри у них обычный fail-fast итератор. Их обход обязан идти под ручной синхронизацией по самой обёртке (`synchronized (list) { for (...) }`), иначе ловите `ConcurrentModificationException` или гонки.

### 7. Как устроен HashSet и почему внутри него обычная HashMap?

`HashSet` — не самостоятельная структура данных, а тонкая обёртка над `HashMap`. Внутри лежит поле `private transient HashMap<E,Object> map`: добавляемый элемент становится ключом, а значением служит одна общая константная заглушка.

```java
// Из исходников HashSet
private static final Object PRESENT = new Object();

public boolean add(E e) {
    return map.put(e, PRESENT) == null;
}
```

- `add()`, `remove()`, `contains()` просто делегируют к `map.put()`, `map.remove()`, `map.containsKey()` — отсюда те же O(1) и те же требования к `equals()`/`hashCode()` элементов, что и у ключей `HashMap`.
- Заглушка нужна, чтобы `add()` мог вернуть `boolean`: если элемента не было, `map.put()` вернёт `null` (результат `true`), если был — вернёт `PRESENT` (результат `false`).
- Всё семейство устроено так же: `LinkedHashSet` — обёртка над `LinkedHashMap` (порядок вставки), `TreeSet` — над `TreeMap` (отсортированный порядок, O(log N)).
- Из семейства выбивается `EnumSet`: это не обёртка над мапой, а битовая маска (один `long`, если констант не больше 64). Все операции — битовые сдвиги, поэтому это самая быстрая и компактная реализация `Set`; порядок итерации — порядок объявления констант enum. Правило простое: для enum-ключей мапы берут `EnumMap` (см. вопрос 10), для enum-множеств — `EnumSet`.

Частый follow-up: почему порядок обхода `HashSet` выглядит случайным. Потому что это порядок бакетов внутренней `HashMap` — он зависит от хэш-кодов элементов и меняется после resize.

### 8. PriorityQueue и пары методов Queue/Deque: offer/poll/peek против add/remove/element

У интерфейса `Queue` каждая базовая операция существует в двух версиях: одна бросает исключение при неудаче, другая возвращает специальное значение.

| Действие | Бросает исключение | Возвращает false/null |
| :--- | :--- | :--- |
| Вставить | `add(e)` → IllegalStateException | `offer(e)` → false |
| Извлечь голову | `remove()` → NoSuchElementException | `poll()` → null |
| Посмотреть голову | `element()` → NoSuchElementException | `peek()` → null |

Две версии нужны потому, что очередь может быть ограниченной по ёмкости (например, `ArrayBlockingQueue`) или пустой — и это штатная ситуация, а не ошибка. На практике почти всегда используют `offer`/`poll`/`peek`. У `Deque` те же пары продублированы для обоих концов: `offerFirst`/`offerLast`, `pollFirst`/`pollLast`, `peekFirst`/`peekLast`.

`PriorityQueue` — реализация `Queue` на бинарной min-куче (обычный массив). Головой очереди всегда минимальный элемент: по natural ordering (`Comparable`) или по `Comparator`, переданному в конструктор. `null`-элементы запрещены — куча обязана сравнивать элементы между собой, иначе получите NPE.

| Операция | Сложность |
| :--- | :---: |
| `offer()` / `poll()` | O(log N) |
| `peek()` | O(1) |
| `contains()` / `remove(Object)` | O(N) |

Ловушка, на которой подстрекают на собеседованиях: итератор `PriorityQueue` **не** обходит элементы в порядке приоритета — он просто идёт по внутреннему массиву кучи. Порядок гарантируется только при последовательном извлечении через `poll()`.

### 9. Iterator и Iterable: зачем нужны, как работает remove() итератора и что скрывается под капотом for-each?

`Iterable` — это обещание «по мне можно итерироваться»: единственный абстрактный метод `iterator()`, возвращающий `Iterator`. Реализуйте `Iterable` — и объект можно использовать в цикле for-each.

`Iterator` — сам курсор. `hasNext()` проверяет наличие следующего элемента и не сдвигает позицию (его можно вызывать сколько угодно раз подряд, ничего не «проскочит»). `next()` возвращает элемент и сдвигается; вызов за границей — `NoSuchElementException`.

for-each — синтаксический сахар. Компилятор разворачивает его примерно так:

```java
for (String s : list) {
    System.out.println(s);
}

// превращается в
Iterator<String> it = list.iterator();
while (it.hasNext()) {
    String s = it.next();
    System.out.println(s);
}
```

Для массивов вместо итератора генерируется обычный цикл по индексу.

`Iterator.remove()` — единственный безопасный способ удалить элемент во время обхода: он удаляет последний возвращённый `next()` элемент и согласует счётчик модификаций коллекции (`modCount`), поэтому `ConcurrentModificationException` не возникает. Ограничения: `remove()` можно вызвать только один раз после каждого `next()`; второй вызов подряд или вызов до первого `next()` — `IllegalStateException`. Удаление через `list.remove(x)` прямо внутри for-each — это fail-fast и `ConcurrentModificationException`. Если нужно удалять по условию без ручного итератора, есть `collection.removeIf(predicate)`.

С Java 8 у `Iterable` появились default-методы, о которых тоже спрашивают: `forEach(Consumer)` — обход без явного итератора, и `spliterator()` — объект, умеющий разбивать источник на части для обхода; именно на сплитераторах построен Stream API и его параллельные стримы.

### 10. Специализированные реализации Map: WeakHashMap, EnumMap и IdentityHashMap

Три мапы для задач, где обычная `HashMap` либо не подходит, либо избыточна.

**`WeakHashMap`** — ключи хранятся через `WeakReference`. Когда на ключ не остаётся сильных ссылок, сборщик мусора удаляет объект-ключ, и запись исчезает из мапы. Классическое применение — прикрепить метаданные к объектам, чей жизненный цикл вы не контролируете (кэш «объект → доп. информация»), не создавая утечку памяти. Ловушка: `size()` может уменьшиться между двумя вызовами без всякого `remove()` — GC работает, когда захочет. Вторая ловушка тоньше: значение не должно сильно ссылаться на свой ключ (прямо или через цепочку), иначе ключ никогда не станет кандидатом на сборку и запись не удалится никогда. И ещё: записи вычищаются не мгновенно, а при ближайшем обращении к мапе, которое разгребёт `ReferenceQueue`, — «мертвые» ключи могут какое-то время висеть в таблице.

**`EnumMap`** — мапа, ключами которой могут быть только константы одного enum. Внутри — просто массив значений, индексом служит `ordinal()` константы: ни хэширования, ни бакетов, ни цепочек. Отсюда максимальная скорость и компактность, а итерация идёт в порядке объявления констант enum. null-ключ запрещён, null-значения разрешены. Если ключи — enum, брать `HashMap` вместо `EnumMap` — всегда ошибка.

**`IdentityHashMap`** — сравнивает ключи по ссылке (`==`) вместо `equals()` и использует `System.identityHashCode()` вместо `hashCode()`. Контракт `Map` нарушен осознанно: нужна именно идентичность объектов. Применяется в сериализации и глубоком копировании (пометить уже обработанные объекты графа, чтобы не зациклиться) и при обходах графов. Побочный плюс: не требует от ключей корректных `equals()`/`hashCode()` и не ломается при их изменении.

### 11. Какие требования предъявляются к объектам в роли ключей HashMap?

Ключ `HashMap` обязан быть фактически иммутабельным и корректно реализовывать `equals()`/`hashCode()`. Компилятор это не проверяет — требование продиктовано устройством хэш-таблицы.

Требования по существу:
- `equals()` и `hashCode()` опираются на одни и те же поля;
- равные по `equals()` ключи обязаны иметь одинаковый `hashCode()` (обратное не требуется — коллизии законны);
- поля, участвующие в `equals()`/`hashCode()`, не должны меняться, пока объект лежит в мапе ключом.

Что ломается при изменении ключа после `put()`:

```java
class Key {
    int id;
    Key(int id) { this.id = id; }

    @Override public int hashCode() { return id; }
    @Override public boolean equals(Object o) {
        return o instanceof Key k && k.id == id;
    }
}

Map<Key, String> map = new HashMap<>();
Key key = new Key(1);
map.put(key, "value");
key.id = 42;                       // поле участвует в hashCode
System.out.println(map.get(key));  // null — элемент «потерялся»
```

При `put()` ключ попал в бакет по старому хэшу. После изменения `get()` вычисляет новый `hashCode()` и идёт в другой бакет — записи там нет. При этом сама запись никуда не делась: она лежит в старом бакете, недостижимая ни для `get()`, ни для `remove()`. По сути это утечка. После `resize()` поведение становится ещё менее предсказуемым — ключ пересчитается по новому хэшу и уедет в третий бакет.

Отдельная ловушка — массивы в роли ключей: у них `equals()`/`hashCode()` унаследованы от `Object` и сравнивают ссылки. Два массива с одинаковым содержимым — разные ключи, достать значение выйдет только по той же самой ссылке.

Поэтому на практике ключами делают `String`, `Integer`, record-классы — всё, что иммутабельно из коробки.

### 12. Неизменяемые коллекции: List.of/Set.of/Map.of против Arrays.asList и Collections.unmodifiableList

Три механизма, которые регулярно путают, — у них разные гарантии.

| | Изменить элемент (`set`) | Добавить/удалить | null | Связь с источником |
| :--- | :--- | :--- | :--- | :--- |
| `Arrays.asList(...)` | можно | UnsupportedOperationException | можно | живая обёртка над массивом |
| `Collections.unmodifiableList(list)` | нельзя | нельзя | можно | живая обёртка над исходным списком |
| `List.of(...)` / `Set.of(...)` / `Map.of(...)` (Java 9+) | нельзя | нельзя | нельзя (NPE) | независимая копия |

- `Arrays.asList()` возвращает список фиксированного размера поверх переданного массива: `list.set(0, x)` работает и меняет сам массив (и наоборот), а `add()`/`remove()` падают с `UnsupportedOperationException`. Это способ «смотреть на массив как на список», а не неизменяемая коллекция.
- `Collections.unmodifiableList()` — декоратор только для чтения, но не копия: если исходный список поменять, изменения видны через обёртку. Защита работает, только если ссылку на исходный список больше никто не держит.
- `List.of()`, `Set.of()`, `Map.of()` (и `copyOf`-варианты) — настоящие иммутабельные реализации: любая модификация — `UnsupportedOperationException`, null-элементы и null-ключи запрещены (NPE ещё при создании), внутри компактное хранение. Для константных коллекций сегодня берут именно их. Две мелочи, которые спрашивают: дубликат в `Set.of("a", "a")` — это `IllegalArgumentException` ещё при вызове фабрики, а не молчаливое слияние; у фабрик перегрузки до 10 аргументов (у `Map.of` — до 10 пар), дальше varargs-версия и `Map.ofEntries(Map.entry(k, v), ...)` для сколько угодно пар.

Частый follow-up: «как сделать неизменяемую копию существующего списка?» — `List.copyOf(list)` (Java 10+); старый вариант — `Collections.unmodifiableList(new ArrayList<>(list))`.

### 13. Vector, Hashtable и Stack: почему они считаются legacy и что использовать вместо них?

Все три класса появились в Java 1.0, до Collections Framework (Java 1.2), и оставлены только ради обратной совместимости. В новом коде им места нет.

- **`Vector`** — аналог `ArrayList`, у которого каждый метод помечен `synchronized`. Проблема в том, что это почти ничего не даёт: составные операции («проверить и добавить», обход) всё равно приходится синхронизировать снаружи, а платите вы за блокировку на каждый вызов. Плюс `Vector` удваивает массив при росте (`ArrayList` — увеличивает в 1.5 раза), то есть тратит больше памяти. Вместо: `ArrayList`; при реальной многопоточности — `CopyOnWriteArrayList` или `Collections.synchronizedList()` с внешней синхронизацией при обходе.
- **`Hashtable`** — та же история для мап: `synchronized` на каждом методе, запрет null-ключей и null-значений, перебор через старый `Enumeration`. Вместо: `HashMap`, в многопоточном коде — `ConcurrentHashMap`.
- **`Stack`** — стек, который наследует `Vector`. Из-за наследования у «стека» есть доступ к любому элементу по индексу, вставка и удаление из середины — это ломает саму идею стека. Javadoc самого класса `Stack` прямо рекомендует использовать `Deque`. Вместо: `Deque<Integer> stack = new ArrayDeque<>()` — методы `push()`/`pop()`/`peek()` на месте, работает быстрее и без лишней синхронизации.

### 14. Как сортируются коллекции: Collections.sort, TimSort, стабильность и сложность сортировки?

`Collections.sort(list)` с Java 8 просто делегирует `list.sort(null)`, который выгружает элементы в массив и вызывает `Arrays.sort()`. А дальше алгоритм зависит от того, что лежит в массиве — примитивы или объекты.

**Для объектов — TimSort** (гибрид сортировки слиянием и вставками, портирован из Python, автор Тим Петерс). Массив сканируется на уже упорядоченные участки (runs), короткие досортировываются вставками, затем runs сливаются, как в merge sort.

- Сложность: худший и средний случай — **O(N log N)**, лучший (почти отсортированные данные) — **O(N)**.
- Стабильность: TimSort **стабилен** — равные по компаратору элементы сохраняют исходный относительный порядок. Это критично для объектов: два разных объекта могут быть «равны» по компаратору, и их порядок нельзя терять (иначе сломается многоуровневая сортировка — сначала по одному полю, потом по другому).
- Цена: до N/2 дополнительной памяти под буфер слияния.

**Для примитивов — Dual-Pivot QuickSort** (`Arrays.sort(int[])`, `long[]` и т.д., разработан Владимиром Ярославским). Вместо одного опорного элемента берутся два (p1 и p2), и массив режется на три части: `< p1`, между пивотами, `> p2` — за счёт этого меньше рекурсивных проходов, чем у классического QuickSort. На маленьких массивах (меньше ~47 элементов) включается быстрая вставочная сортировка.

- Средний случай — O(N log N), худший — O(N²), зато без заметной доп. памяти и очень дружелюбен к процессорному кэшу (примитивы лежат в массиве плотно).
- **Нестабилен** — и это нормально: для примитивов стабильность бессмысленна, два равных `int` неотличимы. Именно поэтому для объектов QuickSort не используют — там стабильность нужна.

Ещё есть **`Arrays.parallelSort()`** (Java 8+): массив режется на куски, сортируется параллельно в `ForkJoinPool.commonPool`, потом куски сливаются. Выигрыш начинается на больших массивах (порядка сотен тысяч элементов и выше) — на мелких накладные расходы на координацию съедят всё ускорение.

```java
int[] primitives = {5, 1, 4, 2};
Arrays.sort(primitives);                 // DualPivotQuicksort, нестабильная (и не нужна)

String[] objects = {"b", "a", "c"};
Arrays.sort(objects);                    // TimSort, стабильная
Arrays.sort(objects, Comparator.reverseOrder());

List<User> users = getUsers();
users.sort(Comparator.comparing(User::getLastName)
                     .thenComparingInt(User::getAge));
// благодаря стабильности внутри одинаковых фамилий порядок по возрасту сохранится
```

Порядок задаётся либо естественно — элементы реализуют `Comparable` (метод `compareTo()`), либо внешним `Comparator`. К компаратору предъявляются обычные требования отношения порядка: транзитивность, антисимметричность, `compare(x, x) == 0`. Если их нарушить, TimSort может упасть с `IllegalArgumentException: Comparison method violates its general contract!`:

```java
// сломанный компаратор: для равных элементов вернёт -1 вместо 0
Comparator<Integer> bad = (a, b) -> a > b ? 1 : -1;

// корректно
Comparator<Integer> good = Integer::compare;
```

Частый follow-up: «почему нельзя отсортировать `int[]` компаратором?» — перегрузки `Arrays.sort` с `Comparator` принимают только `T[]` (объекты). Для примитивов сначала упаковывают (`Arrays.stream(ints).boxed()`), либо используют `IntStream` с `sorted()`.

### 15. LinkedHashMap: порядок вставки, порядок доступа и LRU-кэш из коробки

`LinkedHashMap` наследует `HashMap` и добавляет к каждой записи ссылки `before`/`after`, связывающие все элементы в двусвязный список. Хэш-таблица даёт те же O(1) на get/put, а список — предсказуемый порядок обхода.

Два режима, выбираются конструктором:

```java
// порядок вставки (по умолчанию)
Map<String, Integer> insertionOrder = new LinkedHashMap<>();

// порядок доступа: каждый get() переносит запись в «свежий» конец
Map<String, Integer> accessOrder = new LinkedHashMap<>(16, 0.75f, true);
```

- В обычном режиме обход идёт в порядке `put()` — полезно, когда нужна мапа с детерминированной итерацией (например, для вывода конфигурации).
- В режиме `accessOrder=true` любое обращение (включая `get()` и повторный `put()` существующего ключа) перемещает запись в конец списка. В начале списка оказываются самые давно не использованные записи.

На этом строится LRU-кэш без единой строчки логики — достаточно переопределить один метод:

```java
class LruCache<K, V> extends LinkedHashMap<K, V> {
    private final int maxSize;

    LruCache(int maxSize) {
        super(16, 0.75f, true);   // accessOrder = true
        this.maxSize = maxSize;
    }

    @Override
    protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
        return size() > maxSize;  // вернуть true — и самая старая запись удалится
    }
}
```

Из коробки `removeEldestEntry` всегда возвращает `false` (никогда ничего не вытесняет). Ловушка для собеседования: `LinkedHashMap` не потокобезопасна, и в режиме accessOrder даже `get()` — структурная модификация (перелинковка списка), то есть обход итератором с параллельными `get()` из другого потока даст `ConcurrentModificationException`. Для конкурентного LRU берут `ConcurrentHashMap` + ручную логику или готовый Caffeine.

### 16. TreeMap и NavigableMap: красно-черное дерево и методы навигации

`TreeMap` — сбалансированное красно-черное дерево (самобалансирующееся бинарное дерево поиска: повороты и перекраски при вставке/удалении держат высоту ~log N). Все базовые операции — `get`, `put`, `remove` — за O(log N), а обход итератором идёт в отсортированном порядке ключей.

Ключи обязаны быть взаимно сравнимыми: либо реализуют `Comparable`, либо в конструктор передан `Comparator`. Сравнение через `compareTo`/`compare` полностью заменяет `equals`: два ключа с `compareTo == 0` считаются одним и тем же ключом, даже если `equals()` вернул бы `false`. Расхождение `compareTo` с `equals` — классическая ловушка: `new BigDecimal("1.0")` и `new BigDecimal("1.00")` не равны по `equals`, но `compareTo` даёт 0, и в `TreeMap` они затрут друг друга.

Главная ценность — интерфейс `NavigableMap` с методами навигации, которых нет у хэш-мап:

```java
TreeMap<Integer, String> map = new TreeMap<>();
map.put(10, "a"); map.put(20, "b"); map.put(30, "c");

map.firstKey();          // 10
map.lastKey();           // 30
map.floorKey(25);        // 20 — наибольший ключ <= 25
map.ceilingKey(25);      // 30 — наименьший ключ >= 25
map.lowerKey(20);        // 10 — строго меньше
map.higherKey(20);       // 30 — строго больше
map.headMap(20);         // {10=a} — все ключи < 20
map.tailMap(20);         // {20=b, 30=c} — все ключи >= 20
map.subMap(10, 30);      // {10=a, 20=b} — диапазон [10, 30)
map.descendingMap();     // обратный порядок
```

Все view (`headMap`, `subMap`...) — живые представления, а не копии: изменения видны в обе стороны.

Когда `TreeMap` оправдана: нужен отсортированный порядок, range-запросы («все события за период»), поиск ближайшего значения. Если нужна просто мапа — `HashMap` быстрее на порядок, и брать `TreeMap` «для надёжности» не стоит.

### 17. CopyOnWriteArrayList: устройство и когда она лучше синхронизированного списка

`CopyOnWriteArrayList` — потокобезопасный список с радикальным подходом: **любая модификация создаёт новую копию внутреннего массива**.

- `add()`/`set()`/`remove()` копируют весь массив (O(N) и новый объект на каждую запись), подменяют ссылку на массив (она `volatile`) и отпускают блокировку. Записи между собой сериализованы через внутренний лок.
- Чтение — совершенно свободное: никаких блокировок и CAS, просто текущий массив. Итератор фиксирует снимок массива на момент создания и спокойно обходит его, пока другие потоки пишут (fail-safe, см. вопрос 6). Изменения, сделанные после создания итератора, ему не видны.

Когда это выигрыш: **много чтений, очень мало записей** и короткий список. Классические сценарии — списки слушателей (listeners), подписчики событий, белые списки конфигурации: обход происходит на каждое событие, а подписываются/отписываются раз в жизни приложения.

Когда это провал: частые записи или большой список — копирование массива на каждый `add()` съест и процессор, и память (в момент записи живут две копии). Для такого профиля — `Collections.synchronizedList` или очереди.

Родственный класс — `CopyOnWriteArraySet`: тот же принцип для `Set` (проверка `contains` при добавлении делает запись ещё дороже — O(N) на проверку плюс O(N) на копию).

### 18. ArrayDeque: почему для стека и очереди берут его, а не Stack и LinkedList

`ArrayDeque` — двусторонняя очередь на циклическом массиве (ring buffer): поля `head` и `tail` «бегут» по массиву, при переполнении он удваивается. Операции на обоих концах — `offerFirst/offerLast`, `pollFirst/pollLast`, `peekFirst/peekLast` — амортизированные O(1). null-элементы запрещены, потому что `poll()` возвращает null как признак пустой очереди.

Почему он вытеснил оба «исторических» варианта:

**Как стек (вместо `Stack`):**
```java
Deque<Task> stack = new ArrayDeque<>();
stack.push(task);    // = offerFirst
stack.pop();         // = pollFirst
stack.peek();        // посмотреть верхушку
```
Тот же API, но без `synchronized` на каждом методе (наследие `Vector`) и без доступа по индексу, ломающего абстракцию стека. Javadoc класса `Stack` сам отправляет к `Deque`.

**Как очередь (вместо `LinkedList`):** те же O(1) на концах, но элементы лежат в одном непрерывном массиве вместо разбросанных по куче узлов с двумя ссылками — меньше памяти, никаких аллокаций на вставку, кэш процессора работает. На бенчмарках `ArrayDeque` стабильно быстрее.

Чего `ArrayDeque` не умеет: доступа по индексу (это не `List`) и блокирующего ожидания (для producer-consumer нужны `BlockingQueue`, см. следующий вопрос).

### 19. Блокирующие очереди: ArrayBlockingQueue, LinkedBlockingQueue, SynchronousQueue

`BlockingQueue` (пакет `java.util.concurrent`) — очередь, которая умеет **ждать**: потребитель блокируется, пока очередь пуста, производитель — пока она полна. Это готовый паттерн producer-consumer без ручных `wait/notify`; на них же построены пулы потоков (см. раздел по многопоточности).

Методы снова идут семействами на случай неудачи:

| Действие | Исключение | Спец. значение | Блокировка | С таймаутом |
| :--- | :--- | :--- | :--- | :--- |
| Вставить | `add(e)` | `offer(e)` → false | `put(e)` | `offer(e, t, unit)` |
| Извлечь | `remove()` | `poll()` → null | `take()` | `poll(t, unit)` |

Основные реализации:

- **`ArrayBlockingQueue`** — ограниченная, на циклическом массиве фиксированного размера. Один лок на чтение и запись. «Честная» (fair) версия обслуживает потоки в порядке прихода, но медленнее.
- **`LinkedBlockingQueue`** — на связном списке, по умолчанию фактически неограниченная (`Integer.MAX_VALUE` — легко словить OOM, ёмкость лучше задавать явно). Два раздельных лока (на голову и на хвост), поэтому пропускная способность выше, чем у массивной.
- **`SynchronousQueue`** — очередь без ёмкости вообще: `put()` блокируется, пока другой поток не сделает `take()`, и наоборот. Прямая передача «из рук в руки». На ней построен `Executors.newCachedThreadPool()`.
- **`PriorityBlockingQueue`** — неограниченная, извлекает по приоритету (как `PriorityQueue`, но потокобезопасная).
- **`DelayQueue`** — извлекает элементы только после истечения их индивидуальной задержки (`Delayed.getDelay()`). Основа `ScheduledThreadPoolExecutor`.

Связь с пулами потоков, которую любят спрашивать: `fixedThreadPool` использует неограниченную `LinkedBlockingQueue` (задачи копятся, новые потоки не создаются), `cachedThreadPool` — `SynchronousQueue` (задача не встаёт в очередь, а сразу порождает поток).

### 20. Как выбрать коллекцию под задачу: практическая шпаргалка

На собеседовании регулярно просят не знание устройства, а выбор: «что возьмёте для...». Сводка:

**Список:**
- Дефолт — `ArrayList`. Покрывает 95% случаев.
- Обходы и вставки в конец + работа с двух концов — `ArrayDeque`.
- `LinkedList` — почти никогда (см. вопрос 2).
- Чтение из многих потоков, редкие записи — `CopyOnWriteArrayList`.

**Мапа:**
- Дефолт — `HashMap`.
- Нужен порядок вставки или LRU — `LinkedHashMap`.
- Нужна сортировка по ключу или range-запросы — `TreeMap`.
- Многопоточность — `ConcurrentHashMap`.
- Ключи — enum — `EnumMap`. Кэш с автоочисткой — `WeakHashMap`.

**Множество:**
- Дефолт — `HashSet`. Порядок вставки — `LinkedHashSet`. Сортировка — `TreeSet`.

**Очередь:**
- Однопоточная FIFO/стек — `ArrayDeque`. Приоритетная — `PriorityQueue`.
- Producer-consumer — `LinkedBlockingQueue` с явной ёмкостью.
- Прямая передача задач — `SynchronousQueue`. Отложенные задачи — `DelayQueue`.

Три вопроса, которыми интервьюер проверяет осмысленность выбора: «какая сложность у основных операций выбранной структуры?», «а что будет в многопоточной среде?», «а если порядок важен?». Если на каждый из них есть ответ без паузы — тема закрыта.
