## Байты, символы и ресурсы

### 1. Чем отличаются InputStream, Reader и Stream API?

`InputStream` читает байты, `OutputStream` записывает байты. Они подходят для изображений, архивов и сетевых протоколов. `Reader` и `Writer` работают с символами; между байтами файла и символами требуется кодировка. `InputStreamReader` выполняет декодирование, `OutputStreamWriter` — кодирование. Подмена одного уровня другим может незаметно испортить бинарные данные.

```java
try (Reader reader = new InputStreamReader(
        Files.newInputStream(path), StandardCharsets.UTF_8)) {
    char[] chars = new char[4096];
    for (int n; (n = reader.read(chars)) != -1; ) {
        consume(chars, n); // consume обрабатывает только первые n символов
    }
}
```

`java.util.stream.Stream<T>` — другой механизм: ленивый конвейер обработки элементов. Например, `Files.lines(path)` возвращает `Stream<String>`, но под ним остаётся открытый файловый ресурс, который нужно закрыть. Название «поток» не означает ни отдельный поток исполнения, ни автоматически неблокирующий I/O.

`FileInputStream` получает байты из файла, а `ByteArrayInputStream` — из уже существующего массива в heap. Общий интерфейс позволяет тестировать парсер на массиве, не создавая файл. Однако такой тест не проверяет задержки диска, ошибки доступа и закрытие файлового дескриптора. Закрытие `ByteArrayInputStream` ничего не освобождает вне JVM; переносить это свойство на все `InputStream` нельзя. Сам `InputStream` также не обещает перемотку: `mark/reset` поддерживаются только некоторыми реализациями.

### 2. Почему текст портится при чтении и как явно управлять кодировкой?

Файл содержит байты, а не «строки UTF-8 по умолчанию». Чтобы получить правильный текст, читатель должен использовать кодировку, с которой байты записал отправитель. Кириллическая буква может занимать несколько байтов UTF-8, поэтому преобразование каждого прочитанного блока через `new String(bytes, UTF_8)` ломает символы на границе блоков. `Reader` с одним декодером сохраняет неполную последовательность до следующего чтения.

Для данных, где повреждение нельзя тихо заменить символом `�`, задают строгий декодер:

```java
CharsetDecoder decoder = StandardCharsets.UTF_8.newDecoder()
    .onMalformedInput(CodingErrorAction.REPORT)
    .onUnmappableCharacter(CodingErrorAction.REPORT);
try (Reader reader = new InputStreamReader(
        Files.newInputStream(path), decoder)) {
    parse(reader);
}
```

Ошибка кодировки тогда становится ошибкой импорта с указанием источника, а не испорченным именем в БД. Декодер — объект с состоянием; его нельзя разделять между независимыми параллельными чтениями.

В Java 17 системная кодировка зависит от окружения. Начиная с Java 18 JEP 400 установил UTF-8 как стандартную кодировку для большинства стандартных API; консольный ввод-вывод имеет отдельные особенности. Это не меняет формат старых файлов. `Files.readString(path)` уже использует UTF-8 независимо от JEP 400, но явный `StandardCharsets.UTF_8` делает контракт заметнее. Следует также различать длину в байтах, UTF-16 `char` и пользовательских символах: `String.length()` не измеряет размер HTTP-тела и не всегда считает видимые символы.

### 3. Почему одного read(buffer) недостаточно и что означает available()?

`read(byte[])` возвращает число фактически прочитанных байтов, а не обещание заполнить массив. Конец входа обозначается `-1`. Из файла короткое чтение менее заметно, но из сокета это нормальный результат: отправитель ещё не прислал остальную часть. Запись всего массива вместо первых `n` байтов добавляет к результату старые данные или нули.

```java
byte[] buffer = new byte[8192];
for (int n; (n = in.read(buffer)) != -1; ) {
    out.write(buffer, 0, n);
}
```

Если протокол требует ровно 12 байтов заголовка, это другой контракт:

```java
byte[] header = in.readNBytes(12);
if (header.length != 12) {
    throw new EOFException("Неполный заголовок");
}
```

`DataInputStream.readFully` также подходит для фиксированной длины и сообщает о преждевременном EOF исключением. До выделения массива под тело необходимо проверить заявленный размер: заголовок от клиента с длиной 2 ГБ не должен определять расход памяти сервера.

`available()` оценивает, сколько байтов можно прочитать без блокировки; это не размер всего файла или сообщения и не признак EOF. Ноль может означать «данных пока нет», хотя соединение открыто. `readAllBytes()` удобен только при известном ограниченном объёме: он не превращает недоверенный или бесконечный вход в безопасный. В цикле чтения также нужны ограничения на общий объём и время, иначе корректный с точки зрения API клиент может удерживать ресурс бесконечно.

### 4. Чем различаются buffering, flush и close и кто закрывает ресурс?

Буфер накапливает небольшие операции и уменьшает обращения к нижележащему ресурсу. `BufferedOutputStream` полезен при множестве мелких записей; при записи больших готовых блоков дополнительный буфер может мало изменить. `flush()` передаёт накопленные байты дальше по цепочке, но не гарантирует запись на физический носитель и не означает, что удалённое приложение обработало сообщение.

```java
try (OutputStream out = new BufferedOutputStream(
        Files.newOutputStream(path))) {
    out.write(payload);
} // close закрывает обёртку и нижележащий поток
```

Владелец открытого ресурса отвечает за его закрытие. Если метод получил `OutputStream` от вызывающего кода, нельзя без договорённости закрывать его: это может быть общий HTTP-ответ или `System.out`. Напротив, метод, который сам открыл файл, обычно закрывает его внутри. Контракт владения важнее привычки «всегда закрывать всё».

`try-with-resources` закрывает ресурсы в обратном порядке даже при исключении. Если обработка уже выбросила исключение, а `close()` тоже завершился ошибкой, ошибка закрытия добавляется к первой как suppressed exception; её можно увидеть через `getSuppressed()`. При ручном `finally` легко потерять исходную причину. При успешной обработке ошибка закрытия сама выходит наружу: её нельзя игнорировать, поскольку запись могла не завершиться.

Закрывать только «счастливый путь» после `write()` опасно: исключение оставит дескриптор открытым. Полагаться на GC также нельзя: освобождение Java-объекта не задаёт своевременное освобождение системного ресурса.

## Файлы и границы памяти

### 5. Как выбрать между readString, lines, walk и потоковым чтением большого файла?

Выбор зависит от максимального размера входа и способа обработки. `Files.readString` и `readAllBytes` загружают содержимое целиком. `readAllLines` создаёт ещё и коллекцию строк. Для маленькой контролируемой конфигурации это простой вариант; для многогигабайтного импорта нужна последовательная обработка.

```java
try (Stream<String> lines = Files.lines(path, StandardCharsets.UTF_8)) {
    long errors = lines.filter(line -> line.contains("ERROR")).count();
    System.out.println(errors);
}
```

Ленивость не отменяет закрытие. Даже `findFirst()` может остановиться задолго до EOF, оставив открытый ресурс, если нет `try-with-resources`. `Files.list`, `walk` и `find` тоже возвращают ресурсоёмкие потоки. Ошибка при обходе может возникнуть после создания Stream, уже в терминальной операции, в том числе как `UncheckedIOException`.

Построчная обработка ограничивает память размером текущей строки, но одна строка может оказаться огромной. Для недоверенного формата нужны ограничения длины записи, числа полей и общего объёма. `collect(toList())` в конце такого конвейера снова материализует всё содержимое и уничтожает преимущество потокового чтения.

`parallel()` не делает медленный диск быстрее автоматически: возникают конкуренция за накопитель, память и исполнители. Сначала измеряют пропускную способность чтения и CPU-парсинга отдельно. Если нужны параллельные вычисления, часто проще иметь один последовательный читатель и ограниченную очередь задач; предел очереди не позволит читателю заполнить heap быстрее, чем обработчики успеют разобрать данные.

### 6. Что гарантируют Path.normalize(), toRealPath() и проверка startsWith()?

`Path` описывает путь; сам по себе он не открывает файл и не доказывает его существование. `normalize()` убирает лексические `.` и `..`, но не обращается к файловой системе и не разрешает символические ссылки. `toRealPath()` требует существования объекта, возвращает реальный абсолютный путь и по умолчанию разрешает ссылки.

Для простого случая каталога, который не может менять недоверенный пользователь, проверка выглядит так:

```java
Path root = storage.toAbsolutePath().normalize();
Path candidate = root.resolve(userName).normalize();
if (!candidate.startsWith(root)) {
    throw new SecurityException("Путь вне хранилища");
}
```

Это сравнение компонентов `Path`, а не строковый `startsWith`: `/data/uploads-backup` не находится внутри `/data/uploads`. Но пример защищает только от лексического выхода. Ссылка `uploads/link -> /etc` и гонка между проверкой и открытием делают его недостаточным в каталоге, который способен менять атакующий.

Для существующих файлов можно сравнить реальные пути, однако это само по себе не устраняет гонку подмены. Более надёжный дизайн — генерировать имена на сервере, хранить вне web-root, ограничивать права на каталог и по возможности использовать операции относительно открытого каталога, например `SecureDirectoryStream`, если провайдер их поддерживает. `NOFOLLOW_LINKS` у конкретной операции не следует считать универсальной защитой всех промежуточных компонентов пути. Проверка пути — часть модели доступа, а не замена ей: разрешённый локальный файл ещё должен принадлежать нужному пользователю.

### 7. Как заменить файл без частично записанного содержимого и что значит durability?

Если перезаписать рабочий файл напрямую, читатель или аварийное завершение могут увидеть пустой файл либо только начало новых данных. Обычный подход — полностью записать временный файл в том же каталоге, закрыть его и затем переименовать:

```java
Path target = path.toAbsolutePath();
Path temp = Files.createTempFile(target.getParent(), ".update-", ".tmp");
try {
    Files.writeString(temp, text, StandardCharsets.UTF_8);
    Files.move(temp, target, StandardCopyOption.ATOMIC_MOVE);
} finally {
    Files.deleteIfExists(temp);
}
```

`ATOMIC_MOVE` требует атомарной операции от провайдера; если она невозможна, возникает `AtomicMoveNotSupportedException`. Для существующей цели поведение замены при `ATOMIC_MOVE` зависит от реализации: нельзя обещать переносимую атомарную замену любого файла комбинацией флагов. Это проверяют на целевой файловой системе. При неподдерживаемой атомарности приложение либо отказывает, либо явно принимает более слабый контракт; молчаливый fallback меняет гарантию.

Атомарная видимость и сохранность после потери питания — разные свойства. Закрытие потока не гарантирует физическую запись. `FileChannel.force(true)` позволяет запросить сохранение данных и метаданных файла, но стойкость операции переименования дополнительно зависит от ОС, файловой системы и фиксации каталога; универсального рецепта только на стандартном Java API нет.

Также нужно договориться о конкурентных авторах: два корректных атомарных переименования всё равно могут дать «последний победил». Для защиты от потерянного обновления нужна версия, блокировка или другой протокол согласования.

## NIO, буферы и сетевые соединения

### 8. Правда ли, что NIO всегда неблокирующий и быстрее java.io?

Нет. NIO объединяет буферы, каналы, файловые API и механизмы мультиплексирования. `FileChannel` поддерживает позиционное чтение и отображение файла, но не является `SelectableChannel` и не регистрируется в `Selector`. `SocketChannel` по умолчанию блокирующий; режим меняется явно через `configureBlocking(false)`.

Нужно различать три модели. При блокирующем вызове поток ждёт результат. При неблокирующем вызове операция возвращает управление, если сейчас нет прогресса; приложение ждёт готовности через selector. При асинхронном API результат доставляется позже через `Future` или обработчик завершения. Слово NIO не гарантирует одну конкретную реализацию всех трёх моделей.

Например, сервис с тысячами простаивающих соединений может использовать event loop, чтобы один поток следил за многими каналами. Но CPU-парсинг или блокирующий JDBC-вызов внутри event loop задержит все обслуживаемые им соединения. Сложность управления частичными чтениями и состоянием протокола также никуда не исчезает.

Начиная с Java 21 стабильные virtual threads позволяют писать многие блокирующие сетевые сценарии в последовательном стиле при большом числе конкурентных задач. Они не ускоряют диск, не увеличивают лимит соединений к БД и не отменяют ограничения памяти, таймауты и admission control. В Java 17 virtual threads нет. Выбор модели обосновывают профилем нагрузки и зрелостью используемой библиотеки; замена `InputStream` на `Channel` без измерений не является оптимизацией.

### 9. Как работают position, limit, flip, clear и compact у ByteBuffer?

У буфера есть `capacity` — размер хранилища, `limit` — граница доступных операций и `position` — следующий элемент для относительного `get/put`. Всегда выполняется `0 <= position <= limit <= capacity`. При создании позиция нулевая, limit равен capacity.

```java
ByteBuffer buffer = ByteBuffer.allocate(16);
buffer.putInt(42);       // position = 4, limit = 16
buffer.flip();           // position = 0, limit = 4
int value = buffer.getInt();
buffer.clear();          // position = 0, limit = 16
```

`flip()` переключает от накопления к чтению: делает текущую позицию границей данных. `clear()` готовит к новой записи, но не стирает старые байты. `rewind()` возвращает позицию в ноль, сохраняя limit: можно перечитать уже подготовленный диапазон. Поэтому эти методы не взаимозаменяемы.

В сетевом парсере после чтения может остаться начало следующего сообщения. Тогда `compact()` переносит непрочитанный остаток в начало и ставит position после него; новые байты добавятся следом. `clear()` в этом месте логически потеряет остаток.

Порядок байтов тоже часть протокола: новый `ByteBuffer` использует `BIG_ENDIAN`, а для little-endian формата нужно явно вызвать `order(ByteOrder.LITTLE_ENDIAN)`. `slice()` и `duplicate()` создают представления с собственными индексами, но общими байтами. Изменение содержимого через один view видно другому, поэтому передача slice асинхронной задаче с одновременным переиспользованием исходного буфера приводит к гонке. Сам буфер не становится потокобезопасным от того, что его память общая.

### 10. Почему Channel.read/write могут обработать только часть сообщения?

Канал переносит доступные байты между источником и `ByteBuffer`, а не знает границы прикладных сообщений. Один `write()` не обязан отправить весь буфер. Один `read()` не обязан получить всё, что записал другой процесс. Для неблокирующего сокета `0` означает отсутствие прогресса сейчас, `-1` при чтении — конец входа.

В блокирующем режиме запись оставшихся данных обычно оформляют циклом:

```java
while (buffer.hasRemaining()) {
    channel.write(buffer);
}
```

Для неблокирующего канала такой же цикл может превратиться в busy spin, если `write()` возвращает ноль. Тогда остаток сохраняют в состоянии соединения, подписываются на `OP_WRITE` и продолжают после уведомления о готовности. Когда очередь опустела, интерес к записи отключают: сокет часто готов писать постоянно, и лишний `OP_WRITE` разогревает CPU.

На чтении нужен парсер кадров. Например, сначала собирают четырёхбайтовую длину, проверяют диапазон `0..MAX_FRAME`, затем добирают ровно тело. Несколько кадров могут прийти одним чтением, один кадр — десятком чтений. EOF посреди кадра означает усечённое сообщение, а не успешное завершение.

Очередь неотправленных данных должна иметь предел. Если клиент читает медленно, бесконечное накопление ответов перенесёт проблему из сетевого буфера в heap. Политика перегрузки — приостановить производство, отказать или закрыть соединение — определяется протоколом. Сам факт использования selector не создаёт backpressure автоматически.

### 11. Как Selector связан с TCP и почему готовность не означает готовое сообщение?

`Selector` сообщает о готовности зарегистрированных неблокирующих каналов к операциям: принять соединение, завершить connect, читать или писать. Это позволяет ждать события для многих сокетов одним потоком. Уведомление означает возможность продвинуть I/O, а не «получен полный JSON» или «клиент подтвердил бизнес-операцию».

TCP предоставляет упорядоченный поток байтов. Границы вызовов `write()` в нём не сохраняются. Поэтому протокол обязан задавать framing: длину, разделитель с экранированием, фиксированный размер или иной однозначный формат. HTTP-клиент берёт эту работу на себя; писать собственный HTTP-парсер поверх TCP для обычного backend-клиента обычно незачем.

Типичный цикл selector обрабатывает выбранные ключи и удаляет их из `selectedKeys()`. Иначе старое событие может обрабатываться повторно. После события всё равно проверяют результат `read/write`, состояние соединения и ошибки. Отключение peer может проявиться EOF или исключением; готовность не делает операцию безошибочной.

Внутри event loop допустима короткая обработка состояния протокола. Долгую бизнес-логику выносят в другой исполнитель с ограниченной очередью. При этом нельзя позволять двум потокам независимо менять позицию одного буфера или состояние одного парсера. Полезно иметь одного владельца состояния соединения, которому рабочие задачи возвращают результаты.

Частая ошибка на собеседовании — связать TCP retransmission с повтором HTTP-операции. Повторная передача сетевого сегмента обеспечивает доставку байтов внутри соединения, а повтор запроса после разрыва может повторить уже выполненный платёж. Это разные уровни гарантий.

### 12. Когда нужны direct buffer, memory-mapped file и transferTo?

Эти механизмы уменьшают определённые копирования или меняют способ доступа к данным, но не гарантируют ускорение. `ByteBuffer.allocateDirect()` размещает буфер вне обычного Java heap; при нативном I/O это может избежать промежуточного копирования. Выделение и освобождение дороже, а потребление native memory нужно наблюдать отдельно. Практический кандидат — долгоживущий переиспользуемый сетевой буфер, а не новый direct buffer на каждый маленький запрос.

`FileChannel.map()` отображает участок файла в память. Обращение выглядит как работа с буфером, но page fault может вызвать реальное чтение с диска и задержку. Отображение большого файла не означает, что весь файл уже находится в RAM. В Java 17–21 у `MappedByteBuffer` нет обычного публичного `close()` для немедленного unmap; это осложняет управление жизненным циклом, особенно при удалении и замене файлов на разных ОС.

`transferTo()` может передавать данные между каналами с оптимизациями ОС. Но результат — фактическое число переданных байтов; нужна обработка частичного прогресса. Для неблокирующей цели ноль не повод бесконечно крутить цикл. Нельзя обещать zero-copy при любой ОС, целевом канале и TLS: шифрование и реализация транспорта меняют путь данных.

Выбор подтверждают измерением размера сообщений, throughput, p99 задержек и native memory. Если приложение просто читает небольшой конфиг один раз при старте, `Files.readString` обычно понятнее. Управление off-heap памятью подробнее рассмотрено в [jvm-and-memory.md](jvm-and-memory.md).

## HTTP, TLS и DNS в Java-приложении

### 13. Как использовать HttpClient и чем send отличается от sendAsync?

Стандартный `java.net.http.HttpClient` доступен с Java 11. Клиент неизменяем после построения, используется для многих запросов и управляет соединениями. Создавать новый клиент на каждый вызов обычно мешает переиспользованию соединений и усложняет контроль ресурсов. `HttpRequest` также неизменяем, а его builder не предназначен для совместного изменения потоками.

```java
HttpClient client = HttpClient.newBuilder()
    .connectTimeout(Duration.ofSeconds(2))
    .followRedirects(HttpClient.Redirect.NEVER)
    .build();
HttpRequest request = HttpRequest.newBuilder(URI.create("https://example.com/status"))
    .timeout(Duration.ofSeconds(3))
    .GET().build();
HttpResponse<String> response = client.send(
    request, HttpResponse.BodyHandlers.ofString(StandardCharsets.UTF_8));
```

`send()` блокирует вызывающий поток до результата выбранного `BodyHandler`. `sendAsync()` возвращает `CompletableFuture`, который завершается позже; это не делает всю последующую работу неблокирующей. `join()` сразу после вызова снова заставляет ждать, а тяжёлый callback может занять поток исполнителя.

Ответ `404` или `500` — нормальный HTTP-ответ, его нужно проверять через `statusCode()`: исключение не обязано возникнуть. `ofString()` собирает тело в память. Для большого тела используют потоковый handler и обязательно читают или закрывают полученный `InputStream`, в том числе на ошибочном статусе.

В Java 21 `HttpClient` реализует `AutoCloseable` и получил API завершения; в Java 17 этого ещё нет. При долгоживущем клиенте завершение привязывают к остановке приложения. Непотреблённые потоковые тела могут удерживать ресурсы и мешать корректному завершению клиента.

### 14. Чем connect timeout отличается от request timeout и общего deadline?

`connectTimeout` ограничивает установление нового соединения. Если клиент переиспользует уже открытое, этот лимит не вступает в действие. Таймаут запроса задаётся на `HttpRequest` и ограничивает ожидание ответа согласно контракту HTTP-клиента. Отсутствие такого значения допускает неограниченное ожидание. Однако произвольную обработку ответа приложением этот параметр не контролирует.

Особенно важен потоковый `BodyHandler`: `ofInputStream()` возвращает ответ, когда доступны заголовки и поток тела, а чтение тела идёт позже. Нельзя считать `.timeout(3 seconds)` гарантией, что последующий `input.read()` и парсинг любого тела закончатся за три секунды. Нужны отдельный контроль времени чтения/подписки, ограничение байтов и отмена с закрытием ресурса.

Пример бюджета: входящий запрос имеет deadline через 900 мс. Поиск в БД уже занял 250 мс; внешнему HTTP-вызову можно отдать меньше оставшихся 650 мс, оставив время на ответ. Если каждому этапу независимо назначить 900 мс и добавить два retry, общая задержка выйдет далеко за обещанный предел. При повторах перед каждой попыткой пересчитывают оставшийся бюджет; подробнее стратегии разобраны в [microservices.md](microservices.md).

`future.orTimeout(...)` завершает future с ошибкой по времени, но сам по себе не является доказательством остановки сетевой работы. Требуется продуманная отмена исходной операции и освобождение тела. Даже отмена не доказывает, что сервер не выполнил запрос: результат после timeout может быть неизвестен. Для проверки нужны медленный connect, задержанные заголовки, медленное тело и отмена на каждом этапе, а не только один тест «сервер спит».

### 15. Что Java-клиент проверяет при TLS и чем truststore отличается от keystore?

TLS защищает конфиденциальность и целостность транспорта и позволяет проверить сторону соединения. Для HTTPS важны как доверие к цепочке сертификатов, так и соответствие имени сервера сертификату. Сертификат от доверенного CA для другого hostname не должен приниматься. Стандартный HTTP-клиент выполняет HTTPS-проверки; при низкоуровневом `SSLSocket` проверку имени нужно настраивать согласно используемому API, а не считать автоматическим свойством любого TLS-сокета.

Truststore содержит доверенные сертификаты/CA, с помощью которых клиент проверяет peer. Keystore может содержать собственный private key и цепочку сертификатов; они нужны, например, для клиентской аутентификации mTLS. Это логические роли: формат хранилища вроде PKCS12 сам по себе не определяет, какую роль оно играет.

При ошибке `PKIX path building failed` проверяют реальный hostname, цепочку intermediate certificates, доверенные CA и часы. Отключение `TrustManager` или hostname verification убирает проверку подлинности и делает перехват возможным; это не способ исправить сертификат.

Данные сессии шифруются согласованными симметричными ключами, а не «публичным сертификатом сервера на каждый пакет». Private key не передаётся клиенту. Конкретный обмен ключами зависит от версии TLS и набора алгоритмов, поэтому подробности TLS 1.2 нельзя механически переносить на TLS 1.3.

После TLS termination на балансировщике дальнейший hop защищён только той конфигурацией, которую настроили отдельно. HTTPS также не решает авторизацию пользователя: доверие к серверу и право читать чужой документ — разные проверки.

### 16. Почему после смены DNS Java-приложение продолжает обращаться к старому адресу?

DNS связывает имя с адресами, но запрос не обязательно разрешает имя заново при каждом HTTP-вызове. Влияют кэши резолвера ОС, JVM, библиотек и уже установленные соединения. HTTP keep-alive или HTTP/2 могут продолжать работать через существующее соединение, которому новое DNS-разрешение вообще не требуется.

`InetAddress` кэширует успешные и неуспешные разрешения. В JDK есть security properties `networkaddress.cache.ttl` и `networkaddress.cache.negative.ttl`; фактические значения нужно проверять для используемой версии и конфигурации. Это не обычные произвольные system properties, для которых гарантированно достаточно `-D` с тем же именем. Не стоит обещать универсальное значение TTL по умолчанию для всех Java 17–21 и поставщиков JDK.

Сценарий: сервис получил `UnknownHostException` во время короткого сбоя DNS. DNS уже восстановился, но отрицательный кэш ещё сохраняет неуспешный результат. Обратная ситуация: запись обновили на новый IP, но клиент пользуется старым положительным кэшем или соединением. Перезапуск меняет сразу несколько состояний и потому не доказывает конкретную причину.

При расследовании сравнивают разрешение имени в том же окружении, адрес реально открытого соединения, настройки JVM и поведение пула соединений. Уменьшение TTL увеличивает нагрузку на DNS и не гарантирует мгновенный failover. Для отказоустойчивости нужны также обработка ошибок соединения, несколько адресов и контролируемая политика повторов. Подмена URL на IP для диагностики HTTPS требует аккуратности: меняются hostname verification, SNI и маршрутизация виртуального хоста.
