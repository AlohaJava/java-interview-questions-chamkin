## Идентичность и доступ

### 1. Чем аутентификация отличается от авторизации и почему роли USER недостаточно?

Аутентификация устанавливает, от чьего имени выполняется запрос. Авторизация решает, разрешено ли этому субъекту конкретное действие над конкретным объектом. Успешная проверка пароля или подписи токена не даёт права читать любую запись по идентификатору.

Например, `GET /documents/812` с ролью `USER` должен проверять владельца, tenant и допустимость операции. Проверка только `hasRole("USER")` оставляет доступ к чужим документам по перебору ID. UUID затрудняет угадывание, но не заменяет проверку доступа: ID может попасть в ссылку или лог.

Практичный вариант — сразу получать объект в области доступа пользователя:

```sql
SELECT id, title, body
FROM documents
WHERE id = ? AND owner_id = ? AND tenant_id = ?
```

Параметры пользователя и tenant берутся из проверенного серверного контекста, а не из произвольных полей запроса. Для общего документа модель может включать отношения участника, права редактора и статус публикации; одной роли уже недостаточно.

Проверка должна действовать на каждом доступном пути: чтение, изменение, скачивание, массовый экспорт и фоновые задачи. Обновление полезно выполнять с теми же ограничениями в `UPDATE ... WHERE`, иначе между чтением и записью могут измениться права. Политика по умолчанию — отказ при отсутствии разрешающего правила. В тестах нужны хотя бы владелец, другой пользователь того же tenant, пользователь другого tenant и анонимный запрос.

### 2. Как хранить и проверять пароли и почему SHA-256 недостаточно?

Для пользовательских паролей нужен медленный адаптивный password hashing: например, Argon2id; выбор параметров зависит от требований и доступных библиотек. Обычный SHA-256 слишком быстр: после кражи базы атакующий сможет проверять огромное число догадок. Обратимое шифрование также создаёт лишний риск восстановления всех паролей при утечке ключа.

Каждый пароль получает случайную salt. Она хранится рядом с результатом вместе с алгоритмом и параметрами; секретной salt быть не обязана. Секретный pepper, если применяется, хранится отдельно и имеет собственный жизненный цикл. Проверку выполняют API библиотеки, а не самостоятельное сравнение строк:

```java
String stored = passwordEncoder.encode(rawPassword);
// При следующем входе:
boolean valid = passwordEncoder.matches(candidate, stored);
```

Это пример использования Spring Security `PasswordEncoder`, а не рекомендация любого его возможного encoder: `NoOpPasswordEncoder` не защищает пароль. Формат с идентификатором алгоритма позволяет мигрировать хеш при успешном входе. Параметры измеряют на целевых машинах под ожидаемой конкуренцией: слишком дорогая проверка без лимита входов сама создаёт DoS.

`char[]` можно затереть после использования, тогда как `String` неизменяем и живёт до GC. Это уменьшает время существования одной копии, но не гарантирует удаления всех копий из памяти, фреймворков и дампов. Практический приоритет — исключить пароль из логов и DTO `toString()`, ограничить доступ к дампам и использовать проверенную библиотеку.

### 3. Как сделать вход и восстановление пароля устойчивыми к злоупотреблению?

Надёжное хранение хеша не защищает от массовой проверки паролей через само приложение. Нужны ограничения частоты и конкуренции, наблюдение за аномалиями и, по модели риска, MFA. Лимит только по IP обходится распределённой атакой, а безусловная длительная блокировка аккаунта позволяет атакующему отказать в доступе владельцу. Обычно сочетают сигналы аккаунта, источника и общий бюджет сервиса.

Восстановление пароля — альтернативный путь получения контроля над аккаунтом, поэтому оно не должно быть слабее основного входа. Пользователь получает одинаковый внешний ответ для существующего и отсутствующего адреса, например «Если аккаунт существует, инструкция отправлена». Различия времени ответа тоже могут раскрывать существование пользователя.

Reset token генерируют криптографическим ГСЧ, делают одноразовым и короткоживущим. Например, 32 случайных байта кодируют Base64url; для случайного высокоэнтропийного токена в базе можно хранить SHA-256, поскольку здесь нет человеческого слабого пароля. При смене пароля токен проверяется и погашается атомарно: два параллельных запроса не должны оба воспользоваться им.

URL восстановления формируют из доверенной конфигурации, а не непроверенного `Host`. Его не пишут целиком в логи. После успешного сброса уведомляют владельца и применяют политику отзыва старых сессий; автоматический вход без отдельного анализа добавляет сложность. Нельзя менять или блокировать аккаунт уже на этапе запроса письма: атакующий ещё не доказал контроль над ним.

### 4. Как устроена безопасная серверная сессия и что означает «выйти на всех устройствах»?

Обычно браузер хранит случайный идентификатор, а сервер — состояние сессии: пользователя, срок жизни, время активности и признаки отзыва. Идентификатор является bearer credential: кто его предъявил, тот может использовать сессию. Поэтому его нельзя помещать в URL, где он попадёт в историю, referrer и логи.

Пример cookie после успешного входа:

```http
Set-Cookie: __Host-session=<random>; Secure; HttpOnly; Path=/; SameSite=Lax
```

`Secure` ограничивает передачу HTTPS, `HttpOnly` запрещает чтение cookie через JavaScript, `SameSite` уменьшает некоторые межсайтовые сценарии. Префикс `__Host-` требует `Secure`, `Path=/` и отсутствия `Domain`. Эти атрибуты не заменяют серверные сроки жизни и защиту от CSRF; `HttpOnly` также не мешает XSS отправлять запросы от имени пользователя.

После аутентификации идентификатор меняют, чтобы не оставить заранее навязанную атакующим сессию. Logout должен инвалидировать серверное состояние и удалить cookie; одно удаление cookie не отзывает украденную копию. «Выйти на всех устройствах» означает отозвать все сессии пользователя или изменить проверяемую версию безопасности аккаунта. В распределённой системе нужно учитывать задержки кэшей.

Для интерфейса управления устройствами показывают безопасные метаданные, а не сами session tokens. Отзыв одной сессии проверяет её принадлежность текущему пользователю. Абсолютный срок и idle timeout решают разные задачи; активность не должна продлевать сессию бесконечно, если политика требует повторной аутентификации.

### 5. Какие проверки нужны JWT помимо успешного Base64-декодирования?

Декодировать JWT может любой; это не проверка подлинности. Для типичного подписанного JWT нужно проверить подпись доверенным ключом, разрешённый алгоритм, ожидаемые issuer и audience, временные ограничения и назначение токена. Набор обязательных claims задаёт профиль вашего протокола: отсутствие обязательного `exp` нельзя молча трактовать как бессрочное разрешение.

Например, токен выдан для `billing-api`, но подписан тем же issuer, что и токены для `profile-api`. При проверке только подписи второй сервис примет чужую audience и расширит область использования credential. Похожая ошибка — принять ID token как access token лишь потому, что оба являются JWT.

Список алгоритмов задаёт серверная конфигурация. Header `alg` не должен определять, каким произвольным способом доверять токену. `kid` помогает найти ключ среди доверенных ключей, но не даёт права загружать любой URL из токена. Адрес JWKS связан с доверенным issuer; ротация ключей требует обновления и разумного кэширования.

JWS обычно подписан, но не зашифрован: персональные данные в payload доступны держателю токена. `exp` ограничивает окно использования украденного токена, но не даёт немедленного logout. Для немедленного отзыва нужны дополнительные состояние/интроспекция, либо принимается окно до истечения срока. Нельзя писать самодельный JWT-парсер: используют поддерживаемую библиотеку и негативные тесты на неверные `iss`, `aud`, срок, ключ и тип.

### 6. Чем различаются OAuth 2.0, OpenID Connect, access token и ID token?

OAuth 2.0 описывает делегированный доступ к ресурсам. OpenID Connect добавляет поверх OAuth слой аутентификации и ID token с утверждениями о входе пользователя. JWT — формат, а не синоним любого из этих протоколов: access token может быть непрозрачной случайной строкой и проверяться через introspection.

В сценарии «войти через провайдера» приложение как OIDC client получает ID token и проверяет его по правилам своего flow: issuer, audience, подпись, время и, где применимо, nonce. API как resource server принимает предназначенный ему access token и проверяет scope/permissions вместе с собственной объектной авторизацией. Нельзя отправить ID token в произвольный backend и считать, что вход автоматически разрешил доступ к его данным.

Authorization Code Flow передаёт через браузер короткоживущий код, затем обменивает его на токены. PKCE связывает обмен с инициатором flow и защищает от использования перехваченного кода; он не заменяет проверки redirect URI и остальных параметров протокола. `state` и OIDC `nonce` имеют отдельные роли привязки ответа и защиты flow, поэтому их не следует смешивать в «один случайный параметр для всего».

Refresh token используется для получения новых токенов и не отправляется ресурсному API вместо access token. Его утечка особенно опасна из-за срока жизни; провайдер может применять ротацию и обнаружение повторного использования. Конкретные правила задаёт поддерживаемый профиль провайдера, а не предположение «любой OAuth-поток одинаков».

## Недоверенные данные и браузер

### 7. Почему PreparedStatement защищает от SQL injection, а ORM — не всегда?

SQL injection возникает, когда данные становятся частью синтаксиса запроса. Параметризованный запрос фиксирует структуру SQL отдельно от значений, поэтому строка с кавычкой остаётся значением, а не меняет `WHERE`.

```java
String sql = "SELECT id FROM users WHERE email = ?";
try (PreparedStatement ps = connection.prepareStatement(sql)) {
    ps.setString(1, email);
    try (ResultSet rs = ps.executeQuery()) {
        while (rs.next()) {
            consumeUserId(rs.getLong(1));
        }
    }
}
```

Само создание `PreparedStatement` не помогает, если перед ним SQL уже собрали конкатенацией. Параметры также не подставляют имена таблиц, столбцов и `ASC/DESC`: динамическую сортировку выбирают из фиксированной серверной карты, например `"name" -> "display_name"`. Передавать `ORDER BY ?` вместо идентификатора — не универсальное решение.

Hibernate/JPA безопасно связывают параметры, но строковая сборка JPQL/HQL или native SQL снова допускает injection. Данные из собственной БД также могут содержать вредоносную строку, сохранённую раньше: доверие не появляется от повторного чтения.

Ручное экранирование зависит от диалекта, кодировки и контекста, поэтому не должно заменять binding. Права пользователя БД ограничивают ущерб: приложению чтения не нужны DDL и административные операции. При этом параметризация не решает объектную авторизацию: безопасно выполненный `SELECT WHERE id = ?` всё ещё может вернуть чужой документ.

### 8. Как SSRF возникает в Java HTTP-клиенте и почему проверки строки URL недостаточно?

SSRF — ситуация, когда атакующий заставляет сервер отправить запрос в выбранное им место. Endpoint «скачать картинку по URL» может обратиться к внутреннему admin API, loopback или облачному metadata endpoint с сетевыми возможностями backend-сервера. Корректный `URI` и HTTPS сами по себе не означают допустимый адрес назначения.

Когда набор интеграций известен, безопаснее принимать идентификатор партнёра и выбирать URL из серверной конфигурации. Если нужны произвольные внешние URL, задача сложнее: проверяют схему, порт, hostname, разрешённые адреса IPv4/IPv6 и каждый redirect. По умолчанию автоматические redirects лучше отключить до явной политики. Нельзя передавать внешнему получателю внутренние cookies и `Authorization`.

Проверка DNS перед запросом не гарантирует тот же адрес при фактическом соединении: есть гонки разрешения и DNS rebinding. Поэтому защиту связывают с реальным маршрутом соединения, используют контролируемый egress proxy/сетевые правила и проверенную реализацию. Только `InetAddress.isSiteLocalAddress()` не покрывает все запрещённые диапазоны и варианты адресов.

Проверка политики HTTP-клиента использует заглушку транспорта и категории `ALLOWED_DESTINATION` / `UNLISTED_DESTINATION`. При смене разрешённой категории на запрещённую клиент должен остановиться до нового сетевого обращения; реальные внутренние адреса для такой проверки не нужны. Дополнительно ограничивают время, объём ответа и распаковку: даже разрешённый внешний сервер может отдать бесконечное тело. Не следует публиковать «готовую безопасную функцию» из пары regex: политика адресов требует полноценного разбора и тестирования.

### 9. Когда API нужна защита от CSRF и при чём здесь способ передачи JWT?

CSRF использует то, что браузер автоматически прилагает credential к запросу. Классический случай — session cookie: пользователь вошёл в банк, затем открыл чужой сайт, который инициирует запрос изменения данных в банк. Для атаки необязательно читать ответ, достаточно вызвать действие с полномочиями пользователя.

Поэтому фраза «у нас REST/JWT, можно отключить CSRF» неполна. Если JWT хранится в автоматически отправляемой cookie, риск остаётся. Если приложение принимает только явно установленный `Authorization: Bearer ...`, а браузер не добавляет этот credential сам, классический сценарий иной; нужно проверить все альтернативные способы аутентификации, в том числе refresh/logout endpoints.

Для cookie-based приложения обычно используют встроенную защиту фреймворка: непредсказуемый CSRF token, привязанный к сессии, отправляют отдельным полем или заголовком и проверяют на изменяющих запросах. SameSite cookies, проверка Origin/Referer и Fetch Metadata усиливают защиту в подходящем окружении. Не следует превращать GET в команду изменения состояния: такой endpoint сложнее защищать и он может вызываться предзагрузчиками и ссылками.

CORS не заменяет CSRF: некоторые межсайтовые запросы браузер отправляет без preflight, даже если читать ответ не позволит. XSS в доверенном origin часто обходит CSRF-защиту, поскольку вредоносный код действует внутри приложения. Это аргумент исправить обе проблемы, а не отказаться от одного слоя.

### 10. Что реально делает CORS и почему он не защищает API от curl?

CORS — механизм браузера, которым сервер разрешает JavaScript из другого origin читать ответы. Origin включает схему, хост и порт. Это не проверка личности клиента и не сетевой firewall: `curl`, мобильное приложение или другой backend не обязаны применять браузерные правила.

Например, UI `https://app.example.com` обращается к API `https://api.example.com`. Сервер может вернуть разрешённый конкретный origin и, если нужны cookies, `Access-Control-Allow-Credentials: true`. Для credentialed-запросов `Access-Control-Allow-Origin: *` не является допустимым разрешением чтения. Опасный обход — без проверки отражать любой входящий `Origin` вместе с разрешением credentials: атакующий сайт окажется доверенным.

Preflight `OPTIONS` спрашивает, можно ли выполнить определённый метод с определёнными заголовками. Он не заменяет аутентификацию и авторизацию самого последующего запроса. При динамическом ответе по origin нужно учитывать `Vary: Origin`, иначе общий кэш может смешать варианты для разных сайтов.

В конфигурации перечисляют необходимые origins, методы и заголовки, а не открывают всё для устранения ошибки в DevTools. Сравнивают разобранный origin целиком: проверка строкового суффикса не доказывает принадлежность разрешённому origin. В тесте политики используйте синтетические категории `ALLOWED_ORIGIN` и `UNLISTED_ORIGIN` и проверяйте явный отказ второй категории. Некоторые запросы отправляются без preflight; отсутствие разрешения CORS не гарантирует отсутствия побочного эффекта на сервере. Поэтому успешный тест через curl доказывает доступность API, но ничего не доказывает о корректности браузерной CORS-политики.

### 11. Почему Java backend должен учитывать XSS, даже если возвращает JSON?

XSS возникает, когда недоверенные данные попадают в браузерный контекст как исполняемый код. Backend может сохранить опасный комментарий, который позднее небезопасно отобразят основной UI, административная панель или HTML-письмо. Поэтому ответ «мы только JSON, это проблема frontend» упускает хранение данных и другие места отображения.

Экранирование зависит от места использования. Текст HTML, значение атрибута, URL и JavaScript-строка — разные контексты. Один универсальный `replace("<", "&lt;")` их не покрывает. Обычно безопаснее передавать JSON с корректным `Content-Type`, включать автоэкранирование шаблонизатора и вставлять текст через безопасные DOM API, а не собирать HTML строками.

Например, синтетическая метка `[USER_TEXT]` с символами разметки должна отображаться как текст, а не менять структуру документа. Если бизнес-функция действительно разрешает пользовательский HTML, нужен поддерживаемый HTML sanitizer с ограниченным набором тегов и атрибутов. Удаление слова `script` regex не понимает грамматику HTML и обходится другими конструкциями. В URL дополнительно проверяют разрешённые схемы: HTML-экранирование не превращает запрещённую схему в разрешённую.

Не стоит экранировать всё при записи в БД: один и тот же текст затем используется в разных контекстах, а повторное экранирование портит данные. Защита применяется на границе отображения. Content Security Policy уменьшает последствия некоторых ошибок, но не делает небезопасную вставку HTML корректной. `HttpOnly` затрудняет кражу cookie через JS, однако XSS может выполнять действия от имени пользователя.

## Секреты, ресурсы и зависимости

### 12. Как хранить секреты и что делать, если ключ уже попал в Git?

Секретам нужны контроль доступа, доставка приложению, аудит и возможность отзыва. Пароль БД или private key не должен находиться в исходниках, примере конфигурации с реальным значением, Docker image или URL. Приложение получает только свои credentials через механизм окружения/secret manager; архитектура конфигурации подробнее рассмотрена в [microservices.md](microservices.md).

Base64 — кодирование, не шифрование. Шифрованный конфиг тоже не решает задачу полностью, если ключ дешифрования лежит рядом и доступен тем же людям. Environment variables удобны, но могут попасть в диагностические выводы и доступны процессам с соответствующими правами; они не являются универсальным сейфом.

При утечке сначала отзывают или меняют credential, проверяют использование и обновляют потребителей. Удаление строки новым коммитом не отзывает ключ и не удаляет его из истории, кэшей, форков и уже скачанных копий. Переписывание истории имеет отдельную стоимость и не заменяет ротацию.

Полезный сценарий ротации: сервис временно принимает два подписывающих ключа для проверки, новые токены выдаёт новым, после истечения старых отключает прежний. Для пароля БД конкретная процедура зависит от поддержки нескольких credentials и обновления connection pool. Смена значения в secret manager не гарантирует, что уже открытые соединения или кэш приложения его подхватили. При подозрении на компрометацию окно совместимости может быть недопустимо — тогда нужен немедленный отзыв.

### 13. Как писать полезные логи без утечки паролей, токенов и персональных данных?

Нужно логировать событие и контекст расследования, а не весь запрос автоматически. Для отказа доступа полезны время, тип операции, технический идентификатор субъекта, код причины и trace ID. Пароль, session cookie, полный access/reset token и private key не должны попадать в логи даже на DEBUG.

```java
log.warn("Access denied: actorId={}, documentId={}, reason={}, traceId={}",
    actorId, documentId, "OWNER_MISMATCH", traceId);
```

Это пример структуры события, а не разрешение публиковать любые идентификаторы: их чувствительность, срок хранения и круг доступа определяются контекстом. Полный email, телефон и тело анкеты часто не нужны для диагностики; используют минимизацию или контролируемое маскирование. Хеширование телефона без секретного ключа не делает его анонимным: ограниченное пространство номеров позволяет перебор.

Параметризованный logger предотвращает ненужную сборку строк, но не убирает PII и не всегда защищает от log injection. Недоверенные строки с переводами строк и управляющими символами могут подделывать записи; структурированный формат должен корректно экранировать значения и ограничивать длину. Внешний trace ID также нельзя безусловно считать безопасным текстом.

Секрет может проникнуть через исключение HTTP-клиента с URL, `toString()` DTO или автоматический body logging. Поэтому проверяют весь путь и тестируют ошибочные ответы. Доступ к логам и heap dump ограничивают, устанавливают срок хранения и аудит чтения. Клиенту возвращают понятный код и correlation ID; stack trace, SQL и пути окружения остаются в контролируемой диагностике.

### 14. Как безопасно принимать файлы и почему multipart max-size недостаточно?

Загрузка файла — не одна проверка расширения. Сервер должен ограничивать фактическое число полученных байтов, время загрузки, число параллельных операций и расход временного диска. `Content-Length` может отсутствовать или быть недостоверным; multipart-лимит в приложении также не заменяет согласованную конфигурацию reverse proxy и сервера.

Имя для хранения генерируют на сервере. Исходное имя — недоверенные метаданные: оно может содержать путь, управляющие символы или конфликтовать с чужим файлом. Данные хранят вне исполняемого web-root и выдают через контролируемый download endpoint с проверкой владельца. Проверка расширения, MIME header и сигнатуры вместе полезнее одного из этих признаков, но не доказывает безвредность содержимого.

Пример: архив размером 5 МБ распаковывается в 100 ГБ. Лимит входящего HTTP-тела пройден, но диск закончился. При распаковке нужны отдельные пределы общего результата, числа файлов, глубины вложенности и защита от выхода путей архива за целевой каталог. Для изображения важны размеры в пикселях и затраты декодирования, а не только сжатый размер.

Сложные парсеры запускают с ограничениями ресурсов и прав; антивирус/песочница могут быть дополнительным этапом. До успешной проверки файл не делают доступным другим пользователям. При ошибке, отмене и превышении лимита временный файл удаляют. Удалять только после успешной обработки — значит постепенно заполнить диск ошибочными загрузками.

### 15. Как оценивать риск уязвимой зависимости и почему одного номера CVE недостаточно?

Нужно знать фактически попавшую в сборку версию, включая транзитивные зависимости, и понять условия эксплуатации. Декларация версии в `pom.xml` не всегда совпадает с итоговым dependency tree из-за dependency management, BOM и конфликтов. Отдельно учитывают библиотеки, встроенные в fat jar, контейнер, JDK и инструменты сборки.

Пример: у XML-библиотеки обнаружена уязвимость в обработке внешних сущностей. Риск существенно различается, если приложение никогда не парсит XML, если XML приходит только из контролируемого генератора и если публичный endpoint принимает произвольный XML. Но «метод вроде не вызывается» — гипотеза, которую надо подтвердить: путь может идти через фреймворк или другую зависимость.

Основное исправление — поддерживаемая безопасная версия или официальный backport. Временное отключение уязвимой функции допустимо только с проверяемыми условиями, сроком и ответственным. Замалчивание scanner warning без обоснования просто убирает сигнал. Обновление требует совместимых изменений и проверки реального сценария: сборка может проходить, а сериализация или авторизация измениться.

SBOM и сканирование помогают инвентаризации, но не доказывают отсутствие неизвестных уязвимостей и вредоносных пакетов. Нужны доверенные репозитории, воспроизводимые контролируемые версии и минимальный набор зависимостей. Изменение build plugin тоже риск: его код выполняется с доступом окружения сборки. Решение фиксируют с evidence и датой пересмотра, а не вечным «false positive».

### 16. Чем опасна Java-десериализация недоверенных данных и спасает ли Serializable?

`Serializable` — механизм восстановления графа объектов, а не граница безопасности. `ObjectInputStream.readObject()` может создавать доступные классы и вызывать их специальные методы десериализации. Набор классов в classpath иногда позволяет собрать цепочку действий с нежелательными эффектами ещё до того, как приложение приведёт результат к ожидаемому DTO.

Поэтому проверка `instanceof ExpectedMessage` после `readObject()` запаздывает. `serialVersionUID` управляет совместимостью формы класса, но не проверяет отправителя, содержимое и допустимость действий. Нельзя принимать произвольный Java serialization stream из HTTP, очереди или файла пользователя только потому, что транспорт зашифрован.

Для нового внешнего протокола предпочтительнее ограниченная схема данных с явной валидацией и без произвольных имён классов. Сам JSON тоже не гарантирует безопасность, если включена полиморфная десериализация произвольных типов. Независимо от формата ограничивают размер, глубину и число элементов, затем проверяют бизнес-инварианты.

В Java 17–21 доступны serialization filters (`ObjectInputFilter`): они позволяют ограничить классы, глубину графа, число ссылок, размер массивов и поток байтов. Если legacy-протокол нельзя заменить, используют узкий разрешающий фильтр и проверяют его на реальных допустимых графах. Это снижение риска, а не доказательство безопасности любых разрешённых классов: их поведение тоже требует анализа. Фильтры не следует считать включёнными автоматически для каждого `ObjectInputStream`. Подпись данных дополнительно подтверждает источник, но не отменяет безопасный разбор.
