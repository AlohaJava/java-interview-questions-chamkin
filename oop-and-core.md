## Объекты, контракты и модель ООП

### 2. Фундаментальные принципы ООП

**1. Инкапсуляция:**
Объединение состояния и поведения за контрактом, который защищает инварианты объекта. `private` помогает скрыть представление, но геттеры и сеттеры сами по себе инкапсуляции не обеспечивают: сеттер отрицательного баланса или геттер внутреннего изменяемого списка её нарушают. Например, метод `account.withdraw(amount)` проверяет сумму и допустимый остаток, тогда как `setBalance(...)` отдаёт эти правила вызывающему коду.

**2. Наследование:**
Механизм, позволяющий одному классу перенимать состояние и поведение другого (родительского) класса. Способствует переиспользованию кода. В Java класс может наследоваться только от одного класса, но может реализовывать множество интерфейсов.

**3. Полиморфизм:**
Способность программы обрабатывать объекты разных типов идентичным образом, если они имеют общий интерфейс или базовый класс.
- *Полиморфизм времени компиляции (статический)*: Перегрузка методов (Overloading).
- *Полиморфизм времени выполнения (динамический)*: Переопределение методов (Overriding). Виртуальная машина сама определяет, реализацию какого класса необходимо вызвать в рантайме.

**4. Абстракция:**
Процесс выделения наиболее значимых характеристик объекта с игнорированием незначительных деталей. В Java реализуется через абстрактные классы и интерфейсы, задающие контракт поведения без привязки к конкретной реализации.

**Частые follow-up:**
- *Композиция vs наследование.* Наследование связывает классы жестко: наследник зависит от реализации родителя и наследует всё, включая лишнее. Композиция (объект одного класса как поле другого) дает гибкость и слабую связанность — отсюда принцип «предпочитайте композицию наследованию» (Effective Java, п. 18).
- *Ассоциация, агрегация, композиция.* Ассоциация — любая связь между объектами (один использует другой). Агрегация — слабая «часть-целое»: часть существует независимо (Студент и Кафедра). Композиция — сильная «часть-целое»: часть не существует без целого (Дом и Комната) и обычно создается внутри владельца.

### 6. Абстрактные классы и интерфейсы: ключевые отличия

Оба инструмента служат для достижения абстракции, но имеют различные характеристики и сценарии применения.

**Интерфейс (Interface):**
- Задает контракт (что класс должен делать).
- Поддерживает множественное наследование (класс может имплементировать несколько интерфейсов).
- Все методы по умолчанию `public abstract` (до Java 8). С Java 8 добавлены `default` и `static` методы с реализацией. С Java 9 добавлены `private` методы.
- Все поля неявно `public static final`. Полей экземпляра нет; при этом final-ссылка может указывать на изменяемый объект, поэтому не каждое поле является неизменяемой константой.
- Не может иметь конструкторов.

**Абстрактный класс (Abstract Class):**
- Выступает в роли базового класса (что есть объект).
- Класс может иметь только один непосредственный суперкласс, абстрактный или конкретный.
- Может содержать любые методы (абстрактные и с реализацией) с любыми модификаторами доступа (`protected`, `private`).
- Может содержать поля (переменные экземпляра), определяющие состояние объекта.
- Может иметь конструкторы (для инициализации состояния базового класса).

**Частый follow-up — конфликт default-методов (diamond problem):**
Если класс реализует два интерфейса с одинаковыми default-методами, компилятор отказывается выбирать сам и требует явного переопределения. Внутри переопределения можно вызвать конкретную реализацию через `Interface.super.method()`.

```java
interface A { default void hello() { System.out.println("A"); } }
interface B { default void hello() { System.out.println("B"); } }

class C implements A, B {
    @Override
    public void hello() { // обязаны переопределить, иначе не скомпилируется
        A.super.hello();  // явно выбираем реализацию
    }
}
```

**Когда что выбирать:** интерфейс — для контракта поведения между несвязанными классами (`Comparable`, `AutoCloseable`); абстрактный класс — для общего кода и состояния внутри одной иерархии (шаблонный метод, `AbstractList`).

### 31. Default- и static-методы интерфейсов и diamond problem

С Java 8 интерфейсы могут содержать методы с реализацией: `default` (наследуемые) и `static` (не наследуемые). Коротко это уже затрагивалось в вопросе 6 — здесь разберём подробно, включая разрешение конфликтов.

**Зачем добавили.** Главная причина — эволюция API без слома обратной совместимости. В Java 8 в `Collection` и `Iterable` нужно было добавить `stream()`, `forEach()`, `removeIf()`. Без default-методов каждая из миллионов существующих реализаций `List` перестала бы компилироваться. С `default` новый метод появился с реализацией по умолчанию — старый код не сломался, а JDK смогла двигаться дальше. Вторая причина — убрать классы-утилиты вроде `Collections`: `static`-методы интерфейса (`Comparator.comparing()`, `Predicate.isEqual()`) позволяют держать вспомогательную логику прямо рядом с контрактом.

```java
public interface GreetingService {
    String greet(String name);

    default String greetLoudly(String name) {   // наследуется, можно переопределить
        return greet(name).toUpperCase();
    }

    static GreetingService defaultService() {   // вызов только через имя интерфейса
        return name -> "Hello, " + name;
    }
}
```

Свойства, которые спрашивают:
- `default`-метод наследуется реализациями и может быть переопределён; `static`-метод интерфейса **не наследуется** — вызов только как `GreetingService.defaultService()`, через класс-реализацию или экземпляр обратиться нельзя.
- С Java 9 добавились `private`-методы интерфейсов — чтобы выносить общий код из нескольких default-методов, не открывая его наружу.
- Реализация может «реабстрактить» default-метод: объявить его снова `abstract`, обязав наследников реализовать.

**Diamond problem и его разрешение.** Если класс получает один и тот же default-метод из двух интерфейсов, действуют три правила (по приоритету):

1. **Класс побеждает интерфейс.** Если суперкласс (или сам класс) объявляет метод с той же сигнатурой, default-версия из интерфейса просто игнорируется.
2. **Более специфичный интерфейс побеждает.** Если `B extends A` и переопределяет default-метод, берётся версия из `B`.
3. **Иначе — ошибка компиляции.** Компилятор отказывается угадывать и требует явного переопределения, внутри которого можно выбрать конкретную реализацию через `InterfaceName.super.method()`.

```java
interface A { default void hello() { System.out.println("A"); } }
interface B extends A { default void hello() { System.out.println("B"); } }
interface C { default void hello() { System.out.println("C"); } }

class One implements A, B { }              // ок: правило 2, выведет "B"

class Two implements B, C {                // конфликт: B и C не связаны наследованием
    @Override
    public void hello() {                  // обязаны разрешить явно
        B.super.hello();                   // явно выбираем реализацию
    }
}
```

**Почему это не множественное наследование в полном смысле:** у интерфейсов по-прежнему нет состояния (полей экземпляра), конфликтует только поведение, и любая неоднозначность отсекается компилятором — неоднозначной иерархии в рантайме просто не существует. Тот же `Interface.super` — единственный способ вызвать «родительскую» реализацию default-метода, обычный `super` для интерфейсов не работает.

### 27. Модификаторы доступа: private, package-private, protected и public

Четыре уровня видимости, от самого узкого к самому широкому. Их задача — инкапсуляция: показывать наружу минимум.

| Модификатор | Класс | Пакет | Наследники (другой пакет) | Весь мир |
|---|---|---|---|---|
| `private` | + | − | − | − |
| без модификатора (package-private) | + | + | − | − |
| `protected` | + | + | + | − |
| `public` | + | + | + | + |

**private** — виден только внутри своего класса. Нюанс: «внутри класса» — это весь топ-левел класс целиком, поэтому вложенные классы видят `private`-члены друг друга (в современных JVM доступ поддерживается механизмом nestmates; старые компиляторы генерировали синтетические методы доступа).

**package-private** (default) — модификатор отсутствует, видимость ограничена пакетом. Частая ловушка — забыть модификатор у метода, который задумывался публичным, и удивляться, почему из другого пакета его «нет». Пакет в Java — реальная граница доступа, а не просто папка.

**protected** — то же, что package-private, плюс наследники в любых пакетах. Тонкость, на которой многие спотыкаются: наследник в другом пакете видит `protected`-член только **через ссылку своего типа** (или подтипа), но не через ссылку на родителя:

```java
package a;
public class Parent { protected int value; }

package b;
public class Child extends Parent {
    void test() {
        this.value = 1;            // ок
        Child c = new Child();
        c.value = 1;               // ок
        Parent p = new Child();
        // p.value = 1;            // ошибка компиляции: другой пакет, ссылка типа Parent
    }
}
```

**public** — виден всем.

**Правила применения:**
- Классы верхнего уровня могут быть только `public` или package-private; `private`/`protected` допустимы только для вложенных классов.
- Поля — почти всегда `private`, доступ через методы. Публичное поле — это контракт, который уже не изменить.
- При переопределении метода доступ можно только расширять, сужать нельзя (см. вопрос 23) — иначе сломался бы принцип подстановки Лисков: код, работающий с родителем, не смог бы вызвать метод на наследнике.
- Общий принцип: видимость — минимально необходимая. Легче расширить доступ позже, чем убрать его из-под чужого кода.

### 5. Механизм передачи параметров: по значению или по ссылке

В Java **все параметры передаются исключительно по значению** (pass-by-value). Передачи по ссылке (как в C++) не существует.

- **Примитивные типы:** Передается копия значения. Изменение этой копии внутри метода никак не влияет на оригинальную переменную.
- **Объекты (ссылочные типы):** Передается копия ссылки на объект. Копия указывает на тот же участок памяти, что и оригинальная ссылка.
  - Если изменить состояние объекта внутри метода (например, вызвать сеттер), изменения отразятся на оригинальном объекте.
  - Если присвоить параметру новую ссылку (например, `param = new Object()`), оригинальная ссылка останется неизменной и будет указывать на старый объект.

```java
public void modify(int primitive, StringBuilder reference) {
    primitive = 100; // Не повлияет на оригинал
    reference.append(" modified"); // Повлияет на оригинал
    reference = new StringBuilder("new"); // Не повлияет на оригинал
}
```

### 49. Почему поле и метод одного объекта дают разные ответы после приведения типа?

```java
class Plan {
    String name = "base";
    String label() { return name; }
}

class Trial extends Plan {
    String name = "trial";
    @Override String label() { return name; }
}

Plan p = new Trial();
System.out.println(p.name + " / " + p.label()); // base / trial
```

В объекте два отдельных поля. Выражение `p.name` выбирает поле по типу переменной `Plan`. Для вызова переопределённого метода JVM выбирает реализацию по фактическому классу объекта. Внутри `Trial.label()` имя поля разрешается в контексте `Trial`. Приведение `((Trial) p).name` даст `trial`, потому что у выражения перед точкой теперь другой тип. Состояние самого объекта осталось прежним.

Если вызывающему коду нужны разные имена для разных тарифов, оставьте один метод доступа. Иначе часть программы прочитает одно поле, часть другое, и запись через ссылку родительского типа затронет только родительское поле.

### 1. Контракт между методами equals() и hashCode()

Методы `equals()` и `hashCode()` используются для сравнения объектов и определения их местоположения в хэш-коллекциях (например, `HashMap`, `HashSet`).

**Правила контракта:**
1. Если два объекта равны по методу `equals()`, их хэш-коды (`hashCode()`) должны быть абсолютно одинаковыми.
2. Если хэш-коды двух объектов равны, это не гарантирует их равенства по `equals()` (возникновение коллизии).
3. При многократном вызове `hashCode()` для одного и того же объекта (если состояние, используемое в equals, не изменялось) должно возвращаться одно и то же значение.
4. Хэш должен согласовываться с равенством: нельзя включать в него различия, которые `equals()` игнорирует. Строго одинаковый набор полей не обязателен: постоянный хэш `return 1` законен, но ухудшает производительность. Обычно хэш строят из значимых полей равенства.

Контракт самого `equals()` (по документации `Object`) — рефлексивность (`x.equals(x)` — true), симметричность (`x.equals(y)` ⇔ `y.equals(x)`), транзитивность, консистентность при неизменном состоянии и `x.equals(null)` — всегда false. По умолчанию `equals()` в `Object` сравнивает ссылки (`==`), а `hashCode()` привязан к идентичности объекта.

**Последствия нарушения:**
Если переопределить `equals()`, но не переопределить `hashCode()`, два логически идентичных объекта могут получить разные хэш-коды. Это приведет к тому, что коллекция, основанная на хэшировании, не сможет корректно найти или перезаписать объект, что вызовет утечки памяти и логические ошибки.

**Частый follow-up:** что будет, если изменить поле объекта, уже лежащего в `HashSet`/`HashMap`? Хэш-код объекта изменится, но внутри коллекции он останется в старой корзине — объект «потеряется»: `contains()`/`get()` перестанут его находить, хотя он там есть. Поэтому состояние, участвующее в равенстве и хэшировании ключа, должно оставаться стабильным. `String` и `Integer` удобны; record безопасен только при подходящих компонентах — он не делает вложенные объекты неизменяемыми.

```java
public final class User {
    private final String login;

    public User(String login) {
        this.login = Objects.requireNonNull(login);
    }

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (o == null || getClass() != o.getClass()) return false;
        User user = (User) o;
        return login.equals(user.login);
    }

    @Override
    public int hashCode() {
        return login.hashCode();
    }
}
```

### 10. Как создать неизменяемый (Immutable) класс

Неизменяемый объект после создания не может изменить свое состояние. Такие классы потокобезопасны и могут свободно разделяться между потоками (пример — `String`).

**Правила проектирования:**
1. Объявить класс `final`, чтобы запретить наследование и переопределение поведения.
2. Объявить все поля `private final` и инициализировать их только через конструктор.
3. Не предоставлять сеттеров и иных методов, мутирующих состояние.
4. Для изменяемых полей (коллекции, массивы, `Date`) выполнять **защитное копирование (defensive copy)**: копировать входящие объекты в конструкторе и возвращать копии из геттеров — иначе внешний код сможет изменить внутреннее состояние через полученную ссылку.
5. Методы, «изменяющие» объект, должны возвращать новый экземпляр (как `String.substring()`).

```java
public final class Person {
    private final String name;
    private final List<String> phones;

    public Person(String name, List<String> phones) {
        this.name = name;
        this.phones = new ArrayList<>(phones); // защитная копия на входе
    }

    public String getName() {
        return name;
    }

    public List<String> getPhones() {
        return new ArrayList<>(phones); // защитная копия на выходе
        // либо Collections.unmodifiableList(phones)
    }
}
```

С Java 16 для носителей данных можно использовать `record`: он генерирует поля, конструктор, акцессоры и методы значений. Неизменяемость поверхностная: `record Box(List<String> items)` не копирует список, и `box.items().add(...)` может изменить наблюдаемое состояние. Для этого примера компактный конструктор `public Box { items = List.copyOf(items); }` создаёт независимый неизменяемый список строк.

### 30. Deep copy и Shallow copy: Cloneable, copy-конструктор, сериализация

Shallow copy копирует сам объект, но вложенные объекты разделяет с оригиналом по ссылке. Deep copy рекурсивно копирует весь граф объектов. Разница проявляется сразу: поменяли вложенный объект в shallow-копии — поменялся и в оригинале.

```java
User copy = original.shallowCopy();
copy.getRoles().add("ADMIN"); // у original тот же список — роль добавилась и там
```

**Object.clone() и Cloneable.** `clone()` по умолчанию делает именно shallow copy. Дизайн сломан с рождения: `Cloneable` — маркерный интерфейс без единого метода, а `clone()` живёт в `Object` и имеет модификатор `protected`. Чтобы получить рабочее клонирование, нужно реализовать маркер, расширить видимость до `public`, переопределить метод и вручную докопировать все мутабельные поля. Джошуа Блох прямо рекомендует избегать этот механизм. На собеседовании достаточно знать: «shallow по умолчанию, контракт хрупкий, лучше не использовать».

**Copy-конструктор / статическая фабрика** — рекомендуемый способ: полный контроль над тем, что копируется глубоко, а что по ссылке.

```java
public class User {
    private final String name;
    private final List<String> roles;

    public User(User source) {
        this.name = source.name;                    // String неизменяем — ссылка безопасна
        this.roles = new ArrayList<>(source.roles); // копируем контейнер; String-элементы безопасно разделять
    }
}
```

Неизменяемые объекты (`String`, `Integer`, `LocalDate`, record'ы с иммутабельными полями) копировать глубоко не нужно — их безопасно разделять. Deep copy требуется только для мутабельных ветвей графа.

**Сериализация как deep copy.** Обходной путь: сериализовать объект в байты и десериализовать обратно — обычно восстановится отдельный сериализуемый граф с сохранением общих ссылок и циклов. Это не универсальная полная копия: `transient`, `readResolve` и пользовательские методы меняют результат.

```java
ByteArrayOutputStream bos = new ByteArrayOutputStream();
try (ObjectOutputStream out = new ObjectOutputStream(bos)) {
    out.writeObject(original);
}
byte[] bytes = bos.toByteArray();
try (ObjectInputStream in = new ObjectInputStream(new ByteArrayInputStream(bytes))) {
    User copy = (User) in.readObject();
}
```

Минусы очевидны: медленно, весь граф обязан быть `Serializable`, `transient`-поля теряются, `serialVersionUID` должен совпадать. Для прикладных моделей обычно проще явный copy-конструктор или маппер: они задают границы копирования и не требуют промежуточного текстового формата.

**Follow-up:** циклические ссылки — Java-сериализация их корректно обрабатывает, а вот наивный ручной deep copy зациклится. И обратная сторона: не всякий объект вообще осмысленно копировать (потоки, соединения, файловые дескрипторы).

### 20. Records и sealed-классы

Обе возможности направлены на одно: убрать шаблонный код и сделать модель данных явной.

**Record (Java 16):**
Компактное объявление носителя данных с поверхностной неизменяемостью. Компилятор генерирует: `private final` поля, канонический конструктор, акцессоры (имя совпадает с полем — `x()`, без префикса `get`), `equals()`, `hashCode()` и `toString()`. Класс автоматически `final`, наследоваться от другого класса не может, интерфейсы реализовывать — может. Для валидации аргументов есть компактный конструктор без списка параметров.

```java
public record Point(int x, int y) {
    public Point { // компактный конструктор: валидация
        if (x < 0 || y < 0) throw new IllegalArgumentException();
    }
}

Point p = new Point(1, 2);
System.out.println(p.x());   // акцессор без get
```

Ограничение, о котором спрашивают: record удобен для DTO и значений, но неизменяемость вложенных компонентов нужно обеспечить отдельно. Сеттеров нет по определению; мутируемое поле-коллекцию внутрь кладут с осторожностью — record сам её не скопирует.

**Sealed-классы и интерфейсы (Java 17):**
Позволяют явно перечислить, кто имеет право наследовать тип — через `permits`. Каждый разрешённый наследник обязан объявить себя `final`, `sealed` (своим списком) или `non-sealed`. В именованном модуле прямые наследники должны быть в том же модуле (пакеты могут различаться); в безымянном модуле — в том же пакете.

```java
public sealed interface Shape permits Circle, Rectangle { }

public record Circle(double radius) implements Shape { }              // final по умолчанию
public non-sealed class Rectangle implements Shape { }                // открыт дальше
```

**Главная выгода** — связка с pattern matching в switch: компилятор знает полный список наследников и проверяет исчерпываемость ветвей. Добавите новый наследник — все switch, которые забыли обновить, перестанут компилироваться. Это удобный способ моделировать алгебраические типы данных: результаты операций (`Success | Failure`), деревья выражений, состояния заказа.

### 48. Почему record с массивом не получает равенство по содержимому и как защитить его состояние?

Генерируемое равенство record сравнивает значения компонентов. Для ссылочного компонента применима его семантика `equals`, а у массива она основана на идентичности. Поэтому два record с разными массивами одинакового содержания не равны. Кроме того, final-ссылка на массив не запрещает менять его элементы.

```java
record Packet(byte[] data) { }
Packet a = new Packet(new byte[]{1, 2});
Packet b = new Packet(new byte[]{1, 2});
System.out.println(a.equals(b)); // false

a.data()[0] = 9; // наблюдаемое состояние a изменилось
```

Защитное копирование на входе и на выходе предотвращает внешнее изменение, но само по себе не даёт равенство по содержимому. Если такое равенство требуется, придётся согласованно переопределить `equals` и `hashCode`, используя `Arrays.equals`/`Arrays.hashCode`, и учесть, например, `null`. Также важно сохранить record-инвариант: record, восстановленный из результатов его акцессоров, должен быть равен исходному. Копирующий акцессор вместе с унаследованным сравнением массивов по ссылке этот инвариант нарушит.

Часто проще выделить отдельный неизменяемый тип байтового значения с нужным равенством или выбрать immutable-представление компонентов. Для `List<String>` удобно `List.copyOf`, поскольку строки неизменяемы и список уже определяет равенство по элементам; для списка изменяемых объектов этого мало. Частая ошибка — использовать любой record как ключ карты лишь потому, что компилятор сгенерировал `hashCode`.

### 8. Ключевые слова final, finally и finalize

Несмотря на внешнее сходство, это три совершенно разных механизма языка.

**final — модификатор:**
- *final-переменная* — может быть присвоена только один раз. Это не обязательно константа времени компиляции: ею бывает только `final` переменная примитивного типа или `String`, инициализированная константным выражением. Для ссылочного типа запрещено менять ссылку, но состояние самого объекта изменять можно.
- *final-метод* — не может быть переопределен в подклассах (защита контракта, например `Object.wait()`).
- *final-класс* — не может иметь наследников (например, `String`, `Integer`).

**finally — блок обработки исключений:**
Блок, который выполняется при выходе управления из `try-catch` — независимо от того, возникло исключение или нет, и даже при `return` внутри `try` (сначала выполнится `finally`, потом произойдет возврат). Используется для освобождения ресурсов. Выполнение не гарантировано при завершении процесса/JVM; до него также не дойдут, если `try` не завершится (например, зависнет навсегда). Ловушка: `return` или `throw` внутри `finally` затирает и результат, и исключение из `try` — так делать нельзя. В современном коде для ресурсов предпочтительнее `try-with-resources`.

**finalize — метод класса Object:**
Метод устаревшего механизма финализации: мог вызываться после обнаружения недостижимости объекта, но мог и не выполниться. Deprecated с Java 9, deprecated for removal с Java 18 (см. вопрос 7). Для детерминированного закрытия ресурсов нужен `AutoCloseable`.

```java
final class Constants {
    static final int MAX_SIZE = 100; // константа времени компиляции

    final void print() { // метод нельзя переопределить
        try {
            riskyOperation();
        } finally {
            // выполнится при обычном или исключительном выходе из try
        }
    }
}
```

### 9. Ключевое слово static: поля, методы, блоки и вложенные классы

Модификатор `static` привязывает член к самому классу, а не к его экземплярам.

**Статические поля:**
Существуют в единственном экземпляре на класс и разделяются всеми объектами. Часто используются для констант (`public static final`) и счетчиков экземпляров.

**Статические методы:**
Вызываются через имя класса без создания объекта (`Math.max()`). Не могут быть переопределены — только скрыты (method hiding), полиморфизм на них не работает.

**Статические блоки инициализации:**
Выполняются один раз при инициализации класса, до создания его первого экземпляра. Загрузка и инициализация — разные этапы: например, чтение константы времени компиляции обычно не инициирует класс. Применяются для сложной инициализации статических полей.

**Вложенные статические классы (static nested classes):**
Не хранят неявной ссылки на экземпляр внешнего класса (в отличие от внутренних, inner classes), что предотвращает утечки памяти. Пример — `Map.Entry`.

**Почему из static-метода нельзя обратиться к this:**
`this` — ссылка на конкретный экземпляр, а статический метод существует вне контекста какого-либо экземпляра и может быть вызван, когда ни одного объекта класса еще не создано. По той же причине статический метод не имеет прямого доступа к нестатическим полям и методам.

```java
public class Counter {
    private static int count; // общее для всех экземпляров

    static { // выполнится один раз при загрузке класса
        count = 0;
    }

    public static int getCount() {
        return count; // this.count — ошибка компиляции
    }
}
```

### 28. Порядок инициализации класса и объекта в иерархии наследования

Сначала инициализируется класс (один раз при первом активном использовании), потом — объект. Одна загрузка ещё не означает инициализацию. Внутри иерархии всегда от предка к потомку.

Полный порядок при `new Child()`:

1. **Static-поля и static-блоки класса Parent** — в порядке объявления в коде. Выполняется один раз при инициализации класса.
2. **Static-поля и static-блоки класса Child** — аналогично.
3. Память под объект выделена, все instance-поля (и Parent, и Child) получают значения по умолчанию: `0`, `null`, `false`.
4. **Instance-поля и instance-блоки Parent** — в порядке объявления.
5. **Конструктор Parent.**
6. **Instance-поля и instance-блоки Child.**
7. **Конструктор Child.**

Классическая задача «что выведет код»:

```java
class Parent {
    static { System.out.println("1: static Parent"); }
    { System.out.println("3: instance Parent"); }
    Parent() { System.out.println("4: конструктор Parent"); }
}

class Child extends Parent {
    static { System.out.println("2: static Child"); }
    { System.out.println("5: instance Child"); }
    Child() { System.out.println("6: конструктор Child"); }
}

public class Main {
    public static void main(String[] args) {
        new Child();
    }
}
```

Вывод: `1, 2, 3, 4, 5, 6`. Статика родителя раньше статики потомка, instance-блоки всегда раньше «своего» конструктора, и вся инициализация родителя завершается до начала инициализации потомка.

**Follow-up вопросы:**
- Второй `new Child()` выведет только `3, 4, 5, 6` — класс уже инициализирован, статика не повторяется.
- Обращение к compile-time константе (`static final String X = "a"`) не триггерит инициализацию класса — значение подставляется на этапе компиляции.
- Порядок объявления имеет значение: static-блок не может читать static-поле, объявленное ниже (ошибка «illegal forward reference»), хотя присваивать ему может — с неочевидным результатом.
- Самая коварная ловушка — вызов переопределённого метода из конструктора родителя:

```java
class Parent {
    Parent() { print(); }
    void print() { }
}

class Child extends Parent {
    private final String name = new String("child"); // не compile-time константа

    @Override
    void print() { System.out.println(name); }
}

new Child(); // выведет null
```

Когда конструктор `Parent` вызывает `print()`, диспетчеризация находит версию из `Child`, но поле `name` ещё не инициализировано (шаг 6 наступит после конструктора родителя) — метод видит `null`. Отсюда правило: из конструктора вызывать только `private`, `final` или `static` методы.

### 23. Перегрузка (Overload) и переопределение (Override) методов

Это два разных механизма полиморфизма, и путаница между ними — классика собеседований.

**Перегрузка (Overload) — статический полиморфизм, время компиляции:**
Несколько методов с одинаковым именем, но разными списками параметров (типы, количество, порядок). Выбор конкретного метода делает **компилятор** по статическим типам аргументов. Возвращаемый тип, модификатор доступа и `throws` можно менять как угодно — они в перегрузке не участвуют (одним возвращаемым типом методы различать нельзя — ошибка компиляции).

**Переопределение (Override) — динамический полиморфизм, рантайм:**
Наследник предоставляет свою реализацию метода с той же сигнатурой. Выбор реализации делает **JVM** по фактическому типу объекта. Правила:
1. Сигнатура (имя + параметры) должна совпадать.
2. Возвращаемый тип может быть **ковариантным** — тем же или подтипом исходного (`Number` → `Integer` допустимо).
3. Модификатор доступа можно только расширять (`protected` → `public`), сужать нельзя.
4. Checked-исключения в `throws` — только те же или более узкие; добавить новое checked нельзя (unchecked — без ограничений).
5. Нельзя переопределить `final`, `private` (он просто не виден наследнику) и `static` методы. Статический метод с той же сигнатурой в наследнике — это **сокрытие (hiding)**, а не переопределение: выбор произойдёт по типу ссылки, полиморфизм не сработает.

```java
class Animal {
    public Animal findBuddy() { return new Animal(); }
}

class Dog extends Animal {
    @Override
    public Dog findBuddy() { return new Dog(); } // ковариантный тип — ОК
}
```

**Примеры-ловушки на перегрузку:**
```java
void print(Object o) { System.out.println("Object"); }
void print(String s) { System.out.println("String"); }

print(null); // "String" — выбирается самый специфичный тип

Object obj = "text";
print(obj);  // "Object" — перегрузка выбирается по типу ССЫЛКИ, а не объекта
```

Последний пример — самое важное: перегрузка разрешается на этапе компиляции по статическому типу аргумента, переопределение — в рантайме по фактическому типу объекта. Половина задачек на собеседованиях построена ровно на этом различии.

### 34. Как компилятор выбирает между widening, boxing и varargs при перегрузке?

Перегрузка выбирается по фазам, а не по общей «близости» всех типов. Сначала рассматриваются методы фиксированной арности без boxing/unboxing: допустимы, например, расширения `int → long`. Если подходящих нет, разрешаются boxing/unboxing. Только затем рассматривается variable arity — упаковка аргументов в массив для varargs. Внутри первой успешной фазы выбирается наиболее специфичный применимый метод.

```java
static String pick(long n) { return "long"; }
static String pick(Integer n) { return "Integer"; }
static String pick(int... n) { return "varargs"; }

System.out.println(pick(1));                  // long: widening раньше boxing
System.out.println(pick(Integer.valueOf(1))); // Integer: точное совпадение
System.out.println(pick());                   // varargs
```

Varargs-метод может участвовать в ранней фазе как обычный метод с параметром-массивом: `pick(new int[]{1})` не требует упаковки в новый массив. Это причина, по которой правило «varargs всегда последний» без оговорки неточно.

Java не объединяет любые преобразования в произвольную цепочку: `int` нельзя автоматически расширить до `long`, а затем упаковать в `Long` ради вызова `accept(Long)`. Сначала нужно явно получить подходящий примитив или обёртку.

Частая ошибка — добавлять перегрузки, отличающиеся обёртками и примитивами, в публичный API без проверки старых вызовов: после перекомпиляции выбор метода может измениться. Для разных смыслов часто понятнее разные имена.

### 26. Примитивные типы: размеры, widening и narrowing, переполнение и потеря точности

В Java 8 примитивных типов, и их размеры зафиксированы спецификацией — они не зависят от платформы и JVM.

| Тип | Размер | Диапазон / точность |
|---|---|---|
| `byte` | 1 байт | -128 … 127 |
| `short` | 2 байта | -32768 … 32767 |
| `int` | 4 байта | примерно ±2,1 млрд |
| `long` | 8 байт | примерно ±9,2×10¹⁸ |
| `char` | 2 байта | 0 … 65535 (беззнаковый, UTF-16) |
| `float` | 4 байта | ~7 значащих цифр (IEEE 754) |
| `double` | 8 байт | ~15-16 значащих цифр (IEEE 754) |
| `boolean` | не специфицирован | `true` / `false` |

**Widening (расширение)** — неявное преобразование в более широкий тип: `byte → short → int → long → float → double`, а также `char → int`. Компилятор делает его сам, каст не нужен.

**Narrowing (сужение)** может потерять данные и обычно требует явного каста; исключение — допустимые константные присваивания, например `byte b = 127`. При сужении целого типа сохраняются только младшие биты нужной разрядности. Преобразование `float`/`double` в `int`/`long` сначала округляет к нулю; выход за диапазон даёт соответствующий MIN/MAX, а NaN превращается в 0. Для `byte`/`short`/`char` после преобразования в `int` выполняется целочисленное сужение. `double → float` округляется по IEEE 754 и может дать infinity или ноль из конечного ненулевого значения.

Две тонкости, которые любят спрашивать:
1. Widening не всегда «бесплатен»: при `long → float` или `long → double` теряется точность, потому что значащая точность `float` — 24 бита, `double` — 53 (включая неявный ведущий бит), а в `long` 63 значащих бита. Тип шире по диапазону, но уже по точности.
2. `char` — беззнаковый, остальные целые — знаковые. Арифметика с `byte`, `short`, `char` всегда повышается до `int`.

**Переполнение** в Java тихое: никаких исключений, значение просто «заворачивается» по кольцу (арифметика в дополнительном коде). Для контроля есть `Math.addExact`, `Math.multiplyExact` и др. — они бросают `ArithmeticException`.

```java
int max = Integer.MAX_VALUE;
System.out.println(max + 1);            // -2147483648 — тихое переполнение
System.out.println(Math.addExact(max, 1)); // ArithmeticException

byte b = 1;
// b = b + 1;  // не компилируется: b + 1 имеет тип int
b += 1;       // компилируется: += содержит скрытый каст

long l = 9007199254740993L; // 2^53 + 1
double d = l;               // widening, но с потерей точности
System.out.println(l - (long) d); // 1 — младший бит потерян

int i = (int) 3_000_000_000L; // -1294967296: отрезаны старшие биты
int j = (int) 3_000_000_000d; // 2147483647: ограничение Integer.MAX_VALUE
int n = (int) Double.NaN;    // 0
```

**Частые follow-up:**
- Целочисленный литерал по умолчанию `int`: `long x = 3_000_000_000L;` без `L` не скомпилируется. Классический баг — `long timeout = 24 * 60 * 60 * 1000 * 1000;` — сначала всё умножается в `int` и переполняется, и только потом присваивается в `long`.
- `float`/`double` — двоичные дроби: `0.1 + 0.2 != 0.3`. Для денег — `BigDecimal` (или `long` в минорных единицах).
- Деление `int / int` — целочисленное: `5 / 2 == 2`. Хотите дробь — приводите хотя бы один операнд к `double`.

### 50. Куда пишет выражение с постинкрементом индекса?

```java
int[] samples = {10, 20};
int i = 0;
samples[i++] = i;
System.out.println(Arrays.toString(samples)); // [1, 20]
System.out.println(i);                       // 1
```

Для назначения сначала вычисляются ссылка на массив и индекс. Выражение `i++` даёт индекс 0 и увеличивает `i` до 1. Правая часть затем читает уже единицу. Замена на `++i` выберет индекс 1 и даст массив `[10, 1]`. Для разбора достаточно проследить порядок вычисления в одном потоке.

На ревью перепишите первую версию как `int slot = i; i++; samples[slot] = i;`. Промежуточное имя показывает, какой индекс надо сохранить для записи. Так проще убедиться, что при обработке последнего доступного слота код обращается по нужному адресу.

### 36. Как правильно считать деньги через BigDecimal: scale, precision и округление?

`BigDecimal` хранит десятичное число без ошибки двоичного представления, но правила округления всё равно нужно задать. `scale` определяет положение десятичной точки, `precision` — количество значащих цифр. Это разные ограничения: два знака после запятой не равны двум значащим цифрам.

```java
BigDecimal price = new BigDecimal("19.90");
BigDecimal tax = price.multiply(new BigDecimal("0.20"));
BigDecimal total = price.add(tax).setScale(2, RoundingMode.HALF_UP);
System.out.println(total); // 23.88

BigDecimal third = BigDecimal.ONE.divide(
        BigDecimal.valueOf(3), 2, RoundingMode.HALF_EVEN); // 0.33
```

`new BigDecimal(0.1)` фиксирует уже неточное двоичное значение `double`. Строковый конструктор сохраняет введённую десятичную запись; `BigDecimal.valueOf(0.1)` использует строковую форму double. `divide` без округления бросает `ArithmeticException`, если точный результат — бесконечная десятичная дробь. Методы возвращают новый объект: игнорировать результат `amount.setScale(...)` — ошибка.

Равенство имеет отдельную ловушку: `1.0` и `1.00` равны по `compareTo`, но не по `equals`, учитывающему scale. Это влияет на `HashSet` и ключи `HashMap`; нормализация должна быть частью согласованного бизнес-контракта. Округлять после каждой промежуточной операции или только итог — тоже решение предметной области, которое может изменить сумму.

### 11. Autoboxing и Unboxing: классы-обертки и их ловушки

Каждому примитивному типу соответствует класс-обертка: `int` → `Integer`, `long` → `Long`, `boolean` → `Boolean` и т.д. С Java 5 компилятор автоматически выполняет преобразования:

- **Autoboxing** — примитив в объект: `Integer a = 10;` компилируется в `Integer.valueOf(10)`.
- **Unboxing** — объект в примитив: `int b = a;` компилируется в `a.intValue()`.

**Кэширование Integer:**
`Integer.valueOf()` кэширует объекты для значений от **-128 до 127** (верхняя граница настраивается параметром JVM). Кэш также существует у `Byte`, `Short`, `Character`, `Long` и `Boolean`. Поэтому сравнение оберток через `==` внутри диапазона кэша может вернуть `true`, а вне его — `false`.

**Типичные ловушки:**
1. Сравнение оберток оператором `==` сравнивает ссылки, а не значения — всегда используйте `equals()` или приводите к примитиву.
2. **NullPointerException при unboxing**: если обертка равна `null`, неявное приведение к примитиву выбросит исключение.
3. Скрытые аллокации в циклах: автобоксинг создает объекты и повышает нагрузку на GC — в горячих участках кода следует использовать примитивы.

```java
Integer a = 100, b = 100;
Integer c = 200, d = 200;
System.out.println(a == b); // true — оба из кэша
System.out.println(c == d); // обычно false; вне обязательного кэша результат не гарантирован

Integer e = null;
int f = e; // NullPointerException при unboxing
```

### 3. Класс String: Пул строк и неизменяемость (Immutability)

Класс `String` в Java является неизменяемым (immutable) и объявлен `final` (от него нельзя наследоваться; это не связано с финализацией).

**Неизменяемость:**
После создания объекта типа `String`, его значение не может быть изменено. Методы возвращают строковый результат, не изменяя исходную строку. Когда результат совпадает с исходным, реализация может вернуть тот же объект; создание нового объекта не является обязательным для каждого вызова.
*Преимущества:*
- Потокобезопасность (не требуется синхронизация).
- Стабильность переданных значений (пути, URL, имена классов). Для стираемых секретов часто выбирают массив символов: содержимое `String` нельзя очистить по требованию.
- Возможность кэширования хэш-кода (полезно при использовании строк в качестве ключей `HashMap`).

**Пул строк (String Pool):**
Специальная область в Heap-памяти для кэширования строковых литералов с целью экономии ресурсов.
Если строка создается через литерал (`String s = "Hello"`), JVM проверяет Пул. Если такая строка там есть, возвращается ссылка на нее. Если нет — строка добавляется в Пул.
Если строка создается через конструктор (`String s = new String("Hello")`), создаётся отдельный объект строки; литерал `"Hello"` при этом уже интернирован. `intern()` возвращает канонический объект из пула, а не меняет идентичность исходной строки.

**Нюансы, которые любят спрашивать:**
- До Java 7 пул лежал в PermGen и плохо чистился; с Java 7 он перенесен в Heap, а с Java 8 PermGen вообще заменили на Metaspace — сейчас интернированные строки собираются GC как обычные объекты.
- Строки, вычисленные в рантайме (результат конкатенации переменных, `substring`, `new String(...)`), в пул автоматически не попадают — только литералы и явный `intern()`.

```java
String s1 = "java";
String s2 = "java";
String s3 = new String("java");
String s4 = "ja" + "va";           // склеивается компилятором в литерал
String s5 = "ja";
String s6 = s5 + "va";             // вычисляется в рантайме — новый объект

System.out.println(s1 == s2);            // true, указывают на один объект в пуле
System.out.println(s1 == s3);            // false, s3 - отдельный объект в Heap
System.out.println(s1 == s4);            // true, compile-time константа — из пула
System.out.println(s1 == s6);            // false, рантайм-конкатенация
System.out.println(s1 == s6.intern());   // true
```

### 25. StringBuilder, StringBuffer и конкатенация строк

`String` неизменяем, поэтому любая конкатенация порождает новый объект. Отсюда весь вопрос выбора инструмента.

**Конкатенация через `+`:**
В пределах одного выражения компилятор сам превращает `+` в эффективную сборку строки (с Java 9 — через `invokedynamic` и `StringConcatFactory`). Здесь `+` читаемее и не медленнее. Проблема — конкатенация **в цикле**: на каждой итерации создаётся новый промежуточный объект (без обязательного создания `StringBuilder` в современных JDK), строка копируется заново, итоговая сложность O(n²). В цикле — только `StringBuilder`.

**StringBuilder:**
Изменяемый буфер символов (в отличие от неизменяемой `String`). Методы `append`, `insert`, `delete` работают по месту, без копий. Не синхронизирован — это стандартный выбор для однопоточного кода, что покрывает 99% случаев.

**StringBuffer:**
Тот же API, но все методы `synchronized`. Потокобезопасен, но за это платит блокировками. На практике нужен редко: разделять один текстовый буфер между потоками — почти всегда сомнительная идея. Класс существует со времён Java 1.0, `StringBuilder` появился в Java 5 именно как его несинхронизированная замена.

```java
String s = "a" + "b" + "c";       // ок: одно выражение, JIT/компилятор справятся

String result = "";
for (String part : parts) {
    result += part;               // плохо: O(n²), новый объект каждую итерацию
}

StringBuilder sb = new StringBuilder();
for (String part : parts) {
    sb.append(part);              // правильно
}
String result2 = sb.toString();
```

**Про JIT (частый follow-up):**
JIT действительно умеет оптимизировать конкатенации: escape analysis может вообще убрать аллокации, а короткие склейки в горячем коде иногда становятся такими же быстрыми, как `StringBuilder`. Но на это не стоит закладываться: оптимизация не гарантирована и ломается при малейшем усложнении кода. Правило, которого ждут на собеседовании: одно выражение — `+`, цикл или условная сборка — `StringBuilder`, `StringBuffer` — только если буфер осознанно разделяется между потоками.

### 37. Почему String.length() не всегда равно числу символов на экране?

`String` использует модель UTF-16: `length()` считает кодовые единицы `char`, а не пользовательские символы. Символ вне Basic Multilingual Plane занимает суррогатную пару — два `char`. Ещё один уровень — графемы: буква с комбинируемым знаком или последовательность emoji может содержать несколько Unicode code points, хотя пользователь воспринимает её как один символ.

```java
String s = "A\uD83D\uDE00"; // A и emoji
System.out.println(s.length());                  // 3 char
System.out.println(s.codePointCount(0, s.length())); // 2 code points
s.codePoints().forEach(cp -> System.out.println(Integer.toHexString(cp)));
```

`substring(1, 2)` в этом примере отрежет половину суррогатной пары. Для движения по code points есть `offsetByCodePoints`, для разбора текста на пользовательские границы — подходящие средства сегментации; их поведение зависит от версии Unicode и правил продукта. `chars()` возвращает поток кодовых единиц, `codePoints()` — поток кодовых точек.

Кодировка файла или HTTP-тела — отдельная задача: UTF-8 байты не равны ни `char`, ни code points. Указывайте `StandardCharsets.UTF_8` при преобразовании `String ↔ byte[]`, если это формат протокола. Частая ошибка — ограничивать поле «20 символов» через `length()`, не договорившись, что считают UI, сервер и БД. Похожие визуально строки также могут иметь разные Unicode-последовательности: при необходимости сравнения нужна явно выбранная нормализация.

### 21. Comparable и Comparator

Оба интерфейса задают порядок объектов, разница в том, где живёт логика сравнения.

**`Comparable<T>`** — естественный (natural) порядок, встроенный в сам класс. Метод `compareTo` один, значит и порядок один: `String` сортируется по алфавиту, `Integer` — по возрастанию. `Collections.sort(list)` без компаратора требует, чтобы элементы реализовывали `Comparable`.

**`Comparator<T>`** — внешняя стратегия сравнения. Их может быть сколько угодно: по имени, по дате, по длине строки. Передаётся в `sort`, `TreeMap`, `TreeSet`, `stream().sorted()`. Удобные фабрики: `Comparator.comparing`, `comparingInt`, `thenComparing`, `reversed`.

```java
record User(String name, int age) { }

List<User> users = new ArrayList<>();
users.sort(Comparator.comparing(User::name)                 // по имени
        .thenComparingInt(User::age));                       // при равенстве — по возрасту
users.sort(Comparator.comparingInt(User::age).reversed());  // по возрасту, по убыванию
```

**Контракт compareTo** (его нарушение — любимая ловушка интервьюеров):
1. *Антисимметричность*: знак `a.compareTo(b)` противоположен знаку `b.compareTo(a)`.
2. *Транзитивность*: `a < b` и `b < c` означает `a < c`.
3. Если `a.compareTo(b) == 0`, знаки сравнений `a` и `b` с любым третьим элементом должны совпадать.
4. *Согласованность с equals (рекомендована)*: `compareTo == 0` тогда и только тогда, когда `equals == true`.

**Типичные ошибки:**
- `return a.age - b.age;` — переполнение при больших разницах. Правильно: `Integer.compare(a.age, b.age)` или `comparingInt`.
- Несогласованность с `equals`: `TreeSet` и `TreeMap` используют только `compareTo` и считают элементы с нулевым результатом одинаковыми. Если `compareTo` возвращает 0 для объектов, неравных по `equals`, один из них молча потеряется в множестве.
- Нарушение транзитивности (например, сравнение «частично» по нескольким полям) приводит к непредсказуемой сортировке и даже к `IllegalArgumentException: Comparison method violates its general contract` в `Arrays.sort`.

### 33. Date/Time API (java.time): LocalDateTime, Instant, Duration и Period

Пакет `java.time` (Java 8, JSR-310) — современный API дат и времени: основные типы значений (`Instant`, `LocalDate`, `Duration` и другие) неизменяемы и потокобезопасны, имена методов последовательны (`plus`, `minus`, `of`, `parse`, `format`).

**Основные классы — выбор зависит от того, что вы моделируете:**
- `LocalDate` — дата без времени и зоны: день рождения, дедлайн.
- `LocalTime` — время без даты и зоны: «будильник на 7:30».
- `LocalDateTime` — дата и время без зоны: «встреча 1 августа в 15:00», но без привязки к месту это не момент времени.
- `ZonedDateTime` — дата, время и часовой пояс (с учётом DST): полноценный момент времени в конкретной зоне.
- `OffsetDateTime` — то же, но с фиксированным смещением (`+03:00`), без правил перехода на летнее время; типичный выбор для хранения в БД.
- `Instant` — машинная метка времени: количество секунд и наносекунд от эпохи UTC. Аналог timestamp, лучший формат для хранения и сравнения моментов.

**Duration и Period — два вида промежутков:**
- `Duration` — машинный промежуток в секундах и наносекундах; работает с временем (`Instant`, `LocalDateTime`, `ZonedDateTime`).
- `Period` — человеческий промежуток в годах, месяцах и днях; работает с `LocalDate` и учитывает календарь: «плюс один месяц» — это не «плюс 30 дней».

```java
LocalDate birthday = LocalDate.of(1990, Month.MAY, 15);
LocalDate today = LocalDate.now();
Period age = Period.between(birthday, today);   // календарный возраст; результат зависит от today

ZonedDateTime meeting = ZonedDateTime.of(
        LocalDateTime.of(2026, 8, 1, 15, 0),
        ZoneId.of("Europe/Berlin"));

Instant now = Instant.now();
Duration until = Duration.between(now, meeting.toInstant()); // секунды/наносекунды

DateTimeFormatter fmt = DateTimeFormatter.ofPattern("dd.MM.yyyy");
String s = today.format(fmt);   // форматтер immutable и потокобезопасен
```

**Почему для нового кода выбирают java.time.** Формально deprecated только отдельные конструкторы и методы `Date`, но в новом коде их не используют, и вот почему:
- `Date` мутабельна (`setTime`), неудобна (год считается от 1900, месяцы — с нуля) и по сути является тем же `Instant`, но с ужасным API.
- `SimpleDateFormat` **не потокобезопасен**: внутри он держит мутабельный `Calendar`, и при конкурентном `parse()` из нескольких потоков получаете `NumberFormatException`, странные даты или тихо испорченные данные. Классический продакшн-баг — `private static final SimpleDateFormat FMT` в многопоточном сервисе. Лечилось `ThreadLocal`-обёртками, пока не появился потокобезопасный `DateTimeFormatter`.
- `Calendar` громоздок, мутабелен и содержит те же сюрпризы с месяцами с нуля.

**Follow-up вопросы:**
- Хранить в БД и передавать между системами — `Instant`/`OffsetDateTime` (UTC); перевод в зону пользователя — на границе системы.
- Мост для легаси-кода: `date.toInstant()`, `Date.from(instant)`, `calendar.toInstant()`, а дальше `LocalDateTime.ofInstant(instant, zoneId)`.
- `LocalDateTime` нельзя однозначно сравнивать с `Instant` — это разные категории: первое без зоны не является моментом времени.

### 51. Можно ли сдвинуть элементы в том же массиве через System.arraycopy?

```java
int[] ids = {2, 4, 6, 8};
System.arraycopy(ids, 0, ids, 1, 3);
System.out.println(Arrays.toString(ids)); // [2, 2, 4, 6]
```

При перекрытии диапазонов результат такой, как если бы значения сначала сохранили во временную копию. Простой цикл слева направо прочитал бы уже затёртые ячейки и оставил четыре двойки. При ручном сдвиге вправо копируйте с конца. Для `arraycopy` направление обхода выбирать не требуется.

Есть отдельная ловушка у массивов ссылок. Если копировать `Object[] {"ok", 7}` в `String[2]`, первый элемент запишется, а второй вызовет `ArrayStoreException`. Вызывающий код уже увидит частично изменённый массив. Если обновление должно быть целиком успешным, подготовьте отдельный массив и передайте его потребителю только после успешного копирования.

### 12. Generics: стирание типов и Wildcards (PECS)

**Generics (обобщения)** позволяют параметризовать классы, интерфейсы и методы типами, обеспечивая типобезопасность на этапе компиляции и избавляя от явных приведений типов: `List<String>` вместо сырого `List`.

**Стирание типов (Type Erasure):**
Проверка параметров типа в основном происходит при компиляции. В JVM-дескрипторах тип-параметры заменяются их стиранием (`Object` или левой верхней границей), вставляются приведения и при необходимости bridge-методы. Метаданные `Signature` могут сохранить объявленные generic-типы для рефлексии, но объект `ArrayList` не хранит собственный аргумент `String`. Следствия:
- в рантайме `List<String>` и `List<Integer>` — один и тот же класс, `instanceof List<String>` невозможен;
- нельзя создавать экземпляры и массивы тип-параметра (`new T()`, `new T[10]`);
- нельзя использовать примитивы в качестве тип-параметров (`List<int>` недопустим).

**Инвариантность (частый follow-up):** `List<String>` **не является** подтипом `List<Object>`, хотя `String` — подтип `Object`. Иначе в список строк можно было бы положить `Integer` через ссылку `List<Object>`, и типобезопасность рухнула бы. Именно для таких случаев и нужны wildcards. Массивы, кстати, ковариантны (`String[]` — подтип `Object[]`) — за что расплачиваются `ArrayStoreException` в рантайме.

**Ограниченные тип-параметры (bounded):** `<T extends Comparable<T>>` требует, чтобы T реализовывал нужный интерфейс или наследовал класс — У `Collections.sort` граница гибче: `<T extends Comparable<? super T>>`, поэтому тип может наследовать сравнение с общим предком. Несколько границ: `<T extends Number & Comparable<T>>`.

**Wildcards (шаблоны):**
- `? extends T` — тип T или его наследник. Из такой коллекции читают как T, но нельзя безопасно добавлять произвольный T (кроме `null`, если реализация разрешает). Это не read-only тип: `clear()` и удаление всё ещё могут быть доступны.
- `? super T` — тип T или его родитель. В такую коллекцию можно добавлять элементы типа T, но читать из неё можно только как `Object`.

**Принцип PECS (Producer Extends, Consumer Super):**
Если параметр является **производителем** данных (мы из него читаем) — используем `extends`; если **потребителем** (мы в него пишем) — используем `super`.

```java
public static void copy(List<? super Number> dest, List<? extends Number> src) {
    for (Number n : src) { // src — producer: extends
        dest.add(n);       // dest — consumer: super
    }
}
```

Классический пример из JDK — `Collections.copy(List<? super T> dest, List<? extends T> src)`.

### 38. Когда нужен generic-метод, а когда wildcard, и что такое capture conversion?

Wildcard описывает неизвестный тип, а параметр типа позволяет связать несколько позиций одной сигнатуры. Для метода, который только печатает коллекцию, достаточно `Collection<?>`. Для копирования важно, что источник и приёмник согласованы через один `T`:

```java
static <T> void appendAll(List<? super T> target, List<? extends T> source) {
    for (T element : source) target.add(element);
}
```

Запись `List<?>` не означает `List<Object>`: в неизвестный список нельзя добавлять произвольный объект. Но компилятор способен временно дать неизвестному типу имя — захватить wildcard. Поэтому реализацию перестановки удобно делегировать helper-методу:

```java
static void swapFirstTwo(List<?> list) { swapCaptured(list); }

private static <T> void swapCaptured(List<T> list) {
    T first = list.get(0);
    list.set(0, list.get(1));
    list.set(1, first);
}
```

Helper сохраняет тот же неизвестный тип для чтения и записи. Граница `List<?>` не запрещает изменение списка: она запрещает внесение значения неизвестного подходящего типа извне. Реализация всё ещё может бросить `UnsupportedOperationException`, а для короткого списка нужны проверки индексов — generics не проверяют состояние и изменяемость коллекции.

Частая ошибка — заменять все wildcard-параметры на `Object` или добавлять `@SuppressWarnings`, не разобрав связь типов. Если один тип нужен только в одной позиции и не участвует в возвращаемом значении, wildcard часто проще.

### 39. Что такое heap pollution и почему raw List откладывает ошибку до чтения?

Heap pollution возникает, когда переменная параметризованного типа ссылается на значение, не соответствующее этому типу. Обычные операции с generics предотвращают это при компиляции, но raw types, unchecked-приведения, небезопасный varargs или reflection могут обойти проверку.

```java
List<String> names = new ArrayList<>();
List raw = names;        // legacy raw type
raw.add(42);            // unchecked warning
String first = names.get(0); // ClassCastException здесь, не на add
```

Внутренний массив `ArrayList` хранит `Object`, поэтому запись Integer технически возможна. При чтении компилятор вставляет приведение к `String`, которое и обнаруживает нарушение. Между причиной и местом падения могут пройти тысячи строк кода. Предупреждение unchecked — полезная диагностика будущей ошибки, а не косметика.

`List<?>` безопаснее сырого `List`: из неё можно читать `Object`, но нельзя добавлять `42`, не зная фактического типа элементов. При интеграции со старым API можно скопировать и проверить каждый элемент на границе либо использовать `Collections.checkedList(backing, String.class)` для проверки новых записей через эту обёртку. Она не проверяет старое содержимое и не защищает от записи напрямую в исходный список.

Подавлять warning допустимо локально после обоснования инварианта. Опасная практика — ставить `@SuppressWarnings("unchecked")` на весь класс: так можно скрыть независимые нарушения.

### 40. Почему нельзя перегрузить методы `List<String>` и `List<Integer>`, и зачем bridge-методы?

После стирания `List<String>` и `List<Integer>` имеют один JVM-тип `List`. Поэтому два метода `save(List<String>)` и `save(List<Integer>)` в одном классе имеют одинаковое стирание и не компилируются. Решение — разные имена, разные типы обёрток или один generic-контракт, если смысл операции действительно общий. Возвращаемый тип конфликт не устраняет.

Другая сторона стирания — bridge-методы. Они сохраняют полиморфизм, когда исходный код переопределяет метод с конкретным параметром:

```java
interface Sink<T> { void accept(T value); }

final class TextSink implements Sink<String> {
    @Override public void accept(String value) {
        System.out.println(value.length());
    }
}
```

В интерфейсе после стирания остаётся `accept(Object)`, а в классе объявлен `accept(String)`. Компилятор добавляет синтетический bridge `accept(Object)`, который приводит аргумент к `String` и делегирует настоящему методу. Иначе вызов через `Sink<String>` не попал бы в переопределение. Bridge может появляться и для ковариантного возвращаемого типа.

Проверить это можно `javap -p -c TextSink`; reflection различает такие методы через `Method.isBridge()` и `isSynthetic()`. Частая ошибка при написании сканера аннотаций — считать каждый найденный метод отдельной пользовательской операцией. При передаче Integer через raw `Sink` ошибка проявится в приведении внутри bridge.

### 41. Почему generic varargs вызывает warning и когда допустим @SafeVarargs?

Varargs — это массив, создаваемый или передаваемый при вызове. Массив знает свой тип элемента в рантайме, но `List<String>` не является reifiable-типом: параметр `String` стёрт. Поэтому параметр `List<String>...` создаёт потенциально опасное сочетание массива и generics.

```java
static void broken(List<String>... groups) {
    Object[] aliases = groups;
    aliases[0] = List.of(42); // массив допускает List после стирания
    String value = groups[0].get(0); // ClassCastException
}
```

Аннотация `@SafeVarargs` — обещание автора, что тело безопасно обращается с массивом; она не добавляет проверок и не исправляет код. Её применяют к конструкторам и к `static`, `final` или `private` методам, которые не могут быть небезопасно переопределены. Безопасный метод обычно читает элементы и не отдаёт массив внешнему коду:

```java
@SafeVarargs
static <T> List<T> flatten(List<? extends T>... groups) {
    List<T> result = new ArrayList<>();
    for (List<? extends T> group : groups) result.addAll(group);
    return result;
}
```

Даже здесь отдельно определяют политику для `null` групп и элементов; аннотация отвечает только за риск generic varargs. Если API не требует удобства varargs, параметр `List<? extends List<? extends T>>` убирает проблему массива. Частая ошибка — ставить `@SafeVarargs` ради чистого вывода компилятора на метод, который сохраняет или возвращает varargs-массив.

## Исключения и управление ресурсами

### 4. Иерархия исключений: Checked и Unchecked

В Java механизм исключений основан на классе `Throwable`. Он разделяется на две основные ветви: `Error` и `Exception`.

**Error:**
Серьёзные проблемы, обычно выходящие за рамки обычного восстановления (`OutOfMemoryError`, `StackOverflowError`, ошибки связывания классов). Обычно их не перехватывают в бизнес-коде; узкие обработчики на границе исполнения могут записать диагностику или освободить резерв, но не должны считать сервис здоровым.

**Exception:**
Исключения, возникающие в логике приложения. Подразделяются на:
1. **Checked Exceptions (Проверяемые)**:
   - Классы `Throwable`, которые не относятся к ветвям `RuntimeException` и `Error`. На практике обычно это потомки `Exception`, например `IOException`; прямое наследование от `Exception` не обязательно.
   - Компилятор обязывает разработчика либо обработать их с помощью блока `try-catch`, либо пробросить выше по стеку вызовов с помощью ключевого слова `throws`.
   - Примеры: `IOException`, `SQLException`.
2. **Unchecked Exceptions (Непроверяемые)**:
   - Наследуются от `RuntimeException` или от `Error`.
   - Компилятор не требует их обязательной обработки. Обычно они свидетельствуют о программных ошибках (багах).
   - Примеры: `NullPointerException`, `IllegalArgumentException`, `IndexOutOfBoundsException`.

**Частые follow-up:**
- *Когда какое исключение проектировать*: checked — для ожидаемых ситуаций, из которых вызывающий код реально может восстановиться (нет файла на диске); unchecked — для нарушений контракта и багов (невалидный аргумент, NPE). Современные фреймворки (Spring) массово переупаковывают checked в unchecked (`DataAccessException`), чтобы не засорять сигнатуры.
- *Разница `throw` и `throws`*: `throw` выбрасывает исключение в коде, `throws` объявляет в сигнатуре метода, какие checked-исключения он может пробросить.
- *Multi-catch (Java 7)*: `catch (IOException | SQLException e)` — тип переменной `e` — ближайший общий предок, объединять в одну ветку родителя и наследника нельзя.
- *Ловушка с `return` в `finally`*: если в `try` стоит `return`, а в `finally` — свой `return`, результат `try` будет затерт; выброшенное исключение тоже затирается. Поэтому `return` и `throw` в `finally` — анти-паттерн (см. также suppressed exceptions в вопросе 22).

```java
public void readFile(String path) throws IOException {
    // IOException является Checked, поэтому требуется throws или try-catch
    try (FileReader reader = new FileReader(path)) {
        System.out.println(reader.read());
    }
}
```

### 29. Кастомные исключения: checked и unchecked, когда оправданы

Своё исключение — обычный класс, унаследованный от `Exception` (checked) или `RuntimeException` (unchecked), с парой стандартных конструкторов.

```java
public class InsufficientFundsException extends RuntimeException {
    private final BigDecimal missingAmount;

    public InsufficientFundsException(String message, BigDecimal missingAmount) {
        super(message);
        this.missingAmount = missingAmount;
    }

    public InsufficientFundsException(String message, Throwable cause) {
        super(message, cause);
        this.missingAmount = null; // контекст суммы для этой формы неизвестен
    }

    public BigDecimal getMissingAmount() {
        return missingAmount;
    }
}
```

Конструктор с `Throwable cause` — обязательный минимум: без него при обёртывании теряется исходный стектрейс, и отладка превращается в гадание.

**Checked или unchecked?** (база — вопрос 4)
- Checked — когда вызывающая сторона может и должна осмысленно обработать ситуацию: внешний сбой с возможностью восстановления, часть бизнес-контракта API. Компилятор заставит обработать или пробросить.
- Unchecked — программные ошибки и нарушения бизнес-правил, где обработчик всё равно находится «где-то наверху». Современная практика (Spring, большинство фреймворков) — почти всегда unchecked: checked-исключения загрязняют сигнатуры всех методов по стеку вызовов, а стандартные `Function`/`Consumer` не объявляют checked-исключений. Лямбда может бросать checked, если это разрешает её функциональный интерфейс; для `Stream.map` обычно нужно обработать исключение или выбрать другую организацию кода.

**Иерархия в своём приложении:** обычно одно базовое `ApplicationException extends RuntimeException`, от него — доменные ветки (`PaymentException`, `UserNotFoundException` и т.д.). Это даёт общую точку перехвата и читаемую семантику.

**Когда своё исключение оправдано:**
- нужно отличать конкретную ситуацию в `catch` или в exception handler'е контроллера;
- исключение несёт дополнительный контекст (код ошибки, сумма, id сущности);
- имя само документирует проблему: `InsufficientFundsException` читается лучше, чем `IllegalStateException` с длинным сообщением.

**Когда не стоит:** если подходящее исключение уже есть в JDK — `IllegalArgumentException`, `IllegalStateException`, `UnsupportedOperationException`, `NoSuchElementException`. Зоопарк из сотни классов-исключений — запах так же, как и отсутствие своих.

**Ловушки:** не наследуйтесь напрямую от `Throwable` или `Error`; не делайте checked «на всякий случай»; сообщение — для людей и логов, а не для парсинга (контекст кладите в поля); не включайте в сообщение чувствительные данные (номера карт, пароли).

### 22. try-with-resources и AutoCloseable

`try-with-resources` (Java 7) автоматически закрывает ресурсы, объявленные в скобках после `try`, — у каждого вызывается `close()` при выходе из блока, даже если внутри упало исключение. Требование к ресурсу одно: реализовать `AutoCloseable` (или его наследника `Closeable` для I/O).

```java
try (FileInputStream in = new FileInputStream("a.txt");
     FileOutputStream out = new FileOutputStream("b.txt")) {
    in.transferTo(out);
} // оба close() вызовутся автоматически, в обратном порядке
```

**Порядок закрытия (частый вопрос):**
Ресурсы закрываются **в обратном порядке объявления** — последний открытый закрывается первым. Логика та же, что у вложенных блоков: сначала «сворачивается» то, что построили позже.

**Suppressed exceptions:**
Если исключение брошено и в теле `try`, и при `close()`, то основным остаётся исключение из тела блока, а исключение из `close()` добавляется к нему как **подавленное (suppressed)** — достать его можно через `getSuppressed()`. Это принципиальное отличие от ручного `finally`: там исключение из `close()` затирало исходное, и настоящая причина сбоя терялась.

```java
try (ProblematicResource r = new ProblematicResource()) {
    throw new RuntimeException("основное");
} catch (RuntimeException e) {
    System.out.println(e.getMessage());                 // основное
    System.out.println(e.getSuppressed()[0].getMessage()); // из close()
}
```

Ещё две детали, которые любят спрашивать:
- С Java 9 в скобках можно использовать уже существующую effectively final переменную: `try (reader) { ... }`, без повторного объявления.
- `catch` и `finally` после try-with-resources по-прежнему работают и выполняются **после** закрытия ресурсов.

### 7. Методы класса Object: toString, clone, finalize, wait и notify

Класс `java.lang.Object` является корнем иерархии всех классов в Java, поэтому его методы доступны любому объекту.

**toString():**
Возвращает строковое представление объекта. По умолчанию — имя класса и шестнадцатеричный хэш-код (`User@1b6d3586`). Принято переопределять для удобства логирования и отладки.

**clone():**
Создает копию объекта. По умолчанию выполняет **поверхностное копирование (shallow copy)**: примитивные поля копируются по значению, а ссылочные — копируются как ссылки, то есть копия и оригинал разделяют одни и те же вложенные объекты. Для глубокого копирования (deep copy) метод необходимо переопределить, клонируя и вложенные объекты. Механизм `Cloneable`/`clone()` считается архитектурно неудачным — на практике предпочтительнее конструктор копирования или статический фабричный метод.

**finalize():**
Вызывался сборщиком мусора перед уничтожением объекта. Начиная с Java 9 метод **deprecated**, а с Java 18 помечен для удаления: его выполнение не гарантировано по времени и вообще по факту, он замедляет GC и создает риск утечек. Современная альтернатива — `java.lang.ref.Cleaner`, регистрирующий действие очистки, либо интерфейс `AutoCloseable` с `try-with-resources`.

**wait(), notify(), notifyAll():**
Методы межпоточной синхронизации. `wait()` освобождает монитор объекта и переводит поток в ожидание до вызова `notify()` или `notifyAll()` другим потоком. Вызывать их разрешено только внутри синхронизированного блока (иначе — `IllegalMonitorStateException`), а `wait()` следует помещать в цикл `while` с проверкой условия из-за возможности ложных пробуждений (spurious wakeup).

**Частый follow-up — отличие `wait()` от `sleep()`:** `wait()` — метод `Object`, вызывается внутри `synchronized` и **освобождает монитор**; `Thread.sleep()` — статический метод `Thread`, монитор **не освобождает** и не требует синхронизации. На практике ручные wait/notify почти вытеснены классами из `java.util.concurrent` (`BlockingQueue`, `CountDownLatch`, `Condition`).

```java
synchronized (lock) {
    while (!condition) {
        lock.wait(); // освобождает монитор и ждет
    }
}
```

### 13. Функциональные интерфейсы и лямбда-выражения

**Функциональный интерфейс** — интерфейс ровно с одним абстрактным методом (SAM, Single Abstract Method). Аннотация `@FunctionalInterface` необязательна, но заставляет компилятор проверить это условие. `default` и `static` методы не нарушают контракт. При подсчёте не учитываются методы, совпадающие с публичными методами `Object` (например, `equals` в `Comparator`); наследуемые совместимые абстрактные объявления могут составлять один функциональный контракт. Примеры: `Runnable`, `Comparator`, `Comparable`.

**Лямбда-выражения** — краткий синтаксис реализации функционального интерфейса без создания анонимного класса: компилятор выводит тип из контекста (target typing).

**Захват переменных (частый follow-up):** лямбда может использовать локальные переменные enclosing-метода, только если они `final` или effectively final (не переприсваиваются после инициализации). Причина: значение переменной копируется в лямбду в момент создания, и мутация снаружи сделала бы видимым расхождение копии с оригиналом. Поля класса захватываются свободно — они и так доступны через `this`.

**Отличие лямбды от анонимного класса:** в анонимном классе `this` — это сам анонимный экземпляр (и генерируется отдельный `.class`-файл), а в лямбде `this` — это экземпляр внешнего класса; обычный `javac` использует `invokedynamic`, а среда выполнения может создать или переиспользовать объект реализации. Отсутствие класса или аллокации язык не гарантирует.

**Основные функциональные интерфейсы пакета `java.util.function`:**
- `Function<T, R>` — принимает T, возвращает R: `R apply(T t)`.
- `Consumer<T>` — принимает T, ничего не возвращает: `void accept(T t)`.
- `Supplier<T>` — ничего не принимает, возвращает T: `T get()`.
- `Predicate<T>` — принимает T, возвращает `boolean`: `boolean test(T t)`.

**Method reference (ссылка на метод)** — еще более краткая запись лямбды, если она лишь делегирует вызов существующему методу. Виды: ссылка на статический метод (`Integer::parseInt`), на метод конкретного объекта (`System.out::println`), на метод произвольного экземпляра типа (`String::length`), на конструктор (`ArrayList::new`).

```java
Predicate<String> isEmpty = s -> s.isEmpty();
Function<String, Integer> length = String::length; // method reference
Supplier<List<String>> factory = ArrayList::new;   // ссылка на конструктор
Consumer<String> printer = System.out::println;

printer.accept(String.valueOf(length.apply("java"))); // выведет 4
```

### 52. Когда вычисляется получатель связанной ссылки на метод?

```java
var labels = new ArrayList<>(List.of("A", "B"));
IntSupplier saved = labels.get(0)::length;
IntSupplier current = () -> labels.get(0).length();
labels.set(0, "new");
System.out.println(saved.getAsInt() + " / " + current.getAsInt()); // 1 / 3
```

При создании `saved` выражение `labels.get(0)` уже выполнено. Ссылка запомнила строку `"A"`; сам метод будет вызван позже. Лямбда при каждом `getAsInt()` заново читает первый элемент того же изменяемого списка.

Отсюда разная точка отказа. Если при создании ссылок список пуст, связанная ссылка упадёт сразу при `get(0)`. Лямбду создать удастся, а результат её вызова будет зависеть от содержимого списка к этому моменту. Выбирайте форму по тому, хотите ли зафиксировать конкретного получателя или использовать актуальный.

### 15. Класс Optional: назначение и паттерны использования

`Optional<T>` (Java 8) — контейнер, который либо содержит не-null значение, либо пуст. Его назначение — явно выразить в сигнатуре метода возможность отсутствия результата и позволить выразить обработку отсутствия через API. Это не защита от всех NPE: сама ссылка на Optional или поля внутри значения по-прежнему могут быть `null`.

**Создание:** `Optional.of(value)` (NPE на null), `Optional.ofNullable(value)`, `Optional.empty()`.

**Правильные паттерны:**
- `orElse(default)` — вернуть значение или значение по умолчанию. Аргумент вычисляется **всегда**.
- `orElseGet(supplier)` — вернуть значение или вычислить альтернативу лениво, только если Optional пуст. Предпочтителен, когда вычисление запасного значения затратно.
- `orElseThrow(supplier)` — вернуть значение или выбросить заданное исключение.
- `map`, `filter`, `flatMap` — цепочечные преобразования без вложенных проверок.
- `ifPresent(consumer)` / `ifPresentOrElse` — выполнить действие при наличии значения.

**Неправильные паттерны:**
- Вызов `get()` без проверки `isPresent()` — выбрасывает `NoSuchElementException` и ничем не лучше NPE; сочетание `isPresent()` + `get()` часто можно сделать короче через `ifPresent` или `map`, хотя в императивном коде оно допустимо.
- Использование Optional в качестве поля класса, параметра метода или элемента коллекции — контейнер предназначен в первую очередь для возвращаемых значений. Optional не реализует `Serializable` и не предназначен для полей сущностей.

```java
public Optional<User> findById(long id) { ... }

String name = findById(42)
        .map(User::getName)
        .filter(n -> !n.isBlank())
        .orElseGet(() -> loadDefaultName()); // вычислится только если пусто
```

### 53. Как получить email из Optional, если сам поиск адреса тоже возвращает Optional?

Предположим, `findUser(id)` возвращает `Optional<User>`, а `user.verifiedEmail()` — `Optional<String>`. Здесь участвуют две проверки: пользователь найден и адрес подтверждён.

```java
Optional<Optional<String>> nested = findUser(id).map(User::verifiedEmail);
Optional<String> email = findUser(id).flatMap(User::verifiedEmail);
```

Если пользователь найден, но подтверждённого адреса нет, у `nested` внешний контейнер заполнен, а внутренний пуст. Проверка одного `nested.isPresent()` даст неверный ответ на вопрос об адресе. У `email` обе причины отсутствия дают один результат — `Optional.empty()`. Если нужны разные сообщения пользователю, сохраните различие явно, например отдельными результатами «пользователь не найден» и «адрес не подтверждён».

Граница контракта тоже отличается. Если функция в `map` вернула `null`, получается пустой `Optional`. Функция в `flatMap` обязана вернуть объект `Optional`; возврат `null` для присутствующего входа вызовет `NullPointerException`.

### 14. Stream API: операции, ленивость и Collectors

**Stream API** (Java 8) — декларативный способ обработки последовательностей данных в стиле «что сделать», а не «как делать». Стрим описывает обработку источника и может быть потреблён только один раз. Сам конвейер не предназначен для изменения источника; побочные эффекты пользовательских лямбд могут его изменить и нарушить требования non-interference.

**Промежуточные операции (intermediate):**
Возвращают новый стрим: `filter`, `map`, `flatMap`, `sorted`, `distinct`, `limit`, `skip`. Они **ленивые (lazy)** — не выполняются, пока не вызвана терминальная операция, что позволяет строить конвейер и избегать лишних вычислений (например, `findFirst()` после `filter` не обойдет всю коллекцию).

**Терминальные операции (terminal):**
Запускают вычисление и возвращают результат или побочный эффект: `forEach`, `collect`, `reduce`, `count`, `anyMatch`, `findFirst`. После терминальной операции стрим потреблён и повторно использовать его нельзя. Это не равнозначно `close()`: ресурсы потоков из `Files.lines()` закрывают через try-with-resources.

**Отличие map от flatMap:**
- `map` преобразует каждый элемент один-к-одному (`Stream<T>` → `Stream<R>`).
- `flatMap` преобразует каждый элемент в стрим и «выравнивает» вложенные стримы в один плоский (`Stream<T>` → `Stream<R>` из `Stream<Stream<R>>`).

**collect и Collectors:**
`collect` выполняет изменяемую редукцию; класс `Collectors` предоставляет готовые коллекторы: `toList()`, `toSet()`, `toMap()`, `joining()`, `groupingBy()`, `partitioningBy()`, `counting()`. Отличие `groupingBy` от `partitioningBy`: первый группирует по произвольному ключу в `Map<K, List<T>>`, второй — только по булеву предикату в две группы (true/false).

`Collectors.toList()` не обещает конкретный класс списка и его изменяемость. `Stream.toList()` (Java 16+) гарантирует неизменяемую структуру; для явно изменяемого `ArrayList` используют `collect(Collectors.toCollection(ArrayList::new))`. Это поверхностные гарантии: сами элементы могут оставаться изменяемыми.

**Short-circuiting операции:** `findFirst`, `findAny`, `anyMatch`, `allMatch`, `noneMatch`, `limit` могут завершить обход досрочно, как только ответ найден — отсюда и выигрыш от ленивости.

**Параллельные стримы (ловушка, про которую спрашивают):** обычная реализация `parallelStream()` использует общий `ForkJoinPool.commonPool()`; Stream API не предоставляет параметра для выбора исполнителя. Это общая инфраструктура процесса, которую могут использовать и другие задачи. Блокирующие операции (I/O) внутри параллельного стрима займут все его потоки и подвесят других пользователей пула. Ускорение зависит от размера, делимости источника, стоимости функции и объединения результатов. Для блокирующего I/O обычно нужен отдельный механизм управления конкурентностью; виртуальные потоки доступны стабильно с Java 21.

```java
List<String> names = List.of("Anna", "Bob", "Alex", "Kate");

List<String> result = names.stream()
        .filter(n -> n.length() > 3)   // промежуточная, ленивая
        .map(String::toUpperCase)       // один-к-одному
        .sorted()
        .collect(Collectors.toList());  // терминальная: [ALEX, ANNA, KATE]

List<List<String>> nested = List.of(List.of("a", "b"), List.of("c"));
List<String> flat = nested.stream()
        .flatMap(List::stream)          // выравнивание в один стрим
        .collect(Collectors.toList());  // [a, b, c]
```

### 42. Как собрать Stream в Map, если ключи повторяются и важен порядок?

Сначала нужно решить, что означает повторный ключ: ошибка входных данных, выбор одного значения или накопление нескольких. Двухаргументный `Collectors.toMap` бросает `IllegalStateException` при дубликате. Merge-функция задаёт осмысленное разрешение конфликта; фабрика карты — нужное представление результата.

```java
record Item(String sku, long quantity) { }
List<Item> items = List.of(new Item("A", 2), new Item("B", 1), new Item("A", 3));

Map<String, Long> totals = items.stream().collect(Collectors.toMap(
        Item::sku,
        Item::quantity,
        Math::addExact,
        LinkedHashMap::new)); // {A=5, B=1}, порядок первого появления ключей
```

Сложение сумм здесь выражает бизнес-смысл, а `addExact` предотвращает тихое переполнение. `(oldValue, newValue) -> newValue` подходит только при явно выбранном правиле «последняя запись побеждает». Если нужно сохранить все элементы, естественнее `groupingBy`, а не merge списков вручную.

Не предполагайте конкретный класс и порядок карты у простого `toMap`. Также не переносите допустимость `null` из `HashMap` на коллектор: null-значения для стандартного `toMap` недопустимы; политика null-ключей зависит от выбранной карты. Для отсутствующих данных лучше выбрать явную фильтрацию, ошибку или отдельный объект результата.

В параллельной обработке merge-функция должна быть ассоциативной, чтобы объединение частичных карт не меняло смысл результата.

### 43. Как downstream-коллекторы меняют результат groupingBy?

`groupingBy` отвечает за выбор группы, а downstream-коллектор — за накопление внутри каждой группы. Поэтому необязательно сначала создавать `Map<K, List<T>>`, а затем вторым проходом считать итоги. Можно сразу получить счётчики, множества, суммы или вложенную группировку.

```java
record Employee(String department, String name, int salary) { }
List<Employee> staff = List.of(
        new Employee("dev", "Анна", 100),
        new Employee("dev", "Анна", 120),
        new Employee("ops", "Борис", 90));

Map<String, Set<String>> names = staff.stream().collect(Collectors.groupingBy(
        Employee::department,
        TreeMap::new,
        Collectors.mapping(Employee::name, Collectors.toCollection(TreeSet::new))));
```

Здесь `TreeMap` упорядочивает группы, `mapping` меняет накопляемый тип, а `TreeSet` устраняет повторы имён и сортирует их. Для числа сотрудников достаточно `groupingBy(Employee::department, counting())`; для общей зарплаты — `summingLong(Employee::salary)`, чтобы не ограничивать сумму диапазоном int.

Важное различие: `filter` перед группировкой удалит группу, если ни один её элемент не прошёл условие. `Collectors.filtering` внутри downstream (Java 9+) сохранит встреченную группу с пустым результатом. Это влияет на отчёты, где нужно видеть подразделения без подходящих сотрудников.

`groupingBy` не делает результат потокобезопасным. Даже у `groupingByConcurrent(..., toList())` нельзя автоматически считать вложенные списки пригодными для последующих конкурентных изменений. Частая ошибка — ожидать от имени одного коллектора гарантий всего графа результата.

### 44. На подумать: почему parallel reduce с identity даёт неверную сумму?

Нужно сложить числа, добавив начальный остаток 10 ровно один раз. Разработчик написал:

```java
int total = List.of(1, 2, 3).parallelStream().reduce(10, Integer::sum);
```

Можно ли ожидать 16? А можно ли собирать результат через `reduce(new ArrayList<>(), ...)`, добавляя элементы в исходный список аккумулятора?

<details>
<summary>Разбор</summary>

Для `reduce` identity должен быть нейтральным элементом операции: для сложения это 0, поскольку `0 + x = x`. В параллельном вычислении identity может участвовать в нескольких частичных результатах. Значение 10 нарушает контракт, и итог не обязан совпадать с последовательным вычислением. Исправление:

```java
int total = Math.addExact(10,
        List.of(1, 2, 3).parallelStream().reduce(0, Math::addExact)); // 16
```

Аккумулятор и combiner должны быть совместимы и ассоциативны. Вычитание не ассоциативно; сложение double математически ассоциативно, но из-за округления в машине порядок группировки может менять результат. `addExact` позволяет обнаружить переполнение, хотя при разных группировках переполнение промежуточной суммы тоже может проявляться по-разному.

Изменяемый список как identity — другая ошибка: частичные вычисления могут разделить один объект и одновременно менять его. Для изменяемой редукции нужен `collect`, у которого supplier создаёт независимые контейнеры:

```java
List<Integer> values = List.of(1, 2, 3).parallelStream()
        .collect(ArrayList::new, ArrayList::add, ArrayList::addAll);
```

Опасный ответ — «добавим synchronizedList». Блокировка не исправит ни неправильную нейтральность identity, ни неверный способ разделения состояния.

</details>

### 45. Почему peek может не выполниться и нельзя строить на нём обязательную обработку?

`peek` — промежуточная операция для наблюдения за проходящими элементами, обычно при отладке. Она ленива, зависит от фактически потреблённых элементов, а некоторые стадии конвейера реализация вправе вообще пропустить, если результат терминальной операции от них не зависит.

```java
long size = List.of("a", "b", "c").stream()
        .peek(System.out::println)
        .count(); // допустимо получить 3 без единой напечатанной строки
```

Источник уже знает размер, `peek` его не меняет, поэтому считать элементы перебором необязательно. При `findFirst` или `anyMatch` будут нужны только некоторые элементы; при параллельном выполнении нельзя рассчитывать и на один конкретный поток или привычную последовательность побочных эффектов.

Обязательную запись в БД, аудит или отправку события нельзя помещать в `peek`. Если цель — действие для каждого элемента, её выражают явно, например обычным циклом или терминальным `forEach`; порядок встречаемости при необходимости задают `forEachOrdered`. Но даже терминальная операция не создаёт транзакцию: исключение после части действий оставит частичный результат, и при повторе потребуются идемпотентность или собственный протокол.

Если действие меняет объект, дальнейшие `distinct`, `sorted` и хэширование могут зависеть от момента мутации — это ещё одна причина предпочесть чистое преобразование в `map`. Частая ошибка — исправлять исчезнувший аудит заменой `count` на `collect`, рассчитывая на случайное поведение текущей реализации.

### 46. Чем потребление Stream отличается от close и как повторить обработку файла?

Терминальная операция потребляет конвейер: повторно запускать его нельзя. Закрытие освобождает связанные ресурсы и запускает зарегистрированные `onClose` обработчики. Эти события различны: `collect`, `count` или `findFirst` не обязаны вызывать `close`. Для стримов поверх коллекций ресурс обычно отсутствует, а `Files.lines` держит открытый файл.

```java
Path path = Path.of("events.txt");
try (Stream<String> lines = Files.lines(path, StandardCharsets.UTF_8)) {
    long errors = lines.filter(s -> s.contains("ERROR")).count();
    System.out.println(errors);
}
```

Чтобы повторить вычисление, нужно создать новый stream из источника, а не сохранить ссылку на старый. Для файла повторное открытие может прочитать уже другие данные, если файл изменился. Если необходим единый снимок и размер допустим, можно один раз загрузить строки в список и строить несколько независимых конвейеров. Для большого файла разумнее спроектировать один проход с несколькими агрегатами.

Ошибка чтения во время обхода `Files.lines` может прийти как `UncheckedIOException`, хотя первоначальное открытие объявляет checked `IOException`. Ресурс всё равно должен закрываться при исключении, short-circuit и нормальном завершении. Сам `onClose` без фактического закрытия не решает задачу. Частая ошибка — возвращать файловый stream из метода, не обозначив владельца обязанности `close`, или закрывать его внутри метода до того, как вызывающий начнёт чтение.

### 47. Как Stream работает с null и почему allMatch пустого потока возвращает true?

Ссылочный stream может содержать `null`, но допустимость дальнейшей операции зависит от её контракта. `map(String::length)` упадёт при null-элементе; `filter(Objects::nonNull)` позволяет явно удалить отсутствующие значения. Это решение меняет смысл данных: иногда пропуск недопустим и правильнее выбросить ошибку с контекстом.

```java
List<String> values = Arrays.asList("aa", null, "b");
int letters = values.stream().filter(Objects::nonNull)
        .mapToInt(String::length).sum(); // 3

System.out.println(Stream.empty().allMatch(x -> false));  // true
System.out.println(Stream.empty().anyMatch(x -> true));   // false
System.out.println(Stream.empty().noneMatch(x -> true));  // true
```

Для пустого потока нет контрпримера утверждению «каждый элемент соответствует условию»: это универсальная квантификация, а не доказательство наличия элементов. Предикат вообще не вызывается. Поэтому проверка «все документы подписаны» через `allMatch` может пропустить заказ без документов; требование непустоты проверяют отдельно, если оно есть в предметной области.

`findFirst` и `findAny` возвращают `Optional`, который не может содержать null, и бросают NPE, если выбран null-элемент. Это отличается от `Optional.map`, где null-результат отображения превращается в пустой Optional. Частая ошибка — думать, что наличие Optional в возвращаемом типе автоматически делает источник с null безопасным.

## Механизмы платформы и развитие Java

### 16. Загрузка классов и иерархия ClassLoader

Классы попадают в JVM не все сразу, а лениво — в момент первого обращения, и делают это специальные объекты — загрузчики классов (`ClassLoader`).

**Иерархия встроенных загрузчиков:**
1. **Bootstrap** — корневой, часть самой JVM (написан не на Java, поэтому из кода виден как `null`). Загружает ядро платформы: `java.lang.*`, `java.util.*` и прочие базовые модули.
2. **Platform ClassLoader** (до Java 9 — Extension ClassLoader) — загружает прочие модули JDK, не входящие в ядро.
3. **System (Application) ClassLoader** — загружает классы приложения из `CLASSPATH` (ключи `-cp`/`-classpath`).

**Делегирование родителю (parent-first):**
Когда загрузчику нужен класс, он сначала просит загрузить его своего родителя, и только если родитель не смог — ищет сам. Класс грузится тем загрузчиком, который находится ближе всего к Bootstrap и способен его найти. Так устроена базовая реализация `loadClass`; пользовательские загрузчики могут изменять делегирование, а контейнеры применяют собственные правила изоляции. Ограничения на определение классов `java.*` действуют отдельно.

**Почему нельзя подменить `java.lang.String`:**
Во-первых, из-за parent-first: даже если положить свой `java/lang/String.class` в classpath, запрос уйдёт вверх, и Bootstrap загрузит настоящий `String` раньше. Во-вторых, JVM просто запрещает пользовательским загрузчикам определять классы в пакетах `java.*` — попытка закончится `SecurityException: Prohibited package name: java.lang`.

**Этапы загрузки класса:**
1. *Loading* — поиск и чтение байт-кода, создание объекта `Class`.
2. *Linking* — верификация байт-кода, подготовка статических полей (значения по умолчанию), резолвинг ссылок на другие классы.
3. *Initialization* — выполнение статических блоков и инициализация статических полей.

**Свои загрузчики** пишут редко, но на собеседовании стоит назвать реальные кейсы: плагинные системы, горячая перезагрузка кода, изоляция приложений (Tomcat держит отдельный загрузчик на каждый war-архив). Ещё один частый follow-up: один и тот же класс, загруженный двумя разными загрузчиками, — это два разных класса для JVM, `instanceof` между ними не пройдёт.

```java
System.out.println(String.class.getClassLoader());  // null — Bootstrap
System.out.println(MyApp.class.getClassLoader());   // AppClassLoader / System
System.out.println(MyApp.class.getClassLoader().getParent()); // Platform
```

### 17. Reflection API: назначение, применение и цена

Рефлексия — это API (`java.lang.Class` и пакет `java.lang.reflect`), позволяющий в рантайме инспектировать классы и управлять ими: узнать поля, методы, конструкторы, создать экземпляр, прочитать или изменить приватное поле, вызвать метод по имени.

**Где реально используется:**
- **Spring** — внедрение зависимостей: контейнер находит поля с `@Autowired` и выставляет их через `setAccessible`, создаёт бины через конструкторы, строит прокси.
- **Jackson/Gson** — сериализация объектов в JSON без явного кода маппинга.
- **JPA/Hibernate** — заполнение полей сущностей из ResultSet, доступ к приватным полям без геттеров.
- **JUnit, Mockito** — поиск тестовых методов по аннотациям, создание моков.

**Цена вопроса (это и есть основной follow-up):**
1. *Производительность*: рефлексивный вызов может иметь накладные расходы на проверки, упаковку аргументов и косвенный вызов; результат зависит от JDK и возможности оптимизации JIT. Нельзя утверждать, что инлайнинг всегда невозможен (реализация reflection менялась, в том числе в Java 18). В критичных местах фреймворки кэшируют `Method`/`Field` или генерируют байт-код.
2. *Безопасность типов*: все ошибки (`NoSuchMethodException`, `ClassCastException`) всплывают только в рантайме, компилятор не поможет.
3. *Ломается инкапсуляция*: `setAccessible(true)` открывает приватные члены; с Java 9 модули этому активно сопротивляются (strong encapsulation, нужен `--add-opens`).
4. *Хрупкость к рефакторингу*: имена методов и полей в строках IDE не отслеживает.

```java
class User { private String name = "admin"; }

User user = new User();
Field f = User.class.getDeclaredField("name");
f.setAccessible(true);            // снимаем проверку доступа
f.set(user, "root");
System.out.println(user);         // поле name уже "root"

Method m = User.class.getMethod("toString"); // находит и унаследованный public-метод
System.out.println(m.invoke(user));
```

Правило простое: в прикладном коде рефлексия почти никогда не нужна — это инструмент авторов фреймворков.

### 18. Сериализация: Serializable, transient, serialVersionUID и Externalizable

Сериализация — преобразование объекта в поток байт (и обратно) для передачи по сети или сохранения. Встроенный механизм Java включается маркерным интерфейсом `Serializable` — у него нет ни одного метода, он просто разрешает `ObjectOutputStream` работать с объектом.

**Ключевые моменты:**
- **`transient`** — поле исключается из сериализации (пароли, кэши, ссылки на несериализуемые объекты). После десериализации оно получит значение по умолчанию.
- **`static` поля не сериализуются** — они принадлежат классу, а не объекту. `final` сериализуются, если не `transient`.
- **`serialVersionUID`** — идентификатор версии класса. При десериализации JVM сравнивает его со значением в потоке; не совпал — `InvalidClassException`. Если поле не объявить, JVM вычислит его из структуры класса, и некоторые изменения структуры изменят вычисленное значение, даже если изменение формата данных не планировалось. Поэтому его принято объявлять явно и менять только при сознательном нарушении совместимости.
- **Кастомизация**: приватные методы `writeObject`/`readObject` позволяют встроиться в стандартный процесс (например, зашифровать поле). Интерфейс **`Externalizable`** (`writeExternal`/`readExternal`) отдаёт формат целиком вам — сериализуется только то, что вы сами записали.
- **Синглтон**: десериализация создаёт новый объект и ломает единственность. Лечится методом `readResolve()`, возвращающим существующий экземпляр.

```java
public class Account implements Serializable {
    private static final long serialVersionUID = 1L;

    private String owner;
    private transient String password; // в поток не попадёт
}
```

**Почему Java-сериализация считается опасной:**
Десериализация — это выполнение кода. JVM инстанцирует классы из потока и вызывает их `readObject`, не спрашивая разрешения. Если злоумышленник контролирует входной поток, он собирает «цепочку гаджетов» (gadget chain) из классов, уже лежащих в classpath (классический случай — Apache Commons Collections), и получает выполнение произвольного кода. Отсюда жёсткое правило: **никогда не десериализовать недоверенные данные штатным механизмом**. На практике для обмена обычно берут JSON (Jackson) или Protobuf — обычный обмен данными не требует создания произвольных классов из потока. Однако небезопасная полиморфная десериализация и пользовательские обработчики могут создать риски и в других форматах.

### 19. Вложенные классы: static, inner, локальные и анонимные

Вложенный класс объявляется внутри другого класса и делится на четыре вида; важнейшее различие между ними — есть ли неявная ссылка на экземпляр внешнего класса.

**1. Static nested class (статический вложенный):**
По сути обычный класс, просто живущий в пространстве имён внешнего. Ссылки на внешний экземпляр **нет**, доступ к нестатическим членам внешнего класса — только через явную ссылку. Создаётся независимо: `new Outer.Nested()`. Пример из JDK — `Map.Entry`. Это предпочтительный вариант, если вложенному классу не нужен внешний объект.

**2. Inner class (внутренний, нестатический):**
Каждый экземпляр неявно хранит ссылку `Outer.this`, поэтому создать его можно только от живого внешнего объекта: `outer.new Inner()`. Имеет прямой доступ ко всем членам внешнего класса, включая приватные: обращение вида `Outer.this.field`.

**3. Локальный класс** — объявлен внутри метода, виден только в нём, может читать локальные переменные метода, если они `final` или effectively final (их значение под капотом копируется в поля класса).

**4. Анонимный класс** — локальный класс без имени: объявление и единственный экземпляр создаются одним выражением. До Java 8 был основным способом передать «поведение» (обработчики событий); сейчас там, где интерфейс функциональный, пишут лямбду.

**Ловушка с утечкой памяти (частый follow-up):**
Нестатический внутренний класс держит внешний объект живым, пока жив сам. Если экземпляр inner-класса попадает в долгоживущую структуру — статический кэш, очередь, слушатель — внешний объект со всем своим состоянием не сможет собрать GC. Правило: если внутреннему классу не нужен внешний экземпляр, объявляйте его `static`.

```java
public class Outer {
    private int value = 42;

    static class StaticNested {          // без ссылки на Outer
        void print() { /* value недоступен напрямую */ }
    }

    class Inner {                        // хранит Outer.this
        void print() {
            System.out.println(Outer.this.value); // 42
        }
    }

    Runnable handler = new Runnable() {  // анонимный класс
        @Override public void run() {
            System.out.println(value);   // тоже держит Outer.this
        }
    };
}
```

### 32. Кастомные аннотации: @Target, @Retention и обработка через Reflection

Аннотация — это метаданные, прикреплённые к коду; сама по себе она ничего не делает, пока какой-то обработчик её не прочитает. Своя аннотация объявляется через `@interface` с мета-аннотациями.

```java
@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface Timed {
    String value() default "operation";
}
```

**@Target** — где аннотацию разрешено ставить: `TYPE` (класс/интерфейс), `METHOD`, `FIELD`, `PARAMETER`, `CONSTRUCTOR`, `LOCAL_VARIABLE`, `ANNOTATION_TYPE`, `TYPE_USE` и др. Без `@Target` аннотация применима к большинству контекстов объявлений, но это не разрешает произвольные type-use позиции: для них нужен `ElementType.TYPE_USE`.

**@Retention** — как долго аннотация живёт:
- `SOURCE` — отбрасывается компилятором (`@Override`, `@SuppressWarnings`);
- `CLASS` — сохраняется в байткоде, но недоступна в рантайме. **Это значение по умолчанию** — классическая ловушка: забыли `@Retention(RUNTIME)`, аннотация «не находится» рефлексией, и полчаса дебага;
- `RUNTIME` — доступна через Reflection API в рантайме. Именно она нужна для аннотаций, обрабатываемых фреймворками.

Дополнительные мета-аннотации: `@Documented` (попадёт в Javadoc), `@Inherited` (аннотация класса наследуется подклассами — работает только для классов, не для методов), `@Repeatable` (можно ставить несколько раз).

**Ограничения элементов аннотации:** типами элементов могут быть только примитивы, `String`, `Class`, enum, другие аннотации и массивы из перечисленного. Значения должны быть compile-time константами. Элемент без `default` обязателен к заполнению при использовании.

**Обработка через Reflection:**

```java
for (Method m : service.getClass().getDeclaredMethods()) {
    Timed timed = m.getAnnotation(Timed.class);
    if (timed != null) {
        long start = System.nanoTime();
        Object result = m.invoke(service, args);
        long ms = (System.nanoTime() - start) / 1_000_000;
        System.out.println(timed.value() + " took " + ms + " ms");
    }
}
```

**Чем обрабатывают в реальной жизни** (частый follow-up):
- **AOP**: в Spring аннотация `@Timed` на методе читается аспектом (`@Aspect` + `@Around`), который оборачивает вызов замером — ручной reflection не нужен;
- **Annotation Processing Tool (APT)**: обработка на этапе компиляции, аннотации с `RetentionPolicy.SOURCE`/`CLASS` порождают код — так работают Lombok, MapStruct, Dagger;
- **IDE и статический анализ**: `@NotNull`, `@Deprecated` и т.п.

Собственно, формула ответа: аннотация — декларативный маркер, вся логика живёт в обработчике, и выбранный `@Retention` определяет, какой тип обработчика её вообще сможет увидеть.

### 54. Почему enum.ordinal() опасно сохранять в сообщении или строке БД?

Представьте `enum State { NEW, PAID }`. Заказ со значением `PAID` записали как 1. После добавления `CHECKING` между двумя константами число 1 в следующей версии обозначает другой статус. Само чтение может пройти без ошибки, и заказ уйдёт в неверную ветку обработки.

Дайте внешним значениям постоянные коды, например `"new"`, `"paid"`, `"checking"`, и храните код в поле перечисления. Парсер ищет константу по коду и явно обрабатывает неизвестные значения. На входной команде полезно вернуть ошибку, а для журнала событий может быть разумнее сохранить незнакомый код для повторной обработки.

`name()` выдерживает перестановку, но связывает внешние данные с именами констант. Проверочный тест должен читать сохранённое значение из предыдущей версии, даже когда разработчик переименовал константу или изменил порядок объявления.

### 24. Обзор новшеств Java 9–21

Вопрос-опросник: от вас ждут не энциклопедию, а уверенное перечисление главного с парой примеров.

**Java 9:**
- **Модули (JPMS, Project Jigsaw)**: JDK разбита на модули, приложение описывает зависимости в `module-info.java` (`requires`, `exports`). Сильная инкапсуляция внутренних API.
- `jshell` (REPL), `private` методы в интерфейсах, фабричные методы коллекций: `List.of(...)`, `Map.of(...)`.

**Java 10–11:**
- **`var`** (10) — выведение типа локальной переменной компилятором. Тип остаётся статическим, это не `let` из JavaScript. Не работает для полей, параметров и неинициализированных переменных.
- Стандартный `HttpClient` (11), методы строк `isBlank()`, `lines()`, `strip()`.

```java
var list = new ArrayList<String>(); // тип ArrayList<String>, выведен из правой части
```

**Java 14–16:**
- **Switch expressions** (14): switch как выражение со стрелочным синтаксисом, без `break` и сквозных проваливаний.
- **Text blocks** (15): многострочные строки `"""..."""` для SQL, JSON, HTML.
- **Pattern matching для instanceof** (16): проверка и приведение в одном шаге.
- **Records** (16) — см. вопрос 20.

```java
int code = switch (day) {
    case MONDAY, FRIDAY -> 1;
    case SATURDAY, SUNDAY -> 0;
    default -> throw new IllegalStateException();
};

if (obj instanceof String s) {   // без ручного каста
    System.out.println(s.length());
}
```

**Java 17–21:**
- **Sealed-классы** (17) — см. вопрос 20.
- **Pattern matching для switch** (21): сопоставление по типам, `null`-ветка, guarded patterns (`case String s when s.length() > 3`).
- **Виртуальные потоки** (21, Project Loom): легковесные потоки, которыми управляет JVM поверх небольшого пула платформенных. Позволяют обслуживать много одновременно ожидающих I/O задач без отдельного платформенного потока для каждой. Они не увеличивают число CPU и не отменяют ограничения БД, внешних сервисов и памяти. Создание: `Thread.startVirtualThread(...)` или `Executors.newVirtualThreadPerTaskExecutor()`.

```java
String result = switch (obj) {
    case Integer i        -> "число " + i;
    case String s when s.isBlank() -> "пустая строка";
    case String s         -> "строка " + s;
    case null             -> "null";
    default               -> "что-то ещё";
};
```
