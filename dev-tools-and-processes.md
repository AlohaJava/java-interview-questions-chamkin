## Git и управление зависимостями

### 1. Git: merge против rebase, cherry-pick, revert и reset, стратегии ветвления

**Ответ:**

Это самый частый вопрос по Git: чем merge отличается от rebase. Суть в одном предложении: merge объединяет линии истории (с merge-коммитом либо fast-forward), а rebase переписывает историю, перенося ваши коммиты поверх целевой ветки.

При **merge** (`git merge feature` из `main`) Git находит общего предка веток. Если ветки разошлись, обычно создаётся коммит с двумя родителями; если `main` — предок `feature`, возможен fast-forward: передвигается указатель без нового коммита. История остаётся правдивой: видно, когда ветка отпочковалась и когда влилась. Минус — при активной разработке граф превращается в «рельсы» из merge-коммитов, читать его тяжело.

При **rebase** (`git rebase main` из своей фичи) Git временно «отматывает» ваши коммиты, подтягивает ветку к концу `main` и накатывает ваши коммиты заново, один за другим. Коммиты при этом получают новые SHA — это технически новые коммиты, даже если diff тот же. Результат — линейная история, как будто вы начали работу сегодня, а не неделю назад. Конфликты разрешаются по одному коммиту за раз (`git rebase --continue` после каждого), а не одним большим мержем.

Отсюда **не переписывайте общую историю без согласования с теми, кто от неё зависит**. Rebase переписывает историю: для замены опубликованной истории обычно требуется принудительный push, а у коллег, которые строили работу поверх старых коммитов, история разъедется. Ребейзить можно свою локальную ветку или свою фича-ветку, если договорились, что она только ваша (push с `--force-with-lease` проверяет ожидаемое состояние удалённой ссылки перед заменой; это защита от ряда гонок, а не разрешение переписывать чужую работу).

**Cherry-pick** (`git cherry-pick <sha>`) — перенос одного конкретного коммита в другую ветку. Классический сценарий — хотфикс: поправили в `main`, перенесли коммит в релизную ветку. Коммит копируется с новым SHA. При последующем merge одинаковая правка не обязательно применится дважды: Git объединяет снимки относительно общего предка. Но логически одинаковые коммиты с разными SHA усложняют историю, а расходящиеся последующие правки могут конфликтовать.

**Revert против reset** — вопрос «как откатить изменения»:

- `git revert <sha>` создаёт новый коммит, который отменяет изменения указанного. История не переписывается, поэтому revert подходит для отмены опубликованного изменения без переписывания общей истории. Откат работающего сервиса обычно выполняют предыдущим совместимым артефактом; revert нужен, чтобы исправить ветку исходников.
- `git reset` двигает указатель ветки назад и (в зависимости от режима) меняет индекс и рабочую копию:
  - `--soft` — двигает только HEAD: коммиты «разкоммичиваются», но изменения остаются в индексе (staged). Удобно, чтобы пересобрать несколько коммитов в один.
  - `--mixed` (по умолчанию) — HEAD + индекс: изменения остаются в рабочей копии, но unstaged.
  - `--hard` — HEAD + индекс + рабочая копия: отслеживаемые незакоммиченные изменения перезаписываются. Коммиты часто можно вернуть через `git reflog`, пока записи и объекты не удалены сборкой мусора. Reflog не сохраняет произвольный незакоммиченный текст и не даёт гарантированного срока восстановления.

**Разрешение конфликтов** спрашивают на уровне «что делаете руками»: открываете файлы, где Git проставил маркеры `<<<<<<<`, `=======`, `>>>>>>>`, выбираете/сшиваете нужный вариант, `git add`, дальше `git merge --continue` или `git rebase --continue`. Частый follow-up — «в каком направлении правильно мержить»: в фича-ветку подливают `main` (или ребейзятся на него), чтобы конфликты разрулить у себя, а не в общей ветке.

**Стратегии ветвления:**

- **GitFlow** — долгоживущие `develop` и `main`, плюс `feature/*`, `release/*`, `hotfix/*`. Строгий, но тяжёлый: имеет смысл при релизном цикле (мобильные приложения, ПО с версиями у заказчика), для веб-сервисов с частыми деплоями обычно избыточен.
- **Trunk-based development** — разработчики часто интегрируют изменения в один `main`, фича-ветки держат короткими, недоделанная функциональность прячется за feature flags. Это распространённый подход при частой поставке: короткие ветки = маленькие конфликты и постоянная интеграция.
- **GitHub Flow** — упрощённый вариант: `main` всегда деплойабелен, ветки только под задачи, влитие через pull request с ревью.

Сеньорский нюанс: rebase против merge — не религия, а договорённость команды. Частый рабочий компромисс — ребейзить фичу на `main` для чистоты, а вливать через squash-merge для одного коммита на задачу или через `--no-ff`, если важно сохранить отдельную ветку. Merge-коммит сам по себе не делает граф линейным.

### 2. Maven: жизненный цикл, scopes зависимостей, dependencyManagement и конфликты версий

**Ответ:**

Суть Maven — жизненный цикл: фиксированная последовательность фаз, через которые проходит сборка. Для `default`-цикла основные фазы такие:

```text
validate → compile → test → package → verify → install → deploy
```

- `validate` — проверка структуры проекта;
- `compile` — компиляция исходников в `target/classes`;
- `test` — прогон юнит-тестов (surefire); падение тестов обрывает сборку;
- `package` — упаковка в JAR/WAR;
- `verify` — проверка результатов интеграционных тестов и качества, если соответствующие плагины настроены; сам Maven не подключает Failsafe автоматически;
- `install` — копирование артефакта в локальный репозиторий `~/.m2`, чтобы его видели другие ваши проекты;
- `deploy` — выкладка в удалённый репозиторий (Nexus, Artifactory) для команды.

Ключевое свойство: вызов любой фазы выполняет все предыдущие. `mvn package` — это compile + test + package. Ещё два цикла: `clean` (чистит `target/`) и `site` (документация). Типовая команда на CI — `mvn clean verify`. `clean` — отдельный жизненный цикл: он не выполняется автоматически перед `package`. Failsafe при настройке запускает интеграционные тесты в `integration-test` и проверяет их результат в `verify`.

**Phases против goals** — любимый теоретический подвох. Goal (цель) — конкретная задача плагина, например `compiler:compile` или `surefire:test`. Phase — точка жизненного цикла, к которой цели привязаны. Одна фаза может выполнять несколько целей, и одну цель можно вызвать напрямую: `mvn dependency:tree` — это вызов goal вне цикла.

**Scopes зависимостей:**

- `compile` (по умолчанию) — доступна при компиляции, тестах и выполнении. В обычный JAR зависимости автоматически не встраиваются; способ упаковки определяют JAR/WAR/Boot/Shade-плагины;
- `provided` — нужна для компиляции и тестов, но в артефакт не входит: её предоставит окружение. Классика — `servlet-api` в WAR для Tomcat, Lombok;
- `runtime` — не нужна при компиляции, нужна при выполнении: JDBC-драйверы, когда код работает через интерфейсы `java.sql`;
- `test` — только тесты: JUnit, Mockito;
- `system` (устаревший, не использовать) и `import` (для BOM в `dependencyManagement`) — на уровне «слышал».

**dependencyManagement** — секция, которая только фиксирует версии, не добавляя зависимости. В родительском pom пишете версию один раз, в дочерних модулях зависимость указывается без версии. На этом построены Spring Boot BOM (`spring-boot-dependencies`) и механизм BOM вообще: импортируете BOM со scope `import` — и получаете согласованный набор версий всего стека.

**Конфликты версий.** Если транзитивно приходят две версии одной библиотеки, Maven выбирает по правилу «nearest wins»: побеждает зависимость ближе к корню дерева; при равной глубине — та, что объявлена первой в pom. Это детерминированно, но не всегда то, что нужно: победить может старая версия без нужного метода, и в рантайме получите `NoSuchMethodError`. Диагностика:

```bash
mvn dependency:tree
mvn dependency:tree -Dincludes=com.google.guava:guava
```

Лечение тремя способами: зафиксировать нужную версию в `dependencyManagement`, исключить транзитивную версию через `<exclusions>`, или явно объявить зависимость первого уровня.

**Maven против Gradle.** Maven задаёт жизненный цикл и соглашения через POM; Gradle описывает граф задач в Groovy/Kotlin DSL и предлагает инкрементальное выполнение и build cache. Скорость зависит от проекта, плагинов, корректных входов задач и состояния кэша. Сравнивают одинаковые сценарии: чистую сборку и типичное изменение одного модуля. На интервью называйте только тот практический опыт, который у вас был.

## Диагностика Linux

### 3. Linux для бэкенд-разработчика: диагностика на сервере

**Ответ:**

От Java-разработчика на Linux ждут одного: вы можете зайти на сервер, где «всё тормозит», и последовательно локализовать проблему — CPU, память, диск, сеть или само приложение. Набор команд вокруг этого сценария.

**Нагрузка и процессы.** Первый взгляд — `top` или `htop`: кто ест CPU и память. Число, которое спрашивают отдельно, — **load average** (видно и в `uptime`): среднее число процессов в очереди на выполнение за 1/5/15 минут. Это не только CPU, но и процессы в uninterruptible sleep (обычно ждущие диск или сеть). Грубое правило: LA устойчиво больше числа ядер — система перегружена; LA 8 на четырёх ядрах — повод проверить CPU и I/O, но не доказательство нехватки CPU; в контейнере дополнительно учитывают CPU quota и throttling. Список процессов с деталями: `ps aux | grep java`, дерево — `ps auxf`.

**Память и диск.** `free -h` — сколько памяти занято, сколько в page cache (строка `available` — реально доступная, не путать с `free`). Диск: `df -h` — занятое место по файловым системам (переполненный диск — классическая причина «сломалось всё сразу»: БД не пишет, логи не пишутся), `du -sh /var/log/* | sort -h` — кто именно съел место. Если файл удалили, а место не освободилось — его держит открытый дескриптор процесса: `lsof | grep deleted`.

**Сеть и порты.** Вопрос «кто занял порт 8080» — классика собеседования:

```bash
lsof -i :8080
ss -tulpn | grep 8080
```

`ss` — современная замена `netstat`: `-t` TCP, `-u` UDP, `-l` listening, `-p` процесс, `-n` без резолва имён. Проверить, отвечает ли удалённый порт вообще: `nc -zv host 5432`.

**Логи.** Рабочий минимум:

```bash
tail -f app.log                    # следить за логом вживую
tail -n 1000 app.log | grep ERROR
grep -C 5 "NullPointerException" app.log   # 5 строк контекста до и после
grep -B 10 "OutOfMemoryError" app.log      # 10 строк до
awk '$9 == 500 {print $7}' access.log | sort | uniq -c | sort -rn | head   # топ URL с 500-ками
less app.log                       # поиск по /, навигация G — в конец
```

**curl** — швейцарский нож для проверки API с сервера:

```bash
curl -v https://api.internal/health          # -v: TLS, заголовки, код ответа
curl -X POST -H "Content-Type: application/json" -d '{"id":1}' http://localhost:8080/orders
curl -o /dev/null -s -w "%{http_code} %{time_total}s\n" http://localhost:8080/orders
curl --user "$METRICS_USER" http://localhost:8080/actuator/metrics  # curl запросит пароль
```

**Kill и сигналы.** `kill <pid>` шлёт по умолчанию **SIGTERM (15)** — просьба завершиться: JVM перехватывает его, выполняет shutdown hooks (Spring останавливает контекст, дренирует запросы, закрывает пулы). `kill -9 <pid>` — **SIGKILL**, ядро убивает процесс мгновенно, никакие хуки не выполнятся: могут остаться незавершённые прикладные операции. ACID-БД восстанавливает свои транзакции средствами журналирования; это не отменяет риска внешнего эффекта, который уже произошёл без ответа клиенту. Правильный порядок — сначала 15, подождать, только потом 9. Побочный вопрос: почему Java-приложение в Docker «игнорирует» остановку — часто виноват shell-процесс PID 1, не передающий сигнал дочерней JVM. Exec-форма `ENTRYPOINT ["java", "-jar", "app.jar"]`, `exec java ...` в скрипте или init с forwarding решают эту конкретную проблему; просто иной PID JVM сам по себе не означает потерю сигналов.

## Командный процесс

### 4. Scrum и Kanban: роли, церемонии, оценка задач

**Ответ:**

На интервью полезно различать определение процесса и собственный опыт команды: кто приоритизировал задачи, как выявляли блокеры и что улучшали по результатам обратной связи.

**Scrum** — итеративный фреймворк: работа режется на фиксированные спринты (обычно 2 недели), в начале формулируют Sprint Goal и прогнозируют объём, в конце обсуждают работающий инкремент и обратную связь. Обязательство относится к цели, а не к неизменному списку задач.

Роли:

- **Product Owner** — владеет продуктом и бэклогом: что делаем и в каком порядке, отвечает за ценность;
- **Scrum Master** — владеет процессом: снимает препятствия, следит за церемониями, защищает команду от внешних прерываний;
- **Developers** — участники Scrum Team, создающие инкремент и управляющие планом работы. В Scrum Guide 2020 используются ответственности Product Owner, Scrum Master и Developers; отдельной Development Team внутри команды уже нет.

Церемонии:

- **Planning** — команда берёт задачи из бэклога в спринт и оценивает их;
- **Daily (stand-up)** — 15 минут: что сделал, что буду делать, что блокирует;
- **Review (demo)** — показ инкремента стейкхолдерам, сбор обратной связи;
- **Retrospective** — разбор самого процесса: что улучшить в следующем спринте;
- **Refinement (grooming)** — не официальная церемония, но спрашивают: предварительный разбор и уточнение бэклога между спринтами.

**Story points и оценка.** SP — командная относительная оценка усилий, сложности и неопределённости; это не часы и не точная арифметическая шкала. Story points не обязательны по Scrum Guide. Оценивают командой, часто planning poker (все показывают карту одновременно — так оценка не съезжает к мнению самого громкого). **Velocity** — сколько очков команда в среднем закрывает за спринт; используется для прогноза, а не для сравнения команд и не как KPI разработчика — это отдельная ловушка: «измерять людей velocity» — анти-паттерн, очки мгновенно начинают раздуваться.

**Kanban** — управление потоком работы, совместимое и с итерациями: задачи движутся по доске (To Do → In Progress → Review → Done), ограничение — **WIP-лимиты** (не больше N задач в колонке), цель — минимизировать lead time и выявить узкие места потока. Сам метод не требует Scrum-ролей или спринтов; существующие ритмы команды можно сохранить. Используют метрики потока (cycle time, throughput).

Когда что: Scrum — продуктовая разработка с планируемым ритмом поставки, команде нужен фокус и предсказуемость; Kanban — поток входящих задач с плавающими приоритетами: поддержка, ops, багфиксы, дежурные команды. Гибрид «Scrum-ban» (спринты, но с доской и WIP-лимитами) — то, что реально встречается чаще всего.

**Вопросы-ловушки:**

- «Daily — это отчёт менеджеру?» — нет. Daily — синхронизация команды для команды: выявить блокеры и скорректировать план на день. Как только дейли превращается в отчёт статуса руководителю по кругу — это запах микроменеджмента, и хороший scrum master это пресекает.
- «Можно ли менять scope спринта посередине?» — да, Developers уточняют scope с Product Owner по мере получения информации, сохраняя Sprint Goal. Нельзя вносить изменения, угрожающие цели; отменить спринт при потере актуальности цели может Product Owner.
- «Что делает scrum master, когда у команды всё хорошо?» — правильный ответ не «ничего», а «делает себя ненужным»: процессы работают сами, он занимается системными препятствиями.

### 17. Как превратить повторяющуюся жалобу на ретроспективе в проверяемое улучшение?

Возьмём жалобу «задачи подолгу лежат на тестировании». Посмотрите, когда у нескольких последних задач появилась готовая сборка, когда началась проверка и почему пришлось ждать. Если сборку приходилось запрашивать в чате, проведите эксперимент на один спринт: при успешной выкладке на тестовый стенд в задаче появляется ссылка на сборку, а ответственный отмечает, когда начал проверку.

Заранее договоритесь, по чему судить об эффекте. Сравните время от доступности сборки до начала проверки и число передач с недостающими данными. Если чаще всего очередь ждёт освобождения единственного стенда, автоматическая ссылка сэкономит переписку, но почти не изменит ожидание. Такой результат помогает выбрать следующий эксперимент. При малом количестве задач разберите отдельные долгие ожидания и состав работ, прежде чем делать вывод по среднему.

## Наблюдаемость и выпуск

### 5. Мониторинг и наблюдаемость: метрики, алертинг, SLI/SLO/SLA

**Ответ:**

Метрики, логи и трейсинг — взаимодополняющие источники наблюдаемости, а не полный обязательный список инструментов. Метрики — агрегированные числа во времени (дешёвые, для алертов и дашбордов), логи — события с контекстом, трейсинг — путь запроса через сервисы. На собеседовании по этой теме чаще всего копают именно стек Prometheus + Grafana.

**Prometheus и pull-модель.** Приложение само не отправляет метрики — оно выставляет HTTP-эндпоинт (`/actuator/prometheus` в Spring Boot через Micrometer), а Prometheus периодически (scrape interval, обычно 15–30 с) опрашивает все цели и складывает данные в свою time-series БД. Следствия: Prometheus знает, какие цели живы (метрика `up` показывает успешность scrape, а не полную работоспособность пользовательского сценария), и приложению не нужно знать адрес мониторинга. Минус — короткоживущие задачи (batch jobs) могут не дождаться scrape, для них есть Pushgateway.

Основные типы метрик:

- **Counter** — только растёт (число запросов, ошибок); смысл имеет через `rate()`;
- **Gauge** — произвольное значение вверх-вниз (размер очереди, использованная память);
- **Histogram / Summary** — распределение величин, из которого считают перцентили (p95, p99 latency).

Базовый PromQL, который ожидают на слух:

```promql
rate(http_server_requests_seconds_count{status="500"}[5m])
histogram_quantile(0.95, sum by (le) (rate(http_server_requests_seconds_bucket[5m])))
```

Главный трюк: `rate()` по counter за окном, перцентили — через `histogram_quantile` по бакетам. Среднее полезно для некоторых расчётов, но скрывает хвост задержек; его дополняют p95/p99 и долей запросов, уложившихся в SLO. Перцентили разных инстансов нельзя просто усреднять: сначала агрегируют совместимые бакеты по `le`.

**Методы выбора метрик** — то, что отличает зрелый ответ:

- **RED** (для сервисов, request-driven): Rate — RPS, Errors — доля ошибок, Duration — latency. Три ряда на дашборд каждого сервиса.
- **USE** (для ресурсов/инфраструктуры): Utilization — насколько ресурс занят, Saturation — очередь к ресурсу, Errors — ошибки ресурса. Применяется к CPU, памяти, диску, сети.
- **Four Golden Signals** (Google SRE): latency, traffic, errors, saturation — по сути RED + насыщенность.

**Алертинг и его гигиена.** Алерт — это страница, которая будит человека, поэтому правило одно: алерт должен быть actionable — требовать немедленного действия. Если на алерт нельзя среагировать («CPU 80% — ну подумаешь») — это не алерт, а метрика для дашборда. **Alert fatigue** — состояние, когда алертов слишком много и дежурные начинают их игнорировать; лечится безжалостной чисткой: удалить, перевести в дашборд или поднять порог. Пороги лучше привязывать не к внутренним ресурсам, а к симптомам, видимым пользователю (error rate, latency) — «alert on symptoms, not causes».

**SLI / SLO / SLA** — триада, которую спрашивают всё чаще:

- **SLI** (indicator) — измеряемый показатель: доля запросов быстрее 300 мс, доля успешных ответов;
- **SLO** (objective) — внутренняя цель по SLI: «99,9% запросов успешны за 30 дней»;
- **SLA** (agreement) — внешний контракт с клиентом с штрафами, часто мягче внутренней цели SLO, но это договорённость, а не свойство определения.

Из SLO растёт **error budget**: при SLO 99,9% бюджет — 0,1% плохих событий за выбранное окно. Для SLI по времени это около 43 минут за 30 дней; для SLI по запросам бюджет считают в запросах, а не минутах. Пока бюджет не исчерпан — можно релизиться и рисковать; исчерпан — фичи замораживаются, команда чинит надёжность. Это здоровый ответ на вопрос «как балансируете скорость разработки и стабильность».

### 6. Профилировщики Java: JFR, async-profiler, VisualVM и поиск узких мест

**Ответ:**

Сначала правильный порядок действий, потому что его и проверяют: узкое место ищут сверху вниз — сначала метрики и логи (какой endpoint, какой сценарий деградировал), потом профилирование конкретного сценария. Запускать профилировщик «на всякий случай» без гипотезы — способ утонуть в flame graph на 3000 методов.

**JFR (Java Flight Recorder) + JMC (JDK Mission Control)** — основной production-инструмент, встроен в JDK (с JDK 11 бесплатен). JFR пишет события JVM в кольцевой буфер: аллокации, GC, блокировки, сокеты, sampling стеков. Профиль `default` рассчитан на длительную запись с небольшими расходами; фактическое влияние зависит от событий и нагрузки. Перед постоянным включением проверяют его на своём сервисе. Запуск:

```bash
jcmd <pid> JFR.start duration=60s filename=app.jfr
# или при старте JVM:
java -XX:StartFlightRecording=duration=10m,filename=app.jfr ...
```

Полученный файл открывается в JMC: видно выборки стеков, события аллокаций, contention и GC. Для анализа удержания объектов могут потребоваться специально включённые события либо heap dump; обычная запись не является полным снимком heap. Сильная сторона JFR — системная картина целиком, а не только CPU.

**async-profiler** — низкоуровневый семплирующий профилировщик, ставший стандартом для CPU-анализа. Плюсы перед классическими: не страдает от safepoint bias (обычные семплеры видят стеки только в точках безопасности JVM и искажают картину), умеет несколько режимов:

- `cpu` — горячие методы;
- `alloc` — кто аллоцирует память (источник давления на GC);
- `wall` — wall-clock: видно методы, которые не жрут CPU, но тормозят (ожидание БД, локов, сети) — самый полезный режим для типичного бэкенда;
- `lock` — contention.

```bash
./asprof -e cpu -d 60 -f cpu.html <pid>
./asprof -e wall -d 60 -f wall.html <pid>
```

Результат — flame graph («огненный граф»): по горизонтали — доля времени, по вертикали — стеки; ширина показывает долю выборок в выбранном режиме, а не длительность отдельного вызова. Искать причину нужно по пути в стеке и типу события: широкий кадр ожидания допустим и не всегда требует оптимизации.

**VisualVM / JProfiler / YourKit.** VisualVM — бесплатный инструмент из JDK-экосистемы: быстро подключиться к локальному процессу, посмотреть heap, потоки, грубый sampling. Влияние зависит от режима: sampling и инструментирование имеют разную стоимость; в production сначала оценивают overhead и объём собираемых данных. JProfiler и YourKit — коммерческие, с мощным UI, телеметрией и анализом памяти; их расходы зависят от режима и конфигурации; они удобны для локального воспроизведения и deep-dive.

Когда что, коротко: постоянный продовый мониторинг и «чёрный ящик» инцидента — JFR; горячий CPU или аллокации, flame graph на проде — async-profiler; локальная диагностика и учебные задачи — VisualVM; глубокий коммерческий анализ (memory leak hunting, телеметрия) — JProfiler/YourKit.

Частый follow-up — «у приложения выросло время ответа, ваши действия?». Зрелая цепочка: метрики (какой endpoint, latency p99, error rate) → логи/трейсинг конкретных медленных запросов → гипотеза (БД? GC? лок?) → подтверждение: медленные запросы к БД — лог slow queries и план запроса; подозрение на GC — GC-логи и JFR; подозрение на код — async-profiler в режиме wall. И отдельно: сначала исключить внешние причины (сеть, диск, соседи по железу) — это те же команды из вопроса про Linux.

### 7. CI/CD: как устроен пайплайн и что спрашивают следом

**Ответ:**

На собеседовании «расскажите про ваш CI/CD» ждут связный рассказ об этапах и понимание, зачем каждый нужен, а не знание синтаксиса Jenkinsfile. Канонический пайплайн:

```text
commit → build → test → quality gates → artifacts → deploy (staging → prod)
```

1. **Триггер** — push/MR в ветку. На feature-ветках обычно прогоняют сборку и тесты, полный пайплайн — на main и релизах.
2. **Build** — компиляция и сборка артефакта (`mvn clean verify` / `gradle build`), часто с кэшем зависимостей между прогонами.
3. **Test** — юнит-тесты на каждый коммит, интеграционные (Testcontainers) — отдельным более медленным этапом. Обязательные упавшие проверки блокируют дальнейшие шаги; зелёный pipeline уменьшает риск, но не доказывает отсутствие дефектов.
4. **Quality gates** — статический анализ (SonarQube), проверка покрытия (JaCoCo), сканирование зависимостей на уязвимости (OWASP Dependency-Check, Snyk). Gate — это именно барьер: покрытие ниже порога или новый blocker-issue в Sonar — пайплайн красный, мерж запрещён.
5. **Artifacts** — собранный JAR/Docker-образ публикуется в репозиторий (Nexus/Artifactory, Docker registry) с версией. Принцип «build once, deploy many»: один и тот же артефакт едет на staging и в прод, пересборка под окружение — анти-паттерн, конфигурация отличается через переменные окружения.
6. **Deploy** — на staging автоматически, в прод — автоматически (continuous deployment) или по кнопке (continuous delivery). Стратегии выкатки, которые спрашивают следом: rolling (по одному инстансу), blue-green (две среды, переключение трафика), canary (процент трафика на новую версию с метриками).

**Jenkins против GitLab CI** на уровне этапов: Jenkins — плагинная экосистема, пайплайн как код в `Jenkinsfile` (declarative: `stages { stage('Test') { steps { ... } } }`), гибче и старее, требует администрирования агентов. GitLab CI — пайплайн в `.gitlab-ci.yml` рядом с кодом, раннеры, стадии и джобы из коробки, тесная интеграция с MR. GitHub Actions — та же идея в экосистеме GitHub. На собеседовании достаточно показать, что мыслите стадиями и артефактами, а не конкретным синтаксисом.

**Что спрашивают следом** (готовьте ответы заранее):

- «Как откатываете?» — варианты в зависимости от совместимости и инфраструктуры: redeploy предыдущего артефакта (он уже лежит в registry, откат — минуты), blue-green — мгновенное переключение трафика обратно, в крайнем случае revert коммита и полный прогон пайплайна. Отдельный болезненный пункт — миграции БД: откат кода не откатывает схему, поэтому миграции делают обратносовместимыми (expand-and-contract: сначала добавляем новое, потом удаляем старое отдельным релизом).
- «Где секреты?» — не в репозитории и не в переменных в открытом виде: vault-хранилища (HashiCorp Vault, AWS/GCP Secret Manager), masked-переменные CI (GitLab CI Variables), подставляемые при деплое. Утечка секрета в git — это ротация, а не удаление из истории.
- «Как ускоряете пайплайн?» — кэш зависимостей, параллельные джобы, разделение быстрых и медленных тестов, запуск только затронутых модулей в монорепе.
- «Что такое shift-left?» — перенос проверок как можно раньше: pre-commit хуки, статический анализ и тесты на этапе MR, а не перед релизом — чем раньше найден дефект, тем дешевле его чинить.

### 18. Контракт API регулярно отстаёт от сервиса. Что проверять перед выпуском?

Пусть сервис раньше возвращал `amount` числом, а теперь отдаёт строку. Сначала выберите, где команда фиксирует обещание потребителю: например, это версионируемый файл OpenAPI. На проверке изменения сравните контракт с опубликованной версией и отдельно проверьте поведение приложения: запустите запрос к собранному сервису и проверьте тип поля в реальном ответе. Так видны две разные ошибки: изменение обещания без согласования и расхождение реализации с неизменившимся обещанием.

Если описание генерируется из аннотаций, проверяйте результат генерации для конкретной сборки и публикуйте его вместе с версией API. Показ схемы в браузере сам по себе не проверяет, что потребитель обработает ответ. Даже валидная схема пропустит смену смысла поля, например переход с рублей на копейки. Для такого случая нужен пример с известной суммой и ожидаемым результатом у потребителя.

## Разбор истории и воспроизводимая сборка

### 8. Как найти коммит, после которого появилась регрессия, с помощью git bisect?

`git bisect` выполняет двоичный поиск между заведомо исправным и неисправным коммитами. Сначала нужен воспроизводимый критерий: конкретный тест падает, результат неверен или расход памяти превышает порог в одинаковом сценарии. Фраза «иногда стало медленнее» без контролируемого эксперимента для поиска непригодна.

```bash
git bisect start
git bisect bad HEAD
git bisect good v1.8.0
# На выбранном Git коммите запускаем проверку:
./mvnw -q -Dtest=PriceRegressionTest test
git bisect bad  # либо good по результату проверки
# Повторяем до локализации, затем возвращаемся:
git bisect reset
```

Для автоматизации используют `git bisect run ./check-regression.sh`: код 0 означает good, 1–127, кроме 125, — bad; 125 — пропуск непроверяемой ревизии. Скрипт должен отличать регрессию от ошибки инфраструктуры. Например, недоступный тестовый PostgreSQL нельзя классифицировать как дефект проверяемого коммита.

Перед поиском сохраняют рабочие изменения. Старой ревизии могут требоваться иной JDK, конфигурация и тестовые данные; эти условия фиксируют, а не незаметно меняют между шагами. Для утечки памяти одинаковыми должны быть прогрев, нагрузка и окно измерения. Если ошибка исчезала и возвращалась, предположение об одной границе good/bad нарушается.

Найденный коммит — начало анализа: изменение могло проявить старый дефект или зависеть от соседней миграции. Его не следует автоматически отменять без проверки контракта.

### 9. После разрешения merge-конфликта сборка зелёная, но поведение сломалось. Что проверять?

Git обнаруживает текстовые пересечения, а не несовместимость бизнес-изменений. Две ветки могут без конфликтов поменять контракт разных файлов: одна переименовала событие, другая добавила consumer со старым именем. Зелёная компиляция такого рассогласования не исключает.

Сначала выясняют ожидаемую семантику обеих веток: читают задачу, diff и тесты, сравнивают итоговое дерево с родителями merge-коммита. Для выбранного коммита полезны `git show <merge>`, `git diff <merge>^1 <merge>` и аналогичное сравнение со вторым родителем. Конкретные SHA позволяют не зависеть от текущего положения `HEAD`.

При конфликте не выбирают целиком `ours` или `theirs`, пока не понята каждая сторона. Особенно осторожно работают во время rebase: сторона «ours» там относится к истории, поверх которой переигрывается коммит, и привычная интуиция «это мой код» может подвести. Если разрешение ещё не завершено, можно использовать `git merge --abort` или `git rebase --abort`, предварительно сохранив нужную работу.

После исправления проверяют сценарий, связывающий обе правки: например, production-сериализацию события и чтение настоящим consumer, а не два отдельных mock-теста. Уже опубликованный неудачный merge исправляют новым коммитом или согласованным revert; `reset --hard` общей ветки скрывает историю и создаёт дополнительный риск. Главная ошибка — считать отсутствие маркеров конфликта доказательством корректной интеграции.

### 10. Maven не скачивает зависимость. Как отличить проблему координат, репозитория и доступа?

Сначала читают первую содержательную ошибку и полный адрес артефакта: `groupId`, `artifactId`, версия, type и classifier. `404` у правильного сервера, `401/403`, ошибка DNS и `PKIX path building failed` требуют разных действий. Случайное изменение версии или отключение TLS мешает диагностике.

Проверяют, существует ли версия и куда Maven фактически обращается. Корпоративный Nexus/Artifactory обычно подключают через mirror в пользовательском или CI `settings.xml`; учётные данные задают в `servers` с `id`, совпадающим с ID выбранного репозитория/mirror. `~/.m2/repository` — локальный файловый кэш, а не корпоративный сервер. Активные profiles, proxy и `-s` могут отличать CI от ноутбука.

```bash
./mvnw -version
./mvnw help:active-profiles
./mvnw help:effective-pom
./mvnw -U verify
```

`-U` полезен после исправления публикации или закэшированного отказа разрешения; он не создаст отсутствующий артефакт и не исправит права. Effective settings и подробные `-X`-логи смотрят локально, проверяя отсутствие чувствительных данных перед передачей коллегам.

Если зависимость собирается соседним модулем, возможно, нужен reactor build, а не скачивание. Если проблема только с одним повреждённым файлом кэша, исправляют этот артефакт после проверки причины. Удалять весь `.m2` первым шагом дорого: это скрывает симптом, нагружает репозиторий и делает последующую сборку зависимой от сети.

### 11. Почему возникает NoSuchMethodError, хотя проект успешно скомпилировался?

`NoSuchMethodError` означает несовпадение бинарного контракта: вызывающий класс содержит ссылку на метод с определёнными именем и дескриптором, а загруженный JVM класс такого метода не предоставляет. Обычно код компилировался с одной версией библиотеки, а выполняется с другой. Это отличается от обычной ошибки компиляции и от отсутствия самого класса.

Проверяют дерево зависимостей, effective POM и содержимое именно выпущенного артефакта. Затем выясняют происхождение загруженного класса: для Java 17–21 можно включить `-Xlog:class+load=info` в контролируемом запуске. Дерево Maven не покажет библиотеку, которую отдельно подложил контейнер приложения или startup-скрипт.

Например, клиент собран с `json-lib` версии B, но BOM приложения выбрал версию A без нужной перегрузки. Исправление — согласовать совместимый набор библиотек, а не вслепую поднимать одну транзитивную зависимость. Для Spring Boot сначала проверяют управляемые версии платформы: ручное переопределение может нарушить совместимость соседних модулей.

Ещё один источник — shaded JAR: класс скопирован внутрь другой библиотеки и не виден отдельным узлом dependency tree. В отдельных случаях помогает relocation пакетов, но оно усложняет reflection, ресурсы и сериализованные имена; это не универсальное лечение. После исправления проверяют запуск упакованного приложения, поскольку unit-тест с classpath IDE проблему может не воспроизводить.

### 12. Чем parent POM отличается от aggregator и как собрать один модуль вместе с зависимостями?

Parent задаёт наследуемую конфигурацию, свойства и управление версиями. Aggregator перечисляет `<modules>` и объединяет проекты в reactor build. Один POM может выполнять обе роли, но это не обязательное совпадение: наличие модуля в списке не делает aggregator его родителем, а наследование не включает проект в текущую сборку.

Предположим, `orders-app` зависит от `orders-domain`, оба входят в reactor. Чтобы проверить приложение с актуальными исходниками домена, из корня выполняют:

```bash
./mvnw -pl orders-app -am verify
```

`-pl` выбирает проекты, `-am` добавляет нужные зависимости из reactor. Maven упорядочивает их по реальным зависимостям. Запись версии только в `dependencyManagement` не создаёт зависимости между модулями и не задаёт порядок сборки. `pluginManagement` аналогично задаёт настройки, а не произвольно запускает каждую описанную цель.

Ошибка «у меня работает» часто возникает, когда разработчик предварительно сделал `install` старой версии внутренней библиотеки. Локальная сборка находит её в `.m2`, а чистый runner — нет. Проверка из корня и пустой отдельный локальный репозиторий помогают обнаружить скрытую предпосылку. При этом `verify` не обязан публиковать результаты для другой независимой сборки: для этого нужны `install` локально или `deploy` в общий репозиторий.

Собирать только приложение без модулей-потребителей недостаточно для проверки изменения публичного API библиотеки. На CI выбирают затронутые зависимости и зависимые проекты либо периодически выполняют полную сборку.

### 13. Как расследовать конфликт транзитивных версий в Gradle и закрепить решение?

Сначала изучают конкретную configuration, которая участвует в проблемном запуске. Compile classpath, test runtime и runtime приложения могут иметь разный состав, поэтому список `dependencies` без контекста легко вводит в заблуждение.

```bash
./gradlew :app:dependencies --configuration runtimeClasspath
./gradlew :app:dependencyInsight \
  --dependency jackson-databind \
  --configuration runtimeClasspath
```

`dependencyInsight` показывает пути и причину выбора версии. Gradle не следует правилу Maven «ближайшая зависимость побеждает»: по умолчанию при конфликте версий одного модуля обычно выбирается более высокая, но constraints, platforms, rich versions, substitution и resolution rules могут изменить результат. Смотреть надо объяснение фактического выбора.

Если библиотека платформы должна быть согласована с другими модулями, используют подходящий BOM/platform или constraints, а не случайный `force` на один JAR. Например, обновление одного модуля Jackson без проверки остальных может оставить несовместимый набор. Исключение транзитивной зависимости тоже требует убедиться, что её функции больше никому не нужны.

Для повторяемой сборки фиксируют wrapper, версии плагинов и зависимостей; dependency locking может закрепить разрешённый граф. Сам lockfile не доказывает совместимость и не обнаруживает подмену содержимого: verification артефактов решает другую задачу. Сначала воспроизводят ошибку, затем меняют правило разрешения и запускают проверку упакованного приложения с тем же classpath. Бессистемный сброс кэша даёт мало информации о причине.

## Совместимость релиза и диагностика

### 14. Почему сборка работает локально, но падает на CI или после запуска на Java 17?

Сравнивают не только исходники, но и весь контракт сборки: commit SHA, wrapper, JDK сборщика и runtime, compiler release, активные профили, переменные, ОС и внешние сервисы. На ноутбуке IDE может использовать JDK 21, Maven — другую установленную Java, а контейнер — JRE 17.

```bash
java -version
./mvnw -version
./gradlew --version
```

Если приложение предназначено для Java 17, компиляция на более новом JDK должна учитывать и версию bytecode, и доступность API. Для совместимого Maven Compiler Plugin задают `maven.compiler.release=17`: `--release` ограничивает язык, формат class-файлов и API платформы. Одни `source`/`target` не защищают от вызова API нового JDK. Однако `--release` не понизит bytecode уже готовой сторонней библиотеки: её тоже надо выбирать совместимой.

`UnsupportedClassVersionError` указывает на неподдерживаемую runtime версию class-файла; `NoSuchMethodError` чаще означает иную бинарную несовместимость. Падение теста из-за timezone, порядка файлов или недоступного Docker требует отдельной проверки, а не переключения JDK наугад.

Для воспроизведения запускают тот же wrapper и образ сборки на том же SHA, с явной конфигурацией и чистыми выходными файлами. Кэш зависимостей ускоряет скачивание, но не должен подменять артефакты предыдущей задачи. Верификацию завершают smoke-запуском конечного образа: успешная компиляция не проверяет runtime.

### 19. Как доказать, что на рабочий стенд попала та же сборка, которую проверяли?

Свяжите результат теста с неизменяемым идентификатором артефакта. При сборке контейнера сохраните digest образа, запустите приёмочные проверки именно с ним, затем передавайте этот digest на следующий стенд. Для JAR аналогичную роль может играть проверяемая контрольная сумма. После развёртывания сверьте фактический артефакт работающих экземпляров с проверенным. Совпадение имени ветки или тега `release` такой гарантии не даёт: тег могли переместить, а один коммит можно собрать с разными входными данными.

У образа для нескольких платформ общий digest индекса объединяет разные сборки. Если тесты прошли на `linux/amd64`, а рабочие узлы используют `linux/arm64`, Docker выберет другой вариант из того же индекса. Проверяйте каждый используемый вариант и сохраняйте вместе с результатом теста платформу и digest её манифеста.

Даже один и тот же образ может вести себя по-разному из-за конфигурации и внешних зависимостей. Поэтому в записи о выпуске кроме идентификатора сборки полезны версия конфигурации, применённые миграции и результат короткой проверки после выкладки. Разбирая сбой, можно независимо спросить «тот ли код запущен?» и «с какими настройками он работает?».

### 20. Ошибка есть у пользователя, но на тестовом стенде всё работает. Как сузить поиск?

Попросите время запроса с часовым поясом, идентификатор операции, ожидаемый и фактический результат. По идентификатору проверьте, какая версия сервиса обработала запрос и через какие зависимости он прошёл. Сравните рабочий и тестовый сценарии по одному существенному условию за раз: роль, флаг функции, способ создания данных, часовой пояс, версия схемы. Используйте обезличенный минимальный набор данных и тестовую учётную запись с соответствующими правами.

Например, в журнале жалоб все пропавшие заказы созданы между 00:00 и 01:00 по местному времени. На стенде задайте явную дату, зону и две записи по разные стороны полуночи. Если симптом воспроизводится, добавьте регрессионную проверку на включение нужной записи и исключение соседней. Если гипотеза не подтвердилась, зафиксируйте, какое условие уже исключили, и проверьте следующее. Повтор реальной операции, которая отправляет уведомление или списывает деньги, может сам создать второе событие.

### 15. На подумать: как переименовать поле API и столбец БД при rolling deployment?

Сервис заказов читает `customer_name`, а новый контракт требует `display_name`. Одновременно работают старая и новая версии, часть клиентов обновится через месяц. Предложите последовательность релизов и точку, после которой прежний артефакт уже нельзя безопасно вернуть.

<details>
<summary>Разбор</summary>

Сначала расширяют схему, сохраняя старое представление. Новая версия должна читать данные, созданные старой, и писать так, чтобы активные старые экземпляры продолжали работать. Например, временно добавляют новый столбец, согласованно поддерживают оба значения в одной транзакции и выполняют backfill с контролем прогресса. Независимые записи в две БД без журнала восстановления не обеспечивают такую гарантию.

API развивают отдельно: вводят новое поле с периодом совместимости либо новую версию контракта. При одновременной передаче двух полей задают приоритет и поведение при несовпадении. Нельзя считать добавление поля всегда безопасным: строгие десериализаторы и схемы клиентов могут его отклонять.

После backfill проверяют расхождения и отсутствие старых писателей, включая cron-задачи, consumers и отложенные сообщения. Затем переключают чтение, но до конца согласованного окна отката сохраняют актуальность старого формата для всех новых записей и изменений: например, продолжают dual-write в одной транзакции с проверкой согласованности. Одного начального backfill недостаточно. После завершения окна отката можно прекратить поддержку старой записи и отдельным релизом удалить прежний столбец/контракт. Миграция сама может создавать блокировки и нагрузку, поэтому размер batch и время выполнения проверяют на репрезентативном объёме.

Безопасный откат теряется уже с первым изменением, которое перестало отражаться в старом формате: прежний образ прочитает устаревшие или отсутствующие данные, даже если столбец ещё существует. Перед таким откатом потребуется восстановить старое представление и проверить его полноту, если преобразование вообще обратимо; после DROP нужна ещё и схема. Откат маршрутизации также не отменяет данные и побочные эффекты, уже созданные новой версией. Опасный ответ — «сначала rename столбца, потом обычный rolling»: ещё работающая старая версия немедленно потеряет нужное поле.

</details>

### 16. После релиза вырос p99, но CPU низкий. Как искать причину без случайных рестартов?

Низкий CPU не исключает перегрузку: запросы могут ждать соединение из пула, lock, внешний ответ или свободный executor. Сначала оценивают пользовательский ущерб, сравнивают версии, endpoints и временную границу изменения. Если есть безопасное действие для стабилизации, его выполняют параллельно с ограниченной диагностикой, сохраняя доступные свидетельства.

Например, после релиза p99 вырос с 300 мс до 8 секунд, active connections HikariCP достигли лимита, а длительность SQL не изменилась. Следующая гипотеза — соединения удерживают вне SQL или запросы ждут выдачи соединения. Смотрят pending connections, transaction duration и trace: внешний HTTP-вызов внутри транзакции способен занять весь пул без высокого CPU.

```bash
jcmd <pid> Thread.print -l
jcmd <pid> JFR.start name=latency settings=default duration=60s filename=latency.jfr
```

Несколько thread dump через интервал показывают устойчивое ожидание, JFR и wall-clock profile помогают связать его со стеком. Доступ и параметры `jcmd` проверяют для целевой JVM; диагностические файлы сохраняют в доступный путь с достаточным местом. Сбор тоже имеет стоимость.

Увеличение пула без расчёта может перегрузить БД; рост числа потоков создаёт ещё больше ожидающих. Проверяют таймауты, границы транзакции и число одновременных запросов. После исправления сравнивают ту же нагрузку, p99, ошибки и насыщенность пула, а не только среднюю latency.
