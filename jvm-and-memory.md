## Устройство памяти и жизненный цикл классов

### 3. Чем различаются JDK, JRE и JVM?

- **JVM (Java Virtual Machine)**: виртуальная машина, исполняющая байт-код (`.class` файлы). Именно JVM обеспечивает кроссплатформенность («Write once, run anywhere»).

- **JRE (Java Runtime Environment)**: комплект для **запуска** приложений — JVM + стандартные библиотеки классов.

- **JDK (Java Development Kit)**: комплект для **разработки** — JRE + компилятор `javac`, отладчик, профилировщики и прочие инструменты.

```text
JDK = JRE + компилятор и инструменты разработки
JRE = JVM + стандартные библиотеки
```

Пара нюансов, которые спрашивают следом:

- Oracle перестала предлагать отдельную JRE-поставку начиная с Java 11; облегчённый runtime под модульное приложение можно собрать через `jlink`. Поэтому на сервере часто используют JDK или образ, собранный `jlink`'ом. Отдельные runtime/JRE-сборки могут предоставлять другие поставщики: отсутствие Oracle JRE не означает запрета таких поставок.

- JVM — это спецификация, и реализаций несколько: HotSpot (основная, в OpenJDK), OpenJ9 (Eclipse, экономнее по памяти и быстрее стартует), GraalVM (умеет AOT-компиляцию в native image). И исполняет JVM не только Java: Kotlin, Scala, Groovy компилируются в тот же байт-код.

### 1. Как устроена память в JVM: в чем разница между Heap (кучей) и Stack (стеком)?

```text
+-------------------------------------------------------------+
|                         JVM MEMORY                          |
|  +-----------------------+   +---------------------------+  |
|  |     HEAP (Куча)       |   |      STACK (Стек)         |  |
|  |  (Общая для потоков)  |   | (Свой на каждый поток)    |  |
|  |  Все объекты (new)    |   | Локальные примитивы       |  |
|  +-----------------------+   +---------------------------+  |
|  +-------------------------------------------------------+  |
|  |     METASPACE (Native Memory: метаданные классов)     |  |
|  +-------------------------------------------------------+  |
+-------------------------------------------------------------+
```

1. **Heap (Куча)**:
   - Область памяти, **общая для всех потоков** JVM.
   - Здесь хранятся все создаваемые объекты (`new MyClass()`) и их поля.
   - Очисткой занимается сборщик мусора (Garbage Collector).
   - При нехватке памяти выбрасывается `OutOfMemoryError`.

2. **Stack (Стек)**:
   - Создается **индивидуально для каждого потока** (Thread Stack).
   - Хранит фреймы вызова методов (Stack Frames), локальные примитивы и ссылки на объекты в Heap.
   - Освобождается автоматически при выходе из метода по принципу LIFO.
   - При переполнении выбрасывается `StackOverflowError`.

Частые follow-up:

- **Где лежат статические поля и пул строк?** Статические поля — в куче, внутри объекта `java.lang.Class` соответствующего класса (метаданные класса — в Metaspace, см. вопрос 11). Пул интернированных строк с Java 7 тоже в куче (до этого был в PermGen).

- **Сколько памяти ест стек?** Размер стека потока задается `-Xss` (по умолчанию ~512 КБ–1 МБ в зависимости от ОС и платформы). Для платформенных потоков стек не входит в кучу: тысяча стеков по 1 МиБ резервирует около гигабайта адресного пространства, но фактически используемая физическая память может быть меньше. `unable to create new native thread` бывает также из-за лимита потоков/PID ОС или контейнера. Сначала проверяют число потоков, память и лимиты; уменьшение `-Xss` требует проверки глубины вызовов. У виртуальных потоков стек представлен растущими сегментами в heap, поэтому эта арифметика к ним не переносится.

- **«Объекты могут создаваться в стеке»?** В спецификации JVM такого нет — формально все объекты в куче. JIT через escape analysis может убрать аллокацию вообще (скалярная замена, см. вопрос 12), но это оптимизация конкретного горячего участка, а не правило языка.

### 27. Почему по полям класса нельзя точно назвать размер одного объекта?

Сумма размеров полей не учитывает заголовок объекта и выравнивание. У массива есть ещё длина. Для ссылок значение имеет режим JVM, а в оценке целого графа — какие объекты уже существуют и используются совместно. Спецификация Java не закрепляет единый размер заголовка или одной ссылки для всех реализаций.

Например, миллион `long` в одном `long[]` требует 8 миллионов байт **под значения** плюс служебную часть одного массива и возможное выравнивание. У `Long[]` в самом массиве лежат ссылки. Добавлять стоимость миллиона отдельных обёрток можно, лишь если они действительно созданы и различны. Массив из миллиона ссылок на один объект имеет совершенно другой профиль памяти.

Проверяйте предположения на целевой JVM. JOL показывает расположение полей и выравнивание конкретного класса в данном окружении. В heap dump сравните количество экземпляров и пути ссылок. Замер свободной памяти до и после одного `new` слишком груб: на разницу одновременно влияют прочие аллокации и сборки мусора.

### 7. Как устроена иерархия ClassLoader (Bootstrap, Platform, Application) и что такое делегирование родителю?

ClassLoader — это механизм, который загружает `.class`-файлы в JVM по требованию: момент загрузки может выбираться JVM заранее; загрузку нельзя путать с инициализацией при активном использовании. Загрузчики выстроены в иерархию, и каждый перед загрузкой класса сначала спрашивает родителя — это и есть делегирование.

```text
Bootstrap ClassLoader     — ядро JDK (модуль java.base, классы java.lang.*).
                            Написан на нативном коде, из Java виден как null.
        ↑ родитель
Platform ClassLoader      — остальные модули JDK (java.sql, java.xml и т.д.).
                            До Java 9 назывался Extension ClassLoader.
        ↑ родитель
Application ClassLoader   — классы приложения из CLASSPATH.
        ↑ родитель
Custom ClassLoader        — ваши загрузчики (плагины, hot reload, Tomcat и т.п.)
```

**Как работает делегирование (parent-first):** при запросе класса загрузчик сначала делегирует запрос родителю, и только если вся цепочка родителей класс не нашла — ищет сам. Это дает две вещи: класс грузится один раз (уникальность в рамках загрузчика) и нельзя подменить системный класс своим — ваш `java.lang.String` из classpath никогда не победит тот, что загрузил Bootstrap.

Частый follow-up — разница между `ClassNotFoundException` и `NoClassDefFoundError`:

- **`ClassNotFoundException`** — checked-исключение: класс не найден при **явной** загрузке по имени (`Class.forName("com.Foo")`, `ClassLoader.loadClass()`). Классика — забытый JDBC-драйвер в classpath.

- **`NoClassDefFoundError`** — `Error`: класс был на этапе компиляции, JVM наткнулась на него в коде, но определение найти не смогла. Типичные причины: jar пропал из classpath в рантайме или класс не смог инициализироваться (упал статический блок) — тогда повторные обращения дают именно эту ошибку.

Еще два follow-up из той же серии:

- **Жизненный цикл класса**: загрузка (Loading) → связывание (Linking: верификация байт-кода, подготовка статических полей значениями по умолчанию, резолюция ссылок) → инициализация (выполнение статических блоков и инициализаторов). Инициализация происходит только при первом *активном* использовании класса: `new`, вызов статического метода, обращение к не-константному статическому полю. Чтение `static final` константы, вычисленной на этапе компиляции, класс не инициализирует.

- **Делегирование — не догма.** Tomcat нарочно переворачивает схему: его WebappClassLoader сначала ищет класс у себя в `WEB-INF` (child-first), чтобы два веб-приложения на одном сервере могли таскать разные версии одной библиотеки. К классам JDK и Servlet API он по-прежнему идет через родителя.

### 17. Когда инициализация класса блокирует другие потоки и что произойдёт после ошибки в static-блоке?

Инициализация класса выполняется одним потоком; другие потоки, которым требуется активное использование того же класса, ожидают её завершения. JVM выполняет статические инициализаторы и блоки в порядке объявления. Это обеспечивает безопасную публикацию результата инициализации, на чём основана holder-идиома singleton. Загрузка класса, получение `SomeClass.class` и чтение compile-time константы сами по себе не требуют выполнения его `static`-блока.

Представим инициализатор, который запускает фоновую работу и ждёт её:

```java
class Registry {
    static final String VALUE;
    static {
        var task = new FutureTask<String>(() -> Registry.load());
        new Thread(task).start();
        try {
            VALUE = task.get();
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
            throw new ExceptionInInitializerError(e);
        } catch (ExecutionException e) {
            throw new ExceptionInInitializerError(e.getCause());
        }
    }
    static String load() { return "ready"; }
}
```

Родитель ждёт `Future`, а дочерний поток не может вызвать статический метод класса до завершения его инициализации. Получается циклическое ожидание, хотя в коде нет явного `synchronized`. Поэтому в статической инициализации избегают сети, ожидания задач и взаимозависимых инициализаторов; дорогое создание ресурса выносят в управляемый жизненный цикл приложения.

Если инициализатор завершился исключением, не являющимся `Error`, первый поток обычно получает `ExceptionInInitializerError`. Класс помечается ошибочным для этого определяющего загрузчика; последующие попытки активного использования получают `NoClassDefFoundError`. Это не обязательно пропавший JAR, поэтому ищут самую первую ошибку запуска. Автоматического повторения инициализации того же класса после исправления внешней БД не происходит.

Частая ошибка — считать, что `ClassLoader.loadClass()` всегда запускает статические блоки. Для контролируемого поведения различают загрузку и `Class.forName(name, initialize, loader)`.

### 18. Почему одинаковое имя класса не гарантирует совместимость типов и как это связано с утечкой ClassLoader?

Идентичность обычного класса в JVM определяется парой: бинарное имя и определяющий `ClassLoader`. Поэтому два плагина могут иметь собственные классы `com.example.User`, которые не приводятся друг к другу. Сообщение вида `User cannot be cast to User` не парадокс: полные имена совпадают, загрузчики разные. В диагностике сравнивают `obj.getClass().getClassLoader()` и загрузчик ожидаемого типа; отдельно проверяют фактические версии JAR.

Практическая схема для плагинов: общий интерфейс загружает родитель, реализации — дочерние загрузчики. Через границу передают этот общий интерфейс и типы контракта, а не внутренние классы конкретного плагина. Иначе одинаковые копии API снова оказываются разными типами. Child-first нужен для изоляции зависимостей, но произвольная смена делегирования может нарушить именно общий контракт.

При обновлении плагина создание нового загрузчика не освобождает старый автоматически. Например, главный сервис сохранил listener:

```java
listeners.add(pluginListener); // объект класса из loader версии 1
// загрузили версию 2, но старого listener не удалили
```

Цепочка `GC root → listeners → объект плагина → класс → загрузчик` удерживает старую версию и её метаданные. Другие причины — живой поток с `contextClassLoader`, `ThreadLocal`, незавершённая задача и глобальный реестр драйверов. Закрытие `URLClassLoader` освобождает открытые ресурсы загрузчика, но не обрывает все внешние ссылки.

В heap dump ищут путь удержания загрузчика, в метриках — рост количества загруженных классов после каждого обновления; полезен `jcmd <pid> VM.classloader_stats`. Нормальный рост при старте ещё не утечка. Частая ошибка — лечить повторяемый рост только `MaxMetaspaceSize`: лимит лишь откладывает очередное падение.

### 28. Почему после обновления библиотеки старый клиент по-прежнему видит прежнее значение константы?

Допустим, библиотека публикует `public static final int LIMIT = 7;`, а клиент печатает `Limits.LIMIT`. Для переменной примитивного типа или `String`, объявленной `final` и инициализированной константным выражением, компилятор записывает само значение в байт-код клиента. Если заменить JAR библиотеки, изменив 7 на 9, уже собранный клиент продолжит печатать 7.

Проверьте это двумя сборками: скомпилируйте библиотеку и клиента вместе, затем перекомпилируйте только библиотеку с новым числом. Посмотрите `javap -c Client` — в методе останется инструкция загрузки числа. После пересборки клиента там появится 9.

Не каждое поле `static final` подходит под это правило. Например, результат вызова `Integer.parseInt("7")` не является константным выражением. Для параметра, который издатель библиотеки намерен менять независимо от сборки приложения, обычно удобнее метод доступа или конфигурация.

## Исполнение кода и измерения

### 29. Библиотеку собрали на новом JDK. Как проверить, запустится ли она на старой JVM?

Сначала выясните минимальную поддерживаемую версию Java. Есть как минимум две границы совместимости: формат файла класса и доступность вызываемых API. Старая JVM отвергнет слишком новую версию class-файла с `UnsupportedClassVersionError`. Даже при подходящем формате вызов метода, которого в целевой библиотеке нет, завершится ошибкой связывания.

Пример: проект должен работать на Java 11, а разработчик на JDK 17 использует `Stream.toList()`, появившийся в Java 16. Сборка через `javac --release 11` отклонит вызов уже при компиляции. Одни только `-source 11 -target 11` выбирают язык и формат класса, но когда компилятор видит API собственного JDK, такая сборка всё ещё может принять недоступный на Java 11 метод.

Через `javap -verbose MyClass` можно проверить версию class-файла: для Java 11 это 55, для Java 17 — 61. Затем запускайте тесты на минимальной поддерживаемой JVM с реальными зависимостями. Проверка одного класса ничего не скажет о версии вложенного JAR или о нативной библиотеке, нужной во время запуска.

### 8. Как JVM исполняет код: интерпретатор, JIT-компиляторы C1/C2 и tiered compilation?

JVM не выбирает между интерпретацией и компиляцией — она использует оба. Код стартует в интерпретаторе, а по мере «разогрева» горячие участки компилируются в машинный код все более агрессивно.

1. **Интерпретатор**: читает байт-код и исполняет инструкцию за инструкцией. Старт мгновенный, но каждый вызов метода интерпретируется заново — медленно. Зато именно интерпретатор собирает профиль: какие методы вызываются часто, какие ветки `if` срабатывают.

2. **JIT-компиляторы**: когда метод или цикл пересекает порог вызовов (становится «горячей точкой», hot spot), JIT компилирует его в нативный код, и дальше метод исполняется напрямую процессором.
   - **C1 (client compiler)**: компилирует быстро, с легкими оптимизациями. Дает прирост почти сразу после старта.
   - **C2 (server compiler)**: компилирует долго, но агрессивно оптимизирует, опираясь на собранный профиль. Именно его код обеспечивает пиковую производительность.

3. **Tiered compilation** (включена по умолчанию с Java 8): конвейер из уровней — интерпретатор → C1 с профилированием → C2. Так JVM совмещает быстрый старт и быстрый пик.

Ключевая оптимизация C2 — **инлайнинг**: тело маленького горячего метода подставляется прямо в место вызова, убирая накладные расходы на вызов и открывая дорогу остальным оптимизациям (вплоть до удаления мертвого кода). Поэтому, кстати, на «холодном» микробенчмарке результаты часто врут — JIT просто не успел отработать.

Обратная сторона профильных оптимизаций — **деоптимизация**: C2 компилирует спекулятивно («раз за всё время вызывалась одна реализация интерфейса — подставлю ее напрямую»), и если допущение ломается (загрузилась вторая реализация), скомпилированный код выбрасывается и исполнение откатывается в интерпретатор. Поэтому бенчмарк или нагрузочный тест, не прошедший по всем веткам кода, показывает цифры, которых в проде может не быть.

Посмотреть на процесс компиляции вживую можно флагом `-XX:+PrintCompilation`.

### 30. Что можно узнать об invokedynamic из байт-кода обычной лямбды?

`invokedynamic` обозначает место вызова, для которого способ связывания задаёт bootstrap-метод. В class-файле есть описание ожидаемых аргументов и типа результата. При связывании JVM получает совместимую точку вызова. Это позволяет компилятору описать, например, создание экземпляра функционального интерфейса, а выбор конкретной реализации оставить среде выполнения.

```java
import java.util.function.IntUnaryOperator;

class Ops {
    static IntUnaryOperator add(int step) {
        return x -> x + step;
    }
}
```

Скомпилируйте пример и выполните `javap -c -v Ops`. В обычном выводе `javac` для JDK 17 у метода `add` будет инструкция `invokedynamic`: она получает захваченное значение `step` и возвращает `IntUnaryOperator`. В разделе `BootstrapMethods` найдите связь с `LambdaMetafactory`. Само сложение выполняется позже, когда клиент вызывает `applyAsInt` у полученного оператора. Из этой строки байт-кода нельзя заключить, что при каждом вызове сложения заново происходит связывание.

### 12. Какие оптимизации применяет JVM к коду и данным (Compact Strings, String Deduplication, Escape Analysis)?

Три оптимизации, о которых регулярно спрашивают, потому что они незаметны в коде, но сильно влияют на память и скорость.

- **Compact Strings (Java 9+)**: строка внутри стала `byte[]` вместо `char[]`. Если все символы помещаются в Latin-1 (один байт на символ), строка хранится компактно — экономия почти вдвое на типичном тексте. Для кириллицы, кстати, не сработает: она в Latin-1 не входит, и строки с ней хранятся в UTF-16 как раньше.

- **String Deduplication** (включается `-XX:+UseStringDeduplication`; исторически только в G1, с Java 18 поддерживает и ZGC): GC ищет строки с одинаковым содержимым и заставляет их разделять один backing-массив данных. Помогает, когда приложение хранит много дублей — например, распарсенный JSON с повторяющимися значениями.

- **Escape Analysis**: JIT анализирует, «убегает» ли объект за пределы метода (возвращается ли, кладется ли в поле). Если нет, применяются два трюка:
  - **Скалярная замена**: объект вообще не создается в куче — его поля раскладываются по регистрам/стеку, как набор локальных переменных. Нет объекта — нет работы для GC.
  - **Lock elision**: если объект с синхронизацией не покидает поток, захват монитора удаляется за ненадобностью.

```java
int sum(Point[] points) {
    Point p = new Point(0, 0); // не "убегает" из метода:
    for (Point src : points) { // JIT может не создать его в куче вообще,
        p.x += src.x;          // оставив только два скаляра в регистрах
        p.y += src.y;
    }
    return p.x + p.y;
}
```

На практике это ответ на вопрос «почему аллокация короткоживущих объектов в горячем коде почти бесплатна».

### 25. Почему простой замер nanoTime вокруг метода может обмануть и чем помогает JMH?

JVM оптимизирует код во время исполнения, поэтому один вызов измеряет смесь загрузки классов, интерпретации, компиляции и полезной работы. После прогрева профиль может измениться: инлайнинг, скалярная замена и удаление лишних вычислений делают горячий код другим. Разница двух `nanoTime()` не исправляет эту методологическую проблему и сама добавляет стоимость на коротких операциях.

Показательный неправильный тест:

```java
long start = System.nanoTime();
for (int i = 0; i < 1_000_000; i++) {
    Math.sqrt(123.0); // результат нигде не используется
}
System.out.println(System.nanoTime() - start);
```

JIT может удалить работу или вычислить константу заранее. Если результат использовать, остаются другие ловушки: постоянный вход, слишком предсказуемые ветки, общий профиль двух сравниваемых вариантов и отсутствие реальных аллокаций, которые оптимизатор устранил. Поэтому «метод делает миллион операций» по исходнику ещё не означает миллион таких операций в машинном коде.

JMH помогает организовать прогрев, измерительные итерации и отдельные JVM forks, передавать изменяемое состояние и потреблять результат через возвращаемое значение или `Blackhole`. Он снижает типичные ошибки, но не делает любую постановку правильной: нужно выбрать подходящие размеры данных, состояние на поток/тест и режим конкурентного доступа.

Для latency сервиса микробенчмарк вообще не заменяет нагрузочный тест: там есть очереди, сеть, пул БД и GC нескольких запросов. И наоборот, шумный end-to-end тест плохо показывает разницу двух операций в наносекундах.

На собеседовании сильный ответ начинается с того, какую гипотезу проверяют и какой результат может её опровергнуть. Нельзя обещать ускорение только потому, что код стал короче. Для микробенчмарка на JVM подходит JMH.

## Достижимость и работа сборщиков

### 4. Как устроены поколения в Heap (Young Generation, Old Generation) и процесс сборки мусора?

В основе лежит **гипотеза о слабых поколениях** (weak generational hypothesis): *большинство объектов умирает вскоре после создания*.

- **Young Generation**:
  - `Eden` — сюда обычно попадают небольшие новые объекты в классических поколенческих сборщиках.
  - Два пространства `Survivor` (`S0` и `S1`) — сюда пережившие Minor GC объекты перемещаются, накапливая «возраст».
  - **Minor GC** происходит часто и выполняется быстро.

- **Old (Tenured) Generation**:
  - Сюда попадают объекты, пережившие пороговое число сборок (`-XX:MaxTenuringThreshold`).
  - Старое поколение очищается механизмами выбранного сборщика: например, mixed evacuation у G1 или конкурентными циклами ZGC.

Объект считается мусором, когда до него нельзя добраться из **GC Roots** (локальные переменные активных потоков, статические поля, JNI-ссылки).

Три нюанса, на которых спотыкаются:

- **Термины зависят от сборщика.** «Major GC» не универсальное название строго одного типа события. Для HotSpot лучше назвать конкретную запись лога: Young, Mixed, Concurrent Cycle или Full GC. Full GC не гарантирует освобождения Metaspace: классы выгружаются только при выполнении условий выгрузки.

- **В Old попадают не только «постаревшие».** Крупные объекты могут аллоцироваться сразу в старом поколении, минуя Eden (в G1 это humongous-объекты — больше половины размера региона). А если Survivor-пространства переполнены, объекты промоутятся раньше порога — фактический возраст промоушна JVM определяет динамически.

- **Картинка поколений — логическая.** G1 делит кучу на регионы одинакового размера, и роль региона (Eden/Survivor/Old) назначается динамически — непрерывных областей поколений физически нет. Поколенческий ZGC доступен с Java 21, но до JDK 23 требует отдельного включения; Serial и Parallel используют более классическую раскладку поколений.

Два механизма, которые делают эту схему быстрой (любимый вопрос «почему аллокация в Java почти бесплатна» и «как GC находит ссылки старое → молодое»):

- **TLAB (Thread-Local Allocation Buffer).** Каждый поток получает свой участок Eden. Аллокация объекта — это просто сдвиг указателя внутри своего буфера, без всякой синхронизации с другими потоками. При исчерпании TLAB нужен медленный путь получения следующего буфера; крупные объекты могут выделяться вне TLAB. Также остаются затраты на обнуление, инициализацию и будущую сборку. Отсюда скорость `new` в HotSpot, сравнимая со стековой аллокацией.

- **Card table и write barrier.** При Minor GC нужно найти живые объекты молодого поколения, в том числе те, на которые ссылаются объекты из Old. Сканировать всё старое поколение — дорого, поэтому куча делится на «карточки» (~512 байт), а JIT вставляет в код записи ссылки write barrier: если поток записал ссылку из старого объекта на молодой, соответствующая карточка помечается «грязной». Minor GC сканирует корни плюс только грязные карточки (remembered set), а не весь Old.

### 2. Какие бывают сборщики мусора в JVM (Serial, Parallel, G1, ZGC, Shenandoah, Epsilon)?

- **Serial GC** (`-XX:+UseSerialGC`): однопоточный сборщик, подходит для небольших приложений с кучей до нескольких сотен МБ.

- **Parallel GC** (`-XX:+UseParallelGC`): многопоточный сборщик для максимальной пропускной способности (throughput). Был сборщиком по умолчанию в Java 8.

- **G1 GC (Garbage-First)**: сборщик по умолчанию с Java 9. Разбивает кучу на регионы и в первую очередь собирает регионы с наибольшим количеством мусора. Позволяет задать целевую паузу (`-XX:MaxGCPauseMillis`).

- **ZGC** (`-XX:+UseZGC`): конкурентный сборщик для низких пауз. Production-ready с Java 15. В JDK 21–22 поколенческий вариант включают дополнительно через `-XX:+ZGenerational`; в JDK 23 он стал режимом по умолчанию; в JDK 24 непоколенческий режим удалён. Короткие паузы GC — цель дизайна, а не гарантия p99 всего запроса: важны CPU, запас кучи и скорость аллокаций.

- **Shenandoah** (`-XX:+UseShenandoahGC`): конкурентный сборщик с перемещением объектов, также ориентирован на короткие паузы. Доступность зависит от дистрибутива, платформы и версии; наличие проверяют на целевой сборке JDK. В Oracle JDK он не поставляется. Детали барьеров и поколенческого режима нельзя переносить между версиями без проверки.

- **Epsilon GC** (`-XX:+UseEpsilonGC`): сборщик-пустышка — память выделяет, мусор не собирает, по исчерпании кучи JVM падает. Применяется для тестов производительности, где нужно исключить влияние GC, и короткоживущих задач, гарантированно укладывающихся в кучу.

Для истории: **CMS** (Concurrent Mark Sweep) — первый массовый низколатентный сборщик; deprecated с Java 9 и удален в Java 14. Если спросят «чем G1 лучше CMS», G1 выполняет эвакуацию и уплотнение, уменьшая характерную для CMS фрагментацию обычных объектов. Но фрагментация и неэффективное использование регионов, особенно при humongous-объектах, остаются возможными: недостаток последовательных свободных регионов может вызвать Full GC или отказ выделения даже при достаточном суммарном свободном месте. Этот случай разобран в вопросе 23.

**Как выбирать** (типичный follow-up): маленькая куча или одноразовая утилита — Serial; batch-задачи, где важна пропускная способность, а паузы некритичны — Parallel; универсальный дефолт для сервисов — G1; жесткие требования к latency (p99) на больших кучах — ZGC или Shenandoah. Имейте в виду: «сборщик по умолчанию» выбирается эргономикой JVM — на серверных машинах это G1, но на одноядерной машине с кучей до 2 ГБ JVM может выбрать Serial.

### 6. Что делает метод System.gc() и гарантирует ли он немедленную сборку мусора?

Вызов `System.gc()` (по сути обертка над `Runtime.getRuntime().gc()`) является лишь **рекомендацией** для JVM запустить сборку мусора — спецификация не гарантирует, что сборка действительно произойдет. Решение остается за виртуальной машиной (принудительный запуск можно запретить флагом `-XX:+DisableExplicitGC`).

Ручной вызов `System.gc()` в продакшн-коде считается плохой практикой: он может спровоцировать полную сборку (Full GC) с длинной паузой Stop-The-World, не давая никакой гарантии освобождения памяти.

### 9. Какие бывают типы ссылок в Java (Strong, Soft, Weak, Phantom) и для чего нужна ReferenceQueue?

Тип ссылки определяет, как GC обращается с объектом: чем слабее ссылка, тем охотнее сборщик забирает объект. Это способ сказать GC «этот объект не жалко».

- **Strong** — обычная ссылка (`Object o = new Object()`). Пока объект достижим по сильной ссылке, GC его не тронет. 99% кода живет на них.

- **Soft** (`SoftReference`) — сборщик может очистить мягкую ссылку по своей политике; спецификация требует очистить мягкие ссылки на мягко достижимые объекты перед OOM. Предсказуемой ёмкости и времени жизни это не даёт, поэтому для прикладного кэша обычно нужен явный лимит.

- **Weak** (`WeakReference`) — когда GC определяет слабую достижимость, слабая ссылка очищается; точное время проверки и освобождения памяти не гарантировано. На этом построена `WeakHashMap`: запись исчезает, когда ключ перестал использоваться снаружи.

- **Phantom** (`PhantomReference`) — `get()` всегда возвращает `null`. Ссылка нужна не для доступа к объекту, а чтобы получить уведомление о фантомной достижимости объекта после очистки ссылки, не получая доступ к самому объекту. Применяется для освобождения внешних ресурсов (например, off-heap памяти); с Java 9 для этого есть более удобный `Cleaner`.

```java
// Классический кэш на слабых ключах: как только на Data
// не осталось сильных ссылок снаружи — запись сама уйдет при GC
Map<Data, Metadata> cache = new WeakHashMap<>();

// Узнать об удалении объекта — через ReferenceQueue:
ReferenceQueue<Data> queue = new ReferenceQueue<>();
WeakReference<Data> ref = new WeakReference<>(data, queue);
// Когда ref очищена и поставлена в очередь, queue.poll() может вернуть ref.
```

**ReferenceQueue** — очередь, куда GC складывает зарегистрированные ссылки (weak/soft/phantom) после очистки соответствующих ссылок в соответствии с их типом. Очередь сообщает об изменении достижимости, а не о точном моменте физического освобождения памяти. Так можно удалять служебные записи для исчезнувших ключей. Владение внешними ресурсами всё равно задают явно: очередь и `Cleaner` не заменяют `close()`/`release()`.

Ловушка на собеседовании: `WeakHashMap` держит слабые ссылки на **ключи**, а значения — сильные. Если значение ссылается обратно на свой ключ, запись не соберется никогда.

### 31. Heap почти пуст, а файловые дескрипторы закончились. Поможет ли Cleaner вместо close?

Внешний ресурс живёт по правилам операционной системы. Открытый файл или сокет способен исчерпать лимит дескрипторов раньше, чем у JVM появится повод собрать мусор. Для файла определите владельца и закройте ресурс через `try` с ресурсами. Проверьте исключительный путь: если чтение падает посередине блока, `close()` всё равно вызывается.

У класса, владеющего нативным ресурсом, `Cleaner` может служить запасным механизмом. Он запускает зарегистрированное действие, когда объект достиг соответствующего состояния достижимости, без обещания конкретного срока. Если само действие захватило `this`, например через `cleaner.register(this, this::release)`, оно удерживает владельца, и автоматическая очистка не наступит. Действию передают отдельное состояние — например, объект с нативным дескриптором, без ссылки на владельца. При явном закрытии можно вызвать `Cleanable.clean()`; действие для этой регистрации исполняется не более одного раза.

В тесте замените освобождение ресурса счётчиком, закройте владельца дважды и проверьте одно освобождение. Такой тест проверяет явный контракт закрытия. Обещать вызов автоматической очистки через заданное число миллисекунд нельзя.

### 23. Почему G1 может страдать от humongous-объектов даже при свободной памяти?

G1 делит heap на регионы. Объект размером больше половины региона считается humongous и размещается в последовательности целых регионов старого поколения. Остаток последнего региона нельзя отдать другому обычному объекту. Для крупного массива поэтому важны не только суммарные свободные байты, но и возможность найти подходящую непрерывную последовательность регионов; свободное место может использоваться неэффективно.

Например, при регионе 2 МиБ массив размером чуть больше 1 МиБ уже humongous, хотя приложению он кажется небольшим. Многократная материализация больших JSON, архивов или батчей создаёт такую нагрузку. Полезный первый шаг — потоковая обработка и ограничение пачки: это снижает и объём временных данных, и число крупных выделений.

Проверяют фактический размер региона, строки о humongous regions, причины начала marking и эвакуационные сбои:

```bash
java -Xlog:gc*,gc+humongous=debug:file=gc.log:uptime,level,tags -jar app.jar
```

Лог должен иметь ротацию в длительном запуске. Рост humongous regions ещё не доказывает утечку: часть таких объектов G1 умеет освобождать раньше общего цикла, если выполнены условия. Важно, сколько регионов удерживается после сопоставимых сборок и откуда приходят массивы.

Увеличение `G1HeapRegionSize` иногда переводит конкретный размер ниже humongous-порога, но делает разбиение кучи грубее и может ухудшить другие свойства. Поэтому это эксперимент после профилирования, а не универсальное лечение. Увеличение heap тоже не исправляет бесконтрольное удержание массивов.

Частая ошибка — объяснять любой Full GC «нехваткой Eden» и вслепую фиксировать Young через `-Xmn`: G1 рассчитывает его размер под цель пауз.

### 24. Как корректно сравнить G1 и ZGC и что меняется между JDK 21, 23 и 24?

Сборщик выбирают по результатам на своей нагрузке: latency, throughput, CPU и полному расходу памяти. Короткая Stop-The-World пауза не гарантирует быстрой обработки: конкурентный GC делит CPU с приложением, а при нехватке запаса кучи возможны задержки выделения. Поэтому сравнивают не только максимум GC pause, но и p95/p99 запросов, allocation stalls, загрузку процессора и устойчивость под длительной нагрузкой.

Важна точная команда запуска. В JDK 21–22 поколенческий ZGC требует:

```bash
java -XX:+UseZGC -XX:+ZGenerational -Xmx4g -jar app.jar
```

В JDK 23 при `UseZGC` поколенческий режим выбран по умолчанию. В JDK 24 непоколенческий вариант удалён; `ZGenerational` больше не нужен. Нельзя описывать все три версии фразой «с Java 21 ZGC всегда поколенческий» или механически переносить старые флаги на новый JDK.

Практический эксперимент: фиксируют версию JDK, лимиты CPU/памяти контейнера, входной поток и набор данных; прогревают приложение, затем сравнивают длительные интервалы и пики. Сначала можно менять только GC, затем отдельно оценивать обновление JDK. Иначе невозможно понять, какой фактор дал результат.

Например, переход уменьшил p99 пауз GC, но снизил throughput под CPU quota: цель бизнеса могла стать хуже. Или вырос RSS при одинаковом `-Xmx` — контейнерный бюджет тоже нужно перепроверить. Для конкурентной сборки heap должен вмещать живые объекты и аллокации во время цикла; держать его почти полностью занятым опасно.

Частая ошибка — объявить ZGC всегда быстрее G1 по одному короткому микробенчмарку.

## Диагностика памяти, пауз и падений

### 5. Что такое OutOfMemoryError (OOM) и StackOverflowError и как их отлаживать?

- **`StackOverflowError`**: возникает при переполнении стека вызовов — чаще всего из-за бесконечной или слишком глубокой рекурсии. Диагностируется по стек-трейсу.

- **`OutOfMemoryError: Java heap space`**: куча не может удовлетворить выделение: из-за размера живых данных, всплеска нагрузки, слишком большой аллокации или утечки памяти (объекты остаются достижимыми: статические коллекции, незакрытые ресурсы, бесконтрольные кэши).

- **`OutOfMemoryError: Metaspace`**: переполнение области метаданных классов (типично при утечках класслоадеров, см. вопрос 11).

По тексту сообщения OOM бывают разные, и их стоит различать:

- `Java heap space` — переполнена куча (утечка или слишком маленький `-Xmx`).

- `Metaspace` — переполнены метаданные классов.

- `GC overhead limit exceeded` — в сборщиках, поддерживающих эту проверку, слишком большая доля времени уходит на GC при малом освобождении памяти. Это симптом нехватки полезного запаса кучи; причиной может быть и утечка, и слишком большой живой набор, а не только небольшой `-Xmx`.

- `Requested array size exceeds VM limit` — попытка создать массив размером около или больше 2^31 элементов.

- `unable to create new native thread` — не удаётся создать платформенный поток: проверяют нативную память, число потоков и лимиты PID/пользователя/контейнера.

- `Direct buffer memory` — исчерпана off-heap память direct-буферов (см. вопрос 14).

Оба класса наследуют `Error`, но сами по себе не доказывают повреждение JVM. Обычный бизнес-код не должен ловить их и бесконечно повторять операцию: памяти на обработку может уже не хватить. Политика сервиса — собрать доступную диагностику и восстановить работоспособный экземпляр; `StackOverflowError` также требует устранить причину рекурсии.

Размер стека регулируется `-Xss` (например, `-Xss512k`): уменьшение позволяет держать больше потоков, увеличение — более глубокую рекурсию.

**Инструменты диагностики:**

- Heap Dump (флаг `-XX:+HeapDumpOnOutOfMemoryError`) с последующим анализом в Eclipse MAT, VisualVM или JProfiler.

- `jmap`, `jstat`, Java Flight Recorder (JFR) для наблюдения за памятью в реальном времени.

### 32. JVM внезапно завершилась. Как отличить фатальный сбой HotSpot от OutOfMemoryError и внешнего убийства процесса?

Сначала зафиксируйте момент завершения и соберите три вида данных: последние строки вывода приложения, статус процесса у супервизора и артефакты JVM. Java-исключение с текстом `OutOfMemoryError` сообщает, какой ресурс закончился. Само по себе оно не доказывает, что JVM немедленно завершилась. Heap dump полезен при нехватке Java heap и включённом сборе дампа.

При фатальном сбое HotSpot может сохранить `hs_err_pid<pid>.log`. Смотрите причину сбоя, текущий поток, проблемный кадр, загруженные библиотеки и версию JVM. Кадр внутри нативной библиотеки — место, где обнаружилась проблема, но повреждение памяти могло произойти раньше. Путь для отчёта задают через `-XX:ErrorFile=/logs/hs_err_pid%p.log`; каталог должен существовать, быть доступным на запись и переживать перезапуск.

При внешнем `SIGKILL` процесс не получает времени на запись такого отчёта. Код 137 в типичном Linux-окружении совместим с `SIGKILL`, но сам по себе не объясняет его причину. Сопоставьте его с состоянием контейнера, событиями OOM и действовавшим лимитом памяти. Отсутствие файла при неверном пути или полном диске тоже ничего не доказывает.

### 10. Какие основные флаги JVM нужно знать (-Xms/-Xmx, выбор GC, логи GC, HeapDumpOnOutOfMemoryError)?

Минимальный набор, который реально применяется в проде:

- **Размер кучи**: `-Xms2g` (стартовая), `-Xmx2g` (максимум). Равные значения могут снизить вариативность изменения кучи, но увеличивают нижнюю границу её размера и мешают возвращать память ниже `-Xms`; в контейнере решение принимают по бюджету процесса.

- **Выбор сборщика**: `-XX:+UseG1GC` (по умолчанию с Java 9), `-XX:+UseParallelGC` (throughput), `-XX:+UseZGC` / `-XX:+UseShenandoahGC` (низкие целевые паузы), `-XX:+UseSerialGC` (мелкие приложения).

- **Целевая пауза**: `-XX:MaxGCPauseMillis=200` — цель для эргономики G1, а не жёсткий предел паузы.

- **Логи GC**:
  - Java 8: `-XX:+PrintGCDetails -XX:+PrintGCDateStamps -Xloggc:gc.log`
  - Java 9+: единый лог `-Xlog:gc*:file=gc.log:time,uptime,level,tags`

- **Дамп при OOM**: `-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps/` — без этого после инцидента разбирать будет нечего.

```bash
java -Xms2g -Xmx2g \
     -XX:+UseG1GC -XX:MaxGCPauseMillis=200 \
     -Xlog:gc*:file=logs/gc.log:time,uptime \
     -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=logs/ \
     -jar app.jar
```

Если `-Xms`/`-Xmx` не заданы, HotSpot выбирает размеры эргономикой с учётом доступной памяти, версии и других ограничений. В типичных конфигурациях максимальная доля близка к четверти, но это не универсальная формула. Проверить фактические значения можно так: `java -XX:+PrintFlagsFinal -version | grep HeapSize`.

Частый follow-up про контейнеры: с Java 10 (и начиная с ряда обновлений Java 8, включая 8u191) JVM сама видит лимиты cgroups, а не память хоста. Поэтому в Docker/Kubernetes вместо абсолютного `-Xmx` чаще задают долю от лимита контейнера: `-XX:MaxRAMPercentage=75.0` — оставляя четверть под Metaspace, стеки потоков, direct-буферы и сам нативный код JVM. Ловушка в том, что при `-Xmx`, равном лимиту контейнера, суммарное потребление процесса вылезает за лимит, и ядро Linux убивает процесс при превышении cgroup-лимита (в Kubernetes обычно статус OOMKilled) раньше, чем JVM успевает бросить свой `OutOfMemoryError`.

### 11. Что такое Metaspace, чем он заменил PermGen и как регулируется его размер?

Metaspace — область памяти, где JVM хранит **метаданные классов**: структуру класса, пул констант, байт-код методов, данные аннотаций. Загрузили класс — его описание легло в Metaspace, причем в рамках загрузившего его ClassLoader'а.

**Чем заменил PermGen.** До Java 8 HotSpot размещал метаданные в отдельной постоянной области PermGen с собственным предельным размером (`-XX:PermSize`, `-XX:MaxPermSize`). Угадать размер заранее было почти невозможно, и приложения с динамической загрузкой классов (редеплои на Tomcat, прокси, JSP) регулярно падали с `OutOfMemoryError: PermGen space`. С Java 8 PermGen убрали, а Metaspace разместили в **нативной памяти** процесса, вне кучи.

**Как регулируется:**

- По умолчанию лимита почти нет — Metaspace растет, пока есть свободная нативная память.

- `-XX:MetaspaceSize=64m` — порог, при достижении которого GC впервые почищает Metaspace. Это не минимум и не максимум, а точка срабатывания сборки.

- `-XX:MaxMetaspaceSize=256m` — жесткий потолок. При превышении — `OutOfMemoryError: Metaspace`.

**`OutOfMemoryError: Metaspace`** требует проверить и слишком низкий лимит, и законный объём загруженных классов, и утечку загрузчиков: приложение плодит загрузчики (редеплои, динамические прокси, Groovy/шаблонизаторы, генерирующие классы), а старые не собираются, потому что на них кто-то держит ссылку. Класс выгружается из Metaspace только вместе со своим загрузчиком — пока жив ClassLoader, живы и все его классы.

### 13. Какие инструменты JDK помогают диагностировать проблемы JVM (jps, jstack, jmap, jstat, jcmd, JFR)?

Эти утилиты входят в JDK, но могут отсутствовать в минимальном runtime-образе контейнера. Нужны совместимый JDK, доступ к процессу и корректный PID namespace. Начинают с наименее тяжёлой диагностики; heap dump и некоторые гистограммы могут вызвать паузу и большой дисковый I/O.

- **`jps -lvm`** — список Java-процессов на машине (PID, главный класс, флаги). Стартовая точка: узнать PID нужного процесса.

- **`jstack <pid>`** — снимок стеков всех потоков. Смотреть при: зависании и дедлоках (jstack сам их находит и помечает), высоком CPU, потоках в `BLOCKED`. Классический рецепт для диагностики CPU: `top -H -p <pid>` показывает самый горячий поток, его TID переводите в hex (`printf '%x' <tid>`) и ищете в выводе jstack по `nid=0x...` — получаете стек того, что греет процессор.

- **`jmap -dump:live,format=b,file=heap.hprof <pid>`** — heap dump для разбора в Eclipse MAT; `jmap -histo <pid>` — гистограмма классов по памяти. Смотреть при утечках и OOM.

- **`jstat -gcutil <pid> 1s`** — статистика GC в реальном времени: заполненность областей, число и время сборок. Смотреть, когда подозреваете, что приложение тормозит из-за частых или долгих GC.

- **`jcmd <pid> <команда>`** — швейцарский нож: `GC.heap_dump`, `Thread.print`, `VM.flags`, `GC.class_histogram`. Умеет почти всё, что jmap + jstack, и еще управляет JFR.

- **JFR (Java Flight Recorder)** — встроенный профилировщик, чей overhead зависит от включённых событий и настроек: события GC, аллокации, блокировки, сокеты, CPU. Снимается в проде и разбирается в JDK Mission Control.

```bash
# Запись JFR на лету без рестарта приложения:
jcmd <pid> JFR.start duration=60s filename=profile.jfr

# Или с самого старта:
java -XX:StartFlightRecording=duration=60s,filename=profile.jfr -jar app.jar
```

Шпаргалка «чем смотреть»: тормозит и греет CPU → `jstack`; растет память → `jmap`/`jcmd GC.heap_dump`; подозрение на GC → `jstat`; нужна полная картина в проде → JFR.

### 14. Что такое off-heap память и DirectByteBuffer и где это используется на практике?

Off-heap — это нативная память процесса вне Java-кучи. Главный способ выделять ее из кода — `ByteBuffer.allocateDirect()`: JVM запрашивает память у ОС напрямую, минуя кучу.

```java
ByteBuffer buffer = ByteBuffer.allocateDirect(1024 * 1024); // 1 МБ вне кучи
```

Зачем это нужно:

- **Меньше промежуточных копирований при некоторых I/O.** Direct-буфер позволяет NIO избежать части копирования между heap и нативным буфером. Это не равнозначно zero-copy: копирование между ядром ОС и процессом может сохраняться.

- **Полезные данные находятся вне heap.** Но Java-обёртки остаются в куче, а жизненный цикл нативного выделения связан с достижимостью обёртки; давление на GC и лимит процесса полностью не исчезают.

Расплата:

- Аллокация дороже, чем в куче, поэтому direct-буферы переиспользуют пулами.

- Освобождением занимается GC **косвенно**: нативная память возвращается, когда собран сам объект-буфер (через `Cleaner`). Если куча почти пуста и GC ленится, буферы копятся.

- Лимит регулируется отдельно: `-XX:MaxDirectMemorySize` (по умолчанию равен `-Xmx`). Исчерпание дает `OutOfMemoryError: Direct buffer memory` — heap dump может показать удерживающие `DirectByteBuffer` объекты и цепочки ссылок, но не содержит сами нативные байты. Дополняют его `BufferPoolMXBean`, метриками аллокатора и NMT; NMT не покрывает все выделения сторонних native-библиотек.

**Где встречается на практике:** Netty (весь его I/O построен на direct-буферах и пулах `PooledByteBufAllocator`), NIO (`FileChannel.map` — memory-mapped файлы), Aeron, Chronicle Map и прочие off-heap хранилища.

Частая ловушка: `OutOfMemoryError: Direct buffer memory` на сервисе с Netty при почти пустой куче. Причина обычно не в том, что лимит мал, а в утечке буферов — их взяли из пула и не вызвали `release()`. У Netty для поиска таких утечек есть `-Dio.netty.leakDetectionLevel=PARANOID`.

### 15. Утечки памяти в Java: типичные причины (статические коллекции, ресурсы, слушатели, ThreadLocal, кэши) и как их диагностировать?

Утечка в Java — это не «забыли free()», а объекты, которые больше не нужны, но остаются достижимыми из GC Roots, поэтому сборщик их трогать не имеет права. Куча растет, GC работает все больше и освобождает все меньше, финал — `OutOfMemoryError: Java heap space` или `GC overhead limit exceeded`.

Типичные источники утечек:

- **Статические коллекции.** `private static final List<...> CACHE = new ArrayList<>()` живёт, пока достижим класс и его загрузчик. Записи остаются достижимыми, пока их явно не удалят или не станет недостижим сам владелец. Классика — кэш «на коленке» без ограничения размера.

- **Незакрытые ресурсы.** `Connection`, `InputStream`, `ResultSet`, не закрытые в `finally` (или не через try-with-resources). Течет не только Java-объект, но и нативные ресурсы за ним.

- **Слушатели и коллбэки.** Зарегистрировал listener — отпишись, когда он больше не нужен. Пока источник событий держит слушателя, тот держит весь свой граф объектов. Та же история с незакрытыми подписками в RxJava/Reactor.

- **ThreadLocal в пулах потоков.** Поток в пуле (Tomcat, любой executor) не умирает, а вместе с ним живет его ThreadLocalMap. Забыли `remove()` — значение может удерживаться до очистки записи или завершения потока; особенно долго при живом статическом ThreadLocal. В веб-приложении это еще и перетекает между запросами.

- **Кэши без вытеснения.** Обычная `HashMap` в роли кэша: записи только добавляются. Нужен кэш с явной ёмкостью/весом, сроком жизни и политикой вытеснения. `WeakHashMap` и `SoftReference` не дают предсказуемого ресурсного лимита и не являются универсальным исправлением.

- **Некорректные `equals`/`hashCode` у ключей.** Если поле, участвующее в `hashCode`, мутирует после того, как объект попал в `HashMap`/`HashSet`, запись «теряется» — удалить ее по тому же ключу уже нельзя, и мапа растет. Постоянный `hashCode` прежде всего ухудшает производительность; сам по себе он не создаёт утечку, а в современных `HashMap` часть корзин может преобразовываться в деревья.

Минимальный пример утечки, которая встречается в реальном коде:

```java
public class OrderService {
    // "кэш", который только растет
    private static final Map<Long, Order> cache = new HashMap<>();

    public Order getOrder(long id) {
        return cache.computeIfAbsent(id, this::loadFromDb); // удаления нет нигде
    }
}
```

Воркфлоу диагностики:

1. **Получить дамп.** Заранее включите `-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps/` — тогда дамп снимется сам в момент падения. На живом процессе: `jmap -dump:live,format=b,file=heap.hprof <pid>` или `jcmd <pid> GC.heap_dump heap.hprof`. Ключ `live` заодно делает Full GC, так что на проде снимайте аккуратно.

2. **Открыть в Eclipse MAT.** Первым делом смотрите отчет **Leak Suspects** — MAT сам показывает подозрительные аккумуляции памяти. Затем **Dominator Tree**: сортируйте по Retained Heap и ищите объект, который «держит» непропорционально много памяти. Для найденного объекта — **Path to GC Roots → exclude weak/soft references**: это покажет, какая цепочка ссылок не дает объекту умереть. Ответ почти всегда на виду: `static` поле, очередь слушателей, ThreadLocal.

3. **Сравнить два дампа.** Если рост медленный, снимите дамп вскоре после старта и второй — через несколько часов под нагрузкой. Сравнение гистограмм (`jmap -histo` тоже подойдет) показывает, экземпляры каких классов растут, — от них уже идете в код.

Follow-up, который задают следом: «а почему это не найдет профилировщик аллокаций?» — потому что профилировщик показывает, где объекты *создаются*, а утечка — это про то, кто их *удерживает*. Это разные вопросы, и отвечает на второй именно анализ достижимости в дампе.

### 16. Практика тюнинга JVM/GC: что отвечать на «приходилось ли тюнить» и какие флаги реально крутят?

Отвечайте только о своём опыте; учебный эксперимент так и называйте. Полезная структура: симптом → измерения → гипотеза → изменение → сравнение при одинаковой нагрузке. Например: у сервиса выросла p99, JFR и GC-логи показали частые evacuation pauses, а профилирование аллокаций — создание крупных временных массивов при сериализации.

Первое изменение в таком кейсе — ограничить размер пачки или обрабатывать данные потоком. Затем сравнивают p95/p99, throughput, CPU, allocation rate и используемую память. «После смены GC приложение стало быстрее» без чисел и сопоставимой нагрузки — слабый вывод.

Настройки выбирают под конкретный сборщик:

- Для G1 начинают с достаточного `-Xmx` и реалистичного `-XX:MaxGCPauseMillis`. Жёсткое задание Young через `-Xmn`/`NewRatio` ограничивает эргономику G1 и обычно не нужно. По логам проверяют concurrent marking, mixed collections, humongous allocations и запас для evacuation.

- `SurvivorRatio`, `NewRatio` и размер Young осмысленнее обсуждать в контексте Serial/Parallel и измеренной проблемы раннего продвижения. Порог возраста динамический; `MaxTenuringThreshold` не гарантирует, что объект останется в Young заданное число сборок.

- Для ZGC нужны запас памяти сверх живого набора и CPU для конкурентной работы. Переносить в него настройки Eden/Survivor от Parallel нельзя.

Практический старт диагностики в JDK 17–21:

```bash
java -Xmx2g \
  -Xlog:gc*,safepoint:file=gc.log:time,uptime,level,tags:filecount=5,filesize=20m \
  -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps \
  -jar app.jar
```

Флаги проверяют на той же сборке JDK, где работает сервис. Логи ротируют; для дампа заранее обеспечивают место. Растущий живой набор после сопоставимых циклов GC — повод искать удерживающую ссылку, а не увеличивать heap бесконечно. Пул объектов тоже не универсальная оптимизация: он может увеличить время жизни объектов и конкуренцию.

### 19. Как отличить утечку heap от нормального роста живых данных и временного всплеска аллокаций?

Один график занятой кучи не доказывает утечку: до следующего GC там остаются и уже ненужные объекты. Сравнивают нижнюю границу использования после сопоставимых циклов сборки, интенсивность запросов и размер полезных данных. Пилообразное заполнение с устойчивым минимумом обычно означает нормальные аллокации. Устойчивый рост минимума требует объяснения, но может быть законным: например, прогревается ограниченный кэш или растёт число активных сессий.

Пример: сервис запускают с пустым кэшем на миллион записей. Первые часы live set растёт, затем выходит на плато. Это отличается от списка завершённых запросов, который увеличивается ещё на миллион элементов каждый день. Во втором случае после снижения нагрузки удержание не исчезает, а путь к GC root указывает на коллекцию без удаления.

Проверка состоит из связанных наблюдений:

- GC-логи показывают динамику после сборок и частоту циклов.

- Метрики запросов, очередей, кэшей и сессий объясняют ожидаемый объём данных.

- Профиль аллокаций показывает, какие операции создают много временных объектов.

- Heap dump показывает, кто удерживает уже созданные объекты и сколько памяти они сохраняют достижимой.

Не нужно сразу вызывать `System.gc()` на каждом экземпляре ради «чистого эксперимента»: это меняет поведение и может вызвать паузу. Если нужны дампы, выбирают один экземпляр и сопоставимые точки нагрузки. При временном всплеске полезнее ограничить размер пачки и число задач в работе; при утечке — разорвать конкретную удерживающую цепочку.

Опасный ответ на собеседовании: «куча заняла 90%, значит течёт». Размер heap, доля живых объектов и скорость их создания — разные величины; их нужно связать с поведением приложения.

### 20. Heap свободен, но контейнер OOMKilled: где искать память и как использовать Native Memory Tracking?

`-Xmx` ограничивает Java heap, а контейнер ограничивает более широкий расход памяти. За пределами кучи находятся Metaspace, code cache JIT, стеки платформенных потоков, direct/mapped buffers, структуры GC и нативные библиотеки. В cgroup также могут учитываться другие процессы и файловый кэш. Поэтому процесс с `-Xmx2g` способен превысить контейнерный лимит 3 ГиБ при занятой куче всего 1 ГиБ.

Сначала подтверждают причину завершения: статус контейнера, события cgroup/ядра и временную шкалу. Код выхода 137 сам по себе означает `SIGKILL`, но не доказывает OOM. При убийстве процесс не обязан создать Java OOM или heap dump: ядро не ждёт штатной диагностики JVM.

Для HotSpot NMT включают при запуске:

```bash
java -XX:NativeMemoryTracking=summary -jar app.jar
jcmd <pid> VM.native_memory baseline
jcmd <pid> VM.native_memory summary.diff scale=MB
```

Дельта помогает найти растущую категорию: `Thread`, `Class`, `Code` или другие выделения JVM. `reserved` — адресное пространство, `committed` — предоставленная JVM память; ни то ни другое не равно точно RSS процесса. NMT не является полным профилировщиком всех сторонних native-аллокаций. Его сопоставляют с RSS, cgroup-метриками, `BufferPoolMXBean`, числом потоков и метриками библиотечного аллокатора.

Например, после увеличения executor до тысяч потоков растёт категория стеков; увеличение `-Xmx` только сокращает оставшийся запас. После роста direct-буферов проверяют владельцев и освобождение, а не только их лимит.

Бюджет составляют из измеренного пика heap плюс пика остальных категорий и запаса под колебания. Универсальное «75% контейнера под heap» — стартовая гипотеза, а не гарантия.

### 21. Как построить расследование задержек с JFR, GC-логами и метриками приложения?

Начинают с интервала, где выросла задержка конкретной операции, и проверяют, на что ушло время: CPU, ожидание блокировки, внешний I/O, очередь или остановка JVM. JFR связывает события выполнения и ожидания во времени; GC-логи объясняют работу сборщика; метрики приложения показывают RPS, ошибки, очередь и длительность зависимостей. Любой из этих источников по отдельности легко приводит к неверной причине.

Например, p99 выросла до 800 мс, но сумма GC-пауз за этот интервал мала. В JFR видны длинные socket read, а пул соединений исчерпан. Переключение на ZGC не ускорит внешний сервер. Другой случай: перед каждой задержкой идут крупные аллокации и evacuation pause, а внешние вызовы стабильны — тогда исследуют allocation stack и размер пачки.

Короткую запись можно начать на работающем процессе:

```bash
jcmd <pid> JFR.start name=incident settings=profile duration=60s filename=/dumps/incident.jfr
jfr summary /dumps/incident.jfr
```

`profile` даёт больше подробностей, чем более лёгкий `default`; стоимость зависит от событий и нагрузки. Для редких инцидентов полезнее заранее настроенная ограниченная по размеру/возрасту запись, чем включение после завершения проблемы. Время метрик, логов и записи должно быть сопоставимо; uptime в GC-логе помогает при изменении часов.

Сэмплы CPU показывают статистический профиль, а не точную бухгалтерию каждого запроса. Отсутствие события может означать, что оно отключено или не пересекло порог. Это проверяют перед выводом «блокировок нет». Heap dump оставляют для гипотез об удержании объектов: он хуже отвечает на вопрос о кратком всплеске latency и может сам создать паузу. Доступные команды смотрят через `jcmd <pid> help`, а влияние конкретной команды — в выводе `jcmd <pid> help <команда>`.

### 22. Что означают shallow size, retained size и dominator tree в heap dump? Помогают ли циклические ссылки?

Shallow size — память самого объекта: заголовок, поля и выравнивание, без всех объектов по ссылкам. Retained size — объём, который стал бы недостижимым при удалении этого объекта из графа, с учётом других путей от корней. Поэтому маленькая `ArrayList` может удерживать гигабайты через массив и элементы. Dominator tree помогает найти такие точки удержания: объект A доминирует B, если любой путь от GC roots к B проходит через A.

Пример: две карты ссылаются на одни и те же заказы. У каждой карты большой достижимый граф, но удаление одной не освободит сами заказы — их удерживает вторая. Поэтому суммировать размеры «всего, до чего можно дойти» нельзя: общие объекты будут посчитаны повторно. Retained size отвечает на другой, более полезный вопрос об исключительном удержании.

```java
Node a = new Node();
Node b = new Node();
a.next = b;
b.next = a;
a = null;
b = null;
```

Сам по себе цикл не вызывает утечку. Трассирующий GC Java ищет достижимость от корней, а не считает ссылки; недостижимый цикл может быть собран целиком. Если `static List<Node>` по-прежнему хранит один узел, цикл останется живым из-за этого внешнего корня.

В анализаторе сначала находят крупного удерживающего владельца, затем исследуют пути к корням с учётом сильных и слабых ссылок. Частая ошибка — исправлять место создания `byte[]`, хотя его удерживает забытая очередь задач. При этом dump — снимок состояния: законный большой кэш не становится утечкой только из-за высокого retained size. Нужны ожидаемый жизненный цикл и динамика под сопоставимой нагрузкой; освобождение Java-обёртки также не доказывает немедленное освобождение внешнего ресурса.

### 26. Почему приложение замирает, хотя в GC-логах нет длинной сборки: что такое safepoint?

Safepoint — согласованная точка выполнения, в которой JVM может безопасно провести некоторые глобальные операции, потому что знает состояние Java-потоков и ссылок. Не каждая такая операция — сборка мусора. Пауза может быть связана с диагностикой, обслуживанием JVM или другими VM operations. Поэтому сумма длительностей GC не объясняет автоматически все остановки процесса.

Отдельно различают время достижения safepoint и время самой операции после остановки потоков. Если один поток долго не достигает подходящего состояния, начало общей операции задерживается. Причины зависят от версии HotSpot и исполняемого кода; нельзя по одному большому числу сразу заключить «виноват native-вызов» или «любой длинный цикл блокирует JVM».

Для первоначальной проверки включают совместимые логи:

```bash
java -Xlog:gc*,safepoint:file=vm.log:time,uptime,level,tags -jar app.jar
```

Смотрят поля времени достижения и пребывания в safepoint, тип операции и совпадение с проблемным интервалом. Например, администратор снял тяжёлую гистограмму или heap dump одновременно с ростом p99; сама диагностическая команда могла изменить наблюдаемую картину. Это проверяемая гипотеза, а не доказательство неисправности GC.

Если соответствующей паузы нет, исследуют очередь executor, блокировки, сеть, CPU throttling контейнера и планирование ОС. JFR помогает связать эти причины с временной шкалой, но событие должно быть включено и удовлетворять порогу записи.

Частая ошибка — настроить меньшую целевую паузу G1 и ждать устранения любой задержки. Safepoint, ожидание монитора и очередь к соединению БД — разные механизмы. Самое полезное продолжение ответа: назвать конкретное наблюдение, которое отличит глобальную остановку JVM от ожидания только одного запроса.
