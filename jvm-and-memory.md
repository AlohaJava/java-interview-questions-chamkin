### 1. Как устроена память в JVM: в чем разница между Heap (кучей) и Stack (стеком)?

```text
+-------------------------------------------------------------+
|                         JVM MEMORY                          |
|  +-----------------------+   +---------------------------+  |
|  |     HEAP (Куча)       |   |      STACK (Стек)         |  |
|  |  (Общая для потоков)  |   | (Свой на каждый поток)    |  |
|  |  Все объекты (new)    |   | Локальные примитивы       |  |
|  +-----------------------+   +---------------------------+  |
|  +-------------------------------------------------------+  |
|  |     METASPACE (Native Memory: метаданные классов)     |  |
|  +-------------------------------------------------------+  |
+-------------------------------------------------------------+
```

1. **Heap (Куча)**:
   - Область памяти, **общая для всех потоков** JVM.
   - Здесь хранятся все создаваемые объекты (`new MyClass()`) и их поля.
   - Очисткой занимается сборщик мусора (Garbage Collector).
   - При нехватке памяти выбрасывается `OutOfMemoryError`.

2. **Stack (Стек)**:
   - Создается **индивидуально для каждого потока** (Thread Stack).
   - Хранит фреймы вызова методов (Stack Frames), локальные примитивы и ссылки на объекты в Heap.
   - Освобождается автоматически при выходе из метода по принципу LIFO.
   - При переполнении выбрасывается `StackOverflowError`.

Частые follow-up:

- **Где лежат статические поля и пул строк?** Статические поля — в куче, внутри объекта `java.lang.Class` соответствующего класса (метаданные класса — в Metaspace, см. вопрос 11). Пул интернированных строк с Java 7 тоже в куче (до этого был в PermGen).
- **Сколько памяти ест стек?** Размер стека потока задается `-Xss` (по умолчанию ~512 КБ–1 МБ в зависимости от ОС и платформы). Стеки не входят в кучу: тысяча потоков — это около гигабайта нативной памяти сверх `-Xmx`. Когда ОС не может выделить память под стек нового потока, выбрасывается `OutOfMemoryError: unable to create new native thread` — и увеличение кучи тут не поможет, помогает уменьшение числа потоков или `-Xss`.
- **«Объекты могут создаваться в стеке»?** В спецификации JVM такого нет — формально все объекты в куче. JIT через escape analysis может убрать аллокацию вообще (скалярная замена, см. вопрос 12), но это оптимизация конкретного горячего участка, а не правило языка.

### 2. Какие бывают сборщики мусора в JVM (Serial, Parallel, G1, ZGC, Shenandoah, Epsilon)?

- **Serial GC** (`-XX:+UseSerialGC`): однопоточный сборщик, подходит для небольших приложений с кучей до нескольких сотен МБ.
- **Parallel GC** (`-XX:+UseParallelGC`): многопоточный сборщик для максимальной пропускной способности (throughput). Был сборщиком по умолчанию в Java 8.
- **G1 GC (Garbage-First)**: сборщик по умолчанию с Java 9. Разбивает кучу на регионы и в первую очередь собирает регионы с наибольшим количеством мусора. Позволяет задать целевую паузу (`-XX:MaxGCPauseMillis`).
- **ZGC** (`-XX:+UseZGC`): низколатентный сборщик с паузами Stop-The-World **менее 1 мс** независимо от размера кучи (работает на кучах в сотни ГБ и даже ТБ). Маркировка и перемещение объектов выполняются конкурентно с приложением за счет цветных указателей (colored pointers) и load barrier'ов. Production-ready с Java 15; с Java 21 стал поколенческим (Generational ZGC, JEP 439) — это снизило потребление памяти и CPU, а с Java 23 поколенческий режим включен по умолчанию.
- **Shenandoah** (`-XX:+UseShenandoahGC`): та же цель — субмиллисекундные паузы, но вместо цветных указателей использует Brooks pointers (дополнительный указатель-переадресацию в каждом объекте). Формально входит в OpenJDK, но не во все дистрибутивы: в сборках Oracle JDK его нет, есть в Red Hat, Amazon Corretto и ряде других.
- **Epsilon GC** (`-XX:+UseEpsilonGC`): сборщик-пустышка — память выделяет, мусор не собирает, по исчерпании кучи JVM падает. Применяется для тестов производительности, где нужно исключить влияние GC, и короткоживущих задач, гарантированно укладывающихся в кучу.

Для истории: **CMS** (Concurrent Mark Sweep) — первый массовый низколатентный сборщик; deprecated с Java 9 и удален в Java 14. Если спросят «чем G1 лучше CMS», суть в том, что G1 компактифицирует кучу и не страдает от фрагментации, которая в CMS со временем приводила к непредсказуемому Full GC с полной остановкой приложения.

**Как выбирать** (типичный follow-up): маленькая куча или одноразовая утилита — Serial; batch-задачи, где важна пропускная способность, а паузы некритичны — Parallel; универсальный дефолт для сервисов — G1; жесткие требования к latency (p99) на больших кучах — ZGC или Shenandoah. Имейте в виду: «сборщик по умолчанию» выбирается эргономикой JVM — на серверных машинах это G1, но на одноядерной машине с кучей до 2 ГБ JVM может выбрать Serial.

### 3. Чем различаются JDK, JRE и JVM?

- **JVM (Java Virtual Machine)**: виртуальная машина, исполняющая байт-код (`.class` файлы). Именно JVM обеспечивает кроссплатформенность («Write once, run anywhere»).
- **JRE (Java Runtime Environment)**: комплект для **запуска** приложений — JVM + стандартные библиотеки классов.
- **JDK (Java Development Kit)**: комплект для **разработки** — JRE + компилятор `javac`, отладчик, профилировщики и прочие инструменты.

```text
JDK = JRE + компилятор и инструменты разработки
JRE = JVM + стандартные библиотеки
```

Пара нюансов, которые спрашивают следом:

- С Java 11 отдельного JRE больше не существует как самостоятельной поставки — есть только JDK, а облегченный рантайм под свое приложение собирают через `jlink`. Поэтому вопрос «что поставите на сервер, JRE или JDK?» — ловушка: корректный ответ — JDK или образ, собранный `jlink`'ом.
- JVM — это спецификация, и реализаций несколько: HotSpot (основная, в OpenJDK), OpenJ9 (Eclipse, экономнее по памяти и быстрее стартует), GraalVM (умеет AOT-компиляцию в native image). И исполняет JVM не только Java: Kotlin, Scala, Groovy компилируются в тот же байт-код.

### 4. Как устроены поколения в Heap (Young Generation, Old Generation) и процесс сборки мусора?

В основе лежит **гипотеза о слабых поколениях** (weak generational hypothesis): *большинство объектов умирает вскоре после создания*.

- **Young Generation**:
  - `Eden` — сюда попадают все новые объекты.
  - Два пространства `Survivor` (`S0` и `S1`) — сюда пережившие Minor GC объекты перемещаются, накапливая «возраст».
  - **Minor GC** происходит часто и выполняется быстро.
- **Old (Tenured) Generation**:
  - Сюда попадают объекты, пережившие пороговое число сборок (`-XX:MaxTenuringThreshold`).
  - **Major GC** происходит реже, но тяжелее и может вызывать ощутимые паузы Stop-The-World.

Объект считается мусором, когда до него нельзя добраться из **GC Roots** (локальные переменные активных потоков, статические поля, JNI-ссылки).

Три нюанса, на которых спотыкаются:

- **Major GC ≠ Full GC.** Major GC чистит только старое поколение; Full GC — всю кучу целиком (и Metaspace заодно). Путать их на собеседовании — маркер того, что человек жонглирует терминами.
- **В Old попадают не только «постаревшие».** Крупные объекты могут аллоцироваться сразу в старом поколении, минуя Eden (в G1 это humongous-объекты — больше половины размера региона). А если Survivor-пространства переполнены, объекты промоутятся раньше порога — фактический возраст промоушна JVM определяет динамически.
- **Картинка поколений — логическая.** G1 делит кучу на регионы одинакового размера, и роль региона (Eden/Survivor/Old) назначается динамически — непрерывных областей поколений физически нет. ZGC с Java 21 тоже поколенческий, а Serial и Parallel держат классическую непрерывную раскладку.

Два механизма, которые делают эту схему быстрой (любимый вопрос «почему аллокация в Java почти бесплатна» и «как GC находит ссылки старое → молодое»):

- **TLAB (Thread-Local Allocation Buffer).** Каждый поток получает свой участок Eden. Аллокация объекта — это просто сдвиг указателя внутри своего буфера, без всякой синхронизации с другими потоками. Синхронизация нужна только когда буфер кончился и запрашивается новый. Отсюда скорость `new` в HotSpot, сравнимая со стековой аллокацией.
- **Card table и write barrier.** При Minor GC нужно найти живые объекты молодого поколения, в том числе те, на которые ссылаются объекты из Old. Сканировать всё старое поколение — дорого, поэтому куча делится на «карточки» (~512 байт), а JIT вставляет в код записи ссылки write barrier: если поток записал ссылку из старого объекта на молодой, соответствующая карточка помечается «грязной». Minor GC сканирует корни плюс только грязные карточки (remembered set), а не весь Old.

### 5. Что такое OutOfMemoryError (OOM) и StackOverflowError и как их отлаживать?

- **`StackOverflowError`**: возникает при переполнении стека вызовов — чаще всего из-за бесконечной или слишком глубокой рекурсии. Диагностируется по стек-трейсу.
- **`OutOfMemoryError: Java heap space`**: куча заполнена, обычно из-за утечки памяти (объекты остаются достижимыми: статические коллекции, незакрытые ресурсы, бесконтрольные кэши).
- **`OutOfMemoryError: Metaspace`**: переполнение области метаданных классов (типично при утечках класслоадеров, см. вопрос 11).

По тексту сообщения OOM бывают разные, и их стоит различать:

- `Java heap space` — переполнена куча (утечка или слишком маленький `-Xmx`).
- `Metaspace` — переполнены метаданные классов.
- `GC overhead limit exceeded` — GC тратит ~98% времени и освобождает меньше 2% кучи: приложение фактически мертво, хоть формально и не упало. Классический признак того, что куча чуть-чуть не дотягивает до нужного размера.
- `Requested array size exceeds VM limit` — попытка создать массив размером около или больше 2^31 элементов.
- `unable to create new native thread` — ОС не может выделить память под стек нового потока. Лечится не кучей, а уменьшением числа потоков или `-Xss`.
- `Direct buffer memory` — исчерпана off-heap память direct-буферов (см. вопрос 14).

Оба класса ошибок — это `Error`, а не `Exception`: ловить их в `catch` и «работать дальше» — плохая идея, JVM уже в непредсказуемом состоянии.

Размер стека регулируется `-Xss` (например, `-Xss512k`): уменьшение позволяет держать больше потоков, увеличение — более глубокую рекурсию.

**Инструменты диагностики:**
- Heap Dump (флаг `-XX:+HeapDumpOnOutOfMemoryError`) с последующим анализом в Eclipse MAT, VisualVM или JProfiler.
- `jmap`, `jstat`, Java Flight Recorder (JFR) для наблюдения за памятью в реальном времени.

### 6. Что делает метод System.gc() и гарантирует ли он немедленную сборку мусора?

Вызов `System.gc()` (по сути обертка над `Runtime.getRuntime().gc()`) является лишь **рекомендацией** для JVM запустить сборку мусора — спецификация не гарантирует, что сборка действительно произойдет. Решение остается за виртуальной машиной (принудительный запуск можно запретить флагом `-XX:+DisableExplicitGC`).

Ручной вызов `System.gc()` в продакшн-коде считается плохой практикой: он может спровоцировать полную сборку (Full GC) с длинной паузой Stop-The-World, не давая никакой гарантии освобождения памяти.

### 7. Как устроена иерархия ClassLoader (Bootstrap, Platform, Application) и что такое делегирование родителю?

ClassLoader — это механизм, который загружает `.class`-файлы в JVM по требованию: класс грузится не при старте, а при первом обращении к нему. Загрузчики выстроены в иерархию, и каждый перед загрузкой класса сначала спрашивает родителя — это и есть делегирование.

```text
Bootstrap ClassLoader     — ядро JDK (модуль java.base, классы java.lang.*).
                            Написан на нативном коде, из Java виден как null.
        ↑ родитель
Platform ClassLoader      — остальные модули JDK (java.sql, java.xml и т.д.).
                            До Java 9 назывался Extension ClassLoader.
        ↑ родитель
Application ClassLoader   — классы приложения из CLASSPATH.
        ↑ родитель
Custom ClassLoader        — ваши загрузчики (плагины, hot reload, Tomcat и т.п.)
```

**Как работает делегирование (parent-first):** при запросе класса загрузчик сначала делегирует запрос родителю, и только если вся цепочка родителей класс не нашла — ищет сам. Это дает две вещи: класс грузится один раз (уникальность в рамках загрузчика) и нельзя подменить системный класс своим — ваш `java.lang.String` из classpath никогда не победит тот, что загрузил Bootstrap.

Частый follow-up — разница между `ClassNotFoundException` и `NoClassDefFoundError`:

- **`ClassNotFoundException`** — checked-исключение: класс не найден при **явной** загрузке по имени (`Class.forName("com.Foo")`, `ClassLoader.loadClass()`). Классика — забытый JDBC-драйвер в classpath.
- **`NoClassDefFoundError`** — `Error`: класс был на этапе компиляции, JVM наткнулась на него в коде, но определение найти не смогла. Типичные причины: jar пропал из classpath в рантайме или класс не смог инициализироваться (упал статический блок) — тогда повторные обращения дают именно эту ошибку.

Еще два follow-up из той же серии:

- **Жизненный цикл класса**: загрузка (Loading) → связывание (Linking: верификация байт-кода, подготовка статических полей значениями по умолчанию, резолюция ссылок) → инициализация (выполнение статических блоков и инициализаторов). Инициализация происходит только при первом *активном* использовании класса: `new`, вызов статического метода, обращение к не-константному статическому полю. Чтение `static final` константы, вычисленной на этапе компиляции, класс не инициализирует.
- **Делегирование — не догма.** Tomcat нарочно переворачивает схему: его WebappClassLoader сначала ищет класс у себя в `WEB-INF` (child-first), чтобы два веб-приложения на одном сервере могли таскать разные версии одной библиотеки. К классам JDK и Servlet API он по-прежнему идет через родителя.

### 8. Как JVM исполняет код: интерпретатор, JIT-компиляторы C1/C2 и tiered compilation?

JVM не выбирает между интерпретацией и компиляцией — она использует оба. Код стартует в интерпретаторе, а по мере «разогрева» горячие участки компилируются в машинный код все более агрессивно.

1. **Интерпретатор**: читает байт-код и исполняет инструкцию за инструкцией. Старт мгновенный, но каждый вызов метода интерпретируется заново — медленно. Зато именно интерпретатор собирает профиль: какие методы вызываются часто, какие ветки `if` срабатывают.
2. **JIT-компиляторы**: когда метод или цикл пересекает порог вызовов (становится «горячей точкой», hot spot), JIT компилирует его в нативный код, и дальше метод исполняется напрямую процессором.
   - **C1 (client compiler)**: компилирует быстро, с легкими оптимизациями. Дает прирост почти сразу после старта.
   - **C2 (server compiler)**: компилирует долго, но агрессивно оптимизирует, опираясь на собранный профиль. Именно его код обеспечивает пиковую производительность.
3. **Tiered compilation** (включена по умолчанию с Java 8): конвейер из уровней — интерпретатор → C1 с профилированием → C2. Так JVM совмещает быстрый старт и быстрый пик.

Ключевая оптимизация C2 — **инлайнинг**: тело маленького горячего метода подставляется прямо в место вызова, убирая накладные расходы на вызов и открывая дорогу остальным оптимизациям (вплоть до удаления мертвого кода). Поэтому, кстати, на «холодном» микробенчмарке результаты часто врут — JIT просто не успел отработать.

Обратная сторона профильных оптимизаций — **деоптимизация**: C2 компилирует спекулятивно («раз за всё время вызывалась одна реализация интерфейса — подставлю ее напрямую»), и если допущение ломается (загрузилась вторая реализация), скомпилированный код выбрасывается и исполнение откатывается в интерпретатор. Поэтому бенчмарк или нагрузочный тест, не прошедший по всем веткам кода, показывает цифры, которых в проде может не быть.

Посмотреть на процесс компиляции вживую можно флагом `-XX:+PrintCompilation`.

### 9. Какие бывают типы ссылок в Java (Strong, Soft, Weak, Phantom) и для чего нужна ReferenceQueue?

Тип ссылки определяет, как GC обращается с объектом: чем слабее ссылка, тем охотнее сборщик забирает объект. Это способ сказать GC «этот объект не жалко».

- **Strong** — обычная ссылка (`Object o = new Object()`). Пока объект достижим по сильной ссылке, GC его не тронет. 99% кода живет на них.
- **Soft** (`SoftReference`) — объект собирается **только когда JVM не хватает памяти**, прямо перед `OutOfMemoryError`. Классическое применение — кэши, которые сами сжимаются под давлением памяти.
- **Weak** (`WeakReference`) — объект собирается при **ближайшей** сборке мусора, если сильных и мягких ссылок на него нет. На этом построена `WeakHashMap`: запись исчезает, когда ключ перестал использоваться снаружи.
- **Phantom** (`PhantomReference`) — `get()` всегда возвращает `null`. Ссылка нужна не для доступа к объекту, а чтобы **узнать момент, когда объект финализирован и вот-вот будет удален**. Применяется для освобождения внешних ресурсов (например, off-heap памяти); с Java 9 для этого есть более удобный `Cleaner`.

```java
// Классический кэш на слабых ключах: как только на Data
// не осталось сильных ссылок снаружи — запись сама уйдет при GC
Map<Data, Metadata> cache = new WeakHashMap<>();

// Узнать об удалении объекта — через ReferenceQueue:
ReferenceQueue<Data> queue = new ReferenceQueue<>();
WeakReference<Data> ref = new WeakReference<>(data, queue);
// ... после GC: queue.poll() вернет ref — значит, data собрана
```

**ReferenceQueue** — очередь, куда GC складывает зарегистрированные ссылки (weak/soft/phantom) после того, как их объекты собраны. Это механизм уведомлений о сборке: так `WeakHashMap` узнает, что ключ умер и запись пора удалить, а Netty — что пора вернуть off-heap буфер.

Ловушка на собеседовании: `WeakHashMap` держит слабые ссылки на **ключи**, а значения — сильные. Если значение ссылается обратно на свой ключ, запись не соберется никогда.

### 10. Какие основные флаги JVM нужно знать (-Xms/-Xmx, выбор GC, логи GC, HeapDumpOnOutOfMemoryError)?

Минимальный набор, который реально применяется в проде:

- **Размер кучи**: `-Xms2g` (стартовая), `-Xmx2g` (максимум). На практике в контейнерах их обычно ставят равными, чтобы куча не росла скачками и не было пауз на ресайз.
- **Выбор сборщика**: `-XX:+UseG1GC` (по умолчанию с Java 9), `-XX:+UseParallelGC` (throughput), `-XX:+UseZGC` / `-XX:+UseShenandoahGC` (паузы < 1 мс), `-XX:+UseSerialGC` (мелкие приложения).
- **Целевая пауза**: `-XX:MaxGCPauseMillis=200` — G1 подстроится под нее.
- **Логи GC**:
  - Java 8: `-XX:+PrintGCDetails -XX:+PrintGCDateStamps -Xloggc:gc.log`
  - Java 9+: единый лог `-Xlog:gc*:file=gc.log:time,uptime,level,tags`
- **Дамп при OOM**: `-XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=/dumps/` — без этого после инцидента разбирать будет нечего.

```bash
java -Xms2g -Xmx2g \
     -XX:+UseG1GC -XX:MaxGCPauseMillis=200 \
     -Xlog:gc*:file=logs/gc.log:time,uptime \
     -XX:+HeapDumpOnOutOfMemoryError -XX:HeapDumpPath=logs/ \
     -jar app.jar
```

Если `-Xms`/`-Xmx` не заданы, JVM берет эвристики по железу: стартовая куча ~1/64 RAM, максимальная ~1/4. Проверить фактические значения можно так: `java -XX:+PrintFlagsFinal -version | grep HeapSize`.

Частый follow-up про контейнеры: с Java 10 (и с 8u191 для Java 8) JVM сама видит лимиты cgroups, а не память хоста. Поэтому в Docker/Kubernetes вместо абсолютного `-Xmx` чаще задают долю от лимита контейнера: `-XX:MaxRAMPercentage=75.0` — оставляя четверть под Metaspace, стеки потоков, direct-буферы и сам нативный код JVM. Ловушка в том, что при `-Xmx`, равном лимиту контейнера, суммарное потребление процесса вылезает за лимит, и kubelet убивает под (OOMKilled) раньше, чем JVM успевает бросить свой `OutOfMemoryError`.

### 11. Что такое Metaspace, чем он заменил PermGen и как регулируется его размер?

Metaspace — область памяти, где JVM хранит **метаданные классов**: структуру класса, пул констант, байт-код методов, данные аннотаций. Загрузили класс — его описание легло в Metaspace, причем в рамках загрузившего его ClassLoader'а.

**Чем заменил PermGen.** До Java 8 метаданные жили в PermGen — области с **фиксированным** размером внутри кучи (`-XX:PermSize`, `-XX:MaxPermSize`). Угадать размер заранее было почти невозможно, и приложения с динамической загрузкой классов (редеплои на Tomcat, прокси, JSP) регулярно падали с `OutOfMemoryError: PermGen space`. С Java 8 PermGen убрали, а Metaspace разместили в **нативной памяти** процесса, вне кучи.

**Как регулируется:**
- По умолчанию лимита почти нет — Metaspace растет, пока есть свободная нативная память.
- `-XX:MetaspaceSize=64m` — порог, при достижении которого GC впервые почищает Metaspace. Это не минимум и не максимум, а точка срабатывания сборки.
- `-XX:MaxMetaspaceSize=256m` — жесткий потолок. При превышении — `OutOfMemoryError: Metaspace`.

**`OutOfMemoryError: Metaspace`** почти всегда означает утечку класслоадеров: приложение плодит загрузчики (редеплои, динамические прокси, Groovy/шаблонизаторы, генерирующие классы), а старые не собираются, потому что на них кто-то держит ссылку. Класс выгружается из Metaspace только вместе со своим загрузчиком — пока жив ClassLoader, живы и все его классы.

### 12. Какие оптимизации применяет JVM к коду и данным (Compact Strings, String Deduplication, Escape Analysis)?

Три оптимизации, о которых регулярно спрашивают, потому что они незаметны в коде, но сильно влияют на память и скорость.

- **Compact Strings (Java 9+)**: строка внутри стала `byte[]` вместо `char[]`. Если все символы помещаются в Latin-1 (один байт на символ), строка хранится компактно — экономия почти вдвое на типичном тексте. Для кириллицы, кстати, не сработает: она в Latin-1 не входит, и строки с ней хранятся в UTF-16 как раньше.
- **String Deduplication** (включается `-XX:+UseStringDeduplication`; исторически только в G1, с Java 18 поддерживает и ZGC): GC ищет строки с одинаковым содержимым и заставляет их разделять один массив символов. Помогает, когда приложение хранит много дублей — например, распарсенный JSON с повторяющимися значениями.
- **Escape Analysis**: JIT анализирует, «убегает» ли объект за пределы метода (возвращается ли, кладется ли в поле). Если нет, применяются два трюка:
  - **Скалярная замена**: объект вообще не создается в куче — его поля раскладываются по регистрам/стеку, как набор локальных переменных. Нет объекта — нет работы для GC.
  - **Lock elision**: если объект с синхронизацией не покидает поток, захват монитора удаляется за ненадобностью.

```java
int sum(Point[] points) {
    Point p = new Point(0, 0); // не "убегает" из метода:
    for (Point src : points) { // JIT может не создать его в куче вообще,
        p.x += src.x;          // оставив только два скаляра в регистрах
        p.y += src.y;
    }
    return p.x + p.y;
}
```

На практике это ответ на вопрос «почему аллокация короткоживущих объектов в горячем коде почти бесплатна».

### 13. Какие инструменты JDK помогают диагностировать проблемы JVM (jps, jstack, jmap, jstat, jcmd, JFR)?

Всё перечисленное лежит в `$JAVA_HOME/bin` и не требует ничего ставить на сервер — поэтому именно их ждут в ответе.

- **`jps -lvm`** — список Java-процессов на машине (PID, главный класс, флаги). Стартовая точка: узнать PID нужного процесса.
- **`jstack <pid>`** — снимок стеков всех потоков. Смотреть при: зависании и дедлоках (jstack сам их находит и помечает), высоком CPU, потоках в `BLOCKED`. Классический рецепт для диагностики CPU: `top -H -p <pid>` показывает самый горячий поток, его TID переводите в hex (`printf '%x' <tid>`) и ищете в выводе jstack по `nid=0x...` — получаете стек того, что греет процессор.
- **`jmap -dump:live,format=b,file=heap.hprof <pid>`** — heap dump для разбора в Eclipse MAT; `jmap -histo <pid>` — гистограмма классов по памяти. Смотреть при утечках и OOM.
- **`jstat -gcutil <pid> 1s`** — статистика GC в реальном времени: заполненность областей, число и время сборок. Смотреть, когда подозреваете, что приложение тормозит из-за частых или долгих GC.
- **`jcmd <pid> <команда>`** — швейцарский нож: `GC.heap_dump`, `Thread.print`, `VM.flags`, `GC.class_histogram`. Умеет почти всё, что jmap + jstack, и еще управляет JFR.
- **JFR (Java Flight Recorder)** — встроенный профилировщик с оверхедом около 1%: события GC, аллокации, блокировки, сокеты, CPU. Снимается в проде и разбирается в JDK Mission Control.

```bash
# Запись JFR на лету без рестарта приложения:
jcmd <pid> JFR.start duration=60s filename=profile.jfr

# Или с самого старта:
java -XX:StartFlightRecording=duration=60s,filename=profile.jfr -jar app.jar
```

Шпаргалка «чем смотреть»: тормозит и греет CPU → `jstack`; растет память → `jmap`/`jcmd GC.heap_dump`; подозрение на GC → `jstat`; нужна полная картина в проде → JFR.

### 14. Что такое off-heap память и DirectByteBuffer и где это используется на практике?

Off-heap — это нативная память процесса вне Java-кучи. Главный способ выделять ее из кода — `ByteBuffer.allocateDirect()`: JVM запрашивает память у ОС напрямую, минуя кучу.

```java
ByteBuffer buffer = ByteBuffer.allocateDirect(1024 * 1024); // 1 МБ вне кучи
```

Зачем это нужно:

- **Нет копирования при I/O.** Обычный byte[] при чтении в сокет/файл сначала копируется из кучи в нативный буфер. Direct-буфер уже лежит в нативной памяти, и ОС пишет/читает его напрямую (zero-copy).
- **Нет давления на GC.** Гигабайты буферов не занимают кучу и не провоцируют сборки.

Расплата:

- Аллокация дороже, чем в куче, поэтому direct-буферы переиспользуют пулами.
- Освобождением занимается GC **косвенно**: нативная память возвращается, когда собран сам объект-буфер (через `Cleaner`). Если куча почти пуста и GC ленится, буферы копятся.
- Лимит регулируется отдельно: `-XX:MaxDirectMemorySize` (по умолчанию равен `-Xmx`). Исчерпание дает `OutOfMemoryError: Direct buffer memory` — и heap dump тут ничего не покажет, смотреть надо именно в direct-память (например, `jcmd <pid> VM.native_memory` с включенным NMT).

**Где встречается на практике:** Netty (весь его I/O построен на direct-буферах и пулах `PooledByteBufAllocator`), NIO (`FileChannel.map` — memory-mapped файлы), Aeron, Chronicle Map и прочие off-heap хранилища.

Частая ловушка: `OutOfMemoryError: Direct buffer memory` на сервисе с Netty при почти пустой куче. Причина обычно не в том, что лимит мал, а в утечке буферов — их взяли из пула и не вызвали `release()`. У Netty для поиска таких утечек есть `-Dio.netty.leakDetectionLevel=PARANOID`.
