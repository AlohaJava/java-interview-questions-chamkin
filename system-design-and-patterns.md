## Принципы SOLID

### 1. Что такое принципы SOLID? Подробный разбор каждого принципа.

**Ответ:**

SOLID — это акроним, объединяющий пять базовых принципов объектно-ориентированного программирования и проектирования, сформулированных Робертом Мартином. Их соблюдение позволяет создавать гибкие, масштабируемые и легко поддерживаемые системы.

**1. S — Single Responsibility Principle (Принцип единственной ответственности)**
Каждый класс должен иметь одну и только одну причину для изменения. Речь о связной ответственности и источнике изменений, а не о буквальном ограничении «один метод — один класс». Изменения налоговых правил и транспорта уведомлений приходят по разным причинам.
*Пример нарушения:* Класс `Order` хранит данные о заказе, рассчитывает налоги и отправляет email.
*Правильно:* Разделить на `Order` (данные), `TaxCalculator` (налоги) и `EmailSender` (уведомления).

```java
// Правильная реализация SRP
public class Order {
    private String id;
    private double totalAmount;
    // Геттеры, сеттеры
}

public class OrderRepository {
    public void save(Order order) {
        // Логика сохранения в БД
    }
}
```

**2. O — Open/Closed Principle (Принцип открытости/закрытости)**
Программные сущности должны быть открыты для расширения, но закрыты для модификации. Стабильную часть стараются отделять от ожидаемых вариантов поведения, например через композицию со стратегией. Принцип не запрещает исправлять существующий код и не требует заранее создавать расширения для неизвестных требований.

```java
public interface DiscountPolicy {
    double applyDiscount(double amount);
}

public class VipDiscount implements DiscountPolicy {
    @Override
    public double applyDiscount(double amount) {
        return amount * 0.8;
    }
}
// Добавление новой скидки не требует изменения старого кода.
```

**3. L — Liskov Substitution Principle (Принцип подстановки Барбары Лисков)**
Объекты в программе могут быть заменены их наследниками без изменения свойств программы. Подклассы не должны изменять ожидаемое поведение базового класса.
Формально это контракт: наследник не может усиливать предусловия, ослаблять постусловия и нарушать инварианты базового класса.
*Пример нарушения:* Класс `Ostrich` (Страус) наследует класс `Bird` (Птица), но выбрасывает исключение в методе `fly()`. Канонический пример — `Square` наследует `Rectangle`: квадрат является прямоугольником математически, но ломает контракт `setWidth/setHeight` (у прямоугольника ширину можно менять независимо от высоты). Вывод: наследование строится по поведению, а не по отношению «is-a» из предметной области.

**4. I — Interface Segregation Principle (Принцип разделения интерфейса)**
Клиенты не должны зависеть от интерфейсов, которые они не используют. Лучше создать несколько узкоспециализированных интерфейсов, чем один "толстый".

```java
// Правильно
public interface Printer {
    void print(Document d);
}
public interface Scanner {
    void scan(Document d);
}
```

**5. D — Dependency Inversion Principle (Принцип инверсии зависимостей)**
Модули верхних уровней не должны зависеть от модулей нижних уровней. Оба типа модулей должны зависеть от абстракций. Абстракции не должны зависеть от деталей.

```java
public interface MessageSender {
    void sendMessage(String message);
}

public class NotificationService {
    private final MessageSender sender;

    // Зависимость инжектируется, класс не зависит от конкретной реализации
    public NotificationService(MessageSender sender) {
        this.sender = sender;
    }
}
```

### 2. К чему приводит нарушение принципов SOLID?

**Ответ:**

Сильная связанность и смешение причин изменения усложняют сопровождение. Формальное отклонение от SOLID само по себе не доказывает плохой дизайн, а монолит может иметь строгие внутренние границы.
Основные последствия:

- **Жесткость (Rigidity):** Любое изменение требует каскадных изменений в других модулях.
- **Хрупкость (Fragility):** Изменения в одной части системы приводят к непредсказуемым ошибкам в совершенно других, казалось бы, не связанных частях.
- **Неподвижность (Immobility):** Код невозможно переиспользовать в других проектах или частях системы из-за сильной связности.
- **Вязкость (Viscosity):** Разработчику проще добавить "костыль", чем сделать правильно архитектурно, так как правильное изменение требует огромных усилий.
- **Сложность тестирования:** Классы, выполняющие множество функций или жестко зависящие от реализаций, крайне сложно покрыть модульными тестами.

У Роберта Мартина в списке design smells есть ещё три: **избыточная сложность** (over-engineering — абстракции «на вырост», которые не нужны), **избыточное повторение** (copy-paste вместо переиспользования) и **непрозрачность** (код, который трудно читать).

Частый follow-up — «а бывает ли вред от слепого следования SOLID?» Да: дробление на классы из одного метода и интерфейсы ради интерфейсов — тот же over-engineering. Принципы — ориентир, а не догма; рядом всегда упоминают KISS, DRY и YAGNI.

## Паттерны проектирования

### 3. Что такое паттерны проектирования и антипаттерны? Классификация паттернов.

**Ответ:**

**Паттерн проектирования** — это повторяемая архитектурная конструкция, представляющая собой решение типичной проблемы в рамках часто возникающего контекста проектирования.
**Антипаттерн** — это часто используемое решение, которое в большинстве случаев является неэффективным или контрпродуктивным (например, "God Object", "Magic Numbers", "Spaghetti Code").

Классификация паттернов (по "Банде четырех" - GoF):

1. **Порождающие (Creational):** Решают задачи создания объектов, инкапсулируя логику инстанцирования (Singleton, Builder, Factory Method, Abstract Factory, Prototype).
2. **Структурные (Structural):** Отвечают за композицию классов и объектов, построение удобных структур (Adapter, Decorator, Facade, Proxy, Composite, Bridge, Flyweight).
3. **Поведенческие (Behavioral):** Решают задачи эффективной коммуникации и распределения обязанностей между объектами (Observer, Strategy, Template Method, Chain of Responsibility, Iterator, Command, State, Visitor).

В каталоге GoF (книга "Design Patterns", 1994) — 23 паттерна; позже появились и другие каталоги, например паттерны интеграции (EIP) и паттерны микросервисов.

Другие типичные антипаттерны: "Golden Hammer" (одно знакомое решение на все задачи), "Lava Flow" (мёртвый код, который боятся удалить), "Copy-Paste Programming". Отдельный частый follow-up: Singleton (см. вопрос 4) многие считают антипаттерном — он вводит глобальное состояние и мешает тестированию.

### 4. Паттерн Singleton (Одиночка) и его правильная реализация в Java.

**Ответ:**

**Singleton** гарантирует, что у класса есть только один экземпляр в оговорённой области (обычно в пределах определяющего classloader), и предоставляет к нему глобальную точку доступа.

Наиболее безопасная реализация в Java (по Джошуа Блоху, Effective Java) — через `enum`:
```java
public enum Singleton {
    INSTANCE;

    public void doSomething() {
        // логика
    }
}
```

Почему enum: потокобезопасность и единственность гарантирует сам JVM при загрузке класса, плюс закрыты две классические дыры — десериализация (у enum нельзя создать второй экземпляр через `readObject`) и атака через reflection (рефлексией enum не инстанцировать).

Реализация с отложенной инициализацией (Double-Checked Locking):
```java
public class SingletonDCL {
    private static volatile SingletonDCL instance;

    private SingletonDCL() {}

    public static SingletonDCL getInstance() {
        if (instance == null) {                 // 1-я проверка без лока
            synchronized (SingletonDCL.class) {
                if (instance == null) {         // 2-я проверка внутри лока
                    instance = new SingletonDCL();
                }
            }
        }
        return instance;
    }
}
```

`volatile` здесь обязателен, и это частый follow-up. Без него другой поток может увидеть не-null ссылку на ещё не полностью сконструированный объект: `new` под капотом — это выделение памяти, вызов конструктора и запись ссылки, и JMM разрешает переставить запись ссылки раньше завершения конструктора. `volatile` запрещает такую перестановку и гарантирует видимость (happens-before между записью и чтением).

Более короткая ленивая альтернатива — идиома initialization-on-demand holder:
```java
public class SingletonHolder {
    private SingletonHolder() {}

    private static class Holder {
        static final SingletonHolder INSTANCE = new SingletonHolder();
    }

    public static SingletonHolder getInstance() {
        return Holder.INSTANCE;
    }
}
```
Вложенный `Holder` инициализируется при первом активном использовании его поля. Именно инициализация класса обеспечивает безопасное создание экземпляра — ни `synchronized`, ни `volatile` не нужны.

Минусы, о которых тоже спрашивают: singleton — замаскированное глобальное состояние. Он создаёт скрытые зависимости, мешает модульным тестам (состояние живёт между тестами, mock не подставить) и в среде с несколькими classloader'ами (Tomcat, плагины) перестаёт быть одиночкой. Поэтому в реальных проектах роль singleton обычно играет singleton-бин в DI-контейнере: единственность обеспечивает контейнер, а класс остаётся обычным и тестируемым.

### 5. Паттерн Builder (Строитель).

**Ответ:**

**Builder** позволяет создавать сложные объекты пошагово. Он отделяет конструирование сложного объекта от его представления.
Особенно полезен, когда объект имеет множество параметров, многие из которых опциональны, чтобы избежать антипаттерна "Telescoping Constructor".

```java
public class User {
    private final String firstName; // обязательный
    private final String lastName;  // обязательный
    private final int age;          // опциональный
    private final String phone;     // опциональный

    private User(UserBuilder builder) {
        this.firstName = builder.firstName;
        this.lastName = builder.lastName;
        this.age = builder.age;
        this.phone = builder.phone;
    }

    public static class UserBuilder {
        private final String firstName;
        private final String lastName;
        private int age;
        private String phone;

        public UserBuilder(String firstName, String lastName) {
            this.firstName = firstName;
            this.lastName = lastName;
        }

        public UserBuilder age(int age) {
            this.age = age;
            return this;
        }

        public UserBuilder phone(String phone) {
            this.phone = phone;
            return this;
        }

        public User build() {
            if (firstName == null || lastName == null || age < 0) {
                throw new IllegalArgumentException("Имя, фамилия и неотрицательный возраст обязательны");
            }
            return new User(this);
        }
    }
}

// Использование:
User user = new User.UserBuilder("Ivan", "Ivanov").age(30).build();
```

Частый follow-up — «а что в реальных проектах?» Lombok `@Builder` может сгенерировать код builder, но обязательность полей, проверки инвариантов и неизменяемость объекта требуют отдельного решения. Для простых неизменяемых DTO с небольшим числом полей с Java 16 часто достаточно `record`. Рукописный Builder остаётся актуален там, где полей много, часть опциональна или нужна валидация в `build()` до создания объекта.

### 6. Паттерны Factory Method (Фабричный метод) и Abstract Factory (Абстрактная фабрика).

**Ответ:**

**Factory Method** определяет интерфейс для создания объекта, но оставляет подклассам решение о том, какой класс инстанцировать.

```java
public interface Document { void open(); }
public class PdfDocument implements Document { public void open() {} }

public abstract class Application {
    public abstract Document createDocument(); // Фабричный метод

    public void newDocument() {
        Document doc = createDocument();
        doc.open();
    }
}
```

**Abstract Factory** предоставляет интерфейс для создания семейств взаимосвязанных или взаимозависимых объектов, не специфицируя их конкретных классов.

```java
public interface GUIFactory {              // абстрактная фабрика
    Button createButton();
    Checkbox createCheckbox();
}

public class WinFactory implements GUIFactory {
    public Button createButton() { return new WinButton(); }
    public Checkbox createCheckbox() { return new WinCheckbox(); }
}
// Клиент работает с GUIFactory и получает согласованное семейство
// виджетов одной ОС, не зная конкретных классов.
```

Разница между двумя паттернами — стандартный follow-up. Factory Method создаёт один продукт и обычно строится на наследовании (подкласс переопределяет метод создания). Abstract Factory создаёт семейство согласованных продуктов и строится на композиции (объект-фабрика передаётся клиенту). Абстрактную фабрику выбирают, когда продукты должны быть совместимы между собой: виджеты одной ОС, драйвер и диалект одной БД.

Не путайте термин GoF со статическим фабричным методом: `Calendar.getInstance()` и `NumberFormat.getInstance()` — статические фабрики, но не канонический Factory Method с переопределением в подклассе. `Collection.iterator()` показывает создание продукта через интерфейс, а `DocumentBuilderFactory` и Spring `FactoryBean` — примеры фабричных API, которые нужно анализировать по их конкретному контракту.

### 7. Паттерны Adapter (Адаптер) и Decorator (Декоратор).

**Ответ:**

**Adapter** позволяет объектам с несовместимыми интерфейсами работать вместе. Он выступает в роли "переводчика".

```java
public interface Usb { void connectWithUsb(); }
public class MicroUsbToUsbAdapter implements Usb {
    private final MicroUsb microUsb;
    public MicroUsbToUsbAdapter(MicroUsb microUsb) { this.microUsb = microUsb; }
    @Override
    public void connectWithUsb() {
        microUsb.connectWithMicroUsb();
    }
}
```

**Decorator** динамически добавляет объекту новые обязанности. Является гибкой альтернативой наследованию. Оборачивает объект, реализуя тот же интерфейс, и делегирует ему вызовы, при необходимости добавляя логику до или после вызова.

```java
public interface Notifier { void send(String message); }

public abstract class NotifierDecorator implements Notifier {
    private final Notifier wrappee;
    protected NotifierDecorator(Notifier wrappee) { this.wrappee = wrappee; }
    public void send(String message) { wrappee.send(message); }
}

public class SmsNotifier extends NotifierDecorator {
    public SmsNotifier(Notifier wrappee) { super(wrappee); }
    @Override
    public void send(String message) {
        super.send(message);   // сначала исходное поведение
        sendSms(message);      // потом добавленное
    }
}
// Классический пример из JDK — пакет java.io:
// new BufferedInputStream(new FileInputStream("f.txt"))
```

Разница между Adapter и Decorator — стандартный follow-up: Adapter меняет интерфейс объекта, Decorator меняет (расширяет) поведение, не меняя интерфейс. Proxy в отличие от обоих управляет доступом к объекту.

### 8. Паттерны Proxy (Заместитель) и Facade (Фасад).

**Ответ:**

**Proxy** предоставляет суррогат или объект-заместитель для контроля доступа к другому объекту. Полезен для ленивой инициализации, логирования, контроля доступа (Security Proxy) или удаленных вызовов.

```java
public interface Image { void display(); }

public class LazyImageProxy implements Image {
    private final String filename;
    private RealImage realImage;   // тяжёлый объект

    public LazyImageProxy(String filename) { this.filename = filename; }

    @Override
    public void display() {
        if (realImage == null) {
            realImage = new RealImage(filename);   // создаём при первом вызове
        }
        realImage.display();
    }
}
```

Показанный `LazyImageProxy` не защищён от конкурентной инициализации: два потока могут создать два `RealImage`. Если важна единственность и безопасная публикация, нужен отдельный механизм синхронизации. Прокси окружают нас повсюду, и это хороший ответ на follow-up «где видели вживую»: `java.lang.reflect.Proxy` (динамические прокси в JDK), Spring AOP — в стандартном proxy-режиме `@Transactional` и `@Cacheable` работают через прокси бинов (отсюда ловушка: самовызов метода внутри класса прокси обходит, и транзакция не сработает), ленивая загрузка ассоциаций в Hibernate может использовать прокси, persistent collections или bytecode enhancement.

**Facade** предоставляет унифицированный высокоуровневый интерфейс к набору интерфейсов в подсистеме, что делает подсистему проще в использовании. Фасад скрывает сложность системы от клиента: вместо настройки пяти классов видеоконвертера клиент вызывает один метод `convert("file.mp4", "ogg")`. В реальных проектах роль фасада часто играет сервисный слой, за которым скрываются репозитории, внешние API и кэш. Пример из инфраструктуры — SLF4J: единый фасад над Logback, Log4j2 и JUL.

### 9. Паттерн Observer (Наблюдатель).

**Ответ:**

**Observer** определяет зависимость типа «один ко многим» между объектами таким образом, что при изменении состояния одного объекта все зависящие от него узнают об этом и обновляются автоматически. Идея подписки используется и в реактивных API, но обычный Observer не обеспечивает backpressure, асинхронность или гарантии доставки Reactive Streams.

```java
public interface Observer { void update(String message); }

public class EventManager {
    private List<Observer> listeners = new ArrayList<>();

    public void subscribe(Observer listener) { listeners.add(listener); }
    public void notify(String event) {
        for (Observer listener : listeners) {
            listener.update(event);
        }
    }
}
```

В этом примере уведомление синхронное: медленный слушатель задерживает вызов, а исключение остановит обход, если его не обработать. Изменение списка во время обхода требует отдельного контракта; хранение слушателей может удерживать объекты в памяти.

Нюансы, которые ждут на собеседовании: классический `java.util.Observable` объявлен deprecated с Java 9 (мутабельный, синхронный, неудобный). На практике пишут свои интерфейсы, используют события Spring (`ApplicationEventPublisher` + `@EventListener`) или реактивные стеки. Ещё follow-up — push vs pull: в push-модели субъект сам передаёт данные в `update(...)`, в pull наблюдатель получает ссылку на субъект и забирает нужное сам; pull гибче, когда наблюдателям нужны разные части состояния.

### 10. Паттерн Strategy (Стратегия).

**Ответ:**

**Strategy** определяет семейство алгоритмов, инкапсулирует каждый из них и делает их взаимозаменяемыми. Паттерн позволяет изменять алгоритмы независимо от клиентов, которые ими пользуются. Способствует соблюдению принципа OCP.

```java
public interface PaymentStrategy { void pay(int amount); }

public class CreditCardPayment implements PaymentStrategy {
    public void pay(int amount) { /* логика оплаты картой */ }
}

public class ShoppingCart {
    public void checkout(int amount, PaymentStrategy strategy) {
        strategy.pay(amount);
    }
}
```

С Java 8 стратегии с одним методом часто пишут лямбдами: `PaymentStrategy` — функциональный интерфейс, и вместо отдельного класса достаточно `cart.checkout(amount, a -> chargeCard(a))`. Тот же приём использует JDK: `Comparator` — это стратегия сравнения, `list.sort((a, b) -> ...)`.

### 11. Паттерны Template Method (Шаблонный метод) и Chain of Responsibility (Цепочка обязанностей).

**Ответ:**

**Template Method** определяет костяк алгоритма в базовом классе, делегируя реализацию некоторых шагов подклассам. Сам шаблонный метод обычно объявляют `final`, чтобы подклассы не могли сломать последовательность.

```java
public abstract class DataImporter {
    public final void importData(String path) {      // шаблонный метод
        String raw = readFile(path);
        List<Row> rows = parse(raw);                 // шаг переопределяется
        save(rows);
    }
    protected abstract List<Row> parse(String raw);  // CsvImporter, JsonImporter...
    private String readFile(String path) {
        throw new UnsupportedOperationException("Пример: подключите чтение файла");
    }
    private void save(List<Row> rows) { /* запись в БД */ }
}
```

Примеры: `HttpServlet.service()` раскидывает запрос по `doGet/doPost`, а мы переопределяем шаги; `JdbcTemplate` в Spring — та же идея через callback.

**Chain of Responsibility** позволяет избежать жесткой привязки отправителя запроса к его получателю. Запрос передается по цепочке объектов, каждый из которых может обработать его или передать следующему.

```java
public abstract class SupportHandler {
    private SupportHandler next;
    public SupportHandler linkWith(SupportHandler next) { this.next = next; return next; }

    public void handle(Issue issue) {
        if (!tryHandle(issue) && next != null) {
            next.handle(issue);   // не справились — передаём дальше
        }
    }
    protected abstract boolean tryHandle(Issue issue);
}
```

Живой пример, который ждут на собеседовании, — цепочка сервлетных фильтров (`FilterChain.doFilter`) и middleware в веб-фреймворках.

## System Design

### 12. Основные концепции System Design (Масштабирование, Балансировка нагрузки, Кэширование).

**Ответ:**

- **Вертикальное масштабирование (Scale-Up):** Увеличение ресурсов одного узла (больше RAM, CPU). Имеет физический предел и единую точку отказа.
- **Горизонтальное масштабирование (Scale-Out):** Добавление новых узлов в систему. Ограничено общей БД, разделяемым состоянием, сетью и стоимостью координации. Несколько stateless-инстансов легко добавить, но это не ускорит запрос, упирающийся в блокировку одной строки.
- **Балансировка нагрузки (Load Balancing):** Распределение входящего сетевого трафика между группой серверов для обеспечения высокой доступности и надежности (алгоритмы: Round Robin, Least Connections, IP Hash).
- **Кэширование:** Сохранение копии данных во временном хранилище для быстрого доступа. Снижает нагрузку на БД (Redis, Memcached). Важные концепции: стратегии вытеснения (LRU - Least Recently Used) и инвалидация кэша.

Из того же базового набора, о чём спрашивают дальше: репликация БД (мастер на запись, реплики на чтение), шардирование (горизонтальное разбиение данных по ключу), CDN для статики (кэш ближе к пользователю) и асинхронность через очереди сообщений для сглаживания пиков нагрузки.

### 13. CAP-теорема и выбор базы данных (SQL vs NoSQL).

**Ответ:**

Теорема CAP описывает ограничение при сетевом разделении: нельзя одновременно гарантировать линейризуемость и ответ на каждый запрос к исправному узлу. Consistency здесь — поведение как у единой актуальной копии, а не просто одинаковые значения во всех репликах. Availability — завершение каждой операции согласно контракту, а не любым HTTP-ответом, включая ошибку. Разделение сети приходится учитывать как реальный отказ, а не выбирать отсутствие P настройкой.

При потере связи один сценарий может отказать в записи ради согласованности, а другой вернуть устаревший профиль ради доступности. Поэтому ярлык «SQL — CP, NoSQL — AP» ничего не доказывает: гарантии зависят от операции, топологии, уровня согласованности и конфигурации. Даже в штатном режиме синхронная координация добавляет задержку; это отдельный компромисс, который описывает PACELC.

Реляционную или нереляционную модель выбирают по запросам, ограничениям и транзакционным границам. SQL-БД поддерживают реплики и варианты шардирования; NoSQL-хранилища имеют разные модели, индексы и транзакционные гарантии. Документная БД не обязана быть eventually consistent, а наличие SQL не означает линейризуемость всех чтений. ACID и CAP-consistency — разные понятия.

Например, для заказов с уникальным номером и атомарным изменением нескольких связанных строк разумно начать с реляционной БД. Для распределённого набора ключей сначала проверяют нужный доступ по ключу и модель отказа, а затем конкретное хранилище. При масштабировании считают нагрузку на запись, ограничения ключа шардирования, стоимость JOIN/транзакций между шардами и эксплуатацию — фразы «SQL масштабируется только вверх» недостаточно.

### 14. Монолитная и Микросервисная архитектуры.

**Ответ:**

- **Монолит:** Все компоненты приложения (UI, бизнес-логика, доступ к данным) упакованы в один артефакт.
  *Плюсы:* Прост в разработке, тестировании и первоначальном развертывании.
  *Минусы:* При росте кодовой базы усложняется масштабирование, замедляется процесс сборки, жесткая привязка к одному технологическому стеку.

- **Микросервисы:** Приложение разбито на набор небольших, независимых сервисов, каждый из которых работает в своем процессе и взаимодействует через легковесные механизмы (REST, gRPC, очереди сообщений).
  *Плюсы:* Независимое масштабирование и развертывание, возможность использовать разный стек технологий, изоляция сбоев.
  *Минусы:* Сложность сетевого взаимодействия, распределенные транзакции (Saga), сложность мониторинга и отладки.

Ещё два момента, которые спрашивают. Первый — модульный монолит: один артефакт, но внутри строгие границы модулей; часто это разумная стартовая точка, из которой модули выделяются в сервисы по мере роста. Второй — антипаттерн «распределённый монолит»: формально микросервисы, но они деплоятся и падают вместе из-за жёстких синхронных связей и общей БД. Правило выбора: микросервисы решают организационные проблемы (независимые команды, независимые релизы) ценой технической сложности, поэтому для маленькой команды монолит почти всегда правильнее.

### 15. Redis: основные структуры данных и типовые сценарии (кэш, сессии, rate limiter, pub/sub).

**Ответ:**

Redis — хранилище структур данных, обычно работающее с набором данных в памяти. Задержка зависит от команды, размера данных, сети и persistence; быстрый `GET` не означает, что произвольная операция бесплатна. Кэширование — один из сценариев, а надёжность определяется выбранной конфигурацией и контрактом приложения.

Основные структуры:

- **String** — байтовая строка (до 512 МБ). Кэш объектов (JSON), счётчики (`INCR` атомарен), токены, флаги.
- **Hash** — набор полей внутри одного ключа. Объекты с полями: профиль пользователя, сессия. Можно обновить одно поле, не читая объект целиком.
- **List** — упорядоченная последовательность с операциями на концах; внутреннее представление зависит от версии и размера. Простые очереди (`LPUSH` + `BRPOP`), лента последних N событий (`LPUSH` + `LTRIM`).
- **Set** — неупорядоченное множество уникальных элементов. Теги, «кто лайкнул», пересечения (`SINTER` — общие друзья).
- **Sorted Set (ZSet)** — множество, где у каждого элемента есть score. Лидерборды, отложенные очереди (score = время выполнения), sliding window rate limiter.

Типовые сценарии:

1. **Кэш.** Ключ — идентификатор сущности, значение — сериализованный объект. TTL ограничивает устаревание; альтернативой может быть надёжная явная инвалидация. Отдельно задают лимит памяти и eviction policy — TTL не заменяет их.
2. **Сессии.** `SET session:<id> <payload> EX 1800`. Быстро, легко шарить между инстансами приложения, сессия протухает сама.
3. **Rate limiter.** Для fixed window используют счётчик с TTL на ключ вида `rate:<user>:<minute>`. Связку `INCR` и установки TTL выполняют атомарно, например Lua-скриптом (см. вопрос 20); отдельные команды и pipeline этого не обеспечивают.
4. **Pub/Sub.** `PUBLISH`/`SUBSCRIBE` для рассылки событий. Ловушка в том, что это fire-and-forget: если подписчик офлайн, сообщение потеряно. Нужна надёжность — Redis Streams или Kafka.

Продвинутые структуры — именно про них чаще всего спрашивают на senior-уровне:

- **GEO** — по сути Sorted Set, где score — это закодированные координаты (geohash). `GEOADD drivers 37.62 55.75 driver:1`, `GEOSEARCH drivers FROMLONLAT 37.60 55.70 BYRADIUS 5 km`. Типовые сценарии: «свободные водители рядом с заказом», «ближайшие точки выдачи», «места в радиусе 2 км» — в PostgreSQL похожие задачи решает PostGIS. Выбор требует оценки точности, числа результатов и реальной задержки.
- **Bitmap** — строка, рассматриваемая как массив бит: `SETBIT`/`GETBIT`/`BITCOUNT`/`BITOP`. Классика — DAU-метки: бит с номером userId в ключе `dau:2026-07-26`; `BITCOUNT` даёт DAU за день, `BITOP OR` по ключам недели — активные за неделю. 100 млн пользователей — это ~12 МБ памяти на день. Тот же приём — чекины, «кто смотрел ролик», флаги активности.
- **HyperLogLog** — примерный count distinct с ошибкой ~0,8% и фиксированной памятью около 12 КБ на структуру, независимо от количества элементов. `PFADD uv:page:123 userId`, `PFCOUNT uv:page:123`. Сценарии: уникальные посетители страницы, UV-метрики в аналитике — там, где нужен порядок величины, а не точное число, и Set из миллиардов id не влезает в память.
- **Stream** — append-only лог, где у каждой записи есть ID, плюс consumer groups поверх него. `XADD events * user 42 action login`, чтение группой `XREADGROUP GROUP g1 consumer1 STREAMS events >`, подтверждение обработки `XACK`. Consumer group распределяет записи между консьюмерами, а состояние группы позволяет отслеживать выданные, но неподтверждённые записи. Удаление/trim записей, persistence и политика reclaim всё равно влияют на надёжность. Сценарии: лог событий, очередь задач с подтверждениями и повторной обработкой при корректной конфигурации, когда Kafka избыточна.
- **Bloom filter** (при наличии поддержки RedisBloom в используемой сборке) — вероятностная структура: на вопрос «есть ли элемент» отвечает «точно нет» или «возможно да». Главный сценарий — защита кэша от пробивания (cache penetration): если запросы идут по несуществующим id, каждый промахивается мимо кэша и долбит БД. Фильтр с загруженными валидными id отсекает такие запросы на входе, до кэша и БД. `BF.ADD ids user:42`, `BF.EXISTS ids user:43` → `0` — элемента нет в самом фильтре. Отвечать 404 можно, только если фильтр актуален и содержит все существующие ID; запаздывание его обновления способно скрыть только что созданный объект. Подробнее сама механика разобрана в вопросе 23.

**Инвалидация и TTL.** Три рабочих подхода:

- TTL на каждый ключ, плюс jitter (случайная добавка), чтобы тысячи ключей не истекли одновременно;
- явное удаление ключа при записи в БД (паттерн Cache-Aside, см. следующий вопрос);
- версионирование ключей: `user:42:v7` — при изменении данных меняется версия, старые ключи вымываются по TTL.

Частый follow-up — «что будет, если все одновременно промахнутся мимо кэша?» (cache stampede). Ответы: request coalescing (один поток идёт в БД, остальные ждут), распределённые локи, прогрев кэша.

**Прогрев кэша (cache warmup).** Холодный кэш перед пиковой нагрузкой — отдельная ловушка: после рестарта Redis или деплоя кэш пуст, и весь поток запросов летит напрямую в БД ровно в тот момент, когда нагрузка максимальная (чёрная пятница, старт распродажи). Прогрев — это заранее наполнить кэш горячими данными до того, как на сервис пойдёт трафик. Как это делают на практике: отдельный джоб при деплое проходится по топ-N ключей (популярные товары, справочники) и кладёт их в кэш; либо прогрев идёт асинхронно сразу после старта приложения, а readiness-проба не пускает трафик, пока прогрев не завершился. В blue-green выкатке кэш green-окружения греют до переключения трафика. Дополняет защиту от stampede: request coalescing спасает от единичных массовых промахов, а прогрев — от ситуации, когда промахнулось всё сразу.

### 16. Паттерны кэширования: Cache-Aside, Read-Through, Write-Through и Write-Behind.

**Ответ:**

Паттерны отличаются тем, кто отвечает за синхронизацию кэша и БД и в какой момент это происходит.

**Cache-Aside (Lazy Loading)** — самый частый вариант: приложение работает с кэшем само.

```text
Чтение:                          Запись:
App → Cache: GET key             App → DB: UPDATE
  ├─ hit  → вернуть              App → Cache: DELETE key
  └─ miss → App → DB: SELECT
            App → Cache: SET key (+TTL)
```

Плюсы: в кэше лежит запрошенное; при его отказе возможен fallback в БД, если она выдержит поток. Промах добавляет обращения, но задержка не обязана утраиваться. После записи важно инвалидировать после commit. Гонка остаётся: читатель взял старое значение, писатель закоммитил и удалил ключ, читатель снова положил старое. TTL ограничивает срок такого состояния, а версии данных или согласованный механизм загрузки могут защищать от перезаписи свежего значения старым.

**Read-Through** — то же самое, но логика промаха живёт внутри самого кэша: приложение всегда спрашивает кэш, а тот сам ходит в БД. Код приложения проще, но нужен кэш или прослойка, которая это умеет.

**Write-Through** — запись идёт синхронно в кэш и в БД:

```text
App → Cache: SET → Cache → DB: INSERT/UPDATE → ответ клиенту
```

Плюсы: успешно завершённая запись проходит через слой, синхронно сохраняющий данные в backing store, и может прогреть кэш. Но две системы не становятся общей транзакцией: нужно определить порядок записи, поведение при частичном сбое, конкуренции и внешних изменениях БД. Без этого «кэш всегда консистентен» неверно. Запись обычно дороже, а в кэше могут оказаться данные, которые никто не читает.

**Write-Behind (Write-Back)** — запись сразу попадает в кэш, а в БД сбрасывается асинхронно пачкой:

```text
App → Cache: SET → ответ клиенту
                  Cache → DB: batch flush (асинхронно)
```

Плюсы: минимальная латентность записи, частые апдейты одного ключа схлопываются в одну запись в БД. Минусы: БД отстаёт; без надёжного журнала и восстановления очередь неподтверждённых записей может потеряться при сбое. Допустимость определяется гарантиями подтверждения, восстановления и доменом. Простой volatile-кэш без устойчивой записи не подходит для подтверждения финансового результата.

На практике чаще всего встречается Cache-Aside + TTL, остальные — там, где есть особые требования к консистентности или латентности записи.

## Инфраструктура и DevOps

### 17. Docker: образ, контейнер, слои и кэш Dockerfile. Best practices.

**Ответ:**

**Образ** — неизменяемый шаблон из read-only слоёв (базовая ОС, зависимости, jar). **Контейнер** — запущенный экземпляр образа: изолированный процесс плюс тонкий writable-слой поверх слоёв образа.

**Слои и кэш.** `RUN`, `COPY`, `ADD` обычно добавляют файловые слои; `FROM` выбирает базу, а `ENV`, `USER`, `ENTRYPOINT` задают метаданные/конфигурацию. Не каждая инструкция добавляет файловый слой. При пересборке Docker идёт сверху вниз и берёт слои из кэша до первой изменившейся инструкции — от неё всё пересобирается заново. Отсюда правило: то, что меняется редко, ставим выше; свой код — ниже. Для Java-проекта это значит: сначала копируем `pom.xml` и качаем зависимости, и только потом копируем исходники — тогда правка кода не гоняет скачивание зависимостей заново.

```dockerfile
# --- stage 1: сборка ---
FROM maven:3.9-eclipse-temurin-21 AS build
WORKDIR /app
COPY pom.xml .
RUN mvn dependency:go-offline
COPY src ./src
RUN mvn package -DskipTests  # предполагается, что CI уже выполнил проверки

# --- stage 2: рантайм ---
FROM eclipse-temurin:21-jre
WORKDIR /app
RUN useradd -r appuser
COPY --from=build /app/target/app.jar app.jar
USER appuser
ENTRYPOINT ["java", "-jar", "app.jar"]
```

В примере предполагается `<finalName>app</finalName>` в POM; без этого имя JAR нужно согласовать с результатом сборки.

Практические решения для обсуждения:

- **Multi-stage build** — собираем в тяжёлом образе с Maven, в прод несём только JRE и jar. Образ худеет с ~800 МБ до ~250 МБ.
- **`.dockerignore`** — исключаем `.git`, `target/`, локальные конфиги: меньше контекст сборки, не протекают секреты, не сбивается кэш.
- **Не root** — `USER appuser`: при взломе приложения атакующий не получает root в контейнере.
- Фиксировать образ по digest, когда нужна точная воспроизводимость: даже тег версии можно переназначить. Обновление digest делают отдельным контролируемым изменением.
- Один процесс на контейнер, логи в stdout.
- JVM в контейнере: современные JDK (11+) сами видят cgroup-лимиты, но хип лучше задавать явно через `-XX:MaxRAMPercentage`.

Частый follow-up: «чем контейнер отличается от виртуальной машины?» — контейнер разделяет ядро ОС с хостом (изоляция через namespaces и cgroups), ВМ виртуализирует железо и несёт своё ядро целиком.

### 18. Kubernetes для собеседования: Pod, Deployment, Service, Ingress, ConfigMap и Secret.

**Ответ:**

Kubernetes — оркестратор контейнеров: сам раскладывает их по нодам, перезапускает упавшие, масштабирует. Минимальный набор сущностей:

- **Pod** — наименьшая единица: один или несколько контейнеров с общей сетью и volumes. Напрямую поды почти не создают — ими управляют контроллеры.
- **Deployment** — декларативно описывает «хочу N реплик такого пода». Управляет ReplicaSet, умеет rolling update и откат (`kubectl rollout undo`).
- **Service** — стабильная точка входа к набору подов, у которых эфемерные IP. Типы: `ClusterIP` (внутри кластера), `NodePort`, `LoadBalancer`. Находит поды по label selector.
- **Ingress** — L7-маршрутизация снаружи внутрь: хосты, пути, TLS-терминация. Работает через ingress-контроллер (nginx, traefik).
- **ConfigMap / Secret** — конфигурация и чувствительные данные, подключаются как env-переменные или файлы. Secret отличается от ConfigMap в основном base64 и политиками доступа — шифрование включается отдельно.

Как выглядит путь запроса:

```text
client → Load Balancer → Ingress (TLS, host/path routing)
                       → Service (ClusterIP)
                       → Pod-1 / Pod-2 / Pod-3
```

Как происходит деплой новой версии:

```text
1. CI собрал image myapp:1.4.2 и запушил в registry
2. kubectl apply -f deployment.yaml (image: myapp:1.4.2)
3. API server пишет желаемое состояние в etcd
4. Scheduler выбирает ноды для новых подов
5. Kubelet на нодах тянет образ и стартует контейнеры
6. readinessProbe прошла → под добавляется в endpoints Service
7. Старые поды гасятся постепенно (rolling update)
```

Ловушка в том, что пока `readinessProbe` не зелёная, трафик на под не пойдёт — а если пробу не настроить, Kubernetes начнёт слать запросы на ещё не прогретое приложение. Второй частый follow-up: `livenessProbe` против `readinessProbe` — первая при повторных неудачах приводит к перезапуску контейнера, вторая исключает неготовый Pod из обычного трафика Service. Startup-проба позволяет дождаться медленного старта до включения остальных проверок. Зависимость liveness от общей БД способна вызвать массовые бессмысленные рестарты.

### 19. CI/CD и стратегии деплоя: rolling, blue-green и canary.

**Ответ:**

**CI (Continuous Integration)** — частая интеграция изменений с автоматической сборкой и проверками. Цель — быстрый feedback и работоспособный main; успешные тесты не исключают все дефекты. **CD** — либо Delivery (артефакт всегда готов к релизу, выкатка по кнопке), либо Deployment (выкатка автоматически после зелёного пайплайна).

**Rolling.** Инстансы обновляются партиями: подняли новый, погасили старый. Дефолт в Kubernetes (`maxSurge`, `maxUnavailable`).

- Плюсы: можно сохранить доступность без полного дублирования среды. Для отсутствия простоя нужны рабочие probes, резерв мощности и корректное завершение активных запросов.
- Риски: какое-то время в проде живут две версии — API и схема БД должны быть обратно совместимы. Откат — тот же деплой в обратную сторону, то есть не мгновенный.

**Blue-Green.** Два идентичных окружения: blue (текущее) и green (новое). Деплоим в green, проверяем, переключаем трафик на балансировщике.

- Плюсы: быстрое переключение маршрутизации обратно на blue, если старая версия совместима с текущими данными и фоновые действия новой версии обратимы.
- Риски: двойной расход ресурсов; главная боль — БД: обе версии работают с одной базой, поэтому миграции должны быть совместимы со старой версией (expand-migrate-contract).

**Canary.** Новая версия получает маленький процент трафика, смотрим метрики (ошибки, латентность) и постепенно наращиваем долю.

- Плюсы: баг ловится на 1–5% пользователей, а не на всех; решение принимают реальные метрики.
- Риски: нужна нормальная наблюдаемость и механизм распределения трафика (ingress-веса, service mesh); релиз растягивается по времени.

На практике rolling — рабочая лошадка, blue-green — когда критичен мгновенный откат, canary — для сервисов, где цена ошибки высока.

## System Design: практика

### 20. Rate limiting: алгоритмы token bucket, leaky bucket, fixed window и sliding window.

**Ответ:**

Rate limiter ограничивает число запросов от клиента за период. Алгоритмы отличаются тем, как считают и как ведут себя при всплесках.

**Fixed window counter.** Окно — календарная минута, внутри счётчик. Просто и дёшево, но на границе окон пропускает до 2x лимита: 100 запросов в 12:00:59 и ещё 100 в 12:01:00 — итого 200 запросов за две секунды.

**Sliding window log.** Храним timestamp каждого запроса и считаем за последние 60 секунд. Точно, но память растёт с числом запросов — при лимите 1000/мин это 1000 записей на клиента.

**Sliding window counter.** Компромисс: два соседних fixed-окна плюс взвешивание доли предыдущего. Память на ключ константная, но оценка предполагает достаточно равномерные события внутри прошлого окна; при сильном burst погрешность может быть существенной.

**Token bucket.** В ведре N токенов, они пополняются со скоростью r в секунду; запрос тратит токен, нет токенов — отказ (429). Разрешает короткие пачки до N, средняя скорость не выше r. Так лимитируют большинство публичных API:

```text
        refill: +r tokens/sec
                ↓
        ┌─────────────────┐
        │  bucket (max N) │
        │   ●●●●○○        │
        └────────┬────────┘
  запрос → взять 1 токен → есть? пропускаем : 429 Too Many Requests
```

**Leaky bucket.** Запросы складываются в очередь и обрабатываются с фиксированной скоростью; очередь переполнилась — отказ. В этой трактовке очередь сглаживает выходной поток, но всплеск можно принять в пределах её ёмкости ценой ожидания. Другой вариант leaky bucket работает как meter без очереди; на интервью нужно уточнить используемую модель.

Выбор: нужен средний лимит с допуском на пачки — token bucket; защитить медленный downstream — leaky bucket; дёшево и приблизительно — fixed или sliding counter.

Общее состояние limiter можно хранить в Redis, но отдельные `INCR` и `EXPIRE` не образуют атомарную операцию. Клиент способен упасть между ними, оставив ключ без TTL; pipeline сокращает RTT, но не закрывает это окно. Для счётчика fixed window обе операции можно объединить в Lua:

```lua
-- KEYS[1] содержит ID клиента и номер временного окна
-- ARGV[1] — TTL в миллисекундах; ARGV[2] — лимит
local count = redis.call('INCR', KEYS[1])
if count == 1 then
    redis.call('PEXPIRE', KEYS[1], ARGV[1])
end
return {count <= tonumber(ARGV[2]) and 1 or 0, count}
```

Скрипт выполняется без вклинивания других команд на этом узле; TTL задаётся при создании окна, а не продлевается каждым запросом. Ключ включает номер окна, иначе семантика станет иной. Аргументы предварительно проверяют: Lua не означает rollback уже выполненных команд при ошибке. Атомарность на узле также не гарантирует сохранность счётчика при failover. Отдельно определяют, что делать при недоступности Redis: разрешить запросы, отказать или применить локальный запасной лимит.

### 21. Задача System Design: спроектируй URL shortener.

**Ответ:**

Классика жанра: сервис типа bit.ly — принимает длинный URL, отдаёт короткий, по короткому делает редирект.

**Оценка нагрузки** (примерные цифры, их озвучиваем интервьюеру):

- 100 млн новых ссылок в месяц → ~40 записей/сек;
- чтение:запись = 100:1 → ~4000 редиректов/сек;
- за 5 лет 6 млрд записей × ~500 байт ≈ 3 ТБ — помещается в одну приличную БД, шардирование нужно не сразу.

Преобладание чтений делает кэш кандидатом, но не обязательным компонентом. Сначала оценивают планы запросов, пиковую нагрузку, долю горячих ключей и latency; средние 4000 RPS сами по себе не доказывают необходимость Redis.

**Генерация короткого кода.** Алфавит base62 (`a-zA-Z0-9`): 7 символов дают 62⁷ ≈ 3,5 трлн комбинаций — с запасом. Два подхода:

1. **Счётчик → base62.** Уникальный id (sequence в БД, `INCR` в Redis или выдача диапазонов инстансам) кодируем в base62. Коллизий нет при корректной единой выдаче ID без повторного использования диапазонов; восстановление счётчика из старой копии может это нарушить. Коды предсказуемы, а уникальность дополнительно защищают ограничением БД.
2. **Хэш.** хэш от URL кодируем в выбранный алфавит, берём первые 7 символов, при коллизии бампим или добавляем соль. Детерминировано, но коллизии приходится обрабатывать.

Счётчик удобен при допустимой координации; случайный base62-код с проверкой уникальности удобен, когда важна непредсказуемость. Уникальный индекс и повтор при конфликте нужны для случайной генерации; её коллизии нельзя оценивать только размером пространства без birthday effect.

**Схема БД** — одна таблица:

```text
links
├─ short_code  VARCHAR(7)  PRIMARY KEY
├─ long_url    TEXT
├─ user_id     BIGINT       (nullable)
├─ created_at  TIMESTAMP
└─ expires_at  TIMESTAMP    (nullable)
```

**High-level схема:**

```text
client → LB → [app servers] (stateless)
                ├─→ Redis (кэш short_code → long_url, TTL)
                └─→ БД (мастер + read-реплики)
```

Чтение: ищем в Redis → промах → БД → прогреваем кэш. Запись: генерируем код, пишем в БД, можем сразу положить в кэш.

**Масштабирование:** app-серверы stateless — размножаем за LB; чтение разводим на реплики БД; при дальнейшем росте шардируем по `short_code`. Аналитику кликов выносим асинхронно через очередь, чтобы не тормозить редирект.

Частый follow-up — **301 или 302?** 301 означает постоянный перенос и допускает эвристическое кэширование; 302 означает временный перенос, но тоже может кэшироваться при явной политике свежести. Поэтому «302 гарантирует каждый клик через сервер» неверно. Для изменяемого назначения и серверной аналитики можно вернуть `302` с `Cache-Control: no-store`; это управляет HTTP-кэшами, но не гарантирует точность статистики из-за ботов, повторов и особенностей клиентов. Семантику редиректа и политику кэширования выбирают отдельно.

### 22. Как подходить к задаче System Design на собеседовании.

**Ответ:**

Задача открытая, и проверяют не «правильный ответ», а процесс: как собираете требования, считаете и выбираете компромиссы. Рабочая последовательность:

**1. Уточнение требований (5–10 минут).** Не рисовать ничего, пока не заданы вопросы: что именно делаем (2–3 ключевые фичи, остальное явно выносим за скобки), какой масштаб (DAU, RPS, read/write ratio), что важнее — консистентность или доступность, есть ли жёсткие требования к латентности. Интервьюер ждёт эти вопросы; пропуск шага — типичная ошибка.

**2. Прикидка на салфетке (back-of-envelope).** Считаем вслух порядки величин: QPS, объём хранилища на горизонте нескольких лет, трафик. Цель не точность, а понять, где узкое место: CPU, диск или сеть. Эти цифры потом оправдывают выбор компонентов: «нам хватит одной БД с репликами, шардирование пока не нужно».

**3. High-level дизайн.** Четыре-шесть блоков: клиент, балансировщик, app-серверы, кэш, БД, очередь. Плюс набросок API (3–5 эндпоинтов) и схемы данных. Идти сверху вниз, не ныряя в детали раньше времени.

**4. Углубление.** Спрашиваем интервьюера, куда копать, и детализируем один-два компонента: схему БД, алгоритм (как генерировать коды в URL shortener), поведение при отказе.

**5. Trade-offs и узкие места.** Проговариваем вслух: единая точка отказа, что сломается при росте в 10 раз, что выбрали и чем пожертвовали. Способность назвать слабые места собственного дизайна ценится выше самого дизайна.

Типичные ошибки: молча рисовать (думать надо вслух — это совместная работа, а не экзамен по памяти), начинать с микросервисов и Kafka там, где хватает монолита и PostgreSQL, не оставить время на trade-offs.

## Распределённые системы и сети

### 23. Распределённые механики на пальцах: Consistent Hashing, Leader Election, генерация уникальных ID и фильтр Блума.

**Ответ:**

Четыре приёма, которые встречаются внутри почти любой распределённой системы. Каждый решает свою конкретную проблему.

**Consistent hashing.** Задача: разложить ключи по N узлам (кэшей, шардов). Наивный вариант `hash(key) mod N` ломается при изменении N: добавили один узел — и почти все ключи переезжают на другие машины, кэш-кластер ложится от массовых промахов. Consistent hashing мапит и узлы, и ключи на одно хэш-кольцо; ключ обслуживает ближайший узел по часовой стрелке:

```text
                 ключ "user:7"
                      ↓
        ┌─────────[узел B]─────────┐
   [узел A]                    [узел C]
        └─────────[узел D]─────────┘
   ключ идёт к первому узлу по часовой стрелке от своей точки
```

При добавлении/удалении узла переезжает только его дуга — при равномерном распределении примерно доля ключей одного узла вместо почти всех. Тонкость: узлы попадают на кольцо неравномерно, поэтому каждый физический узел представляют несколькими виртуальными точками (vnodes), число которых зависит от реализации — распределение выравнивается, а при выходе узла его нагрузка равномерно разъезжается по всем остальным. Где встречается: Cassandra, DynamoDB, клиентское шардирование Memcached/Redis, sticky-балансировщики.

**Leader election.** В кластере часто нужен один узел, принимающий решения: мастер на запись, координатор, выдающий диапазоны id. Когда он падает, оставшиеся должны выбрать нового — и гарантировать, что двух лидеров одновременно не будет (split-brain: два «мастера» пишут расходящиеся данные). Идея Raft: у каждого узла три состояния — follower, candidate, leader; время делится на термы (сроки полномочий). Лидер шлёт всем heartbeat; heartbeat пропал — узел становится candidate, увеличивает номер терма и просит голосов. Получил большинство — стал лидером этого терма. Большинство и правила термов обеспечивают безопасность подтверждённых записей Raft. Старый лидер после разрыва связи может некоторое время считать себя лидером, поэтому для внешних побочных эффектов нужны проверки актуальности полномочий, например fencing tokens; само слово «выборы» этого не решает. Zab в ZooKeeper — та же идея с поправками на репликацию лога. На практике выборы не пишут руками, а берут готовые: etcd, ZooKeeper, Consul.

**Генерация уникальных ID.** В одной БД хватает `AUTO_INCREMENT`, при распределённой выдаче выбор зависит от нагрузки: центральный счётчик может стать узким местом и требует продуманного восстановления. При умеренном потоке одна надёжная sequence может оставаться достаточной.

- **UUID** — 128 бит, генерируется локально на любом узле без координации. Минусы: занимает 16 байт, для случайных UUIDv4 вставки распределяются по B-tree, что может ухудшать локальность и увеличивать число page splits. UUIDv7 помещает timestamp в старшие биты, улучшая временную локальность; строгая глобальная монотонность между узлами не гарантируется. В Java 17–21 `UUID.randomUUID()` создаёт v4, для v7 нужна отдельная корректная реализация.
- **Snowflake (Twitter)** — 64 бита: timestamp в миллисекундах + id машины + локальный sequence. Компактнее UUID (bigint в БД), сортируются по времени, предел скорости зависит от числа бит sequence; при 12 битах это до 4096 ID за миллисекунду на worker при корректных часах. Плата: надо раздавать machine id и следить за часами — при откате времени возможны коллизии или остановка генератора.

Правило выбора: не нужна сортировка и хочется нулевой координации — UUID(v7); нужны компактные и k-sortable идентификаторы для индексов и шардирования по времени — Snowflake-подобная схема.

**Фильтр Блума.** Вероятностная структура «есть ли элемент в множестве»: битовый массив и k хэш-функций. При добавлении выставляются k бит, при проверке читаются те же k бит: хоть один ноль — элемента точно нет; все единицы — возможно, есть (false positives бывают, false negatives отсутствуют для добавленных элементов корректного неизменённого фильтра; потеря/запаздывание обновлений системы — отдельная проблема). Цена вопроса — байты на элемент против мегабайт на полное множество. Сценарии: защита кэша от пробивания (отсев запросов по несуществующим id до похода в БД, см. вопрос 15), «показать пользователю только непрочитанное», отсев чтений в LSM-хранилищах (Cassandra, RocksDB проверяют фильтр перед поиском на диске).

### 24. Сети для бэкенд-разработчика: TCP vs UDP, TLS handshake, HTTP/1.1 vs HTTP/2 vs HTTP/3, keep-alive и DNS.

**Ответ:**

**TCP vs UDP.** TCP — соединение с гарантиями: прежде чем слать данные, стороны договариваются рукопожатием из трёх шагов — SYN → SYN-ACK → ACK. Дальше протокол сам следит за доставкой: каждый сегмент нумеруется, получатель подтверждает приём, потерянное пересылается, порядок восстанавливается, плюс контроль перегрузки сети. UDP ничего этого не делает: отправил дейтаграмму и забыл — ни соединения, ни гарантий доставки и порядка. У UDP меньше встроенных механизмов и накладных расходов, но это само по себе не гарантирует меньшую прикладную задержку. UDP берут там, где потерять пакет дешевле, чем ждать его повторной передачи: DNS-запросы, голос и видео, онлайн-игры, а также как основа для своих протоколов — QUIC (HTTP/3) поверх UDP реализует надёжность сам.

**TLS handshake.** После TCP-рукопожатия клиент и сервер договариваются о шифровании: клиент шлёт ClientHello (поддерживаемые версии и наборы шифров, случайное число), сервер отвечает ServerHello и присылает сертификат. Клиент проверяет цепочку доверия: сертификат домена подписан промежуточным CA, тот — корневым, а корневой уже лежит в trust store системы или JVM. Затем стороны через обмен ключами (обычно ECDHE — эфемерный Диффи-Хеллман, дающий forward secrecy) вычисляют общий симметричный сессионный ключ, и дальше весь трафик идёт быстрым симметричным шифром. В TLS 1.3 всё это ужато до одного RTT, а возобновление может разрешать 0-RTT early data. Это не отменяет handshake и несёт риск повторного воспроизведения ранних запросов. Что в сертификате: домен, публичный ключ, срок действия и подпись CA; выпуск давно бесплатен и автоматизирован (Let's Encrypt). Частый follow-up из Java-мира: ошибки TLS различают по причине: неизвестный CA, неполная цепочка сервера, истёкший срок, несовпадение имени, протоколы или алгоритмы. Проверять только truststore недостаточно; отключать проверку сертификата для исправления нельзя.

**HTTP/1.1 vs HTTP/2 vs HTTP/3.**

- **HTTP/1.1** — текстовый протокол; в обычном обмене соединение обслуживает запрос и ответ последовательно. Pipelining допускает несколько запросов, но порядок ответов создаёт head-of-line blocking; на практике часто открывают несколько соединений.
- **HTTP/2** — бинарный, внутри одного TCP-соединения мультиплексируются потоки: запросы и ответы идут параллельно и не блокируют друг друга. Плюс сжатие заголовков (HPACK) и server push. Но HoL-blocking остался на уровне TCP: потерян один сегмент — TCP останавливает все потоки сразу, пока перешлёт.
- **HTTP/3** — мультиплексирование перенесено в QUIC поверх UDP: потеря данных одного потока не заставляет транспорт ждать их для выдачи данных всех остальных потоков. Пакет может нести данные нескольких потоков, а congestion control и общие лимиты соединения всё ещё влияют на них совместно. Handshake совмещён с TLS 1.3 (быстрее установка соединения), а connection migration позволяет соединению пережить смену сети — телефон переехал с Wi-Fi на LTE, соединение не оборвалось.

**Keep-alive.** Переиспользование установленного TCP-соединения для нескольких запросов вместо нового handshake на каждый. В HTTP/1.1 постоянные соединения используются по умолчанию, отдельный заголовок `Connection: keep-alive` не обязателен. Экономия заметная: TCP-handshake + TLS-handshake — это 2–3 RTT на каждое соединение. На практике важны таймауты и лимиты: балансировщик или сервер может закрыть простаивающее соединение раньше клиента, и клиент обязан уметь переоткрывать; в Java-клиентах это настройки connection pool (max connections, keep-alive duration).

**DNS-запрос по шагам.** Как браузер или сервис превращает `api.example.com` в IP:

```text
1. Кэш браузера/клиента          → есть? конец
2. Кэш ОС (и /etc/hosts)         → есть? конец
3. Рекурсивный резолвер (провайдер, 8.8.8.8)
4.   → корневой сервер: «кто отвечает за .com?»
5.   → TLD-сервер .com: «кто отвечает за example.com?»
6.   → authoritative-сервер example.com: A-запись → 93.184.216.34
7. Ответ кэшируется на каждом уровне на время TTL
```

Каждый уровень кэширует ответ, поэтому корневые серверы видят малую долю реальных запросов. Что спрашивают дальше: типы записей (A — IPv4, AAAA — IPv6, CNAME — алиас на другое имя), роль TTL (при миграции сервиса на новый IP заранее занижают TTL, чтобы клиенты быстрее увидели изменение), и почему DNS часто использует UDP для короткого обмена. При усечённом ответе и в других сценариях нужен TCP; также существуют DNS over TLS/HTTPS. Ограничиваться только UDP при диагностике доступа к DNS нельзя.

## Границы и контракты Java-приложения

### 25. Чем гексагональная архитектура отличается от внедрения зависимостей через Spring?

Гексагональная архитектура отделяет прикладные сценарии и доменную логику от способов входа и внешних систем. Порты задают требуемые контракты, адаптеры связывают их с HTTP, SQL, брокером или тестовым окружением. DI — механизм сборки объектов; можно использовать конструкторы Spring и при этом напрямую связать бизнес-логику с API поставщика.

Например, сценарию расчёта доставки нужна стоимость для маршрута. Он объявляет контракт в понятиях своей задачи:

```java
public interface ShippingQuotePort {
    Quote quote(Route route);
}

public final class CalculateOrder {
    private final ShippingQuotePort shipping;

    public CalculateOrder(ShippingQuotePort shipping) {
        this.shipping = shipping;
    }
}
```

HTTP-адаптер преобразует внешний JSON в `Quote`, определяет таймаут и переводит технические сбои в согласованную модель ошибки. Прикладной код не должен принимать случайный `ResponseEntity` только потому, что его возвращает HTTP-клиент. Тест сценария использует простую реализацию порта, а отдельный интеграционный тест проверяет адаптер и реальный формат ответа.

Граница полезна там, где отделяет разные причины изменения или делает важный сценарий проверяемым. Создавать порт для каждого вызова приватного метода не нужно. Ошибка — поменять имя пакета на `domain`, сохранив внутри SDK поставщика и исключения транспорта. Другая крайность — требовать полного отсутствия любых framework-аннотаций вне инфраструктуры без оценки стоимости: цель в управляемых зависимостях, а конкретную степень изоляции выбирает команда.

### 26. Как выбрать границы модулей в Java-монолите, чтобы их можно было менять независимо?

Начинают с бизнес-правил и владельца данных, затем проверяют реальные связи сценариев. Разделение на `controllers`, `services`, `repositories` описывает технические слои, но не границы предметных областей: изменение заказа всё ещё затрагивает десятки общих классов. Модуль `orders` может содержать свои слои и узкий публичный API для соседей.

Например, `billing` не должен напрямую менять строки заказа через `OrderRepository`, обходя проверку перехода статуса. Он вызывает согласованный сценарий модуля заказов или обрабатывает опубликованное изменение. В одном процессе допустима общая транзакция, если она действительно нужна; возможность сделать её сегодня не означает, что при выделении сервисов та же атомарность сохранится автоматически.

Практические признаки границы: определены разрешённые зависимости, публичный контракт мал, внутренние модели не используются повсюду, нет циклов и обходных записей в чужие таблицы. Это подкрепляют package visibility, отдельными build-модулями или архитектурными проверками — выбранный механизм должен реально ограничивать доступ, а не существовать только на диаграмме.

Если каждый запрос требует синхронного обмена между будущими сервисами, а почти все изменения выпускаются совместно, граница пока не даёт независимости. Полезнее сначала уменьшить связанность внутри монолита, чем выносить сетевой вызов вместо обычного метода. Частая ошибка — «одна таблица — один сервис»: инвариант может охватывать несколько таблиц, а общая справочная таблица сама по себе не определяет владельца сценария.

### 27. Когда нужен интерфейс и Strategy, а когда достаточно метода или switch?

Интерфейс полезен, когда представляет устойчивый контракт, через который требуется подставлять разные реализации или изолировать внешнюю зависимость. Само наличие класса не требует парного `SomethingService`/`SomethingServiceImpl`. Единственная реализация тоже может оправдывать интерфейс на важной границе, но аргументом должна быть эта граница, а не привычка.

Для нескольких тарифов Strategy позволяет выбрать алгоритм без изменения вызывающего сценария. Например, `DiscountPolicy` принимает сумму и возвращает скидку; сложные правила можно тестировать по отдельности и регистрировать явно. У всех стратегий при этом должны совпадать смысл результата, правила округления и обработка недопустимых входов. Общая сигнатура без общего контракта взаимозаменяемости не даёт.

Если различие — два простых стабильных случая, обычный метод с `switch` по `enum` может быть яснее фабрики, реестра и десятка классов. Чтобы добавить новый вариант, придётся изменить switch; это приемлемая стоимость, если набор намеренно централизован. В Java 17–21 не стоит незаметно подменять такой пример preview-возможностями: достаточно стабильных конструкций языка.

Выбор проверяют ожидаемым изменением: добавление нового правила затронет один изолированный алгоритм или десятки ветвлений? Будет ли конфигурация гарантировать наличие стратегии для каждого тарифа? Ошибки — создавать расширение «на будущее» без случая использования либо разносить один и тот же switch по всем слоям. OCP помогает управлять изменениями, а не запрещает редактировать существующие файлы.

### 28. Обеспечивает ли локальный Observer или Spring event надёжную отправку после commit?

Нет, сам паттерн Observer описывает уведомление подписчиков и не задаёт транзакционные гарантии. Обычный вызов слушателя может быть синхронным, происходить до commit и завершаться исключением. Асинхронность добавляет другое окно: процесс способен остановиться после успешного изменения БД, но до выполнения обработчика.

Например, обработчик `OrderCreated` отправляет письмо, а затем основная транзакция откатывается. Пользователь получит сообщение о несуществующем заказе. `@TransactionalEventListener` позволяет привязать обработку к фазе транзакции, по умолчанию `AFTER_COMMIT`. Но это не устойчивая очередь: при падении процесса после commit доставка может потеряться. Если события нет внутри управляемой транзакции, поведение также зависит от настройки `fallbackExecution`.

Для некритичного обновления локального кэша такая потеря может быть приемлема при ограниченном TTL. Для обязательного внешнего эффекта нужен сохраняемый механизм: например, запись outbox вместе с заказом в одной транзакции, отдельная отправка с повтором и идемпотентность получателя. Если отправка завершилась, а отметка результата не сохранилась, повтор возможен — «ровно один вызов» обещать нельзя.

На интервью сначала называют требование к потере и дубликатам, затем выбирают механизм. Ошибка — считать `@Async` гарантией доставки или полагать, что событие после commit автоматически запускает новую надёжную транзакцию для всей работы слушателя. Фаза вызова, управление транзакцией и устойчивое хранение — разные свойства.

### 29. Почему JPA entity, DTO HTTP API и доменная модель не всегда должны быть одним классом?

Эти модели меняются по разным контрактам. Entity описывает persistence и жизненный цикл в JPA, HTTP DTO — публичный формат обмена, доменная модель — разрешённые состояния и переходы. Совместить их можно в простом приложении, но нужно понимать, какие зависимости это создаёт; отдельный класс на каждом шаге тоже не бесплатен.

Например, entity заказа содержит двусторонние связи, lazy-коллекцию строк и техническую версию. Прямая сериализация может вызвать дополнительные запросы, рекурсию по связям или ошибку доступа вне persistence context. Незаметное добавление поля в entity способно раскрыть внутренние данные клиенту. Это проблемы выбранного доступа и конфигурации, а не неизбежный результат каждой сериализации JPA.

Ответ API с явными полями, например `OrderView(id, status, total)`, фиксирует нужный контракт. Входной `CreateOrderRequest` не должен позволять клиенту задавать произвольный внутренний статус. Проверка допустимого перехода остаётся в прикладной/доменной логике: наличие DTO само по себе не обеспечивает бизнес-инвариант.

Для простого CRUD допустимо ограничиться DTO и entity, не создавая вторую полноценную модель заказа без причины. При сложных правилах или независимом развитии persistence отделение становится полезнее. Ошибка — делать универсальный mapper, который без разбора переносит все поля входного запроса в управляемую entity. Обсуждать разделение лучше на конкретном изменении: кто может менять поле, где проверяется инвариант и не изменится ли внешний контракт из-за внутренней миграции.

### 30. На подумать: платёжный HTTP-вызов выполняется внутри транзакции заказа. Где провести границу?

Метод `placeOrder()` помечен `@Transactional`: сохраняет заказ, вызывает платёжного провайдера и записывает результат. Провайдер иногда отвечает через 15 секунд; при timeout неизвестно, списались ли деньги. Пул БД — 20 соединений, параллельно приходит 100 запросов. Поможет ли вынести HTTP-вызов из транзакции?

<details>
<summary>Разбор</summary>

Это уменьшит время удержания соединения после обращения к БД, но само по себе не согласует две системы. Локальная транзакция не отменяет внешний платёж. Если провайдер списал деньги, а ответ потерялся, rollback заказа не вернёт списание автоматически. Увеличение пула тоже не решает неопределённость и может лишь отложить насыщение.

Один вариант: короткой транзакцией сохранить заказ в `PAYMENT_PENDING` и стабильный идентификатор платёжной попытки; после commit вызвать провайдера с тем же ключом идемпотентности; следующей короткой транзакцией сохранить подтверждённый результат. Повторный запрос не создаёт новый ключ только потому, что предыдущий завершился timeout. При неизвестном исходе выполняют сверку статуса по контракту провайдера, а не сразу объявляют платёж неуспешным.

Между шагами возможен crash, поэтому незавершённые попытки должны быть обнаружимы и возобновляемы: worker, журнал задач или outbox в зависимости от требований к синхронному ответу. Изменения статуса защищают от конкуренции и повторного подтверждения; учитывают истечение резервов и отмену заказа.

Критерии ответа: короткие транзакции, явные промежуточные состояния, стабильная идентичность операции, восстановление после сбоя и измеримые таймауты. Опасный ответ — «обернуть всё в `@Transactional`, тогда будет атомарно»: HTTP-провайдер в эту транзакцию не входит. Допустимо и другое решение, если оно объясняет все окна отказа и требуемый результат пользователя.

</details>
