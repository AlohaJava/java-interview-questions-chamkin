## Принципы SOLID

### 1. Что такое принципы SOLID? Подробный разбор каждого принципа.

**Ответ:**

SOLID — это акроним, объединяющий пять базовых принципов объектно-ориентированного программирования и проектирования, сформулированных Робертом Мартином. Их соблюдение позволяет создавать гибкие, масштабируемые и легко поддерживаемые системы.

**1. S — Single Responsibility Principle (Принцип единственной ответственности)**
Каждый класс должен иметь одну и только одну причину для изменения. Это означает, что класс должен решать только одну задачу.
*Пример нарушения:* Класс `Order` хранит данные о заказе, рассчитывает налоги и отправляет email.
*Правильно:* Разделить на `Order` (данные), `TaxCalculator` (налоги) и `EmailSender` (уведомления).

```java
// Правильная реализация SRP
public class Order {
    private String id;
    private double totalAmount;
    // Геттеры, сеттеры
}

public class OrderRepository {
    public void save(Order order) {
        // Логика сохранения в БД
    }
}
```

**2. O — Open/Closed Principle (Принцип открытости/закрытости)**
Программные сущности должны быть открыты для расширения, но закрыты для модификации. Новое поведение должно добавляться путем написания нового кода (например, через наследование или реализацию интерфейсов), а не путем изменения старого.

```java
public interface DiscountPolicy {
    double applyDiscount(double amount);
}

public class VipDiscount implements DiscountPolicy {
    @Override
    public double applyDiscount(double amount) {
        return amount * 0.8;
    }
}
// Добавление новой скидки не требует изменения старого кода.
```

**3. L — Liskov Substitution Principle (Принцип подстановки Барбары Лисков)**
Объекты в программе могут быть заменены их наследниками без изменения свойств программы. Подклассы не должны изменять ожидаемое поведение базового класса.
Формально это контракт: наследник не может усиливать предусловия, ослаблять постусловия и нарушать инварианты базового класса.
*Пример нарушения:* Класс `Ostrich` (Страус) наследует класс `Bird` (Птица), но выбрасывает исключение в методе `fly()`. Канонический пример — `Square` наследует `Rectangle`: квадрат является прямоугольником математически, но ломает контракт `setWidth/setHeight` (у прямоугольника ширину можно менять независимо от высоты). Вывод: наследование строится по поведению, а не по отношению «is-a» из предметной области.

**4. I — Interface Segregation Principle (Принцип разделения интерфейса)**
Клиенты не должны зависеть от интерфейсов, которые они не используют. Лучше создать несколько узкоспециализированных интерфейсов, чем один "толстый".

```java
// Правильно
public interface Printer {
    void print(Document d);
}
public interface Scanner {
    void scan(Document d);
}
```

**5. D — Dependency Inversion Principle (Принцип инверсии зависимостей)**
Модули верхних уровней не должны зависеть от модулей нижних уровней. Оба типа модулей должны зависеть от абстракций. Абстракции не должны зависеть от деталей.

```java
public interface MessageSender {
    void sendMessage(String message);
}

public class NotificationService {
    private final MessageSender sender;

    // Зависимость инжектируется, класс не зависит от конкретной реализации
    public NotificationService(MessageSender sender) {
        this.sender = sender;
    }
}
```

### 2. К чему приводит нарушение принципов SOLID?

**Ответ:**

Нарушение принципов SOLID ведет к созданию так называемого "спагетти-кода" или монолитной, жестко связанной архитектуры. 
Основные последствия:
- **Жесткость (Rigidity):** Любое изменение требует каскадных изменений в других модулях.
- **Хрупкость (Fragility):** Изменения в одной части системы приводят к непредсказуемым ошибкам в совершенно других, казалось бы, не связанных частях.
- **Неподвижность (Immobility):** Код невозможно переиспользовать в других проектах или частях системы из-за сильной связности.
- **Вязкость (Viscosity):** Разработчику проще добавить "костыль", чем сделать правильно архитектурно, так как правильное изменение требует огромных усилий.
- **Сложность тестирования:** Классы, выполняющие множество функций или жестко зависящие от реализаций, крайне сложно покрыть модульными тестами.

У Роберта Мартина в списке design smells есть ещё три: **избыточная сложность** (over-engineering — абстракции «на вырост», которые не нужны), **избыточное повторение** (copy-paste вместо переиспользования) и **непрозрачность** (код, который трудно читать).

Частый follow-up — «а бывает ли вред от слепого следования SOLID?» Да: дробление на классы из одного метода и интерфейсы ради интерфейсов — тот же over-engineering. Принципы — ориентир, а не догма; рядом всегда упоминают KISS, DRY и YAGNI.

## Паттерны проектирования

### 3. Что такое паттерны проектирования и антипаттерны? Классификация паттернов.

**Ответ:**

**Паттерн проектирования** — это повторяемая архитектурная конструкция, представляющая собой решение типичной проблемы в рамках часто возникающего контекста проектирования. 
**Антипаттерн** — это часто используемое решение, которое в большинстве случаев является неэффективным или контрпродуктивным (например, "God Object", "Magic Numbers", "Spaghetti Code").

Классификация паттернов (по "Банде четырех" - GoF):
1. **Порождающие (Creational):** Решают задачи создания объектов, инкапсулируя логику инстанцирования (Singleton, Builder, Factory Method, Abstract Factory, Prototype).
2. **Структурные (Structural):** Отвечают за композицию классов и объектов, построение удобных структур (Adapter, Decorator, Facade, Proxy, Composite, Bridge, Flyweight).
3. **Поведенческие (Behavioral):** Решают задачи эффективной коммуникации и распределения обязанностей между объектами (Observer, Strategy, Template Method, Chain of Responsibility, Iterator, Command, State, Visitor).

В каталоге GoF (книга "Design Patterns", 1994) — 23 паттерна; позже появились и другие каталоги, например паттерны интеграции (EIP) и паттерны микросервисов.

Другие типичные антипаттерны: "Golden Hammer" (одно знакомое решение на все задачи), "Lava Flow" (мёртвый код, который боятся удалить), "Copy-Paste Programming". Отдельный частый follow-up: Singleton (см. вопрос 4) многие считают антипаттерном — он вводит глобальное состояние и мешает тестированию.

### 4. Паттерн Singleton (Одиночка) и его правильная реализация в Java.

**Ответ:**

**Singleton** гарантирует, что у класса есть только один экземпляр, и предоставляет к нему глобальную точку доступа.

Наиболее безопасная реализация в Java (по Джошуа Блоху, Effective Java) — через `enum`:
```java
public enum Singleton {
    INSTANCE;
    
    public void doSomething() {
        // логика
    }
}
```

Почему enum: потокобезопасность и единственность гарантирует сам JVM при загрузке класса, плюс закрыты две классические дыры — десериализация (у enum нельзя создать второй экземпляр через `readObject`) и атака через reflection (рефлексией enum не инстанцировать).

Реализация с отложенной инициализацией (Double-Checked Locking):
```java
public class SingletonDCL {
    private static volatile SingletonDCL instance;

    private SingletonDCL() {}

    public static SingletonDCL getInstance() {
        if (instance == null) {                 // 1-я проверка без лока
            synchronized (SingletonDCL.class) {
                if (instance == null) {         // 2-я проверка внутри лока
                    instance = new SingletonDCL();
                }
            }
        }
        return instance;
    }
}
```

`volatile` здесь обязателен, и это частый follow-up. Без него другой поток может увидеть не-null ссылку на ещё не полностью сконструированный объект: `new` под капотом — это выделение памяти, вызов конструктора и запись ссылки, и JMM разрешает переставить запись ссылки раньше завершения конструктора. `volatile` запрещает такую перестановку и гарантирует видимость (happens-before между записью и чтением).

Более короткая ленивая альтернатива — идиома initialization-on-demand holder:
```java
public class SingletonHolder {
    private SingletonHolder() {}

    private static class Holder {
        static final SingletonHolder INSTANCE = new SingletonHolder();
    }

    public static SingletonHolder getInstance() {
        return Holder.INSTANCE;
    }
}
```
Вложенный класс загружается только при первом обращении к `getInstance()`, а сама загрузка классов потокобезопасна по спецификации — ни `synchronized`, ни `volatile` не нужны.

Минусы, о которых тоже спрашивают: singleton — замаскированное глобальное состояние. Он создаёт скрытые зависимости, мешает модульным тестам (состояние живёт между тестами, mock не подставить) и в среде с несколькими classloader'ами (Tomcat, плагины) перестаёт быть одиночкой. Поэтому в реальных проектах роль singleton обычно играет singleton-бин в DI-контейнере: единственность обеспечивает контейнер, а класс остаётся обычным и тестируемым.

### 5. Паттерн Builder (Строитель).

**Ответ:**

**Builder** позволяет создавать сложные объекты пошагово. Он отделяет конструирование сложного объекта от его представления.
Особенно полезен, когда объект имеет множество параметров, многие из которых опциональны, чтобы избежать антипаттерна "Telescoping Constructor".

```java
public class User {
    private final String firstName; // обязательный
    private final String lastName;  // обязательный
    private final int age;          // опциональный
    private final String phone;     // опциональный

    private User(UserBuilder builder) {
        this.firstName = builder.firstName;
        this.lastName = builder.lastName;
        this.age = builder.age;
        this.phone = builder.phone;
    }

    public static class UserBuilder {
        private final String firstName;
        private final String lastName;
        private int age;
        private String phone;

        public UserBuilder(String firstName, String lastName) {
            this.firstName = firstName;
            this.lastName = lastName;
        }

        public UserBuilder age(int age) {
            this.age = age;
            return this;
        }

        public UserBuilder phone(String phone) {
            this.phone = phone;
            return this;
        }

        public User build() {
            return new User(this);
        }
    }
}

// Использование:
User user = new User.UserBuilder("Ivan", "Ivanov").age(30).build();
```

Частый follow-up — «а что в реальных проектах?» Вручную билдер пишут редко: Lombok `@Builder` генерирует то же самое одной аннотацией. Для простых неизменяемых DTO с небольшим числом полей с Java 16 часто достаточно `record`. Рукописный Builder остаётся актуален там, где полей много, часть опциональна или нужна валидация в `build()` до создания объекта.

### 6. Паттерны Factory Method (Фабричный метод) и Abstract Factory (Абстрактная фабрика).

**Ответ:**

**Factory Method** определяет интерфейс для создания объекта, но оставляет подклассам решение о том, какой класс инстанцировать.

```java
public interface Document { void open(); }
public class PdfDocument implements Document { public void open() {} }

public abstract class Application {
    public abstract Document createDocument(); // Фабричный метод
    
    public void newDocument() {
        Document doc = createDocument();
        doc.open();
    }
}
```

**Abstract Factory** предоставляет интерфейс для создания семейств взаимосвязанных или взаимозависимых объектов, не специфицируя их конкретных классов.

```java
public interface GUIFactory {              // абстрактная фабрика
    Button createButton();
    Checkbox createCheckbox();
}

public class WinFactory implements GUIFactory {
    public Button createButton() { return new WinButton(); }
    public Checkbox createCheckbox() { return new WinCheckbox(); }
}
// Клиент работает с GUIFactory и получает согласованное семейство
// виджетов одной ОС, не зная конкретных классов.
```

Разница между двумя паттернами — стандартный follow-up. Factory Method создаёт один продукт и обычно строится на наследовании (подкласс переопределяет метод создания). Abstract Factory создаёт семейство согласованных продуктов и строится на композиции (объект-фабрика передаётся клиенту). Абстрактную фабрику выбирают, когда продукты должны быть совместимы между собой: виджеты одной ОС, драйвер и диалект одной БД.

Примеры из JDK и Spring: `Calendar.getInstance()` и `NumberFormat.getInstance()` — фабричные методы, `Collection.iterator()` — тоже; `DocumentBuilderFactory` — абстрактная фабрика; в Spring — `BeanFactory`/`FactoryBean`.

### 7. Паттерны Adapter (Адаптер) и Decorator (Декоратор).

**Ответ:**

**Adapter** позволяет объектам с несовместимыми интерфейсами работать вместе. Он выступает в роли "переводчика".

```java
public interface Usb { void connectWithUsb(); }
public class MicroUsbToUsbAdapter implements Usb {
    private final MicroUsb microUsb;
    public MicroUsbToUsbAdapter(MicroUsb microUsb) { this.microUsb = microUsb; }
    @Override
    public void connectWithUsb() {
        microUsb.connectWithMicroUsb();
    }
}
```

**Decorator** динамически добавляет объекту новые обязанности. Является гибкой альтернативой наследованию. Оборачивает объект, реализуя тот же интерфейс, и делегирует ему вызовы, при необходимости добавляя логику до или после вызова.

```java
public interface Notifier { void send(String message); }

public abstract class NotifierDecorator implements Notifier {
    private final Notifier wrappee;
    protected NotifierDecorator(Notifier wrappee) { this.wrappee = wrappee; }
    public void send(String message) { wrappee.send(message); }
}

public class SmsNotifier extends NotifierDecorator {
    public SmsNotifier(Notifier wrappee) { super(wrappee); }
    @Override
    public void send(String message) {
        super.send(message);   // сначала исходное поведение
        sendSms(message);      // потом добавленное
    }
}
// Классический пример из JDK — пакет java.io:
// new BufferedInputStream(new FileInputStream("f.txt"))
```

Разница между Adapter и Decorator — стандартный follow-up: Adapter меняет интерфейс объекта, Decorator меняет (расширяет) поведение, не меняя интерфейс. Proxy в отличие от обоих управляет доступом к объекту.

### 8. Паттерны Proxy (Заместитель) и Facade (Фасад).

**Ответ:**

**Proxy** предоставляет суррогат или объект-заместитель для контроля доступа к другому объекту. Полезен для ленивой инициализации, логирования, контроля доступа (Security Proxy) или удаленных вызовов.

```java
public interface Image { void display(); }

public class LazyImageProxy implements Image {
    private final String filename;
    private RealImage realImage;   // тяжёлый объект

    public LazyImageProxy(String filename) { this.filename = filename; }

    @Override
    public void display() {
        if (realImage == null) {
            realImage = new RealImage(filename);   // создаём при первом вызове
        }
        realImage.display();
    }
}
```

Прокси окружают нас повсюду, и это хороший ответ на follow-up «где видели вживую»: `java.lang.reflect.Proxy` (динамические прокси в JDK), Spring AOP — `@Transactional` и `@Cacheable` работают через прокси бинов (отсюда ловушка: самовызов метода внутри класса прокси обходит, и транзакция не сработает), ленивая загрузка ассоциаций в Hibernate — тоже прокси.

**Facade** предоставляет унифицированный высокоуровневый интерфейс к набору интерфейсов в подсистеме, что делает подсистему проще в использовании. Фасад скрывает сложность системы от клиента: вместо настройки пяти классов видеоконвертера клиент вызывает один метод `convert("file.mp4", "ogg")`. В реальных проектах роль фасада часто играет сервисный слой, за которым скрываются репозитории, внешние API и кэш. Пример из инфраструктуры — SLF4J: единый фасад над Logback, Log4j2 и JUL.

### 9. Паттерн Observer (Наблюдатель).

**Ответ:**

**Observer** определяет зависимость типа «один ко многим» между объектами таким образом, что при изменении состояния одного объекта все зависящие от него узнают об этом и обновляются автоматически. Это основа реактивного программирования (Reactive Streams, RxJava).

```java
public interface Observer { void update(String message); }

public class EventManager {
    private List<Observer> listeners = new ArrayList<>();
    
    public void subscribe(Observer listener) { listeners.add(listener); }
    public void notify(String event) {
        for (Observer listener : listeners) {
            listener.update(event);
        }
    }
}
```

Нюансы, которые ждут на собеседовании: классический `java.util.Observable` объявлен deprecated с Java 9 (мутабельный, синхронный, неудобный). На практике пишут свои интерфейсы, используют события Spring (`ApplicationEventPublisher` + `@EventListener`) или реактивные стеки. Ещё follow-up — push vs pull: в push-модели субъект сам передаёт данные в `update(...)`, в pull наблюдатель получает ссылку на субъект и забирает нужное сам; pull гибче, когда наблюдателям нужны разные части состояния.

### 10. Паттерн Strategy (Стратегия).

**Ответ:**

**Strategy** определяет семейство алгоритмов, инкапсулирует каждый из них и делает их взаимозаменяемыми. Паттерн позволяет изменять алгоритмы независимо от клиентов, которые ими пользуются. Способствует соблюдению принципа OCP.

```java
public interface PaymentStrategy { void pay(int amount); }

public class CreditCardPayment implements PaymentStrategy {
    public void pay(int amount) { /* логика оплаты картой */ }
}

public class ShoppingCart {
    public void checkout(int amount, PaymentStrategy strategy) {
        strategy.pay(amount);
    }
}
```

С Java 8 стратегии с одним методом часто пишут лямбдами: `PaymentStrategy` — функциональный интерфейс, и вместо отдельного класса достаточно `cart.checkout(amount, a -> chargeCard(a))`. Тот же приём использует JDK: `Comparator` — это стратегия сравнения, `list.sort((a, b) -> ...)`.

### 11. Паттерны Template Method (Шаблонный метод) и Chain of Responsibility (Цепочка обязанностей).

**Ответ:**

**Template Method** определяет костяк алгоритма в базовом классе, делегируя реализацию некоторых шагов подклассам. Сам шаблонный метод обычно объявляют `final`, чтобы подклассы не могли сломать последовательность.

```java
public abstract class DataImporter {
    public final void importData(String path) {      // шаблонный метод
        String raw = readFile(path);
        List<Row> rows = parse(raw);                 // шаг переопределяется
        save(rows);
    }
    protected abstract List<Row> parse(String raw);  // CsvImporter, JsonImporter...
    private String readFile(String path) { /* чтение файла */ }
    private void save(List<Row> rows) { /* запись в БД */ }
}
```

Примеры: `HttpServlet.service()` раскидывает запрос по `doGet/doPost`, а мы переопределяем шаги; `JdbcTemplate` в Spring — та же идея через callback.

**Chain of Responsibility** позволяет избежать жесткой привязки отправителя запроса к его получателю. Запрос передается по цепочке объектов, каждый из которых может обработать его или передать следующему.

```java
public abstract class SupportHandler {
    private SupportHandler next;
    public SupportHandler linkWith(SupportHandler next) { this.next = next; return next; }

    public void handle(Issue issue) {
        if (!tryHandle(issue) && next != null) {
            next.handle(issue);   // не справились — передаём дальше
        }
    }
    protected abstract boolean tryHandle(Issue issue);
}
```

Живой пример, который ждут на собеседовании, — цепочка сервлетных фильтров (`FilterChain.doFilter`) и middleware в веб-фреймворках.

## System Design

### 12. Основные концепции System Design (Масштабирование, Балансировка нагрузки, Кэширование).

**Ответ:**

- **Вертикальное масштабирование (Scale-Up):** Увеличение ресурсов одного узла (больше RAM, CPU). Имеет физический предел и единую точку отказа.
- **Горизонтальное масштабирование (Scale-Out):** Добавление новых узлов в систему. Практически безгранично, но требует сложных подходов (балансировка, распределенные транзакции).
- **Балансировка нагрузки (Load Balancing):** Распределение входящего сетевого трафика между группой серверов для обеспечения высокой доступности и надежности (алгоритмы: Round Robin, Least Connections, IP Hash).
- **Кэширование:** Сохранение копии данных во временном хранилище для быстрого доступа. Снижает нагрузку на БД (Redis, Memcached). Важные концепции: стратегии вытеснения (LRU - Least Recently Used) и инвалидация кэша.

Из того же базового набора, о чём спрашивают дальше: репликация БД (мастер на запись, реплики на чтение), шардирование (горизонтальное разбиение данных по ключу), CDN для статики (кэш ближе к пользователю) и асинхронность через очереди сообщений для сглаживания пиков нагрузки.

### 13. CAP-теорема и выбор базы данных (SQL vs NoSQL).

**Ответ:**

**CAP-теорема** утверждает, что распределенная система хранения данных не может одновременно обеспечивать более двух из трех свойств:
1. **Consistency (Согласованность):** Все узлы видят одни и те же данные в один и тот же момент времени.
2. **Availability (Доступность):** Каждый запрос получает успешный ответ, но без гарантии, что это самая последняя версия данных.
3. **Partition tolerance (Устойчивость к разделению):** Система продолжает работать несмотря на потерю связи между узлами.
В условиях сетевых разделений (P) система должна выбирать между C (согласованностью) и A (доступностью).

Типичные примеры, которые ждут на follow-up: Cassandra и DynamoDB — AP-системы (отвечают всегда, сходятся eventually); ZooKeeper, etcd, HBase — CP (при разделении часть узлов недоступна, но данные согласованы). PostgreSQL в одиночной установке вне классификации — CAP про распределённые системы. Современное уточнение теоремы — PACELC: даже без разделения (Else) система выбирает между Latency и Consistency.

- **SQL (Реляционные):** Гарантируют ACID-свойства, строгую схему. Подходят для сложных транзакций (финансы). Обычно масштабируются вертикально.
- **NoSQL (Нереляционные):** Гибкая схема, отлично масштабируются горизонтально. Выбирают компромисс в сторону доступности (BASE-архитектура — Basically Available, Soft state, Eventually consistent). Подходят для больших объемов неструктурированных данных. Уточнение на случай follow-up: «NoSQL = без транзакций» — миф; MongoDB поддерживает многодокументные ACID-транзакции, а PostgreSQL умеет горизонтально масштабироваться через реплики на чтение и шардирование (Citus).

### 14. Монолитная и Микросервисная архитектуры.

**Ответ:**

- **Монолит:** Все компоненты приложения (UI, бизнес-логика, доступ к данным) упакованы в один артефакт. 
  *Плюсы:* Прост в разработке, тестировании и первоначальном развертывании. 
  *Минусы:* При росте кодовой базы усложняется масштабирование, замедляется процесс сборки, жесткая привязка к одному технологическому стеку.
- **Микросервисы:** Приложение разбито на набор небольших, независимых сервисов, каждый из которых работает в своем процессе и взаимодействует через легковесные механизмы (REST, gRPC, очереди сообщений).
  *Плюсы:* Независимое масштабирование и развертывание, возможность использовать разный стек технологий, изоляция сбоев.
  *Минусы:* Сложность сетевого взаимодействия, распределенные транзакции (Saga), сложность мониторинга и отладки.

Ещё два момента, которые спрашивают. Первый — модульный монолит: один артефакт, но внутри строгие границы модулей; часто это разумная стартовая точка, из которой модули выделяются в сервисы по мере роста. Второй — антипаттерн «распределённый монолит»: формально микросервисы, но они деплоятся и падают вместе из-за жёстких синхронных связей и общей БД. Правило выбора: микросервисы решают организационные проблемы (независимые команды, независимые релизы) ценой технической сложности, поэтому для маленькой команды монолит почти всегда правильнее.

### 15. Redis: основные структуры данных и типовые сценарии (кэш, сессии, rate limiter, pub/sub).

**Ответ:**

Redis — in-memory хранилище ключ-значение: данные в памяти, операции занимают микросекунды. Поэтому его ставят перед БД как кэш и используют везде, где важна скорость.

Основные структуры:

- **String** — байтовая строка (до 512 МБ). Кэш объектов (JSON), счётчики (`INCR` атомарен), токены, флаги.
- **Hash** — набор полей внутри одного ключа. Объекты с полями: профиль пользователя, сессия. Можно обновить одно поле, не читая объект целиком.
- **List** — связный список. Простые очереди (`LPUSH` + `BRPOP`), лента последних N событий (`LPUSH` + `LTRIM`).
- **Set** — неупорядоченное множество уникальных элементов. Теги, «кто лайкнул», пересечения (`SINTER` — общие друзья).
- **Sorted Set (ZSet)** — множество, где у каждого элемента есть score. Лидерборды, отложенные очереди (score = время выполнения), sliding window rate limiter.

Типовые сценарии:

1. **Кэш.** Ключ — идентификатор сущности, значение — сериализованный объект. TTL ставим всегда, иначе кэш превращается в свалку устаревших данных.
2. **Сессии.** `SET session:<id> <payload> EX 1800`. Быстро, легко шарить между инстансами приложения, сессия протухает сама.
3. **Rate limiter.** Классика — `INCR` + `EXPIRE` на ключ вида `rate:<user>:<minute>`, либо ZSet для sliding window.
4. **Pub/Sub.** `PUBLISH`/`SUBSCRIBE` для рассылки событий. Ловушка в том, что это fire-and-forget: если подписчик офлайн, сообщение потеряно. Нужна надёжность — Redis Streams или Kafka.

**Инвалидация и TTL.** Три рабочих подхода:
- TTL на каждый ключ, плюс jitter (случайная добавка), чтобы тысячи ключей не истекли одновременно;
- явное удаление ключа при записи в БД (паттерн Cache-Aside, см. следующий вопрос);
- версионирование ключей: `user:42:v7` — при изменении данных меняется версия, старые ключи вымываются по TTL.

Частый follow-up — «что будет, если все одновременно промахнутся мимо кэша?» (cache stampede). Ответы: request coalescing (один поток идёт в БД, остальные ждут), распределённые локи, прогрев кэша.

### 16. Паттерны кэширования: Cache-Aside, Read-Through, Write-Through и Write-Behind.

**Ответ:**

Паттерны отличаются тем, кто отвечает за синхронизацию кэша и БД и в какой момент это происходит.

**Cache-Aside (Lazy Loading)** — самый частый вариант: приложение работает с кэшем само.

```text
Чтение:                          Запись:
App → Cache: GET key             App → DB: UPDATE
  ├─ hit  → вернуть              App → Cache: DELETE key
  └─ miss → App → DB: SELECT
            App → Cache: SET key (+TTL)
```

Плюсы: в кэше лежит только реально запрошенное, падение кэша не фатально — просто идём в БД. Минусы: промах = тройная задержка (кэш → БД → кэш), данные могут устареть до истечения TTL.

**Read-Through** — то же самое, но логика промаха живёт внутри самого кэша: приложение всегда спрашивает кэш, а тот сам ходит в БД. Код приложения проще, но нужен кэш или прослойка, которая это умеет.

**Write-Through** — запись идёт синхронно в кэш и в БД:

```text
App → Cache: SET → Cache → DB: INSERT/UPDATE → ответ клиенту
```

Плюсы: кэш всегда консистентен с БД, чтение почти всегда hit. Минусы: запись медленнее (два синхронных вызова); в кэше оседает то, что, возможно, никто не читает — поэтому обычно комбинируют с TTL.

**Write-Behind (Write-Back)** — запись сразу попадает в кэш, а в БД сбрасывается асинхронно пачкой:

```text
App → Cache: SET → ответ клиенту
                  Cache → DB: batch flush (асинхронно)
```

Плюсы: минимальная латентность записи, частые апдейты одного ключа схлопываются в одну запись в БД. Минусы: при падении кэша до сброса данные теряются, БД отстаёт — для денег так делать нельзя.

На практике чаще всего встречается Cache-Aside + TTL, остальные — там, где есть особые требования к консистентности или латентности записи.

## Инфраструктура и DevOps

### 17. Docker: образ, контейнер, слои и кэш Dockerfile. Best practices.

**Ответ:**

**Образ** — неизменяемый шаблон из read-only слоёв (базовая ОС, зависимости, jar). **Контейнер** — запущенный экземпляр образа: изолированный процесс плюс тонкий writable-слой поверх слоёв образа.

**Слои и кэш.** Каждая инструкция Dockerfile (`FROM`, `RUN`, `COPY`) создаёт слой. При пересборке Docker идёт сверху вниз и берёт слои из кэша до первой изменившейся инструкции — от неё всё пересобирается заново. Отсюда правило: то, что меняется редко, ставим выше; свой код — ниже. Для Java-проекта это значит: сначала копируем `pom.xml` и качаем зависимости, и только потом копируем исходники — тогда правка кода не гоняет скачивание зависимостей заново.

```dockerfile
# --- stage 1: сборка ---
FROM maven:3.9-eclipse-temurin-21 AS build
WORKDIR /app
COPY pom.xml .
RUN mvn dependency:go-offline
COPY src ./src
RUN mvn package -DskipTests

# --- stage 2: рантайм ---
FROM eclipse-temurin:21-jre
WORKDIR /app
RUN useradd -r appuser
COPY --from=build /app/target/app.jar app.jar
USER appuser
ENTRYPOINT ["java", "-jar", "app.jar"]
```

Best practices, которые ждут на собеседовании:
- **Multi-stage build** — собираем в тяжёлом образе с Maven, в прод несём только JRE и jar. Образ худеет с ~800 МБ до ~250 МБ.
- **`.dockerignore`** — исключаем `.git`, `target/`, локальные конфиги: меньше контекст сборки, не протекают секреты, не сбивается кэш.
- **Не root** — `USER appuser`: при взломе приложения атакующий не получает root в контейнере.
- Фиксированные теги вместо `latest` — воспроизводимость сборок.
- Один процесс на контейнер, логи в stdout.
- JVM в контейнере: современные JDK (11+) сами видят cgroup-лимиты, но хип лучше задавать явно через `-XX:MaxRAMPercentage`.

Частый follow-up: «чем контейнер отличается от виртуальной машины?» — контейнер разделяет ядро ОС с хостом (изоляция через namespaces и cgroups), ВМ виртуализирует железо и несёт своё ядро целиком.

### 18. Kubernetes для собеседования: Pod, Deployment, Service, Ingress, ConfigMap и Secret.

**Ответ:**

Kubernetes — оркестратор контейнеров: сам раскладывает их по нодам, перезапускает упавшие, масштабирует. Минимальный набор сущностей:

- **Pod** — наименьшая единица: один или несколько контейнеров с общей сетью и volumes. Напрямую поды почти не создают — ими управляют контроллеры.
- **Deployment** — декларативно описывает «хочу N реплик такого пода». Управляет ReplicaSet, умеет rolling update и откат (`kubectl rollout undo`).
- **Service** — стабильная точка входа к набору подов, у которых эфемерные IP. Типы: `ClusterIP` (внутри кластера), `NodePort`, `LoadBalancer`. Находит поды по label selector.
- **Ingress** — L7-маршрутизация снаружи внутрь: хосты, пути, TLS-терминация. Работает через ingress-контроллер (nginx, traefik).
- **ConfigMap / Secret** — конфигурация и чувствительные данные, подключаются как env-переменные или файлы. Secret отличается от ConfigMap в основном base64 и политиками доступа — шифрование включается отдельно.

Как выглядит путь запроса:

```text
client → Load Balancer → Ingress (TLS, host/path routing)
                       → Service (ClusterIP)
                       → Pod-1 / Pod-2 / Pod-3
```

Как происходит деплой новой версии:

```text
1. CI собрал image myapp:1.4.2 и запушил в registry
2. kubectl apply -f deployment.yaml (image: myapp:1.4.2)
3. API server пишет желаемое состояние в etcd
4. Scheduler выбирает ноды для новых подов
5. Kubelet на нодах тянет образ и стартует контейнеры
6. readinessProbe прошла → под добавляется в endpoints Service
7. Старые поды гасятся постепенно (rolling update)
```

Ловушка в том, что пока `readinessProbe` не зелёная, трафик на под не пойдёт — а если пробу не настроить, Kubernetes начнёт слать запросы на ещё не прогретое приложение. Второй частый follow-up: `livenessProbe` против `readinessProbe` — первая перезапускает под, вторая просто выводит его из-под трафика.

### 19. CI/CD и стратегии деплоя: rolling, blue-green и canary.

**Ответ:**

**CI (Continuous Integration)** — каждый коммит собирается и прогоняет тесты: быстрый фидбек, main всегда в рабочем состоянии. **CD** — либо Delivery (артефакт всегда готов к релизу, выкатка по кнопке), либо Deployment (выкатка автоматически после зелёного пайплайна).

**Rolling.** Инстансы обновляются партиями: подняли новый, погасили старый. Дефолт в Kubernetes (`maxSurge`, `maxUnavailable`).
- Плюсы: нулевой простой, лишних ресурсов почти не надо.
- Риски: какое-то время в проде живут две версии — API и схема БД должны быть обратно совместимы. Откат — тот же деплой в обратную сторону, то есть не мгновенный.

**Blue-Green.** Два идентичных окружения: blue (текущее) и green (новое). Деплоим в green, проверяем, переключаем трафик на балансировщике.
- Плюсы: мгновенный откат — переключить трафик обратно на blue.
- Риски: двойной расход ресурсов; главная боль — БД: обе версии работают с одной базой, поэтому миграции должны быть совместимы со старой версией (expand-migrate-contract).

**Canary.** Новая версия получает маленький процент трафика, смотрим метрики (ошибки, латентность) и постепенно наращиваем долю.
- Плюсы: баг ловится на 1–5% пользователей, а не на всех; решение принимают реальные метрики.
- Риски: нужна нормальная наблюдаемость и механизм распределения трафика (ingress-веса, service mesh); релиз растягивается по времени.

На практике rolling — рабочая лошадка, blue-green — когда критичен мгновенный откат, canary — для сервисов, где цена ошибки высока.

## System Design: практика

### 20. Rate limiting: алгоритмы token bucket, leaky bucket, fixed window и sliding window.

**Ответ:**

Rate limiter ограничивает число запросов от клиента за период. Алгоритмы отличаются тем, как считают и как ведут себя при всплесках.

**Fixed window counter.** Окно — календарная минута, внутри счётчик. Просто и дёшево, но на границе окон пропускает до 2x лимита: 100 запросов в 12:00:59 и ещё 100 в 12:01:00 — итого 200 запросов за две секунды.

**Sliding window log.** Храним timestamp каждого запроса и считаем за последние 60 секунд. Точно, но память растёт с числом запросов — при лимите 1000/мин это 1000 записей на клиента.

**Sliding window counter.** Компромисс: два соседних fixed-окна плюс взвешивание доли предыдущего. Погрешность небольшая, память константная.

**Token bucket.** В ведре N токенов, они пополняются со скоростью r в секунду; запрос тратит токен, нет токенов — отказ (429). Разрешает короткие пачки до N, средняя скорость не выше r. Так лимитируют большинство публичных API:

```text
        refill: +r tokens/sec
                ↓
        ┌─────────────────┐
        │  bucket (max N) │
        │   ●●●●○○        │
        └────────┬────────┘
  запрос → взять 1 токен → есть? пропускаем : 429 Too Many Requests
```

**Leaky bucket.** Запросы складываются в очередь и обрабатываются с фиксированной скоростью; очередь переполнилась — отказ. Всплесков не пропускает вообще, зато идеально сглаживает нагрузку на систему ниже.

Выбор: нужен средний лимит с допуском на пачки — token bucket; защитить медленный downstream — leaky bucket; дёшево и приблизительно — fixed или sliding counter.

Где реализуют: API gateway (nginx, Kong, Spring Cloud Gateway) или в приложении поверх Redis — счётчики общие для всех инстансов, атомарность через Lua-скрипт или связку `INCR` + `EXPIRE`.

### 21. Задача System Design: спроектируй URL shortener.

**Ответ:**

Классика жанра: сервис типа bit.ly — принимает длинный URL, отдаёт короткий, по короткому делает редирект.

**Оценка нагрузки** (примерные цифры, их озвучиваем интервьюеру):
- 100 млн новых ссылок в месяц → ~40 записей/сек;
- чтение:запись = 100:1 → ~4000 редиректов/сек;
- за 5 лет 6 млрд записей × ~500 байт ≈ 3 ТБ — помещается в одну приличную БД, шардирование нужно не сразу.

Система сильно read-heavy → кэш перед БД обязателен.

**Генерация короткого кода.** Алфавит base62 (`a-zA-Z0-9`): 7 символов дают 62⁷ ≈ 3,5 трлн комбинаций — с запасом. Два подхода:
1. **Счётчик → base62.** Уникальный id (sequence в БД, `INCR` в Redis или выдача диапазонов инстансам) кодируем в base62. Коллизий нет в принципе, но коды предсказуемы.
2. **Хэш.** MD5/SHA от URL, берём первые 7 символов, при коллизии бампим или добавляем соль. Детерминировано, но коллизии приходится обрабатывать.

На практике обычно выбирают счётчик: проще и без коллизий.

**Схема БД** — одна таблица:

```text
links
├─ short_code  VARCHAR(7)  PRIMARY KEY
├─ long_url    TEXT
├─ user_id     BIGINT       (nullable)
├─ created_at  TIMESTAMP
└─ expires_at  TIMESTAMP    (nullable)
```

**High-level схема:**

```text
client → LB → [app servers] (stateless)
                ├─→ Redis (кэш short_code → long_url, TTL)
                └─→ БД (мастер + read-реплики)
```

Чтение: ищем в Redis → промах → БД → прогреваем кэш. Запись: генерируем код, пишем в БД, можем сразу положить в кэш.

**Масштабирование:** app-серверы stateless — размножаем за LB; чтение разводим на реплики БД; при дальнейшем росте шардируем по `short_code`. Аналитику кликов выносим асинхронно через очередь, чтобы не тормозить редирект.

Частый follow-up — **301 или 302?** 301 (permanent) кэшируется браузером: меньше нагрузки на нас, но мы теряем статистику кликов и возможность поменять назначение. 302 (temporary) — каждый переход идёт через нас. Сервису с аналитикой нужен 302.

### 22. Как подходить к задаче System Design на собеседовании.

**Ответ:**

Задача открытая, и проверяют не «правильный ответ», а процесс: как собираете требования, считаете и выбираете компромиссы. Рабочая последовательность:

**1. Уточнение требований (5–10 минут).** Не рисовать ничего, пока не заданы вопросы: что именно делаем (2–3 ключевые фичи, остальное явно выносим за скобки), какой масштаб (DAU, RPS, read/write ratio), что важнее — консистентность или доступность, есть ли жёсткие требования к латентности. Интервьюер ждёт эти вопросы; пропуск шага — типичная ошибка.

**2. Прикидка на салфетке (back-of-envelope).** Считаем вслух порядки величин: QPS, объём хранилища на горизонте нескольких лет, трафик. Цель не точность, а понять, где узкое место: CPU, диск или сеть. Эти цифры потом оправдывают выбор компонентов: «нам хватит одной БД с репликами, шардирование пока не нужно».

**3. High-level дизайн.** Четыре-шесть блоков: клиент, балансировщик, app-серверы, кэш, БД, очередь. Плюс набросок API (3–5 эндпоинтов) и схемы данных. Идти сверху вниз, не ныряя в детали раньше времени.

**4. Углубление.** Спрашиваем интервьюера, куда копать, и детализируем один-два компонента: схему БД, алгоритм (как генерировать коды в URL shortener), поведение при отказе.

**5. Trade-offs и узкие места.** Проговариваем вслух: единая точка отказа, что сломается при росте в 10 раз, что выбрали и чем пожертвовали. Способность назвать слабые места собственного дизайна ценится выше самого дизайна.

Типичные ошибки: молча рисовать (думать надо вслух — это совместная работа, а не экзамен по памяти), начинать с микросервисов и Kafka там, где хватает монолита и PostgreSQL, не оставить время на trade-offs.
