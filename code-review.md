## Подход к ревью и обсуждение замечаний

### 1. Как отвечать на «поревьюйте этот код»

Сервис хранит число принятых заказов в поле `int accepted`. Метод обработки вызывает `accepted++`. Интервьюер показывает только этот фрагмент. С какого вопроса вы начнёте ревью? Какое замечание сможете доказать после ответа?

<details>
<summary>Разбор</summary>

Сначала выясните, какой результат нужен и кто имеет доступ к счётчику. Допустим, экземпляр сервиса общий для нескольких потоков и после завершения десяти заказов счётчик должен увеличиться на десять. Теперь можно показать потерю обновления. Два потока читают 7, каждый прибавляет 1 и записывает 8. Оба заказа приняты, а счётчик вырос на единицу.

Если счётчик хранится в одном процессе и нужен только атомарный инкремент, подойдёт `AtomicInteger.incrementAndGet()`. Для счётчика по нескольким экземплярам сервиса придётся уточнить, где сводятся результаты. Для финансового или другого долговечного учёта нужно также выяснить, что произойдёт при перезапуске процесса и повторной обработке заказа.

**Как проверить свою правку.** Задайте начальное значение, дождитесь завершения всех обработчиков и сравните разницу с количеством принятых заказов. Для демонстрации исходной гонки можно показать расписание двух чтений и двух записей. Один удачный параллельный прогон ещё допускает ошибку при другом расписании.

Для следующего фрагмента повторите ту же последовательность: сформулируйте контракт, покажите пример нарушения и предложите способ проверить исправление. Когда вывод зависит от настройки транзакции, владельца ресурса или входных данных, прямо назовите это условие.

</details>

### 10. Как проводить код-ревью в команде

В запросе на слияние вы нашли два замечания. При ошибке записи метод всё равно сообщает клиенту об успехе. Ещё локальную переменную назвали `data`. До релиза час. Какие комментарии вы оставите и при каком условии одобрите изменение?

<details>
<summary>Разбор</summary>

Сначала опишите наблюдаемое последствие ошибки записи. Например, «Если база отклонит изменение, клиент получит подтверждение и покажет пользователю сохранённый заказ. После обновления страницы заказ исчезнет. Предлагаю согласовать ответ при сбое и добавить тест с отказом БД». Назовите это условием слияния, если контракт обещает подтверждать только сохранённые заказы.

Переименование стоит предложить отдельно, если оно объясняет смысл данных. Например, `pendingOrders` помогает понять, какие заказы попали в выборку. Автор сможет обсудить название, пока готовит исправление блокирующего дефекта.

**Когда можно одобрить.** Посмотрите на фактический путь ошибки и проверку: отказ записи приводит к согласованному результату, успешная запись по-прежнему подтверждается. Если автор ссылается на повторную попытку клиента, уточните, как клиент узнает о сбое при полученном успехе. На собеседовании можно дополнить ответ случаем из своей команды и объяснить, как удалось договориться о критерии готовности.

</details>

## Контракты Java и работа с коллекциями

### 4. Сниппет: equals, hashCode и коллекции

```java
public class Employee {
    private String department;
    private Long personnelNumber;

    public Employee(String department, Long personnelNumber) {
        this.department = department;
        this.personnelNumber = personnelNumber;
    }

    public void setDepartment(String department) {
        this.department = department;
    }

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (o == null || getClass() != o.getClass()) return false;
        Employee employee = (Employee) o;
        return department.equals(employee.department)
                && personnelNumber.equals(employee.personnelNumber);
    }
}

public class SalaryRegistry {
    private final Map<Employee, BigDecimal> salaries = new HashMap<>();

    public void assignSalary(Employee employee, BigDecimal salary) {
        salaries.put(employee, salary);
    }

    public BigDecimal findSalary(Employee employee) {
        return salaries.get(employee);
    }

    public boolean isCached(Long personnelNumber, Long cachedNumber) {
        return personnelNumber == cachedNumber;
    }
}
```

Найдите проблемы.

<details>
<summary>Разбор</summary>

1. **`equals` без `hashCode`.** Контракт нарушен: два равных по `equals` объекта могут иметь разные `hashCode()`. Хеш `Object` не обязан быть адресом и не обязан быть уникальным. `Employee` используется как ключ `HashMap`, поэтому `findSalary(new Employee("IT", 42L))` может вернуть null, хотя равный сотрудник уже лежит в мапе: `get` сначала ищет bucket по хешу, а тот не совпадёт. Правило простое: переопределяете `equals` — всегда переопределяйте `hashCode` (в идеале — `Objects.hash(department, personnelNumber)` или генерация IDE).

2. **Мутация ключа в мапе.** У `Employee` есть сеттер `setDepartment`, а `department` участвует в `equals` (и, после починки, в `hashCode`). Если сотрудник уже лежит ключом в `HashMap`, и кто-то переведёт его в другой отдел — хеш ключа изменится, а объект останется в старом bucket'е. Запись «потеряется»: `get` и даже `containsKey` перестанут её находить, а в `keySet()` она при этом будет видна. Классическая причина, почему ключи коллекций должны быть immutable: поля ключа — final, сеттеров нет.

3. **Сравнение `Long` через `==`.** В `isCached` сравниваются два `Long` оператором `==`, а он сравнивает ссылки, не значения. Для значений −128..127 ссылки, полученные через `Long.valueOf`, совпадут; для других значений полагаться на идентичность нельзя. Прямое создание объектов тоже меняет картину. Самое коварное, что на маленьких тестовых данных код «работает», а в проде с реальными номерами ломается. Лечится `Objects.equals(a, b)` или распаковкой в `long` с проверкой на null.

4. `department.equals(...)` и `personnelNumber.equals(...)` требуют non-null полей. Это нужно обеспечить в конструкторе или определить равенство через `Objects.equals`. Возврат отсутствия зарплаты через `null` допустим при явном контракте; `Optional` — вариант API, а не обязательное исправление.

Практичнее отделить неизменяемый идентификатор от изменяемых данных сотрудника:

```java
record EmployeeKey(long personnelNumber) {}

final class SalaryRegistry {
    private final Map<EmployeeKey, BigDecimal> salaries = new HashMap<>();

    void assignSalary(EmployeeKey key, BigDecimal salary) {
        salaries.put(Objects.requireNonNull(key), Objects.requireNonNull(salary));
    }

    Optional<BigDecimal> findSalary(EmployeeKey key) {
        return Optional.ofNullable(salaries.get(key));
    }

    boolean isCached(Long number, Long cached) {
        return Objects.equals(number, cached);
    }
}
```

Это корректно, если табельный номер глобально уникален. Если номер уникален только в организации, организация тоже должна входить в ключ. Операции ожидаемо O(1), память O(n).

</details>

### 14. Сниппет: удаление элементов при обходе

Код должен удалить все отрицательные значения из изменяемого `ArrayList<Integer>` без null:

```java
void removeNegative(List<Integer> values) {
    for (Integer value : values) {
        if (value < 0) values.remove(value);
    }
}
```

Пройдите фрагмент вручную на списках из двух и трёх отрицательных чисел. Что останется в каждом случае и получит ли вызывающий код исключение?

<details>
<summary>Разбор</summary>

Enhanced for использует iterator, но удаление идёт через сам список. В результате нарушается протокол обхода. Fail-fast итератор способен бросить `ConcurrentModificationException` и в одном потоке. Это не механизм синхронизации и не гарантированная диагностика: некоторые последовательности приведут к преждевременному завершению обхода без исключения. Тест «у меня не упало» корректность не доказывает.

Здесь `value` имеет тип `Integer`, поэтому выбран `remove(Object)`. Если заменить его на `int`, будет вызван `remove(int index)`: исчезнет элемент по индексу либо появится `IndexOutOfBoundsException`.

```java
void removeNegative(List<Integer> values) {
    values.removeIf(value -> value < 0);
}
```

Контракт требует изменяемый список и non-null элементы. У `ArrayList` в Java 17–21 bulk-удаление выполняется за O(n), перемещая оставшиеся элементы, и использует служебную память для отметок. Нельзя переносить эту стоимость на произвольный `List`. Универсальный вариант — `Iterator.remove()`, но отдельные удаления из `ArrayList` могут суммарно стоить O(n²) из-за сдвигов; у связного списка иной профиль.

Проверьте пустой вход, два отрицательных подряд, отрицательные только в конце и все отрицательные. `List.of(...)` не соответствует контракту: удаление не поддерживается. Замена на concurrent-коллекцию ради однопоточного удаления скрывает проблему выбора API и меняет семантику.

</details>

### 15. Какие строки останутся в результате firstTen?

Сервис собирает маленький результат из большого изменяемого списка:

```java
List<String> firstTen(List<String> rows) {
    List<String> result = rows.subList(0, Math.min(10, rows.size()));
    rows.clear();
    return result;
}
```

Можно ли прочитать результат после выхода из метода? Покажите, что должен получить клиент для двенадцати входных строк и для пустого списка.

<details>
<summary>Разбор</summary>

`subList` — представление диапазона исходного списка. Изменения элементов видны через обе ссылки. Структурное изменение исходного списка в обход представления делает семантику представления неопределённой по контракту; у `ArrayList` дальнейшая работа обычно приводит к `ConcurrentModificationException`. Поэтому результат нельзя безопасно вернуть после `rows.clear()`.

Даже без `clear` маленькое представление `ArrayList` может сохранять ссылку на корневой список и удерживать его backing array. Если нужно независимое хранилище ссылок, скопируйте диапазон до изменения входа:

```java
List<String> firstTen(List<String> rows) {
    int end = Math.min(10, rows.size());
    List<String> result = new ArrayList<>(rows.subList(0, end));
    rows.clear();
    return result;
}
```

Предполагается изменяемый список, эксклюзивный доступ и осознанное требование очистить вход. Если очистка не нужна бизнесу, её лучше убрать. Для `ArrayList` копирование первых k элементов стоит O(k) времени и памяти, очистка входа — O(n), поскольку освобождаются ссылки. Содержимое строк не копируется, но `String` immutable.

Проверьте размеры 0, 9, 10 и 11; после вызова вход пуст, результат содержит первые min(10, n) значений. Для списка изменяемых объектов копирование списка не обеспечивает глубокую независимость элементов: это нужно обсуждать отдельно, а не обещать «полную копию».

</details>

<a id="16-сниппет-comparator-переполнение-и-потерянные-элементы-treeset"></a>

### 16. В каком порядке диспетчер покажет заявки с разным приоритетом?

В коллекции должны сохраниться все заявки с уникальным id, отсортированные по приоритету:

```java
record Job(long id, int priority) {}

Set<Job> jobs = new TreeSet<>((a, b) -> a.priority() - b.priority());
jobs.add(new Job(1, Integer.MIN_VALUE));
jobs.add(new Job(2, Integer.MAX_VALUE));
jobs.add(new Job(3, Integer.MAX_VALUE));
```

Назовите все заявки, которые должны попасть в результат, и их порядок. Сравните это с поведением фрагмента.

<details>
<summary>Разбор</summary>

Вычитание `int` может переполниться и поменять знак. Например, MIN_VALUE − MAX_VALUE даёт положительное значение, хотя первый приоритет меньше. Более того, для MIN_VALUE и 0 оба направления сравнения могут оказаться отрицательными: нарушается требование противоположных знаков.

Вторая проблема независима от переполнения: `TreeSet` считает элементы одинаковыми по результату comparator == 0. Две разные заявки с одинаковым приоритетом сольются в одну. Нельзя «починить» это возвратом 1 вместо 0: тогда нарушится контракт сравнения объекта с самим собой.

```java
Comparator<Job> byPriorityThenId = Comparator.comparingInt(Job::priority)
        .thenComparingLong(Job::id);
Set<Job> jobs = new TreeSet<>(byPriorityThenId);
```

Так заявки с одинаковым приоритетом и разными id сохранятся, порядок будет детерминированным. Для record `Job` сравнение равно 0 ровно при равенстве обоих компонентов, что согласовано с `equals`. Если бизнес считает id единственной идентичностью, нужен отдельный индекс по id; сортирующий `TreeSet` не проверит уникальность id с различными приоритетами.

Вставка и поиск O(log n), память O(n). Проверьте экстремальные приоритеты, одинаковые приоритеты разных id и повтор одной и той же записи. Результат comparator — отрицательное число, ноль или положительное число; он не обязан возвращать ровно −1/0/1. Поля, участвующие в сравнении элементов уже внутри дерева, менять нельзя.

</details>

<a id="17-сниппет-record-со-списком-не-становится-глубоко-immutable"></a>

### 17. Кто сможет изменить состав команды после создания DTO?

DTO объявлен immutable и передаётся между компонентами:

```java
record Team(List<String> members) {}

List<String> source = new ArrayList<>(List.of("Анна"));
Team team = new Team(source);
source.add("Борис");
team.members().clear();
```

Предскажите состав команды после каждой из двух последних строк. Какой контракт нужен компоненту, принявшему DTO?

<details>
<summary>Разбор</summary>

У record final-ссылка на список, но сам список остаётся изменяемым. Изменение `source` меняет DTO, а accessor `members()` возвращает ссылку, через которую можно очистить его содержимое. В `equals` и `hashCode` record участвует содержимое списка: если такой DTO используется ключом хеш-таблицы, мутация сломает и поиск ключа.

`Collections.unmodifiableList(source)` запрещает изменения через обёртку, но не закрывает доступ через `source`. Нужен независимый снимок:

```java
record Team(List<String> members) {
    Team {
        members = List.copyOf(members);
    }
}
```

Компактный конструктор присваивает компоненту уже скопированное значение. Снимок нельзя структурно менять, а строки immutable, поэтому для этой модели достаточно поверхностной копии. Вызов с null-списком или null-элементом завершится NPE: это осознанный контракт `List.copyOf`, а не случайная проверка.

Время и память построения O(n) в общем случае; повторное копирование уже подходящего immutable-списка реализация может оптимизировать. Accessor O(1), копировать список на каждом чтении не требуется. Проверьте мутацию исходного списка после создания, попытку `add` через accessor и пустой список. Если элементом станет изменяемый `Member`, структура останется закрытой, но `member.setName(...)` изменит наблюдаемое состояние: нужны immutable-элементы либо их защитные копии.

</details>

<a id="18-сниппет-tomap-теряет-бизнес-правило-при-дублях"></a>

### 18. Как построить индекс состояний по истории изменений?

Из событий требуется построить индекс последнего состояния по id:

```java
record Change(long id, long version, String value) {}

Map<Long, Change> index(List<Change> changes) {
    return changes.stream().collect(Collectors.toMap(Change::id, change -> change));
}
```

Два изменения одной записи пришли в обратном порядке версий. Какой результат нужен читателю индекса, в том числе при конфликтующих версиях?

<details>
<summary>Разбор</summary>

У `toMap` без merge-функции повтор ключа вызывает `IllegalStateException`. Добавление `(a, b) -> b` устраняет исключение, но лишь выбирает последнее встреченное значение для упорядоченного входа. Это не гарантирует максимальную бизнес-версию: старое событие может прийти позже нового.

Зафиксируем контракт: выбираем максимальную версию, точный дубль допустим, конфликт одной версии — ошибка. Значения `value` могут быть null, сами `Change` — нет.

```java
record ChangeKey(long id, long version) {}

Map<Long, Change> index(List<Change> changes) {
    Map<ChangeKey, Change> byVersion = new HashMap<>();
    for (Change change : changes) {
        ChangeKey key = new ChangeKey(change.id(), change.version());
        Change previous = byVersion.putIfAbsent(key, change);
        if (previous != null && !previous.equals(change)) {
            throw new IllegalArgumentException("Конфликт версии для id=" + change.id());
        }
    }
    return byVersion.values().stream().collect(Collectors.toMap(
            Change::id,
            change -> change,
            (left, right) -> left.version() >= right.version() ? left : right));
}
```

Полученная карта не обещает порядок обхода и конкретный тип. При валидном входе результат не зависит от перестановки событий, поскольку выбирается максимальная версия. Дополнительный индекс по `(id, version)` нужен именно для проверки всей истории: одна свёртка с выбором максимума способна скрыть конфликт старых версий после объединения с новой.

Ожидаемое время O(n), память O(u + k), где u — число различных пар `(id, version)`, k — число id. Проверьте пустой вход, точные дубли, старое событие после нового и конфликт исторической версии при наличии более новой. Нельзя выбирать merge-функцию только ради того, чтобы коллектор перестал падать: сначала требуется правило разрешения конфликтов.

</details>

<a id="19-сниппет-orelse-запускает-дорогую-операцию-даже-при-найденном-значении"></a>

### 19. Когда нужно обращаться к внешнему сервису за значением?

Сервис должен вернуть значение из кэша, если оно есть. Внешний вызов разрешён только для получения отсутствующего значения.

```java
String resolve(Optional<String> cached, Supplier<String> remoteCall) {
    return cached.orElse(remoteCall.get());
}
```

Сколько раз вызовется поставщик при заполненном и пустом кэше? Что получит клиент, если поставщик бросит исключение?

<details>
<summary>Разбор</summary>

До входа в `orElse` Java вычисляет его аргумент, поэтому `remoteCall.get()` выполнится независимо от наличия значения в `cached`. Только после этого `orElse` выберет результат. Если внешний вызов бросит исключение, метод завершится ошибкой даже при заполненном `Optional`.

```java
String resolve(Optional<String> cached, Supplier<String> remoteCall) {
    return cached.orElseGet(() -> Objects.requireNonNull(
            remoteCall.get(), "Удалённый сервис вернул null"));
}
```

`orElseGet` принимает вычисление, а не готовое значение: supplier вызывается только при пустом `Optional`. Контракт примера запрещает null-ответ fallback, поэтому проверка находится внутри ленивой ветви. `cached` и `remoteCall` также должны быть non-null.

Управляющая логика O(1), но стоимость пустой ветви равна стоимости внешнего вызова и может включать сеть. `Optional` не кэширует вычисление, не синхронизирует потоки и не предотвращает несколько одновременных remote-запросов: два вызова `resolve` с пустым значением выполнят fallback дважды. Если нужна загрузка один раз, это отдельная задача управления состоянием.

Проверьте supplier со счётчиком вызовов: при заполненном Optional счётчик остаётся 0, при пустом становится 1. Ещё случаи — исключение и null из fallback. `orElse("константа")` совершенно уместен для дешёвого готового значения; проблема здесь в нежелательном вычислении аргумента.

</details>

### 21. Что останется в списке после удаления единицы?

Ожидается изменяемый список чисел, из которого нужно удалить значение 1:

```java
int[] source = {1, 2, 3};
List<int[]> numbers = Arrays.asList(source);
numbers.remove(1);
```

Предскажите размер списка перед последней строкой. Что произойдёт при её выполнении и как проверить ожидаемый результат?

<details>
<summary>Разбор</summary>

`Arrays.asList(T...)` работает с ссылочными T. Примитивный `int` не подходит как generic-параметр, а весь `int[]` является объектом, поэтому результат — список из одного элемента, самого массива. Это не список из трёх Integer. Кроме того, `Arrays.asList` возвращает список фиксированного размера с общим хранилищем с массивом: `set` допустим, структурные `add`/`remove` — нет.

`remove(1)` выбирает перегрузку удаления по индексу, поскольку литерал имеет тип int. На этом неподходящем списке операция завершится исключением, а вовсе не удалит число 1. Даже для изменяемого `List<Integer>` такой вызов удалил бы второй элемент.

```java
int[] source = {1, 2, 3};
List<Integer> numbers = Arrays.stream(source)
        .boxed()
        .collect(Collectors.toCollection(ArrayList::new));
numbers.remove(Integer.valueOf(1)); // первая единица по значению
```

Здесь `Arrays.stream(int[])` создаёт `IntStream`, у которого действительно есть `boxed()`. Полученный `ArrayList` независим от массива и поддерживает удаление. Если нужно удалить все единицы, используйте `removeIf(value -> value == 1)`.

Преобразование O(n) по времени и памяти; удаление одного элемента по значению из ArrayList — O(n) из-за поиска и сдвига. Проверьте пустой массив, отсутствие 1 и несколько единиц. Замена на `Integer[]` исправит тип элементов `asList`, но не добавит поддержку изменения размера.

</details>

### 7. Сниппет: BigDecimal и деньги

```java
public class PaymentCalculator {

    public double calculateTotalWithCommission(double amount, double commissionRate) {
        double commission = amount * commissionRate;
        double total = amount + commission;
        return Math.round(total * 100) / 100.0;
    }

    public boolean isPaymentComplete(double paid, double expected) {
        return paid == expected;
    }

    public BigDecimal convertToPoints(double amount) {
        BigDecimal points = new BigDecimal(amount);
        return points.multiply(new BigDecimal("10"));
    }

    public BigDecimal splitBill(double total, int people) {
        BigDecimal bill = new BigDecimal(total);
        return bill.divide(new BigDecimal(people));
    }
}
```

Найдите проблемы.

<details>
<summary>Разбор</summary>

1. **`double` для денег.** Весь класс считает суммы в `double`, а double — бинарная арифметика с погрешностью: `0.1 + 0.2 != 0.3`. На комиссиях и округлениях ошибка копится и периодически «всплывает» в копейку — сводки не сойдутся, платёж не пройдёт сверку. Деньги считаются в `BigDecimal` (или в минорных единицах — копейках — в `long`). `Math.round(total * 100) / 100.0` — попытка округлить double, которая сама страдает от той же погрешности и теряет само понятие scale.

2. **Сравнение `double` через `==`.** `paid == expected` не гарантирует ожидаемую бизнес-семантику: `0.1 + 0.2 == 0.3` — это `false`. Некоторые значения представляются точно и сравнятся успешно; ошибка проявляется на конкретных вычислениях, а не на любом сравнении. Если уж сравнивать double — то с эпсилоном, но правильный ответ — `BigDecimal.compareTo` (не `equals`: у `equals` учитывается scale, `1.0` и `1.00` не равны) или сравнение в копейках.

3. **`new BigDecimal(double)`.** Конструктор от double берёт точное бинарное представление: `new BigDecimal(0.1)` — это `0.1000000000000000055511151231257827021181583404541015625`. Погрешность вносится на входе, и дальше BigDecimal честно её размножает. Правильно: `BigDecimal.valueOf(double)` (берёт каноническую строку) или лучше `new BigDecimal("0.1")` — от строки, когда значение известно на старте.

4. **Деление без scale и rounding mode.** `bill.divide(new BigDecimal(people))` для суммы, которая не делится нацело (100 / 3), бросит `ArithmeticException: Non-terminating decimal expansion`. В платёжном коде это 500-ка пользователю на обычном «разделить счёт». Нужно выбрать scale и режим округления по контракту, например `divide(divisor, 2, RoundingMode.HALF_EVEN)`. Но 100.00 / 3 → 33.33 на человека оставляет 0.01 нераспределённым: для точного распределения остаток назначают участникам в минорных единицах. `people <= 0` отклоняют.

```java
BigDecimal totalWithCommission(BigDecimal amount, BigDecimal rate) {
    if (amount.signum() < 0 || rate.signum() < 0) {
        throw new IllegalArgumentException("Отрицательная сумма или ставка");
    }
    return amount.multiply(BigDecimal.ONE.add(rate))
            .setScale(2, RoundingMode.HALF_EVEN);
}

boolean paymentComplete(BigDecimal paid, BigDecimal expected) {
    return paid.compareTo(expected) == 0;
}
```

Вход — не-null десятичные суммы одной валюты, ставка задана долей (`0.025` означает 2.5%). Здесь округляется только итог: если бизнес требует отдельно округлять комиссию, формула должна измениться. Сложность операций зависит от числа разрядов, считать BigDecimal безусловным O(1) нельзя.

</details>

### 8. Сниппет: строки и даты

```java
public class CsvExportService {

    private static final SimpleDateFormat DATE_FORMAT = new SimpleDateFormat("yyyy-MM-dd HH:mm:ss");

    public String buildCsv(List<Transaction> transactions) {
        String csv = "id;amount;date;status\n";
        for (Transaction tx : transactions) {
            csv += tx.getId() + ";"
                    + tx.getAmount() + ";"
                    + DATE_FORMAT.format(tx.getCreatedAt()) + ";"
                    + tx.getStatus() + "\n";
        }
        return csv;
    }

    public boolean isCompleted(Transaction tx) {
        return tx.getStatus().equals("COMPLETED");
    }

    public boolean sameReference(Transaction a, Transaction b) {
        return a.getReference() == b.getReference();
    }
}
```

Найдите проблемы.

<details>
<summary>Разбор</summary>

1. **`SimpleDateFormat` в static-поле.** `SimpleDateFormat` не thread-safe: внутри у него мутабельный `Calendar`, и конкурентные `format()`/`parse()` перемешивают его состояние. В многопоточном сервисе это даёт не исключение, а тихую порчу данных: в CSV периодически попадают даты с чужими годом или месяцем. Самая коварная ошибка в списке — тестами ловится плохо. Лечится `DateTimeFormatter` (immutable, thread-safe) + `java.time`, либо `ThreadLocal`, но это уже костыль прошлого.

2. **Конкатенация строк в цикле.** `csv += ...` на каждой итерации создаёт новый `String` и копирует всё накопленное содержимое: десять тысяч транзакций — квадратичная работа и куча мусора для GC. Компилятор оптимизирует конкатенацию внутри одного выражения, но не между итерациями цикла. Лечится `StringBuilder` (или запись в `Writer` без промежуточной строки, если файл большой).

3. **`equals` в неправильном порядке.** `tx.getStatus().equals("COMPLETED")` бросит NPE, если статус null — а для черновиков транзакций null-статус вполне реален. Константа слева (`"COMPLETED".equals(tx.getStatus())`) или `Objects.equals(...)` делает сравнение null-безопасным. На собеседовании стоит добавить: enum со сравнением `tx.getStatus() == Status.COMPLETED` тоже null-безопасен; вызов `.equals` на null-enum всё равно бросит NPE.

4. **`==` для строк.** `a.getReference() == b.getReference()` сравнивает ссылки. Иногда «работает» из-за interning и строковых литералов, поэтому баг любит прятаться в тестах, но две строки с одинаковым содержимым, пришедшие из разных источников (из БД и из запроса), дадут `false`. Лечится `Objects.equals(a.getReference(), b.getReference())`.

</details>

### 9. Сниппет: Optional и Stream API

```java
public class RecommendationService {

    private final ProductRepository productRepository;
    private final List<Product> blacklisted = new ArrayList<>();

    public String getDefaultCategoryName(long userId) {
        Optional<User> user = findUser(userId);
        return user.get().getPreferences().getDefaultCategory().getName();
    }

    public List<String> getTopProductNames(List<Long> ids, int limit) {
        List<String> names = new ArrayList<>();
        ids.stream()
                .map(productRepository::findById)
                .filter(Optional::isPresent)
                .map(Optional::get)
                .sorted((p1, p2) -> Double.compare(p2.getRating(), p1.getRating()))
                .limit(limit)
                .forEach(p -> {
                    names.add(p.getName());
                    if (p.getRating() < 3.0) {
                        blacklisted.add(p);
                    }
                });
        return names;
    }

    public List<Integer> getPrices(List<Product> products) {
        return products.stream()
                .map(Product::getPrice)
                .map(price -> price * 1.2)
                .boxed()
                .collect(Collectors.toList());
    }

    private Optional<User> findUser(long userId) {
        return Optional.empty();
    }
}
```

Найдите проблемы.

<details>
<summary>Разбор</summary>

1. **`optional.get()` без проверки.** Весь смысл `Optional` — заставить обработать отсутствие значения; `get()` без `isPresent()` отбрасывает эту защиту и бросает `NoSuchElementException` — фактически тот же NPE, только дороже читается. Здесь пользователь может не найтись, и метод упадёт. Нормальные варианты: `map(User::getPreferences).map(...).orElse("Без категории")`, `orElseThrow(() -> new UserNotFoundException(userId))`. Отдельно: цепочка `getPreferences().getDefaultCategory()` — ещё два кандидата на обычный NPE.

2. **Side-effect в `forEach`.** Стрим используется как цикл с побочными эффектами: наполняет внешний `names` и, что хуже, мутирует поле сервиса `blacklisted` — разделяемое состояние синглтон-бина. При параллельных запросах это race condition на `ArrayList` (а если кто-то добавит `.parallel()` — ещё и на самом стриме). Сборку результата надо делать через `collect(toList())`, а бизнес-эффект «добавить в чёрный список» — отдельным явным шагом после стрима, и не в поле сервиса, а в репозиторий. Плюс логика странная сама по себе: в «чёрный список» попадают только те товары, что прошли `limit`, — завтра лимит поменяют, и поведение молча изменится.

3. **Фрагмент `getPrices` не компилируется.** После `Stream<Product>.map(...)` получается объектный `Stream<R>`. У него нет метода `boxed()` — такой метод есть у `IntStream`, `LongStream`, `DoubleStream`. После умножения на `1.2` результат также не соответствует объявленному `List<Integer>`. Это ошибка типов, а не лишняя операция, которую можно оставить. Сначала определите денежный контракт, затем исправляйте API:

```java
record PricedProduct(BigDecimal price) {}

List<BigDecimal> getPrices(List<PricedProduct> products) {
    return products.stream()
            .map(PricedProduct::price)
            .map(price -> price.multiply(new BigDecimal("1.20"))
                    .setScale(2, RoundingMode.HALF_EVEN))
            .toList();
}
```

Здесь элементы и цена не-null, валюты совпадают, наценка округляется отдельно для каждой позиции. Получаем немодифицируемый список; если нужен изменяемый — `toCollection(ArrayList::new)`. По числу товаров — O(n) плюс стоимость десятичной арифметики и O(n) памяти результата.

4. Бонус для разговора: `filter(Optional::isPresent).map(Optional::get)` — идиома, которая на Java 9+ пишется как `.flatMap(Optional::stream)`.

</details>

### 22. В каком порядке диспетчер покажет ближайшие задания?

Диспетчер хранит сроки в `PriorityQueue<Integer>` с естественным порядком чисел. На экране нужны три самых ранних срока по возрастанию. После просмотра очередь должна остаться доступной обработчику. На время вызова у метода исключительный доступ к очереди.

```java
static List<Integer> preview(PriorityQueue<Integer> due) {
    return due.stream().limit(3).toList();
}
```

Какой тест отличит корректный предпросмотр от случайно удачного результата?

<details>
<summary>Разбор</summary>

Очередь гарантирует, что `peek()` и `poll()` обращаются к минимальному элементу при естественном порядке. Обход всей кучи, в том числе через stream, не обязан следовать этому порядку. Для четырёх сроков недостаточно проверить только голову.

```java
static List<Integer> preview(PriorityQueue<Integer> due) {
    var copy = new PriorityQueue<>(due);
    var next = new ArrayList<Integer>(3);
    while (next.size() < 3 && !copy.isEmpty()) {
        next.add(copy.remove());
    }
    return next;
}
```

Копия сохраняет порядок приоритета исходной очереди и оставляет оригинал целым. Если метод должен принимать очередь с произвольным компаратором, для вывода именно трёх самых ранних сроков используйте `due.stream().sorted().limit(3).toList()`; проверьте также очередь с обратным порядком. Цена — дополнительная память пропорционально размеру очереди. Если предпросмотр вызывают часто на огромной очереди, стоит измерить цену копирования.

**Проверка.** Добавьте по порядку 1, 4, 2, 3. Ожидайте список `[1, 2, 3]`. После вызова извлеките из исходной очереди все четыре числа по порядку. Добавьте проверки пустой очереди и одинаковых сроков. Тест не должен требовать конкретного внутреннего порядка обхода неотсортированной кучи.

</details>

### 23. Как обрезать название для экспорта?

Поле экспорта вмещает первые три кодовые точки Unicode. На входе корректный текст, включая эмодзи. Для строки короче лимита нужно вернуть её целиком.

```java
static String label(String text) {
    return text.substring(0, Math.min(text.length(), 3));
}
```

Что попадёт в экспорт для строки `"AB😀C"`? Предложите тест, проверяющий точный результат до сериализации.

<details>
<summary>Разбор</summary>

В строке `"AB😀C"` пять единиц UTF-16 и четыре кодовые точки. Смещение 3 проходит внутри суррогатной пары эмодзи. В результате останутся буквы и одиночный старший суррогат. При отображении или кодировании этого значения поведение может зависеть от обработчика некорректного текста.

```java
static String label(String text) {
    int end = 0;
    for (int n = 0; n < 3 && end < text.length(); n++) {
        end = text.offsetByCodePoints(end, 1);
    }
    return text.substring(0, end);
}
```

Проверяйте равенство результата строке `"AB😀"`, а для `"😀😀"` — исходной строке. Договоритесь о единице длины с владельцем формата. База с лимитом в байтах и интерфейс с лимитом в визуально воспринимаемых символах потребуют других правил. Например, буква с комбинируемым знаком может состоять из двух кодовых точек.

</details>

### 24. Куда добавить новое время отправления?

Список минут отсортирован по возрастанию и не содержит повторов. Метод должен вставить новое время либо сохранить расписание как есть, если такое время уже есть.

```java
static void addDeparture(List<Integer> times, int minute) {
    int index = Collections.binarySearch(times, minute);
    if (index < 0) times.add(-index, minute);
}
```

Проверьте расписание `[10, 30]` для трёх независимых вызовов с минутами 5, 20 и 40.

## Конкурентность, ресурсы и время жизни задач

### 2. Сниппет: многопоточный синглтон и счётчик

```java
public class RateLimiterService {

    private static RateLimiterService instance;

    private long totalRequests = 0;
    private final Map<String, Integer> requestsByClient = new HashMap<>();

    public static RateLimiterService getInstance() {
        if (instance == null) {
            synchronized (RateLimiterService.class) {
                if (instance == null) {
                    instance = new RateLimiterService();
                }
            }
        }
        return instance;
    }

    public void registerRequest(String clientId) {
        totalRequests++;
        Integer count = requestsByClient.get(clientId);
        if (count == null) {
            requestsByClient.put(clientId, 1);
        } else {
            requestsByClient.put(clientId, count + 1);
        }
    }

    public long getTotalRequests() {
        return totalRequests;
    }
}
```

Найдите проблемы.

<details>
<summary>Разбор</summary>

1. **Broken double-checked locking.** Паттерн написан правильно по форме, но поле `instance` не объявлено `volatile`. Без `volatile` второй поток может увидеть не-null ссылку на объект, чей конструктор ещё не отработал до конца (переупорядочивание инструкций: запись ссылки может произойти раньше инициализации полей объекта). Поток получит «полуинициализированный» синглтон. Лечится `private static volatile RateLimiterService instance`, а ещё лучше — вообще уйти от ручного DCL: enum-синглтон или holder-идиома (`private static class Holder { static final RateLimiterService INSTANCE = new RateLimiterService(); }`) — проще и безопаснее.

2. **Race condition на инкременте.** `totalRequests++` — это три операции (прочитать, прибавить, записать), и между ними вклинивается другой поток. При конкурентных вызовах счётчик теряет обновления. Классический пример неатомарного read-modify-write. Лечится `AtomicLong` и `incrementAndGet()`, либо синхронизацией всего метода.

3. **Непотокобезопасный `HashMap` под конкурентной записью.** `registerRequest` вызывается из многих потоков, а `HashMap` не thread-safe: конкурентные `put` могут не только терять записи, но и повредить внутреннюю структуру (на старых JDK — бесконечный цикл при resize). Плюс сам блок «get → проверка → put» — это check-then-act, тоже race. Лечится `ConcurrentHashMap` и `merge(clientId, 1, Integer::sum)` — атомарно и в одну строку.

4. Конструктор не закрыт: у public-класса без явного конструктора есть доступный public-конструктор, поэтому `getInstance()` не обеспечивает единственность экземпляра. Для singleton требуется private-конструктор. Отдельно статический singleton затрудняет изоляцию тестов из-за общего состояния.

Исправление отдельных полей через `AtomicLong` и `ConcurrentHashMap.merge` не делает обновление двух счётчиков одной атомарной операцией. Если читатель должен видеть согласованный снимок, нужен общий lock для регистрации и чтения снимка. Название `RateLimiterService` тоже требует вопроса: где окно времени, лимит и удаление старых clientId? Сейчас это накопительный счётчик с неограниченным ростом карты, а не ограничитель запросов.

Минимальный исправленный счётчик для одной JVM:

```java
final class RequestCounter {
    private long total;
    private final Map<String, Long> byClient = new HashMap<>();

    synchronized void register(String clientId) {
        Objects.requireNonNull(clientId);
        long nextTotal = Math.incrementExact(total);
        long nextClient = Math.incrementExact(byClient.getOrDefault(clientId, 0L));
        byClient.put(clientId, nextClient);
        total = nextTotal;
    }

    synchronized Map<String, Long> snapshot() {
        return Map.copyOf(byClient);
    }

    synchronized long total() {
        return total;
    }
}
```

Раздельные `snapshot()` и `total()` всё ещё относятся к разным моментам времени; если нужны вместе, возвращайте один объект снимка под тем же lock. Регистрация O(1) ожидаемо, копирование снимка O(k) по числу клиентов. Очистка и распределённый лимит — отдельные требования.

</details>

### 3. Сниппет: ресурсы и исключения

```java
public class ReportExporter {

    private final DataSource dataSource;

    public ReportExporter(DataSource dataSource) {
        this.dataSource = dataSource;
    }

    public void exportUserReport(long userId, String outputPath) throws Exception {
        Connection connection = dataSource.getConnection();
        PreparedStatement statement = connection.prepareStatement(
                "SELECT id, name, email, created_at FROM users WHERE id = " + userId);
        ResultSet rs = statement.executeQuery();

        FileInputStream template = new FileInputStream("templates/report.html");
        byte[] content = template.readAllBytes();

        try (FileWriter writer = new FileWriter(outputPath)) {
            if (rs.next()) {
                String report = new String(content)
                        .replace("${name}", rs.getString("name"))
                        .replace("${email}", rs.getString("email"));
                writer.write(report);
            }
        } catch (IOException e) {
        }

        rs.close();
        statement.close();
        connection.close();
    }
}
```

Найдите проблемы.

<details>
<summary>Разбор</summary>

1. **Ресурсы утекают при исключении.** `Connection`, `PreparedStatement` и `ResultSet` закрываются вручную в конце метода, а `FileInputStream` вообще не закрывается. Если любая строка выше бросит исключение (упал `executeQuery`, не нашёлся файл шаблона), до `close()` выполнение не дойдёт — соединение останется висеть в пуле, файловый дескриптор — открытым. При повторяющихся вызовах это исчерпает пул соединений или лимит файловых дескрипторов. Лечится try-with-resources на все четыре ресурса: они закроются в правильном порядке даже при исключении.

2. **Проглоченное исключение.** Пустой `catch (IOException e) {}` — худший вариант обработки: отчёт молча не запишется, вызывающий код решит, что всё хорошо, а в логах будет пусто. Как минимум — залогировать, как правило — пробросить дальше или завернуть в своё доменное исключение. «Молчаливый catch» на ревью — всегда первый кандидат в комментарии.

3. **`throws Exception` в сигнатуре.** Метод заявляет, что может бросить что угодно: вызывающий код не понимает, к чему готовиться, и вынужден либо ловить `Exception` (та же болезнь уровнем выше), либо тоже писать `throws Exception`, и зараза расползается по коду. Нужны конкретные типы: `SQLException`, `IOException` — или своё unchecked-исключение с понятным именем.

4. **SQL-инъекция как бонус.** `"... WHERE id = " + userId` — конкатенация вместо параметра. Здесь `userId` — `long`, поэтому реально проэксплуатировать не выйдет, но это повод на ревью потребовать привычку всегда писать `WHERE id = ?` и `statement.setLong(1, userId)`: завтра на это место кто-то поставит строку из запроса. Отдельно: шаблон читается при каждом вызове, хотя его можно загрузить один раз. Явно задайте UTF-8 при чтении и записи: default charset зависит от среды и версии JDK. Если шаблон — HTML, вставляемые имя и email нужно экранировать для конкретного HTML-контекста; простая подстановка не обеспечивает этого. Нужно также определить поведение при SQL NULL и отсутствии пользователя, иначе получится NPE или пустой отчёт вместо явного результата.

</details>

<a id="20-сниппет-future-с-таймаутом-не-останавливает-задачу"></a>

### 20. Что происходит с чтением отчёта через секунду?

Каждый запрос создаёт поток для чтения отчёта и ждёт максимум секунду:

```java
String load(Callable<String> task) throws Exception {
    ExecutorService executor = Executors.newSingleThreadExecutor();
    Future<String> future = executor.submit(task);
    return future.get(1, TimeUnit.SECONDS);
}
```

Разберите успешное чтение, превышение секунды и прерывание ожидающего потока. Кто отвечает за ресурсы после каждого исхода?

<details>
<summary>Разбор</summary>

`get` с таймаутом ограничивает ожидание вызывающего потока, а не выполнение задачи. После `TimeoutException` задача продолжит работу. Executor не закрывается ни при успехе, ни при ошибке, что на потоке запросов приведёт к утечке потоков. У сетевого клиента при этом нужны собственные connect/read/request deadlines: interrupt поддерживается не любой операцией.

Проще принимать executor с жизненным циклом приложения, а не создавать его на каждый запрос. Следующий метод им не владеет и не выключает его:

```java
String load(ExecutorService executor, Callable<String> task)
        throws InterruptedException, ExecutionException, TimeoutException {
    Future<String> future = executor.submit(task);
    try {
        return future.get(1, TimeUnit.SECONDS);
    } catch (TimeoutException | InterruptedException failure) {
        future.cancel(true);
        throw failure;
    }
}
```

Метод пробрасывает `InterruptedException`, передавая обработку вызывающему коду. Если на верхнем уровне его преобразуют в unchecked-исключение, там восстанавливают interrupt-флаг. `cancel(true)` лишь просит прервать работу; кооперативная задача проверяет interrupt и корректно освобождает ресурсы. При `ExecutionException` сама задача уже завершилась ошибкой; причину следует сохранить.

Проверьте успешную задачу, исключение внутри task, превышение таймаута и interrupt ожидающего потока. Размер пула и очереди должны быть ограничены по нагрузке, иначе накопление задач останется проблемой. Для Java 17 нельзя написать try-with-resources с `ExecutorService`: поддержка `AutoCloseable` появилась позже. Асимптотику обработки отчёта определяет task; таймаут не превращает её сложность в O(1).

</details>

### 12. Завершатся ли два встречных перевода?

Задача в лайвкодинг-формате: дан код перевода денег между двумя счетами. Нужно найти в нём проблему и исправить.

```java
public final class Account {
    private final long id;
    private long balance;

    public Account(long id, long balance) {
        this.id = id;
        this.balance = balance;
    }

    public long getId() {
        return id;
    }

    public long getBalance() {
        return balance;
    }

    public void withdraw(long amount) {
        balance -= amount;
    }

    public void deposit(long amount) {
        balance += amount;
    }
}
```

```java
public class TransferService {

    public void transfer(Account from, Account to, long amount) {
        // порядок блокировок выбираем по балансу:
        // сначала блокируем счёт с меньшим балансом
        Account first = from.getBalance() <= to.getBalance() ? from : to;
        Account second = (first == from) ? to : from;

        synchronized (first) {
            try {
                Thread.sleep(100); // имитация работы: например, запись в аудит-лог
            } catch (InterruptedException e) {
                Thread.currentThread().interrupt();
            }
            synchronized (second) {
                if (from.getBalance() < amount) {
                    throw new IllegalStateException("Недостаточно средств");
                }
                from.withdraw(amount);
                to.deposit(amount);
            }
        }
    }
}
```

```java
public class Main {
    public static void main(String[] args) {
        Account account1 = new Account(1, 10_000);
        Account account2 = new Account(2, 10_000);
        TransferService service = new TransferService();

        Thread thread1 = new Thread(() -> service.transfer(account1, account2, 1000));
        Thread thread2 = new Thread(() -> service.transfer(account2, account1, 2000));

        thread1.start();
        thread2.start();
    }
}
```

Рассмотрите два одновременных перевода между указанными счетами. Завершатся ли оба? Обоснуйте ответ последовательностью действий и предложите проверку. Затем разберите перевод на тот же счёт и случай недостаточного остатка.

<details>
<summary>Разбор</summary>

**Почему зависает.** Оба счёта стартуют с одинаковым балансом 10_000. Поток 1 переводит account1 → account2: балансы равны, условие `<=` выбирает `from`, то есть account1 — он захватывает блокировку account1 первым. Поток 2 переводит account2 → account1: по той же логике его `first` — account2. Дальше `sleep(100)` повышает вероятность такого чередования, но ничего не гарантирует: поток 1 держит account1 и ждёт account2, поток 2 держит account2 и ждёт account1. Каждый ждёт то, что держит другой, — циклическое ожидание, дедлок. Одновременно выполняются четыре условия Коффмана: взаимное исключение, удержание и ожидание, отсутствие вытеснения, циклическое ожидание. Ломаем любое — дедлока нет; проще всего сломать цикл, упорядочив захват блокировок.

**Почему баланс — неправильный критерий.** Во-первых, он изменяется: два перевода, идущие навстречу друг другу, могут вычислить порядок по разным снимкам состояния. Во-вторых, он может совпадать — как в примере, где равенство и даёт противоположные порядки. В-третьих, значение баланса два потока читают в разные моменты времени, и уже между чтением и захватом блокировки баланс мог поменяться. В-четвёртых, само чтение баланса — обращение к разделяемому состоянию, которое по-хорошему тоже требует синхронизации: получается, что для выбора блокировки уже нужна блокировка. Вывод: порядок захвата должен определяться неизменяемым уникальным значением. У счёта такое значение есть — `id`.

**Базовое исправление.**

```java
public void transfer(Account from, Account to, long amount) {
    Objects.requireNonNull(from, "from");
    Objects.requireNonNull(to, "to");
    if (amount <= 0) {
        throw new IllegalArgumentException("Сумма перевода должна быть положительной");
    }
    if (from == to) return; // по контракту self-transfer — no-op
    if (from.getId() == to.getId()) {
        throw new IllegalArgumentException("Разные объекты с одинаковым id");
    }

    Account first = from.getId() < to.getId() ? from : to;
    Account second = (first == from) ? to : from;

    synchronized (first) {
        synchronized (second) {
            if (from.getBalance() < amount) {
                throw new IllegalStateException("Недостаточно средств");
            }
            Math.addExact(to.getBalance(), amount); // проверяем ДО списания
            from.withdraw(amount);
            to.deposit(amount);
        }
    }
}
```

Теперь оба потока захватывают блокировки в одном глобальном порядке (сначала счёт с меньшим id), цикл невозможен, дедлок устранён. Заодно обработан перевод «самому себе»: без проверки `from == to` мы бы вошли в `synchronized` на одном объекте дважды (что само по себе безопасно — монитор реентрантен — но перевод себе бессмысленен, а в варианте с независимыми локами по id привёл бы к дедлоку потока с самим собой, если бы лок не был реентрантным).

**Можно ли `synchronized(account.getId())`?** Нет, по двум причинам. Первая: `id` здесь `long`, примитив — `synchronized` на примитиве просто не скомпилируется, синхронизироваться можно только на объекте. Вторая тоньше: если getter возвращает уже сохранённый `Long`, автоупаковки при вызове нет: возвращается та же ссылка поля. Но одинаковые id разных экземпляров всё равно не обязаны быть одним объектом, а кеш `Long.valueOf` может создавать нежелательные общие мониторы. Если же явно боксировать примитив при каждом вызове, ссылки за пределами кеша могут различаться. Поведение блокировки не должно зависеть от кеша обёрток — блокируются на стабильных объектах, чей жизненный цикл контролируете вы сами.

**Сильный ответ: разные объекты с одним id.** Решение предполагает ровно один `Account` на каждый id в одной JVM и единый протокол блокировок для всех чтений и записей баланса. Открытые `withdraw`, `deposit` и `getBalance` из исходной модели позволяют обойти этот протокол: их следует скрыть за сервисом либо защищать тем же монитором. Отрицательный исходный баланс нужно отклонить в конструкторе, а переполнение получателя — проверить до списания, как показано выше.

Два загруженных из repository экземпляра одного счёта содержат независимые копии баланса. Даже общий `ReentrantLock` по id не превращает их в единое состояние: после захвата lock нужно прочитать актуальный баланс из общего хранилища и атомарно сохранить оба изменения. Для БД используйте транзакцию с блокировками строк в порядке id либо версии и повтор операции целиком. Реестр локов имеет смысл только вместе с корректной моделью состояния; он не исправляет stale copy сам по себе. Простое удаление «свободного» lock из карты опасно: другой поток уже мог получить ссылку на него, а третий создаст новый lock для того же id.

**Проверка средств — до или после блокировок?** Только внутри критической секции. `if (from.getBalance() < amount)` до захвата блокировок — это check-then-act: между проверкой и списанием другой перевод может снять деньги, и баланс уйдёт в минус. Проверять можно и дважды (до — как дешёвый фильтр, чтобы зря не захватывать локи; и обязательно внутри — как гарантию), но проверка внутри секции не опциональна.

**Как оценивать ответ кандидата:**

- Middle−: видит дедлок, предлагает упорядочить захват по id.
- Middle: объясняет, почему баланс не подходит; проверку средств ставит внутрь критической секции; обрабатывает перевод на тот же счёт и невалидные аргументы.
- Middle+: объясняет, почему нельзя блокироваться на `getId()` (примитив, кеш `Long.valueOf`); видит проблему разных объектов с одним id и требует общего актуального состояния, а не только общего lock.
- Senior: замечает, что всё решение работает в пределах одной JVM. Для кластера предлагает транзакцию БД с пессимистичной блокировкой (`SELECT ... FOR UPDATE` в порядке id) или оптимистичную (`@Version` с ретраями); обсуждает `tryLock` с таймаутом как способ не висеть вечно и вопрос очистки реестра локов.

</details>

### 13. Задача: банкомат (ATM)

Классическая задача в двух частях.

**Часть 1. Выдача суммы.** В банкомате есть кассеты с купюрами номиналов 5000, 2000, 1000, 500, 100. Напишите метод, который по запрошенной сумме возвращает, сколько купюр каждого номинала выдать. Продумайте граничные случаи.

**Часть 2. Потокобезопасность.** К банкомату одновременно обращаются несколько клиентов. Что нужно изменить в решении, чтобы оно было корректным? Что произойдёт, если двое одновременно снимают последние 1000 рублей?

<details>
<summary>Разбор</summary>

**Часть 1. Подбор с учётом ограниченного запаса.** Жадный выбор не решает исходную задачу полностью: при {5000: 1, 2000: 3} сумму 6000 можно выдать тремя купюрами 2000, хотя выбор 5000 приводит в тупик. Для полного решения используем DP по сумме в единицах 100 рублей. Здесь требуется любой допустимый набор, а не минимум купюр. Для учебного примера вводим лимит одной выдачи 1 000 000 рублей, чтобы ограничить память таблицы.

```java
public class Atm {
    private static final int[] NOMINALS = {5000, 2000, 1000, 500, 100};
    private final int[] counts = new int[NOMINALS.length];

    public synchronized void load(int nominal, int count) {
        if (count < 0) throw new IllegalArgumentException("count < 0");
        for (int i = 0; i < NOMINALS.length; i++) {
            if (NOMINALS[i] == nominal) {
                counts[i] = Math.addExact(counts[i], count);
                return;
            }
        }
        throw new IllegalArgumentException("Неподдерживаемый номинал");
    }

    public synchronized Map<Integer, Integer> withdraw(int amount) {
        if (amount <= 0 || amount > 1_000_000 || amount % 100 != 0) {
            throw new IllegalArgumentException("Сумма: 100..1000000, кратная 100");
        }
        int target = amount / 100;
        boolean[] previous = new boolean[target + 1];
        previous[0] = true;
        int[][] taken = new int[NOMINALS.length][target + 1];
        for (int i = 0; i < NOMINALS.length; i++) {
            int value = NOMINALS[i] / 100;
            int[] used = new int[target + 1];
            Arrays.fill(used, -1);
            boolean[] current = new boolean[target + 1];
            for (int sum = 0; sum <= target; sum++) {
                if (previous[sum]) {
                    used[sum] = 0;
                } else if (sum >= value && used[sum - value] >= 0
                        && used[sum - value] < counts[i]) {
                    used[sum] = used[sum - value] + 1;
                }
                current[sum] = used[sum] >= 0;
                taken[i][sum] = used[sum];
            }
            previous = current;
        }
        if (!previous[target]) throw new IllegalStateException("Нет набора купюр");

        Map<Integer, Integer> result = new LinkedHashMap<>();
        int remainder = target;
        for (int i = NOMINALS.length - 1; i >= 0; i--) {
            int count = taken[i][remainder];
            if (count > 0) result.put(NOMINALS[i], count);
            remainder -= count * (NOMINALS[i] / 100);
        }
        // До этой точки кассеты не менялись: неудачный подбор ничего не списывает.
        result.forEach((nominal, count) -> {
            for (int i = 0; i < NOMINALS.length; i++) {
                if (NOMINALS[i] == nominal) counts[i] -= count;
            }
        });
        return result;
    }
}
```

На стадии номинала i `used[sum]` хранит минимальное число купюр именно этого номинала, необходимое для достижения суммы вместе с ранее рассмотренными номиналами, либо −1, если сумма недостижима. Если сумма была достижима раньше, берём 0; иначе пробуем продлить меньшую сумму текущей купюрой, не превышая запас. Таблица `taken` позволяет восстановить набор по стадиям. При d номиналах и A = amount / 100 время O(dA), память O(dA), включая восстановление. Минимальное число купюр этот алгоритм не оптимизирует.

Ключевые моменты, которые проверяет задача:

- **Валидация входа.** Сумма должна быть положительной и кратной 100, загрузка — с разрешённым номиналом и неотрицательным количеством. Пустой ATM корректно сообщает об отсутствии набора вместо ошибки доступа к первому или последнему ключу.
- **Купюр может не хватить.** «Не хватает денег вообще» и «денег хватает, но не теми номиналами» — разные ситуации. В кассете может лежать 100_000 купюрами по 5000, а сумму 300 выдать всё равно нечем.
- **Списываем купюры только после того, как сумма набрана целиком.** Если уменьшать кассету по ходу подбора и в конце обнаружить, что остаток не выдать, — купюры уже списаны, клиент ничего не получил, а банкомат «похудел». Это самая частая логическая ошибка в решении.
- **Жадность не всегда даёт решение.** Для канонических номиналов с неограниченным запасом жадный алгоритм оптимален, но с ограниченным числом купюр он может промахнуться: кассета {5000: 1, 2000: 3}, сумма 6000 — жадный возьмёт 5000, останется 1000, которую выдать нечем, хотя решение есть: 2000 × 3. Это хороший follow-up вопрос интервьюера. DP выше учитывает ограниченный запас; при облегчённой постановке с неограниченным запасом и доказанно канонической системой номиналов можно выбрать жадный вариант.

**Часть 2. Потокобезопасность.** Проверка «сумму можно выдать» и списание купюр — это check-then-act на разделяемом состоянии. Без синхронизации двое клиентов одновременно снимают последние 1000: оба видят в кассете одну купюру 1000, оба решают, что выдать можно, оба списывают — одна купюра выдана дважды, в кассете −1. Самое неприятное, что на тестах с одним потоком это не воспроизводится никогда.

В примере `withdraw` и `load` уже синхронизированы на одном объекте: подбор, списание и загрузка не перемешиваются. Синхронизация только `withdraw` при несинхронизированном `load` оставила бы гонку. Для одного ATM этого достаточно: клиенты физически обслуживаются по очереди, и узким местом здесь всё равно является механика выдачи. Если интервьюер спрашивает про более тонкую блокировку — можно синхронизироваться на объекте кассеты, но гранулярнее одной кассеты дробить не стоит: выдача затрагивает несколько номиналов сразу, и блокировать каждый номинал отдельно — прямой путь к дедлоку из предыдущей задачи.

Сеньорское дополнение: блокировка внутри JVM защищает только локальные кассеты этого объекта; несколько независимых ATM могут иметь разные локальные кассеты. Общий баланс счёта клиента — уже другой ресурс. Реальные ATM — это тысячи устройств, снимающих со счетов через общий бэкенд, и общий банковский баланс защищают транзакцией базы: пессимистичная блокировка счёта (`SELECT ... FOR UPDATE`) на время списания или оптимистичная по версии с ретраем. Проверка баланса и списание должны быть в одной транзакции — тот же check-then-act, только уровнем выше. Физическая выдача купюр не откатывается транзакцией БД: для сбоя устройства между списанием и выдачей нужен журнал операции и протокол сверки, чего учебная модель не реализует.

**Типичные ошибки кандидатов:**

- нет валидации суммы (отрицательная, нулевая, не кратная минимальному номиналу);
- купюры списываются из кассеты по ходу подбора, при неудаче не откатываются;
- деньги в `double` или `float` (см. сниппет про BigDecimal);
- метод возвращает просто `int` («выдал/не выдал») вместо набора купюр — требование задачи прочитано невнимательно;
- про потокобезопасность кандидат вспоминает только после прямого вопроса, а не предлагает сам;
- `synchronized` расставлен «для страховки» на все методы подряд без понимания, какое состояние защищается.

</details>

### 5. Сниппет: JPA и Spring

```java
@Entity
public class Order {
    @Id
    private Long id;

    @ManyToOne(fetch = FetchType.EAGER)
    private Customer customer;

    @OneToMany(fetch = FetchType.EAGER)
    private List<OrderItem> items;

    @Override
    public String toString() {
        return "Order{id=" + id + ", customer=" + customer + ", items=" + items + "}";
    }
}

@Service
public class OrderService {

    @Autowired
    private OrderRepository orderRepository;

    public List<Order> getOrdersWithTotals() {
        List<Order> orders = orderRepository.findAll();
        for (Order order : orders) {
            Customer customer = order.getCustomer();
            order.setCustomerName(customer.getName());
            List<OrderItem> items = order.getItems();
            order.setTotal(items.stream().map(OrderItem::getPrice).reduce(BigDecimal.ZERO, BigDecimal::add));
        }
        return orders;
    }

    @Transactional
    private void recalculateOrder(Order order) {
        orderRepository.save(order);
    }

    public void recalculateAll() {
        List<Order> orders = orderRepository.findAll();
        for (Order order : orders) {
            recalculateOrder(order);
            log.info("Recalculated: {}", order);
        }
    }
}
```

Найдите проблемы.

<details>
<summary>Разбор</summary>

1. **N+1.** `findAll()` тянет все заказы, а потом в цикле для каждого заказа обращается к `customer` и `items`. Даже при EAGER (с ним Hibernate часто делает дополнительные select'ы вместо join'а), при LAZY без fetch-плана и с доступом к связям возможны дополнительные запросы. Их число зависит от повторяющихся customer, persistence context, batch fetching и кэша — N+1 не гарантирован одним словом LAZY. Тысяча заказов — тысячи запросов к базе. Лечится `JOIN FETCH` в JPQL/`@EntityGraph` для конкретного запроса, либо выборкой сразу нужных полей в проекцию.

2. **`@Transactional` на private-методе не работает.** Spring создаёт транзакционный прокси, а private-метод не перехватывается прокси. Для JDK-прокси транзакционный метод должен быть public и объявлен в интерфейсе; начиная со Spring 6 class-based proxy также может перехватывать protected и package-visible методы, вызванные извне. `recalculateOrder` private и вызывается из `recalculateAll` того же класса — это self-invocation, вызов идёт напрямую, минуя прокси. Аннотация здесь не создаёт сервисную транзакцию. При этом методы Spring Data repository могут иметь собственные транзакции; это не объединяет весь `recalculateAll` в одну атомарную операцию. Лечится: вынести метод в отдельный бин и вызывать через него, или сделать public и вызывать извне, или весь `recalculateAll` пометить `@Transactional`.

3. **LAZY-коллекция в `toString` / вне транзакции.** Допустим, кто-то «починит» N+1, поставив LAZY (типичная первая реакция). Тогда `log.info("Recalculated: {}", order)` сработает `toString()`, который обращается к `items` — а сессия к этому моменту уже закрыта, потому что транзакции, напомним, нет. Получаем `LazyInitializationException`. Печатать entity в `toString` целиком с коллекциями — плохая привычка: логируйте id и скалярные поля, коллекции исключайте.

4. **EAGER везде.** `@ManyToOne(fetch = EAGER)` — дефолт в JPA, который надо явно переопределять в LAZY, а `@OneToMany(fetch = EAGER)` — просто минное поле: каждый заказ тянет все позиции всегда, даже когда нужен только номер и дата. EAGER требует загрузить связь, но не обещает один JOIN в любом запросе. Обычно предпочитают LAZY и явный fetch-план либо DTO-проекцию для сценария. Коллекционный `JOIN FETCH` с пагинацией тоже требует осторожности: возможны размножение строк и пагинация в памяти. Это проверяется числом SQL-запросов и планом, а не заменой всех связей одним правилом.

На собеседовании стоит проговорить именно связку: N+1 виден сразу, а `@Transactional` на private — вопрос «на засыпку», который отличает человека, писавшего Spring руками.

</details>

### 6. Сниппет: REST API контроллер

```java
@RestController
@RequestMapping("/api/users")
public class UserController {

    private final JdbcTemplate jdbcTemplate;
    private final UserRepository userRepository;

    public UserController(JdbcTemplate jdbcTemplate, UserRepository userRepository) {
        this.jdbcTemplate = jdbcTemplate;
        this.userRepository = userRepository;
    }

    @GetMapping("/search")
    public ResponseEntity<?> searchUsers(@RequestParam String name) {
        try {
            String sql = "SELECT * FROM users WHERE name LIKE '%" + name + "%'";
            List<User> users = jdbcTemplate.query(sql, new BeanPropertyRowMapper<>(User.class));
            if (users.isEmpty()) {
                return ResponseEntity.ok("Users not found");
            }
            return ResponseEntity.ok(users);
        } catch (Exception e) {
            return ResponseEntity.ok("Error: " + e.getMessage());
        }
    }

    @PostMapping
    public ResponseEntity<User> createUser(@RequestBody User user) {
        User saved = userRepository.save(user);
        return ResponseEntity.ok(saved);
    }
}
```

Найдите проблемы.

<details>
<summary>Разбор</summary>

1. **SQL-инъекция.** `name` из запроса конкатенируется прямо в SQL. Это смешивает недоверенные данные со структурой команды. В защитном тесте передайте обычное имя с апострофом и убедитесь, что оно остаётся значением связанного параметра, а текст SQL не меняется. Это критическая уязвимость, первый комментарий на любом ревью. Лечится параметризованным запросом: `jdbcTemplate.query("SELECT * FROM users WHERE name LIKE ?", mapper, "%" + name + "%")`.

2. **200 OK на ошибку.** И «не найдено», и исключение возвращаются со статусом 200 и строкой в теле. Клиент не может отличить успех от сбоя без парсинга текста; мониторинг по статус-кодам показывает, что всё здорово, когда сервис лежит. Правильно: пустой результат — 200 с пустым списком (это не ошибка), исключение — 500 через `@ControllerAdvice`/`@ExceptionHandler`, битый запрос — 400. И в ответ клиенту не должен уходить `e.getMessage()` — там могут быть детали схемы БД и внутренних адресов.

3. **Наружу торчит entity.** `createUser` принимает и возвращает JPA-сущность `User` напрямую. Последствия: клиент может прислать любые поля, включая те, что не должен ставить сам (id, роль, флаги) — mass assignment; в ответе уезжают все поля entity, включая хеш пароля; схема API жёстко сшита со схемой БД. Нужны отдельные DTO на вход и выход с маппингом.

4. **Нет валидации входа.** `@RequestBody User user` без `@Valid` — сохранится и пользователь с пустым email, и с отрицательным возрастом, всё зависит от милости констрейнтов в базе. Минимум: `@Valid @RequestBody CreateUserRequest` с `@NotBlank`, `@Email` и обработчиком `MethodArgumentNotValidException`, который вернёт 400 со списком ошибок.

Отдельный повод для разговора: `BeanPropertyRowMapper` с `SELECT *` хрупок к переименованию колонок, а `LIKE '%...%'` обычно не использует обычный B-tree для поиска подстроки (в PostgreSQL возможен trigram-индекс) — но это уже следующий уровень после безопасности и контракта.

</details>

### 11. Сниппет: внешние вызовы внутри @Transactional

```java
@Service
public class OrderService {

    private static final Logger log = LoggerFactory.getLogger(OrderService.class);

    private final OrderRepository orderRepository;
    private final RestTemplate restTemplate;
    private final KafkaTemplate<String, Object> kafkaTemplate;

    public OrderService(OrderRepository orderRepository,
                        RestTemplate restTemplate,
                        KafkaTemplate<String, Object> kafkaTemplate) {
        this.orderRepository = orderRepository;
        this.restTemplate = restTemplate;
        this.kafkaTemplate = kafkaTemplate;
    }

    @Transactional
    public Order createOrder(CreateOrderRequest request) {
        Order order = new Order(request.getUserId(), request.getItems());
        orderRepository.save(order);

        try {
            PaymentResponse payment = restTemplate.postForObject(
                    "https://payments.internal/api/charge",
                    new PaymentRequest(order.getId(), order.getTotal()),
                    PaymentResponse.class);
            order.setPaymentId(payment.getPaymentId());
        } catch (Exception e) {
            log.warn("Payment call failed: {}", e.getMessage());
        }

        kafkaTemplate.send("orders", new OrderCreatedEvent(order.getId(), order.getTotal()));

        order.setStatus(OrderStatus.CONFIRMED);
        return orderRepository.save(order);
    }
}
```

Найдите проблемы.

<details>
<summary>Разбор</summary>

1. **Сетевой вызов внутри транзакции держит соединение из пула.** После первого SQL в этой транзакции соединение обычно остаётся занятым до её завершения; точный момент получения зависит от transaction manager и настроек. В данном коде `save` перед сетевым вызовом способен инициировать SQL. `restTemplate.postForObject` — синхронный HTTP-вызов, который может отвечать секунды (если таймауты не настроены, ожидание может оказаться очень долгим). Всё это время соединение с базой простаивает, но не возвращается в пул. Под нагрузкой: 20 потоков одновременно создают заказы, платёжный сервис притормозил — все соединения пула заняты ждущими транзакциями, и сервис перестаёт отвечать даже на запросы, которым платежи вообще не нужны. Классическое истощение пула. Правило: транзакция должна быть короткой — чтение и запись в базу, без сети, без очередей, без файлов.

2. **Двойная запись: Kafka и база не согласованы.** `kafkaTemplate.send()` выполняется до коммита транзакции. Если после отправки транзакция откатится (конфликт при втором `save`, сработал constraint, упал commit) — событие `OrderCreatedEvent` уже ушло в Kafka, а заказа в базе нет. Консьюмеры увидят фантомный заказ и начнут его обрабатывать: спишут со склада, отправят письмо клиенту. Обратная картина тоже возможна: коммит прошёл, а send упал — заказ есть, события нет. Проблема называется dual write, и транзакцией она не лечится: Kafka не участвует в транзакции базы (распределённые транзакции/XA здесь не используют). Правильное решение — паттерн Transactional Outbox: событие пишется в таблицу `outbox` в той же транзакции, что и заказ, а отдельный релей читает таблицу и публикует в Kafka с ретраями (подробнее — в microservices.md). Облегчённый вариант без гарантий доставки — `@TransactionalEventListener(phase = AFTER_COMMIT)`: слушатель сработает только после успешного коммита. Это убирает фантомные события, но не защищает от потери события при падении между коммитом и отправкой.

3. **Проглоченное исключение отключает откат.** `catch (Exception e)` с одним `log.warn` проглатывает ошибку платежа. Метод идёт дальше, ставит статус `CONFIRMED`, транзакция коммитится — и в базе оказывается подтверждённый, но не оплаченный заказ. Spring по умолчанию помечает транзакцию для отката при вышедшем из прокси метода `RuntimeException` или `Error`; checked-исключения требуют правила rollback. Перехваченная ошибка HTTP сама по себе откат не вызовет. При этом транзакция могла уже получить rollback-only от другого участника, так что «проглотил — всегда будет коммит» тоже неверно. Плюс `log.warn` без самого исключения теряет стектрейс: в логах будет текст без причины. Минимум — пробросить дальше, чтобы заказ откатился, либо явно перевести его в статус «ошибка оплаты» осознанным решением, а не побочным эффектом пустого catch.

4. **Ретрай без стабильной идентичности операции — двойное списание.** Допустим, платёжный сервис списал деньги, но ответ потерялся. Повтор всего `createOrder` в показанном коде создаёт новый `Order` с новым ID, поэтому передача `order.getId()` как ключа сама по себе не дедуплицирует запросы. Клиент создаёт ключ логической покупки до первой попытки и повторно передаёт его. Сервер атомарно сохраняет сопоставление ключа с заказом и значимыми параметрами в одной DB-транзакции; UNIQUE в области клиента/операции закрывает гонку одновременных повторов. Повтор с теми же параметрами использует уже созданный заказ, а с другими — получает конфликт. Стабильный ID платёжной операции сохраняют до первого вызова провайдера и используют при всех его повторах; ID заказа подходит только при гарантированном повторном использовании того же заказа и одной платёжной операции. Провайдер должен поддерживать соответствующую дедупликацию. При timeout исход остаётся неизвестным: нужны запрос статуса и восстановление обработки, а не новая покупка или новый платёжный ключ. Срок хранения сопоставления согласуют с горизонтом повторов. См. [задачу 24 о HTTP-таймауте](reasoning-questions.md#24-http-таймаут-заказ-не-создан-или-ответ-потерян) и [задачу 30 о границе транзакции](system-design-and-patterns.md#30-на-подумать-платёжный-http-вызов-выполняется-внутри-транзакции-заказа-где-провести-границу).

5. **`kafkaTemplate.send()` без обработки результата.** В Spring Kafka 3.x `send` возвращает `CompletableFuture`, который здесь игнорируется (в старых версиях API был `ListenableFuture`). Асинхронная ошибка может остаться без реакции приложения. Внутренние ретраи producer зависят от конфигурации и не заменяют долговечную доставку. Как минимум — `whenComplete` с логированием ошибки; см. пункт 2 про Outbox: он обеспечивает долговечное намерение отправки при корректной работе БД и релея. Возможна повторная публикация, поэтому consumer обязан быть идемпотентным; нужны мониторинг, ретраи и политика неотправляемых событий.

Как выглядит правильная архитектура: короткая транзакция создаёт заказ в статусе `PENDING` либо находит его по стабильному ключу покупки, сохраняет идентичность платёжной операции и событие в `outbox`; платёжный вызов идёт уже вне транзакции, с тем же платёжным ключом и таймаутом; по его результату вторая короткая транзакция обновляет статус; событие публикует релей из outbox. Незавершённые операции должны быть обнаружимы и возобновляемы после сбоя. Короткие транзакции не держат соединения во время HTTP-ожидания, а outbox сохраняет намерение отправки вместе с соответствующим состоянием заказа.
