## Владение ресурсами и выполнение задач

<a id="1-файл-закрывается-раньше-асинхронного-чтения"></a>

### 1. Как передать чтение файла рабочему потоку?

Требование: вернуть `Future<Long>` с числом непустых строк. Метод владеет открываемым файлом, executor принадлежит приложению. После возвращения метода чтение может ещё не начаться. При любом исходе начатого чтения файл нужно закрыть.

Плохой код:

```java
Future<Long> count(Path path, ExecutorService executor) throws IOException {
    try (Stream<String> lines = Files.lines(path, StandardCharsets.UTF_8)) {
        return executor.submit(() -> lines.filter(s -> !s.isBlank()).count());
    }
}
```

Проверьте три исхода: чтение началось сразу, задача ждёт в очереди, исполнитель отказал в приёме. Когда в каждом случае можно закрыть файл?

<details>
<summary>Разбор</summary>

`Files.lines` возвращает ленивый поток. `submit` передаёт вычисление исполнителю, но не обещает закончить его до выхода из метода. Блок `try` закрывает поток сразу после постановки задания; worker затем использует уже закрытый источник. Удачный запуск при свободном worker не доказывает корректность: закрытие может пересечься с обходом. Здесь try-with-resources присутствует, однако охватывает неверный срок жизни ресурса. Блокировать вызывающий поток через `get()` ради сохранения этого блока нельзя без изменения асинхронного контракта.

Владелец файла должен совпадать с задачей, которая его читает. Перенесём открытие и закрытие внутрь `Callable`:

```java
static Future<Long> count(Path path, ExecutorService executor) {
    return executor.submit(() -> {
        try (Stream<String> lines = Files.lines(path, StandardCharsets.UTF_8)) {
            return lines.filter(s -> !s.isBlank()).count();
        }
    });
}
```

Отклонённая или отменённая до запуска задача вообще не откроет файл. Ошибка открытия или чтения попадёт в результат Future как причина `ExecutionException`; ресурс, успевший открыться, закроется и при исключении. Исполнитель здесь заимствован: метод не вызывает его `shutdown`. Отмена запущенного чтения не гарантирует немедленного окончания файлового I/O; для требования о жёстком deadline нужен отдельный протокол и подходящий источник.

Для проверки займите единственный worker задачей, ожидающей latch, вызовите `count`, затем освободите worker. Исправление должно вернуть верное количество. Отдельно проверьте отсутствующий файл, пустой файл и отмену задания в очереди. В тесте executor закрывает создавший его код. Компромисс переноса открытия: между вызовом метода и началом работы файл может измениться. Если нужен снимок именно на момент вызова, надо явно копировать содержимое или использовать другой контракт; удержание открытого дескриптора само по себе также не гарантирует неизменности файла.


</details>

<a id="2-отклонённая-задача-оставляет-вечный-future"></a>

### 2. Что получит клиент занятого пула при отправке задания?

Требование: очередь содержит максимум одно ожидающее задание, worker один. Каждый вызов `submit` либо возвращает Future реально принятой задачи, либо сразу сообщает об отказе. Молчаливые потери запрещены. Владелец пула выполняет штатный `shutdown` и дожидается принятых задач.

Плохой код:

```java
ThreadPoolExecutor pool = new ThreadPoolExecutor(
        1, 1, 0, TimeUnit.SECONDS, new ArrayBlockingQueue<>(1),
        new ThreadPoolExecutor.DiscardPolicy());
Future<String> result = pool.submit(() -> "saved");
return result.get();
```

Один worker занят, ещё одна задача в очереди. Как вызывающий код узнает исход третьей отправки?

<details>
<summary>Разбор</summary>

При насыщении `DiscardPolicy` молча выбрасывает переданный `Runnable`. В случае обычного `ThreadPoolExecutor.submit` этим объектом служит Future-задача. Обработчик не запускает её и не переводит в cancelled или failed. Вызвавший код получает Future, который остаётся незавершённым; `get()` без ограничения времени способен ждать бесконечно. Это не медленная задача: её вообще нет в очереди. Метрика успешных ответов `submit` при этом создаёт ложное впечатление нормального приёма.

Контракт требует наблюдаемого отказа, поэтому достаточно стандартной политики с исключением:

```java
static ThreadPoolExecutor newPool() {
    return new ThreadPoolExecutor(
            1, 1, 0, TimeUnit.SECONDS, new ArrayBlockingQueue<>(1),
            new ThreadPoolExecutor.AbortPolicy());
}

static Future<String> submitSave(ExecutorService pool, Callable<String> save) {
    // RejectedExecutionException означает: задание не принято.
    return pool.submit(save);
}
```

`RejectedExecutionException` нужно преобразовать в понятный отказ на границе сервиса; возвращать вместо него «успех» запрещено. У принятой задачи всё ещё возможны ошибка или длительное выполнение, которые отражаются её Future. Заявленный инвариант касается приёма, а не гарантированной доставки после падения процесса. Если требуется переживать рестарт, необходим долговечный журнал либо брокер с отдельным подтверждением.

Проверка должна воспроизводить насыщение без случайных задержек: первая задача занимает worker и сигнализирует latch, вторая заполняет очередь, третья обязана синхронно выбросить исключение. После освобождения первой обе принятые задачи должны закончиться. После `shutdown` новое задание также должно явно отклоняться. Владелец завершает пул через `shutdown` и ограниченное `awaitTermination`; при аварийном `shutdownNow` судьбу возвращённых невыполненных Future-задач нужно обработать отдельно, например отменить их.

Компромисс — вместо скрытой потери клиент увидит перегрузку. Повтор допустим только по оговорённой политике и при безопасной повторяемости операции. Бесконечный retry из обработчика отказа превратит ограниченную очередь в скрытое ожидание на вызывающих потоках.

</details>

<a id="3-отмена-возвращает-permit-до-окончания-работы"></a>

### 3. Сколько запросов к партнёру может выполняться после отмены?

Требование: одновременно выполняются максимум два синхронных вызова `partner.call()`. Вызов может временно игнорировать interrupt, но eventually возвращается. Отмена Future не должна разрешать третий вызов, пока один из первых двух физически не закончился. Executor общий.

Плохой код:

```java
permits.acquire();
FutureTask<String> task = new FutureTask<>(partner::call) {
    @Override protected void done() { permits.release(); }
};
executor.execute(task);
return task;
```

Проследите за двумя запущенными вызовами, отменой одного из них и отправкой третьей задачи. В каждый момент посчитайте активные вызовы.

<details>
<summary>Разбор</summary>

`FutureTask.done()` вызывается после перехода Future в завершённое состояние, включая отмену. `cancel(true)` может завершить Future и вызвать `done`, пока `partner.call()` ещё исполняется: interrupt — запрос, а не принудительное уничтожение Java-стека. Если в этот момент вернуть permit, следующий worker войдёт к партнёру, и физически активных вызовов станет три. Отдельный дефект: permit взят до `execute`; при `RejectedExecutionException` задача не запустится, а разрешение останется потерянным.

Ограничитель должен защищать реальный участок работы. Захватываем permit внутри задачи и освобождаем только после выхода из синхронного вызова:

```java
static <T> Future<T> submitLimited(
        ExecutorService executor, Semaphore permits, Callable<T> operation) {
    return executor.submit(() -> {
        permits.acquire();
        try {
            if (Thread.currentThread().isInterrupted()) {
                throw new InterruptedException("cancelled before operation");
            }
            return operation.call();
        } finally {
            permits.release();
        }
    });
}
// Все вызовы используют один Semaphore(2).
```

Если `acquire` прервётся, управление не войдёт в `try`, поэтому лишнего `release` не будет. Отмена до запуска ничего не захватывает. Отмена во время операции оставляет permit занятым до её реального возврата или исключения. Даже гонка отмены сразу после проверки interrupt не нарушает ограничение конкуренции: операция может стартовать, но разрешение удерживается. Для асинхронного клиента, возвращающего результат до окончания сетевой операции, такой scope недостаточен: permit надо связывать с её фактическим завершением.

Проверьте это управляемой заглушкой: два вызова вошли и ждут latch, игнорируя interrupt. Отмените их Future и отправьте третий; до освобождения latch заглушка не должна зарегистрировать третий вход. Затем проверьте отмену ожидающего permit и отказ executor: после окончания работы доступны ровно два разрешения.

Компромисс — потоки могут ожидать semaphore, поэтому очередь executor и общее число ожидающих заданий тоже ограничивают. Этот код гарантирует предел активных вызовов, но не ограничивает backlog и не делает зависший партнёрский вызов отменяемым.

</details>

<a id="4-ограниченный-пул-пропускает-слишком-много-вызовов"></a>

### 4. Как поведёт себя пул при ста одновременных запросах?

Требование: партнёр разрешает максимум четыре одновременных синхронных запроса от этой JVM. Все запросы к нему идут через один выделенный пул; очередь — максимум 16. При насыщении допустим быстрый отказ, выполнение на HTTP-потоке запрещено.

Плохой код:

```java
ExecutorService pool = new ThreadPoolExecutor(
        4, 4, 0, TimeUnit.SECONDS, new ArrayBlockingQueue<>(16),
        new ThreadPoolExecutor.CallerRunsPolicy());
// Вызывают одновременно 100 HTTP-потоков:
return pool.submit(partner::call);
```

Назовите потоки, на которых будут сделаны запросы при полностью занятом пуле. Как проверить численное ограничение?

<details>
<summary>Разбор</summary>

После заполнения очереди `CallerRunsPolicy` исполняет отклонённую задачу прямо в потоке, который вызвал `execute` внутри `submit`. Четыре worker продолжают работать, а дополнительные HTTP-потоки одновременно входят к партнёру. `maximumPoolSize` ограничивает только потоки самого executor. Если caller-потоков много, реальная конкуренция существенно превысит четыре. Backpressure отдельному producer не равен глобальному ограничению допуска: несколько producer одновременно создают дополнительные исполнители.

В данных условиях лучше принять явный отказ и сохранить единый путь исполнения:

```java
static ThreadPoolExecutor partnerPool() {
    return new ThreadPoolExecutor(
            4, 4, 0, TimeUnit.SECONDS, new ArrayBlockingQueue<>(16),
            new ThreadPoolExecutor.AbortPolicy());
}

static <T> Future<T> callPartner(
        ExecutorService dedicatedPool, Callable<T> synchronousCall) {
    return dedicatedPool.submit(synchronousCall);
}
```

Исправление действительно обеспечивает максимум четыре активных тела задачи только при условии, что этот пул один на JVM и каждый синхронный вызов остаётся внутри своего worker до завершения. Создание такого пула на запрос нарушит ограничение. Запуск клиентом фонового HTTP-вызова с немедленным возвратом тоже разрушит соответствие «занятый worker = активный запрос»: тогда нужен отдельный semaphore на завершение операции. Если один общий лимит действует на несколько JVM, локального пула недостаточно.

Проверка: четыре заглушки занимают worker и ждут latch, следующие 16 заданий успешно ставятся в очередь, ещё одно отклоняется без входа в заглушку. Запускайте отправителей параллельно и измеряйте максимум активных вызовов атомарным счётчиком в самой заглушке. После освобождения проверьте результаты всех принятых задач и штатно завершите принадлежащий тесту пул.

Цена — отказ части запросов и задержка стоящих в очереди. Ёмкость 16 имеет смысл только если ожидаемое время очереди укладывается в deadline; максимальную длину выбирают по latency-бюджету, а не ради красивого числа.

</details>

## Гонки при публикации и кэшировании

<a id="5-два-volatile-поля-дают-смешанную-конфигурацию"></a>

### 5. Какую конфигурацию маршрута увидит запрос во время обновления?

Требование: один updater публикует конфигурацию маршрутизации. Для каждого запроса endpoint и token должны принадлежать одной версии. Других writers нет, строки неизменяемые. Нельзя держать lock во время HTTP-вызова.

Плохой код:

```java
volatile URI endpoint = URI.create("https://old.example");
volatile String token = "old-token";

void reload(URI newEndpoint, String newToken) {
    endpoint = newEndpoint;
    token = newToken;
}
void send() { http.post(endpoint, token); }
```

Покажите, какие пары endpoint и token допустимы, если запрос совпал с публикацией новой версии.

<details>
<summary>Разбор</summary>

Видимость каждого volatile-поля здесь обеспечена, но требование относится к паре. Updater может записать новый endpoint, после чего request прочитает его и ещё старый token. Возможен и другой порядок пересечения двух чтений с reload. Результат — неверная авторизация или отправка секрета другому endpoint. Утверждение «все поля volatile, значит гонок нет» смешивает гарантии отдельных обращений с атомарностью составного состояния.

Нужно публиковать одну неизменяемую версию целиком и один раз читать её в локальную переменную:

```java
record Route(URI endpoint, String token) {
    Route {
        Objects.requireNonNull(endpoint);
        Objects.requireNonNull(token);
    }
}
final class Routes {
    private volatile Route current;
    Routes(Route initial) { current = Objects.requireNonNull(initial); }

    void reload(URI endpoint, String token) {
        current = new Route(endpoint, token);
    }
    Route snapshot() { return current; }
}

// На один запрос берётся ровно один снимок:
Route route = routes.snapshot();
http.post(route.endpoint(), route.token());
```

Создание `Route` завершается до volatile-публикации ссылки. URI и String неизменяемые, поэтому снимок остаётся согласованным после reload; lock вокруг медленного вызова не нужен. Важно действительно сохранить одну ссылку: `http.post(routes.snapshot().endpoint(), routes.snapshot().token())` опять допускает смешение версий. Если Route содержит изменяемый список или credential-буфер, record сам по себе их не замораживает; потребуется копирование и правила уничтожения секретов.

Проверьте последовательность с барьером между записями плохой версии: она должна показать смешанную пару. Для исправления многократно публикуйте пары с одним номером версии в обоих компонентах, а readers проверяют совпадение номера одного снимка. Такой стресс полезен, но доказательство гарантии даёт публикация единственного неизменяемого объекта, а не отсутствие падений в тысяче запусков.

Компромисс: уже начатый запрос продолжит использовать старую, но внутренне согласованную конфигурацию. Немедленное прекращение использования отозванного token — отдельное требование с другой координацией. Несколько writers с частичными изменениями также потребуют CAS или сериализации, иначе полная замена может потерять чужое изменение.

</details>

<a id="6-старое-чтение-воскрешает-сброшенный-кэш"></a>

### 6. Какое значение вернёт кэш после обновления записи?

Требование: одна JVM кэширует один неизменяемый `String`. Все изменения хранилища проходят через этот объект. После успешного `update("new")` новые вызовы `get()` не должны получать старое значение. Store синхронный, read после успешного write видит запись; отсутствующих значений нет, при исключении write ничего не меняет.

Плохой код:

```java
volatile String cached;
String get() {
    String value = cached;
    if (value != null) return value;
    value = store.read();
    cached = value;
    return value;
}
void update(String value) {
    store.write(value);
    cached = null;
}
```

Разберите расписание с двумя чтениями и одной записью. Что гарантировано читателю, который начал работу после завершения обновления?

<details>
<summary>Разбор</summary>

Пусть reader увидел пустой кэш и прочитал из store `old`, затем остановился перед присваиванием. Writer записал `new`, сбросил кэш и успешно вернулся. Reader продолжил и положил `old` обратно. Все последующие cache hit возвращают устаревшее значение, хотя операция обновления уже завершена. Volatile обеспечивает видимость этих присваиваний, а атомарный `remove` у ConcurrentHashMap дал бы тот же сценарий: проблема в общей последовательности load и update.

Для одного значения самый простой корректный вариант — сериализовать загрузку и изменение одним монитором и сразу публиковать подтверждённую запись:

```java
interface Store {
    String read();
    void write(String value);
}
final class SingleValueCache {
    private final Store store;
    private String cached;

    SingleValueCache(Store store) { this.store = store; }

    synchronized String get() {
        if (cached == null) cached = Objects.requireNonNull(store.read());
        return cached;
    }
    synchronized void update(String value) {
        Objects.requireNonNull(value);
        store.write(value);
        cached = value; // Только после подтверждённой записи.
    }
}
```

Загрузка больше не может завершить публикацию после конкурентного update: writer либо ждёт её завершения, либо выполняется первым, и get видит новую запись. Если write бросил исключение без изменения store, старый кэш остаётся допустимым. Предположения о синхронном store и единственном пути записи существенны. При внешних writers, реплике с lag или неопределённом исходе write эта реализация не обеспечивает заявленную свежесть; понадобятся версии, единый источник чтения и отдельная обработка неизвестного результата.

Проверяйте управляемым store: остановите read после получения `old`, запустите update и убедитесь, что он ждёт; затем отпустите read, дождитесь успешного update и вызовите get повторно. Старый код в таком расписании возвращает old, исправленный — new. Добавьте проверку исключения write и отсутствия повторного read на cache hit.

Компромисс — даже cache hit ждёт монитор, а медленный store блокирует других callers. Для заданного одного ключа это понятная цена простоты. На большом кэше используют координацию по ключу или проверку поколения загрузки перед публикацией, отдельно решая очистку служебных ключей. «Удалять кэш ещё раз через секунду» не доказывает инвариант и зависит от расписания.

</details>

<a id="7-concurrenthashmap-не-защищает-списки-внутри"></a>

### 7. Как вернуть снимок событий одного клиента?

Требование: конкурентные writers добавляют строковые события по tenant. Ни одно успешно добавленное событие не теряется; `snapshot(tenant)` возвращает неизменяемый снимок конкретного момента, который не меняется после возврата. Tenant из ограниченного набора, в каждом максимум 1000 событий.

Плохой код:

```java
ConcurrentHashMap<String, List<String>> events = new ConcurrentHashMap<>();
void add(String tenant, String event) {
    events.computeIfAbsent(tenant, key -> new ArrayList<>()).add(event);
}
List<String> snapshot(String tenant) {
    return Collections.unmodifiableList(events.get(tenant));
}
```

Проверьте двух авторов одного tenant и читателя. Какие события должен увидеть уже выданный снимок после очередного добавления?

<details>
<summary>Разбор</summary>

Атомарно создаётся отображение `tenant → list`, но следующий `ArrayList.add` выполняется уже вне операции карты. Несколько writers меняют одни и те же поля списка без координации: возможны потерянные элементы и несогласованное чтение. `unmodifiableList` запрещает запись через возвращённую ссылку, однако остаётся представлением исходного списка. Его содержимое продолжает меняться; безопасной публикации каждой последующей мутации карта не обеспечивает. Замена ArrayList на синхронизированный список защитила бы отдельные методы, но снимок всё равно потребовал бы отдельного копирования под соответствующей блокировкой.

При заданном небольшом пределе удобно хранить неизменяемые версии и заменять значение атомарной операцией по ключу:

```java
final class Events {
    private final ConcurrentHashMap<String, List<String>> values =
            new ConcurrentHashMap<>();

    void add(String tenant, String event) {
        Objects.requireNonNull(tenant);
        Objects.requireNonNull(event);
        values.compute(tenant, (key, old) -> {
            if (old != null && old.size() >= 1000) {
                throw new IllegalStateException("tenant limit reached");
            }
            List<String> next = new ArrayList<>(old == null ? List.of() : old);
            next.add(event);
            return List.copyOf(next);
        });
    }
    List<String> snapshot(String tenant) {
        return values.getOrDefault(tenant, List.of());
    }
}
```

Операции `compute` для одного ключа сериализуют изменения. Каждая новая версия включает предыдущую плюс событие, а опубликованный список больше не мутируется. Reader может получить версию до или после конкурентной записи; обе являются допустимым снимком. Строки неизменяемые, поэтому дополнительного глубокого копирования здесь не требуется. Лимит проверяется внутри той же атомарной операции: два writers не смогут одновременно обойти проверку ёмкости.

Для проверки запустите несколько writers с уникальными событиями, дождитесь их завершения и сравните размер и множество ожидаемых значений. Сохраните промежуточный snapshot, сделайте ещё add и убедитесь, что старый снимок не изменился. Конкурентная попытка добавить 1001-й элемент должна завершиться явным отказом без потери уже записанных данных.

Компромисс — каждое добавление копирует O(n) ссылок, последовательность из n записей потребует O(n²) копирований. Для больших потоков нужны другая структура, очереди или журнал; нельзя переносить это решение без заданного малого предела. Callback `compute` должен быть коротким и без сетевого I/O. Гарантии относятся к одному ключу, а не к снимку всей карты.

</details>

## Конкурентная запись и выборка из БД

<a id="8-сохранение-черновика-затирает-чужую-правку"></a>

### 8. Как сохранить черновик, который редактируют два автора?

Требование: PostgreSQL 17, `READ COMMITTED`. Пользователь редактирует текст черновика вне транзакции. Два пользователя открыли версию 7. Первый успешно сохранил свой текст. Второй должен получить конфликт, а не затереть первый результат. Автоматическое слияние текстов запрещено.

Плохой код:

```sql
-- После минут редактирования в браузере:
UPDATE draft SET body = :new_body WHERE id = :id;
-- API возвращает 200, если изменилась одна строка.
```

Какой HTTP-ответ получит второй автор при сохранении и какой текст останется в базе?

Дополнительный вопрос. Черновик версии 7 содержал «Июнь». Другой автор поменял текст на «Июль», затем вернул «Июнь». Можно ли вместо версии передавать прежний текст и сравнивать его в `WHERE`, если по требованиям нужно заметить любую промежуточную правку?

<details>
<summary>Разбор</summary>

База сериализует сами записи одной строки, но не знает, на какой версии основано решение пользователя. Второй UPDATE корректно дождётся первого, а затем заменит его body. Оба запроса затронут одну строку и вернут успех. Это потерянное обновление на уровне пользовательского намерения: правка происходила между запросами и не входила в удерживаемую DB-транзакцию. Держать `FOR UPDATE` несколько минут, пока человек печатает, дорого и ненадёжно; браузер может исчезнуть, а остальные редакторы останутся заблокированы.

Передавайте в ответе чтения номер версии и требуйте его при сохранении. Сравнение версии и запись должны составлять один условный UPDATE:

```sql
-- draft: id bigint PK, body text NOT NULL,
--        version bigint NOT NULL DEFAULT 0 CHECK (version >= 0).
UPDATE draft
SET body = :new_body,
    version = version + 1
WHERE id = :id
  AND version = :expected_version
RETURNING id, body, version;
```

Одна возвращённая строка означает успех и содержит новую версию. Ноль строк означает отсутствие подходящей версии: API отвечает конфликтом либо отдельным результатом «не найдено» после оговорённой проверки. Скрывать конфликт повтором с актуальной версией запрещено: такой retry снова затрёт чужой текст и отменит смысл optimistic locking. Клиенту нужно показать актуальную правку и предложить осознанное повторное редактирование. Все пути изменения body обязаны увеличивать version; административный UPDATE без этого нарушит протокол.

Проверка использует две DB-сессии. Обе читают version=7; первая обновляет и держит транзакцию открытой, вторая выполняет UPDATE с expected_version=7. После commit первой второй запрос должен вернуть ноль строк. Повторите сценарий с rollback первой: тогда вторая вправе успешно сохранить версию 8. Проверьте также, что API действительно различает пустой `RETURNING` и успешный результат.

**Ответ на дополнительный вопрос.** Проверка по тексту пропустит обе правки, поскольку исходное значение восстановилось. При увеличении версии с каждым сохранением у строки теперь версия 9. Обновление с ожидаемой версией 7 затронет ноль строк, хотя текст совпадает. Это отдельный тест на конфликт после возврата к прежнему значению.

Цена — явные конфликты и необходимость UX для их разрешения. Это подход для редактирования целого значения. Для независимых приращений счётчика уместнее атомарная арифметика в БД, а для совместного текста — отдельная модель слияния. На другом уровне изоляции дополнительно возможна ошибка сериализации; её нельзя автоматически превращать в успех.

</details>

<a id="9-skip-locked-не-резервирует-задание-после-commit"></a>

### 9. Какой обработчик получит следующее задание из очереди?

Требование: несколько workers забирают задания из PostgreSQL 17. Одно задание должно быть передано только одному worker. Внешней обработки пока нет: нужно атомарно перевести одну строку из `ready` в `running` и вернуть её payload. Все workers используют одинаковый протокол.

Плохой код:

```sql
-- JDBC connection работает с autoCommit=true.
SELECT id, payload FROM job WHERE state = 'ready'
ORDER BY id FOR UPDATE SKIP LOCKED LIMIT 1;
-- Java читает ResultSet и закрывает Statement.
UPDATE job SET state = 'running' WHERE id = :selected_id;
```

Пройдите шаги двух обработчиков до и после завершения каждой транзакции. Что позволяют заключить возвращённые строки?

<details>
<summary>Разбор</summary>

`FOR UPDATE SKIP LOCKED` пропускает строки, которые сейчас заблокированы другими транзакциями. Он не помечает строку навсегда занятой. При autocommit транзакция SELECT завершается после окончания statement, и её row lock освобождается. До следующего UPDATE другой worker вправе выбрать ту же строку со state=ready. Оба получат payload и сообщат о владении заданием. Сам по себе SKIP LOCKED решает ожидание конкурентов в момент чтения, но не создаёт долговечную бронь.

Объедините выбор и изменение одной SQL-командой; возвращаемое значение ещё нельзя отдавать обработчику до успешного commit:

```sql
BEGIN;
WITH picked AS (
    SELECT id
    FROM job
    WHERE state = 'ready'
    ORDER BY id
    LIMIT 1
    FOR UPDATE SKIP LOCKED
)
UPDATE job AS j
SET state = 'running',
    worker_id = :worker_id,
    started_at = clock_timestamp()
FROM picked
WHERE j.id = picked.id
RETURNING j.id, j.payload;
COMMIT;
-- Только теперь передаём payload выбранному worker.
```

SELECT держит lock до конца этой же транзакции, а UPDATE меняет условие пригодности задания. Другой worker либо пропустит заблокированную строку, либо после commit уже не найдёт её среди ready. Пустой результат означает «сейчас ничего не забрали», а не обязательно «во всей системе нет ready»: подходящая строка могла быть заблокирована. Ошибка commit означает, что передавать задание как подтверждённо своё нельзя. Для неопределённого исхода commit нужен идентификатор попытки и сверка состояния.

Проверяйте двумя сессиями: первая выполняет CTE и останавливается перед commit; вторая должна забрать другое задание либо получить пустой результат. После commit первой повторный захват не должен вернуть её id. После rollback первой её задание снова доступно. Проверка уникальности полученных id при параллельном запуске дополняет, но не заменяет это расписание.

Компромисс: если worker упадёт после commit, запись останется running. Для полноценной очереди нужны lease/heartbeat, правила повторного захвата и идемпотентная обработка; приведённый код гарантирует только атомарное первоначальное резервирование. Он также не обещает строгую FIFO-очерёдность при блокировках.

</details>

<a id="10-jdbc-batch-не-ограничивает-persistence-context"></a>

### 10. Сколько памяти займёт импорт миллиона строк?

Требование: импортировать миллион независимых строк одной транзакцией с rollback всего импорта при ошибке. Источник отдаёт `Iterator<Row>`, не удерживающий прошлые строки. Entity без связей, listener не накапливает объекты. ID генерируется sequence с подходящим allocationSize. Hibernate 6.6, Java 17. Одновременно в persistence context должно быть O(50) новых сущностей.

Плохой код:

```java
// hibernate.jdbc.batch_size=50
@Transactional
public void importRows(Iterator<Row> source) {
    while (source.hasNext()) {
        entityManager.persist(new ImportEntity(source.next()));
    }
}
```

Оцените число объектов в памяти после сотой и миллионной строки. Как проверить границу памяти при сохранении общего rollback?

<details>
<summary>Разбор</summary>

Настройка JDBC batching группирует совместимые SQL-команды для отправки драйверу. Она не удаляет managed entities из persistence context. После миллиона persist сессия может удерживать миллион объектов и служебные структуры, даже если SQL уже отправлялся пакетами. Автоматический flush тоже не означает очистки контекста. Поэтому увеличение batch_size не обеспечивает заявленную границу памяти и иногда добавляет давление на heap.

Обрабатываем источник последовательно и после каждого небольшого блока сначала отправляем изменения, затем отсоединяем сущности. Метод вызывается извне через Spring-прокси; entityManager — выделенный для этой операции транзакционный контекст:

```java
@Transactional
public void importRows(Iterator<Row> source) {
    entityManager.unwrap(org.hibernate.Session.class).setJdbcBatchSize(50);
    int pending = 0;
    while (source.hasNext()) {
        entityManager.persist(new ImportEntity(source.next()));
        if (++pending == 50) {
            entityManager.flush();
            entityManager.clear();
            pending = 0;
        }
    }
    if (pending != 0) {
        entityManager.flush();
        entityManager.clear();
    }
}
```

`clear` перед flush потерял бы ещё не синхронизированные изменения. Правильный порядок ограничивает managed-набор примерно текущими 50 независимыми сущностями. После clear старые объекты detached: последующие изменения их полей автоматически не сохранятся. Не следует применять такой clear к общему persistence context с чужими незавершёнными изменениями. Источник тоже обязан оставаться потоковым; переданный Iterator от огромного List не освобождает сам список.

Flush не делает commit, поэтому последующий rollback отменит SQL всех обработанных блоков. Проверьте ошибку ближе к концу импорта: после отката в таблице не должно быть ни одной новой строки. Через Hibernate statistics или профилирование проверьте число managed entities и отсутствие роста удержанных сущностей с объёмом импорта. Логи драйвера/метрики должны отдельно подтвердить фактические JDBC batches; последовательность вызовов persist не доказывает их наличие.

Компромисс — одна длинная транзакция всё равно удерживает соединение, создаёт WAL и может усиливать конкуренцию. Если нужна короткая транзакция на блок, придётся изменить требование общей атомарности или импортировать в staging. Генератор IDENTITY может отключать insert batching; sequence выбрана в условии сознательно.

</details>

<a id="11-join-fetch-превращает-страницу-в-полную-выборку"></a>

### 11. Как получить страницу заказов со всеми позициями?

Требование: вернуть первые 20 заказов с `id > afterId` по возрастанию id и со всеми items. У заказа максимум 50 items, есть заказы без items. Нужен один согласованный снимок чтения. PostgreSQL 17, Hibernate 6.6. Загружать все заказы ради одной страницы запрещено.

Плохой код:

```java
return em.createQuery("""
        select o from Order o left join fetch o.items
        where o.id > :after order by o.id
        """, Order.class)
    .setParameter("after", afterId)
    .setMaxResults(20)
    .getResultList();
```

Сравните результат и объём чтения на заказах с нулём, одной и пятьюдесятью позициями.

<details>
<summary>Разбор</summary>

Один заказ после соединения представлен несколькими SQL-строками. Ограничение до 20 таких строк могло бы обрезать items последнего заказа и вернуть меньше 20 родителей. Чтобы сохранить коллекции, Hibernate при сочетании collection fetch join и ограничения результатов может загрузить большой набор и применить пагинацию в памяти. Отсутствие N+1 тогда куплено чтением всех подходящих заказов. `select distinct o` не превращает 20 SQL-строк в 20 полных коллекций: SQL и объектная дедупликация работают с разной гранулярностью.

Сначала ограничиваем родителей без fetch join, затем загружаем коллекции только выбранных id. Ниже метод Spring-бина с обычным транзакционным `EntityManager` и `JpaTransactionManager`. Внешний вызов через прокси создаёт отдельную read-only `REPEATABLE READ`-транзакцию и чистый persistence context; extended context здесь не используется:

```java
@Transactional(readOnly = true, isolation = Isolation.REPEATABLE_READ,
               propagation = Propagation.REQUIRES_NEW)
public List<Order> page(long afterId) {
    List<Long> ids = em.createQuery("""
            select o.id from Order o
            where o.id > :after order by o.id
            """, Long.class)
        .setParameter("after", afterId).setMaxResults(20).getResultList();
    if (ids.isEmpty()) return List.of();

    return em.createQuery("""
            select distinct o from Order o left join fetch o.items
            where o.id in :ids order by o.id
            """, Order.class)
        .setParameter("ids", ids).getResultList();
}
```

Второй запрос не имеет limit, поэтому включает все items выбранных заказов; left join сохраняет родителей без items. Один снимок не позволяет удалению между запросами превратить выбранные 20 id в неполную страницу. Порядок возвращённых заказов явно восстановлен через order by, а порядок items отдельно задаётся mapping или сортировкой. Если допустимы меняющиеся данные между двумя SELECT, можно выбрать более слабый контракт и READ COMMITTED, но это уже другое требование.

Проверка: создайте больше 20 заказов, неодинаковое число items, включая ноль. Убедитесь, что вернулись именно первые 20 id и полные коллекции. В SQL первого запроса должен присутствовать limit; второй должен фильтроваться этими id. Включите `hibernate.query.fail_on_pagination_over_collection_fetch=true`, чтобы случайное возвращение старого запроса проваливалось явно.

Цена — два запроса и память для items выбранной страницы. Ограничение «50 items на заказ» существенно: без него даже страница одного родителя может быть огромной. Для такого случая нужна отдельная пагинация детей или DTO-агрегация. Долгую транзакцию не следует переносить между HTTP-страницами; `REQUIRES_NEW` внутри другой транзакции также потребует отдельного connection.

</details>

## Потоковая обработка и память

<a id="12-limit-стоит-после-материализации-всего-файла"></a>

### 12. Как выбрать первые сто различных идентификаторов из файла?

Требование: файл содержит до 10 миллионов строк, каждая — непустой ID длиной максимум 1000 символов. Вернуть первые 100 различных ID в порядке первого появления, либо все, если различных меньше 100. Дополнительная память должна зависеть от 100 ID, а не от размера файла. Сортировка не нужна.

Плохой код:

```java
try (Stream<String> lines = Files.lines(path, StandardCharsets.UTF_8)) {
    List<String> all = lines.distinct().toList();
    return all.stream().limit(100).toList();
}
```

Сравните два файла: в первом сотый различный ID встретился в начале, во втором его вообще нет. Сколько данных потребуется прочитать и сохранить?

<details>
<summary>Разбор</summary>

Первый `toList` заканчивает pipeline и полностью обходит источник. Чтобы получить все различные ID, `distinct` удерживает состояние для уже встреченных значений, а список сохраняет весь результат. Поздний limit работает уже с материализованным набором и не уменьшает работу первого pipeline. Слово Stream само по себе не означает ограниченное потребление памяти: важны состояние промежуточных операций, положение short-circuit операции и выбранный terminal operation.

При заданной семантике limit можно включить в тот же последовательный pipeline сразу после distinct:

```java
static List<String> firstUnique(Path path) throws IOException {
    try (Stream<String> lines = Files.lines(path, StandardCharsets.UTF_8)) {
        return lines.sequential()
                .distinct()
                .limit(100)
                .toList();
    }
}
```

Последовательный упорядоченный обход сохраняет первое появление каждого ID. После сотого различного значения downstream прекращает запрос новых элементов. Пока накоплено меньше ста уникальных строк, множество distinct тоже содержит меньше ста; после достижения границы больше не растёт. Результирующий список содержит максимум сто строк, источник закрывается при выходе из try. Ограниченная длина строки нужна для оценки памяти: даже одна произвольно длинная строка могла бы нарушить абсолютный byte-budget.

Для n прочитанных строк время ожидаемо O(n) с хешированием строк, дополнительное состояние — O(min(u,100) × L), где u — число различных ID, L — ограничение длины. Если во всём файле только 99 уникальных ID, придётся прочитать файл до конца; bounded memory не означает bounded I/O. `limit(100).distinct()` неравнозначен: он проверит только первые сто строк и может вернуть слишком мало уникальных значений.

Проверяйте файл с повторами перед сотым уникальным ID, файл с 99 различными и очень длинным хвостом, пустой файл и порядок результата. Для проверки ранней остановки удобно отдельно прогнать эквивалентный pipeline на счётчике через `peek`: после сотого нового ID хвост не должен обрабатываться. Не делайте `parallel()` частью решения без измерений: упорядоченный distinct в параллельном pipeline может потребовать существенной буферизации. Если нужна глобальная сортировка всех уникальных ID, перенести limit таким образом уже нельзя: потребуется другая задача, например top-k или внешняя сортировка.

</details>

## Контекст выполнения, блокировки и вычисления

### 13. Какой язык увидит следующая задача пула?

Однопоточный executor обслуживает независимые запросы. Если заголовок языка отсутствует, обработчик должен выбрать английский по умолчанию. Метод вызывается на верхней границе каждого запроса; вложенных вызовов нет.

```java
static final ThreadLocal<String> language = new ThreadLocal<>();

static void serve(String header, Runnable handler) {
    if (header != null) language.set(header);
    handler.run();
}
```

Первый запрос передал `"fr"`, а его обработчик завершился исключением. Затем тот же executor выполнил запрос без заголовка. Как проверить результат без ожидания по таймеру?

<details>
<summary>Разбор</summary>

`ThreadLocal` принадлежит потоку, который пул повторно использует. После первого запроса в потоке осталось `"fr"`. У второго запроса нет явного значения, но вызов `language.get()` всё ещё увидит старое.

```java
static void serve(String header, Runnable handler) {
    try {
        language.set(header == null ? "en" : header);
        handler.run();
    } finally {
        language.remove();
    }
}
```

Тест отправляет первый запрос через `submit`, вызывает `get()` и проверяет причину `ExecutionException`. В том же однопоточном executor второй запрос записывает увиденный язык в доступный тесту результат. Ожидайте `"en"` внутри второго вызова и `null` при отдельном чтении в том же рабочем потоке после завершения запроса. Вложенные области контекста потребовали бы восстановления внешнего значения; здесь граница одного запроса задана явно.

</details>

### 14. Что вернёт обновление занятого отчёта?

Фоновый расчёт и ручное обновление одного отчёта используют общий `ReentrantLock`. Ручной вызов должен вернуть `false` сразу, если расчёт уже идёт в другом потоке.

```java
boolean refresh() {
    try {
        if (!lock.tryLock()) return false;
        rebuild();
        return true;
    } finally {
        lock.unlock();
    }
}
```

Что фактически получит вызывающий код на каждой ветке, включая исключение из `rebuild()`?

<details>
<summary>Разбор</summary>

После неудачного `tryLock()` Java выполняет `finally` до возврата значения. Поток не владеет замком, поэтому `unlock()` бросит `IllegalMonitorStateException` вместо обещанного `false`. При успешном захвате замок освобождается штатно, даже если `rebuild()` бросил исключение.

```java
boolean refresh() {
    if (!lock.tryLock()) return false;
    try {
        rebuild();
        return true;
    } finally {
        lock.unlock();
    }
}
```

Для проверки занятый замок должен удерживать **другой** поток: повторный захват владельцем разрешён. Пусть владелец сигнализирует через `CountDownLatch` после захвата и держит замок до явного сигнала теста. Проверьте `false` и ноль вызовов `rebuild()`, затем освободите владельца. Отдельно заставьте `rebuild()` бросить исключение и убедитесь, что после него замок доступен другому потоку.

</details>

### 15. Сколько начислит параллельный расчёт баллов?

За отчёт начисляется 100 приветственных баллов плюс сумма всех операций. Пустой отчёт тоже даёт 100 баллов. Вход помещается в память, итог и промежуточные суммы помещаются в `long`.

```java
static long points(List<Long> deltas) {
    return deltas.parallelStream().reduce(100L, Long::sum);
}
```

Последовательная версия прошла проверку на операциях 2 и 3. Сохранится ли результат, если эти две записи попадут в разные части при параллельной обработке?

<details>
<summary>Разбор</summary>

`reduce(identity, op)` требует нейтрального значения: `op(identity, x)` должно давать `x`. Для сложения это ноль. Если две части обрабатываются отдельно, первая может дать 102, вторая 103, а после объединения выйдет 205. Конкретное разбиение реализации не обещано. Приветственные баллы относятся ко всему отчёту и прибавляются один раз после объединения.

```java
static long points(List<Long> deltas) {
    return 100L + deltas.parallelStream().mapToLong(Long::longValue).sum();
}
```

Проверяйте пустой список (100), `[2, 3]` (105) и `[2, -2]` (100). Проверку свойства разбиения можно сделать детерминированно: посчитайте чистые суммы двух произвольных половин отдельно, объедините их и прибавьте бонус один раз. Результат должен совпадать с обычным циклом для любого места разреза. Корректность отделена от вопроса о скорости: параллельный проход для коротких списков может добавить накладные расходы.

</details>
