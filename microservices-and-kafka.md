### 1. Архитектурный стиль REST и принципы RESTful API

REST (Representational State Transfer) — это архитектурный стиль взаимодействия компонентов распределенного приложения в сети. API называется RESTful, если оно удовлетворяет шести ограничениям (принципам) REST:

1. **Client-Server (Клиент-Сервер):** Разделение ответственности. Клиент отвечает за пользовательский интерфейс, а сервер — за хранение данных и бизнес-логику.
2. **Stateless (Отсутствие состояния):** Сервер не хранит информацию о состоянии клиента между запросами. Каждый запрос содержит всю необходимую информацию для его обработки.
3. **Cacheable (Кэшируемость):** Ответы сервера должны явно указывать, могут ли они быть кэшированы клиентом, что улучшает производительность.
4. **Uniform Interface (Единообразный интерфейс):** Ключевое ограничение, раскладывается на четыре подправила: ресурсы идентифицируются через URI (`/users/42`); манипуляция ресурсом идет через его представление (JSON); сообщения самоописательны (Content-Type, метод); HATEOAS — ответ содержит ссылки на связанные действия и ресурсы, и клиент ориентируется по ним.
5. **Layered System (Многоуровневая система):** Клиент не должен знать, взаимодействует ли он напрямую с конечным сервером или с промежуточными балансировщиками нагрузки.
6. **Code on Demand (Код по требованию, опционально):** Сервер может отправлять клиенту исполняемый код (например, JavaScript).

Частый follow-up: «все ли HTTP API являются RESTful?» — нет. Из-за HATEOAS большинство реальных API формально не REST, а «HTTP API в стиле REST». Зрелость API принято описывать Richardson Maturity Model: уровень 0 — один endpoint и один метод (RPC поверх POST), уровень 1 — ресурсы и отдельные URI, уровень 2 — HTTP-методы и статус-коды по назначению, уровень 3 — HATEOAS. Большинство продакшен-API живут на уровне 2, и это нормально.

**Пример реализации RESTful контроллера на Spring Boot:**
```java
@RestController
@RequestMapping("/api/v1/users")
public class UserController {

    @GetMapping("/{id}")
    public ResponseEntity<UserDto> getUserById(@PathVariable Long id) {
        UserDto user = userService.findById(id);
        return ResponseEntity.ok(user);
    }

    @PostMapping
    public ResponseEntity<UserDto> createUser(@RequestBody @Valid UserCreationDto dto) {
        UserDto created = userService.create(dto);
        URI location = URI.create("/api/v1/users/" + created.getId());
        return ResponseEntity.created(location).body(created); // 201 + заголовок Location
    }
}
```

### 2. HTTP-методы, идемпотентность и безопасность

В REST API ресурсы управляются с помощью стандартных HTTP-методов. Важными концепциями являются "безопасность" (метод не изменяет состояние сервера) и "идемпотентность" (многократное выполнение метода дает тот же результат, что и однократное).

*   **GET:** Получение ресурса. Безопасный и идемпотентный.
*   **HEAD:** То же, что GET, но без тела ответа — только заголовки. Безопасный и идемпотентный.
*   **POST:** Создание нового ресурса или запуск операции, не укладывающейся в CRUD. Небезопасный и неидемпотентный.
*   **PUT:** Полная замена ресурса или создание нового по заданному URI. Небезопасный, но идемпотентный.
*   **PATCH:** Частичное обновление ресурса. Небезопасный и неидемпотентный (зависит от реализации, но по спецификации не гарантирует идемпотентность).
*   **DELETE:** Удаление ресурса. Небезопасный, но идемпотентный.
*   **OPTIONS:** Запрос поддерживаемых методов для ресурса (используется браузерами в CORS preflight). Безопасный и идемпотентный.

Нюансы, которые спрашивают следом:

*   Идемпотентность — про **состояние сервера**, а не про код ответа. Повторный DELETE вернет 404, но состояние сервера такое же, как после первого вызова — значит, метод идемпотентен.
*   Безопасный метод может писать в логи и считать статистику — это не нарушение. Безопасность означает, что клиент не просил изменений ресурса и не отвечает за них.
*   PUT против PATCH: PUT заменяет ресурс целиком — поля, не переданные в теле, обнуляются; PATCH меняет только указанное. PATCH с операциями вида `increment` или `add to array` (JSON Patch) неидемпотентен: повтор даст +2 вместо +1.
*   Создание через PUT тоже легально — `PUT /users/123`, если id назначает клиент; если id генерирует сервер — только POST.

### 3. Коды ответов HTTP в REST API

RESTful API должно возвращать корректные HTTP статусы:
*   **1xx (Информационные):** Запрос получен, продолжается обработка (на практике почти не встречаются).
*   **2xx (Успешные):**
    *   200 OK — успешный запрос (GET, PUT, PATCH).
    *   201 Created — ресурс успешно создан (POST), положено вернуть заголовок `Location` с URI нового ресурса.
    *   202 Accepted — запрос принят, но обработается асинхронно (задача в очереди, долгая операция). Тело обычно содержит ссылку, где проверить статус.
    *   204 No Content — успешный запрос, не требующий возврата тела (часто при DELETE).
*   **3xx (Перенаправления):** 301 Moved Permanently, 304 Not Modified (ответ на условный GET с `If-None-Match` — ресурс не менялся, берите из кэша).
*   **4xx (Клиентские ошибки):**
    *   400 Bad Request — неверный синтаксис запроса (битый JSON, не прошла валидация формата).
    *   401 Unauthorized — требуется аутентификация (мы не знаем, кто вы).
    *   403 Forbidden — отказ в доступе (аутентификация пройдена, но прав не хватает).
    *   404 Not Found — ресурс не найден.
    *   405 Method Not Allowed — ресурс есть, но метод не поддерживается; в ответе заголовок `Allow` со списком допустимых.
    *   409 Conflict — конфликт состояний (например, дубликат email при регистрации, версия документа устарела).
    *   415 Unsupported Media Type — прислали XML там, где ждут JSON.
    *   422 Unprocessable Content — синтаксис валиден, но семантически запрос не проходит (бизнес-валидация: сумма отрицательная, дата в прошлом). В старых текстах — Unprocessable Entity, в RFC 9110 переименован.
    *   429 Too Many Requests — сработал rate limiter; полезно вернуть `Retry-After`.
*   **5xx (Серверные ошибки):**
    *   500 Internal Server Error — необработанное исключение внутри сервиса.
    *   502 Bad Gateway — прокси/gateway получил некорректный ответ от upstream-сервиса.
    *   503 Service Unavailable — сервис перегружен или на обслуживании, повторите позже (`Retry-After`).
    *   504 Gateway Timeout — upstream не ответил вовремя.

Различия, которые любят спрашивать: 400 против 422 (синтаксис против семантики), 401 против 403 (не аутентифицирован против не авторизован), 502 против 504 (плохой ответ против отсутствия ответа). Отдельная боль — API, которые на любую ошибку возвращают 200 с `"error": "..."` в теле: это ломает мониторинг, кэши и ретраи на стороне клиента.

### 4. Сравнение REST и SOAP

*   **Протокол/Стиль:** SOAP (Simple Object Access Protocol) — это протокол обмена структурированными сообщениями, REST — архитектурный стиль.
*   **Формат данных:** SOAP использует исключительно XML. REST поддерживает различные форматы: JSON (наиболее популярен), XML, Plain Text, HTML.
*   **Транспорт:** SOAP может использовать различные протоколы (HTTP, SMTP, TCP). REST жестко привязан к HTTP.
*   **Интерфейс:** SOAP предоставляет строгий контракт через WSDL (Web Services Description Language) — из него генерируются клиентские стабы. В REST контракт описывается через OpenAPI (Swagger), исторически WADL.
*   **Производительность:** REST требует меньше пропускной способности, так как JSON легче и нет тяжелой XML-обертки сообщений. Ответы REST можно кэшировать средствами HTTP; SOAP-запросы идут через POST и не кэшируются.
*   **Состояние:** REST по определению stateless. SOAP допускает stateful-операции.
*   **Безопасность и транзакции:** у SOAP есть целый стек стандартов WS-*: WS-Security (шифрование и подпись на уровне самого сообщения, а не транспорта), WS-AtomicTransaction (распределенные транзакции), WS-ReliableMessaging. В REST безопасность почти всегда сводится к HTTPS/TLS + OAuth2/JWT.
*   **Обработка ошибок:** в SOAP ошибки стандартизированы — элемент SOAP Fault в теле ответа. В REST это HTTP-статусы плюс произвольный формат тела (де-факто стандарт — Problem Details, RFC 7807/9457).

Где SOAP еще жив: банковская и госсфера, legacy-интеграции — там ценятся формальные контракты, WS-Security и готовая кодогенерация. Для новых публичных API берут REST, для межсервисного взаимодействия — REST или gRPC.

### 5. Сравнение REST и gRPC

gRPC (Google Remote Procedure Call) — современный фреймворк для удаленного вызова процедур, часто используемый для межсервисного взаимодействия.

*   **Транспорт:** REST обычно работает поверх HTTP/1.1. gRPC работает поверх HTTP/2, что обеспечивает мультиплексирование (много запросов в одном соединении без head-of-line blocking на уровне HTTP), сжатие заголовков и двунаправленный стриминг.
*   **Формат данных:** REST использует текстовый формат (JSON). gRPC использует бинарный формат Protocol Buffers (Protobuf), что делает сериализацию и десериализацию значительно быстрее и сообщения компактнее.
*   **Интерфейс:** REST использует URI и HTTP-методы. gRPC вызывает удаленные методы как локальные объекты (RPC стиль).
*   **Контракт:** gRPC использует строгий контракт, описываемый в `.proto` файлах, с кодогенерацией клиента и сервера под все основные языки.
*   **Стриминг:** gRPC из коробки поддерживает четыре вида вызовов: unary (запрос-ответ), server-streaming (сервер шлет поток), client-streaming и bidirectional. В REST стриминг приходится городить вручную (SSE, WebSocket — это уже другой протокол).
*   **Эволюция схемы:** поля в Protobuf идентифицируются номерами, а не именами. Добавить новое поле можно обратно совместимо; удалять или менять номер существующего нельзя (нужный номер помечают `reserved`).

Ограничения gRPC, о которых спрашивают следом: бинарный формат не читается глазами и не отлаживается curl'ом; в браузере gRPC напрямую не работает (нужен gRPC-Web через прокси вроде Envoy); нет встроенного HTTP-кэширования. Поэтому типичное разделение: gRPC — внутреннее межсервисное общение с высокой нагрузкой, REST — публичные API и браузерные клиенты.

**Пример Protobuf файла (.proto):**
```protobuf
syntax = "proto3";

service UserService {
  rpc GetUser (UserRequest) returns (UserResponse);
}

message UserRequest {
  int64 id = 1;
}

message UserResponse {
  int64 id = 1;
  string name = 2;
}
```

### 6. Архитектура и основные компоненты Apache Kafka

Apache Kafka — это распределенная платформа потоковой передачи событий (event streaming platform), обеспечивающая высокую пропускную способность, отказоустойчивость и горизонтальное масштабирование.

*   **Broker (Брокер):** Отдельный узел (сервер) в кластере Kafka, который принимает сообщения от продюсеров, сохраняет их на диск и отдает консьюмерам.
*   **Topic (Топик):** Логический канал или категория, куда публикуются сообщения. Топики делятся на партиции — единицы параллелизма и хранения (подробнее в вопросе 7).
*   **Producer (Продюсер):** Приложение, которое публикует сообщения в топики.
*   **Consumer (Консьюмер):** Приложение, которое подписывается на топики и читает из них сообщения.
*   **Zookeeper / KRaft:** Zookeeper исторически использовался для управления метаданными кластера и координации брокеров. Начиная с версии 2.8, Kafka получила внутренний протокол консенсуса KRaft (Kafka Raft); с 3.3 KRaft production-ready, а в Kafka 4.0 поддержка Zookeeper удалена полностью.

Что стоит знать глубже:

*   **Сообщение (record):** ключ, значение, timestamp, заголовки и offset — порядковый номер в партиции. Значение для Kafka — непрозрачный массив байт; сериализация (JSON, Avro, Protobuf) на стороне клиентов, схемы обычно хранят в Schema Registry.
*   **Репликация:** у каждой партиции есть лидер и реплики (followers) на других брокерах. Запись и чтение идут через лидера; реплики синхронно догоняют его. Набор реплик, поспевающих за лидером, называется ISR (In-Sync Replicas) — при падении лидера новым лидером становится реплика из ISR.
*   **Controller:** один из брокеров управляет метаданными кластера — назначает лидеров партиций, обрабатывает отказы брокеров. В KRaft-режиме это роль узлов кворума контроллеров.
*   **Почему Kafka быстрая:** партиция — это append-only лог, запись всегда последовательная (для диска это почти скорость RAM); данные не копируются через userspace лишний раз — брокер отдает их через zero-copy (sendfile) прямо из page cache ОС; продюсер и консьюмер работают батчами со сжатием. Лог пишется сегментными файлами, что упрощает удаление старых данных (вопрос 9).

### 7. Принципы работы Partition и Consumer Group в Kafka

**Partition (Партиция):** 
Топик разбивается на несколько партиций. Партиция — это упорядоченная, неизменяемая последовательность сообщений. 
*   **Масштабируемость:** Партиции могут быть распределены по разным брокерам, что позволяет параллельно записывать и читать данные.
*   **Порядок:** Порядок сообщений гарантируется только в пределах одной партиции.
*   **Ключи:** Если продюсер отправляет сообщение с ключом (key), Kafka хеширует ключ, чтобы гарантировать попадание сообщений с одинаковым ключом в одну и ту же партицию.

**Consumer Group (Группа консьюмеров):**
Консьюмеры объединяются в группы. 
*   Каждая партиция в топике может читаться только одним консьюмером из конкретной группы. Это обеспечивает балансировку нагрузки (Parallel Processing).
*   Если консьюмеров в группе больше, чем партиций, лишние консьюмеры будут простаивать. Отсюда правило: максимальный параллелизм обработки равен числу партиций.
*   Если один консьюмер падает, происходит **Rebalance (Ребалансировка)**, и партиции переназначаются оставшимся консьюмерам (подробно в вопросе 20).

Группы дают обе семантики обмена на одном топике. Консьюмеры внутри одной группы делят сообщения между собой — это competing consumers, классическая очередь. Разные группы читают топик независимо, каждая получает все сообщения — это pub-sub (fan-out). Типичная картина: топик `orders` читают группа `billing` (начисления), группа `notifications` (письма) и группа `analytics` (витрина) — три независимых потребителя потока, у каждого свой offset.

**Пример конфигурации Spring Kafka Consumer:**
```java
@KafkaListener(topics = "orders-topic", groupId = "orders-processing-group")
public void listen(ConsumerRecord<String, OrderDto> record) {
    System.out.println("Received order: " + record.value() + " from partition: " + record.partition());
}
```

### 8. Гарантии доставки сообщений (Acks, Exactly-once) и управление Offset

**Offset (Смещение):** Уникальный последовательный номер сообщения в партиции. Консьюмер отслеживает, какие сообщения он прочитал, сохраняя (коммитя) текущий offset. Закоммиченные оффсеты хранятся в служебном топике `__consumer_offsets` по ключу (group, topic, partition) — поэтому после рестарта или ребаланса другой консьюмер группы продолжает с того же места.

**Управление оффсетами.** По умолчанию включен автокоммит (`enable.auto.commit=true`, интервал `auto.commit.interval.ms=5000`): клиент периодически коммитит оффсеты последнего вернувшегося `poll()`. Ловушка в том, что автокоммит не знает, закончилась ли обработка: poll вернул батч, оффсеты уехали, приложение упало посреди обработки — сообщения потеряны (фактически at-most-once). Для at-least-once автокоммит выключают и коммитят вручную после успешной обработки (`commitSync`/`commitAsync`; в Spring Kafka — `AckMode.MANUAL` с `Acknowledgment.acknowledge()` или `AckMode.RECORD/BATCH`).

**Acks (Подтверждения от брокера продюсеру):**
*   `acks=0`: Продюсер не ждет подтверждения. Возможна потеря данных.
*   `acks=1`: Продюсер ждет подтверждения только от Leader-партиции. Если лидер упадет сразу после записи, не успев отреплицироваться, сообщение потеряно.
*   `acks=all (или -1)`: Продюсер ждет подтверждения от лидера и всех синхронизированных реплик (In-Sync Replicas - ISR). Максимальная надежность.

Нюанс, который спрашивают следом: `acks=all` сам по себе не гарантирует сохранность — он ждет только текущих ISR. При `replication.factor=3` и дефолтном `min.insync.replicas=1` подтверждение может дать один лидер, если реплики отстали и вывалились из ISR. Классическая надежная связка: `replication.factor=3`, `min.insync.replicas=2`, `acks=all` — тогда запись выживает отказ любого одного брокера, а при деградации ISR ниже двух брокер отвечает ошибкой, а не молчаливой потерей.

**Семантика доставки сообщений консьюмеру:**
1.  **At-most-once (Не более одного раза):** Сообщение может быть потеряно, но никогда не будет дублировано. (Коммит offset до обработки).
2.  **At-least-once (Не менее одного раза):** Сообщение никогда не потеряется, но может быть обработано несколько раз. (Коммит offset после обработки). Дефолтный выбор на практике + идемпотентный консьюмер (вопрос 16).
3.  **Exactly-once (Точно один раз):** Сообщение обрабатывается ровно один раз. В Kafka реализуется транзакционным API (Transactional Producer с `transactional.id`) поверх идемпотентного продюсера (`enable.idempotence=true`): консьюмер читает из топика, обрабатывает и пишет результат в другой топик в одной транзакции (consume-transform-produce). Консьюмеры с `isolation.level=read_committed` не видят незакоммиченные транзакции. Внешние системы (БД, HTTP API) эта семантика не покрывает.

### 9. Хранение данных в Kafka: Retention Policy и Log Compaction

Kafka хранит данные на диске (в виде append-only логов), в отличие от традиционных брокеров очередей, которые удаляют сообщение после прочтения.

*   **Retention Policy (Политика удержания):** Определяет, как долго сообщения хранятся в топике. Настраивается по времени (например, `log.retention.hours=168` — 7 дней) или по объему (например, `log.retention.bytes=1073741824` — 1 ГБ на партицию). Старые сегменты лога удаляются целиком. Это `cleanup.policy=delete` — дефолт.
*   **Log Compaction (Сжатие лога):** Режим `cleanup.policy=compact`. Вместо удаления по времени Kafka сохраняет как минимум самое последнее сообщение для каждого уникального ключа, вычищая устаревшие версии. Полезно для восстановления состояния (например, кэша или конфигураций): новый консьюмер читает компактный топик с нуля и получает актуальный «снимок» по всем ключам. Можно совместить оба режима: `[compact,delete]` — и компакшн, и ограничение по времени.

Как работает компакшн изнутри: лог партиции делится на сегменты; фоновый log cleaner переписывает только неактивные (закрытые) сегменты, оставляя последнее значение каждого ключа. Активный сегмент, куда идет запись, не трогается. После компакшна оффсеты выживших сообщений не меняются — в последовательности просто появляются «дырки». Агрессивность регулируется `min.cleanable.dirty.ratio` (доля «грязных» сообщений, после которой сегмент чистится) и `segment.bytes` / `segment.ms`.

Частые follow-up:

*   **Tombstone:** сообщение с ключом и значением `null` — маркер удаления. Компакшн держит его `delete.retention.ms` (по умолчанию 24 часа), чтобы все консьюмеры успели увидеть удаление, затем вычищает ключ совсем.
*   **Гарантии компакшна слабые:** он обещает лишь «последнее значение ключа не потеряется», но не то, что старые версии исчезнут быстро — читатель всегда должен быть готов к встрече с устаревшими значениями одного ключа.
*   Компактный топик — не key-value база: нельзя спросить «дай значение по ключу», можно только читать поток оффсет за оффсетом.

### 10. Сравнение Apache Kafka и RabbitMQ

*   **Архитектура:** RabbitMQ — это брокер сообщений на основе очередей (Smart Broker / Dumb Consumer). Kafka — распределенный лог (Dumb Broker / Smart Consumer).
*   **Хранение:** RabbitMQ удаляет сообщения после их успешной обработки (ack). Kafka хранит сообщения на диске заданное время, что позволяет перечитывать их (replay) — отмотать offset назад или подключить нового консьюмера к истории.
*   **Модель доставки:** RabbitMQ пушит сообщения консьюмерам (push, темп регулируется prefetch/QoS). Консьюмер Kafka сам тянет данные (pull), контролируя темп и позицию чтения.
*   **Маршрутизация:** RabbitMQ имеет гибкую систему маршрутизации (Exchanges, Bindings, Routing Keys, topic-шаблоны, fanout). В Kafka маршрутизация базируется на топиках и ключах сообщений; «отфильтровать» сообщение на брокере нельзя — консьюмер читает всё и отбрасывает лишнее сам.
*   **Возможности очереди:** у RabbitMQ из коробки есть TTL на сообщение и очередь, приоритетные очереди, dead letter exchange (DLX) для необработанных сообщений, отложенная доставка через плагины. В Kafka это собирается вручную (отдельные retry/DLQ-топики).
*   **Порядок:** в Kafka порядок гарантирован внутри партиции, и при правильном ключе (вопрос 21) параллелизм его не ломает. В RabbitMQ порядок держится только при одном консьюмере на очередь — несколько конкурирующих консьюмеров с ретраями и nack порядок разрушают.
*   **Производительность:** Kafka выдерживает значительно бОльшую пропускную способность (миллионы сообщений в секунду) благодаря последовательной записи на диск и отсутствию сложных индексов. RabbitMQ оптимизирован под низкую задержку доставки, а не под объем.

Когда что выбирать: RabbitMQ — классические очереди задач (фоновые джобы, отправка писем), сложная маршрутизация, низкая латентность, скромные объемы. Kafka — поток событий с высокой нагрузкой, несколько независимых потребителей одного потока, replay истории, стрим-обработка (Kafka Streams), event sourcing.

### 11. Микросервисная архитектура: преимущества, недостатки и отличие от монолита

**Монолитная архитектура** представляет собой единое приложение, где все модули (UI, бизнес-логика, доступ к данным) скомпилированы и развернуты вместе.

**Микросервисная архитектура** разбивает приложение на набор небольших, слабо связанных сервисов. Каждый сервис работает в собственном процессе, имеет свою базу данных и выполняет конкретную бизнес-задачу (Bounded Context).

**Преимущества:**
*   **Независимое развертывание:** Обновление одного сервиса не требует перезапуска всей системы.
*   **Масштабируемость:** Можно масштабировать только те сервисы, которые испытывают высокую нагрузку (например, через Kubernetes).
*   **Технологическое разнообразие (Polyglot persistence/programming):** Каждый сервис может быть написан на оптимальном языке и использовать подходящую БД.
*   **Изоляция сбоев:** Падение одного микросервиса не приводит к отказу всей системы.

**Недостатки:**
*   **Сложность инфраструктуры:** Требуются инструменты CI/CD, контейнеризация (Docker), оркестрация (Kubernetes), Service Mesh.
*   **Сеть вместо вызова метода:** Межмодульное взаимодействие превращается в сетевые вызовы — латентность, сериализация, частичные отказы (сервис Б недоступен, а А жив). Отсюда весь набор резилентности из вопросов 12–13.
*   **Распределенные транзакции:** Сложно поддерживать согласованность данных (ACID) между сервисами, приходится использовать паттерн Saga и Eventual Consistency.
*   **Сложность отладки и мониторинга:** Требуется распределенная трассировка (Zipkin, Jaeger) и централизованное логирование (ELK).
*   **Сложность тестирования:** End-to-end тест требует поднять связку сервисов; на помощь приходят контрактные тесты (вопрос 19).

Два нюанса, которые отличают зрелый ответ на собеседовании:

*   **Распределенный монолит** — антипаттерн: система разбита на сервисы, но они тесно связаны (общая БД, синхронные цепочки вызовов) и релизятся только вместе. Получаются все минусы микросервисов без плюсов. Границы сервисов должны совпадать с границами бизнес-контекстов (DDD, Bounded Context), а не нарезаться по техническим слоям.
*   **Когда микросервисы не нужны:** маленькая команда и молодой продукт с размытыми границами домена. Микросервисы решают в первую очередь организационную проблему — независимые команды и релизы (закон Конвея: архитектура копирует структуру коммуникаций). Разумный путь — начать с модульного монолита (четкие границы модулей в одном артефакте) и выделять сервисы по мере появления реальных причин: независимое масштабирование, отдельная команда, другой жизненный цикл.

### 12. Паттерны взаимодействия микросервисов (API Gateway, Saga, Circuit Breaker)

*   **API Gateway (Шлюз API):** Единая точка входа для всех клиентов. Инкапсулирует внутреннюю архитектуру, обеспечивает аутентификацию, маршрутизацию, балансировку нагрузки, rate limiting. В Spring-стеке — Spring Cloud Gateway. Правило: бизнес-логике на gateway не место, только сквозные concerns. Разновидность — BFF (Backend for Frontend): отдельный gateway на каждый тип клиента (web, mobile), агрегирующий ответы под конкретный UI.
*   **Circuit Breaker (Предохранитель):** Предотвращает каскадные сбои. Если сервис А вызывает сервис Б, и сервис Б начинает долго отвечать или падать, Circuit Breaker в сервисе А "размыкается" и сразу возвращает ошибку или fallback-значение, не перегружая больной сервис Б. Популярная реализация: Resilience4j (подробный пример в вопросе 13). Классический follow-up — три состояния автомата:
    *   **Closed (замкнут):** нормальный режим, вызовы проходят, брейкер считает долю ошибок в скользящем окне.
    *   **Open (разомкнут):** доля ошибок превысила порог — вызовы не выполняются вообще, сразу fallback. Сервис Б получает передышку на восстановление.
    *   **Half-Open (полуоткрыт):** по истечении `waitDurationInOpenState` брейкер пропускает несколько пробных вызовов. Успешные — переход в Closed, провальные — обратно в Open с новым таймаутом.
*   **Saga:** Паттерн управления распределенными транзакциями. Транзакция разбивается на локальные транзакции в каждом сервисе. Если одна из них завершается ошибкой, запускаются компенсирующие транзакции для отката предыдущих шагов. Реализуется через хореографию (события, Kafka) или оркестрацию (централизованный координатор).

Пример саги на заказе: Order Service создает заказ (статус NEW) и публикует событие → Payment Service списывает деньги → Inventory Service резервирует товар → заказ подтвержден. Если резерв не удался, запускается компенсация в обратном порядке: вернуть деньги, отменить заказ (статус CANCELLED). Компенсация — это не rollback: данные уже закоммичены и видны другим, поэтому «откат» делается новой бизнес-операцией, а промежуточные состояния (деньги списаны, товара нет) система обязана переживать.

Хореография против оркестрации: при хореографии каждый сервис слушает события и сам знает, что делать дальше — нет центральной точки, легко добавлять шаги, но flow размазан по коду и его сложно увидеть целиком. При оркестрации центральный координатор (Camunda, Temporal, свой Saga orchestrator) командует шагами и хранит состояние процесса — flow наглядный, но координатор становится точкой связанности и должен быть отказоустойчивым.

### 13. Резилентность микросервисов: Retry, Timeout, Rate Limiter и Bulkhead (Resilience4j)

Circuit Breaker (см. вопрос 12) — только часть набора. Resilience4j — это модульная библиотека: каждый паттерн подключается отдельной зависимостью и оборачивает вызов внешнего сервиса.

*   **Retry:** Повторный вызов при временных сбоях (сетевая ошибка, 503). Обязательно с backoff — пауза растет между попытками (100 мс, 200 мс, 400 мс...), иначе ретраи добивают и так перегруженный сервис. Плюс jitter — случайный разброс паузы, чтобы тысячи клиентов, упавших одновременно, не долбили сервис синхронными волнами (thundering herd). Важно: ретраить можно только идемпотентные операции — повторный POST без ключа идемпотентности создаст дубликаты.
*   **Timeout (TimeLimiter):** Жесткое ограничение времени ожидания ответа. Без него потоки зависают на медленном downstream-сервисе, пул исчерпывается, и падает уже наш сервис — классический каскадный сбой.
*   **Rate Limiter:** Ограничение числа вызовов в единицу времени. Используется в двух ролях: не задушить чужой API (у внешних интеграций есть лимиты) и защитить свой сервис от всплесков.
*   **Bulkhead (Переборка):** Изоляция ресурсов. Отдельный пул потоков/семафор на каждый внешний вызов: если один downstream завис и занял все свои потоки, остальные вызовы продолжают работать. Аналогия — отсеки корабля: течь в одном не топит весь корабль.

Связка с Circuit Breaker: обычно оборачивают вместе — сначала Retry повторяет одиночный вызов, Circuit Breaker следит за статистикой ошибок и размыкается при системном отказе (чтобы не ретраить заведомо мертвый сервис), Bulkhead и TimeLimiter ограничивают ресурсы.

**Пример конфигурации (application.yml):**
```yaml
resilience4j:
  retry:
    instances:
      paymentService:
        maxAttempts: 3
        waitDuration: 200ms
        enableExponentialBackoff: true
        exponentialBackoffMultiplier: 2
        retryExceptions:
          - org.springframework.web.client.ResourceAccessException
  circuitbreaker:
    instances:
      paymentService:
        failureRateThreshold: 50
        slidingWindowSize: 10
        waitDurationInOpenState: 30s
  bulkhead:
    instances:
      paymentService:
        maxConcurrentCalls: 20
```

```java
@Retry(name = "paymentService")
@CircuitBreaker(name = "paymentService", fallbackMethod = "paymentFallback")
public PaymentResult charge(PaymentRequest request) {
    return paymentClient.charge(request);
}

public PaymentResult paymentFallback(PaymentRequest request, Throwable ex) {
    return PaymentResult.deferred(request.getOrderId()); // отложим оплату, вернем 202
}
```

Частый follow-up: «чем Resilience4j лучше Hystrix?» — Hystrix в maintenance mode с 2018 года, Resilience4j легче (без тащущегося за собой rxjava), работает на Java 8+ functional style и живее развивается.

### 14. Service Discovery: Eureka, Consul, client-side и server-side discovery

В микросервисах адреса инстансов не фиксированы: контейнеры перезапускаются, масштабируются, IP меняются. Service Discovery решает вопрос «по какому адресу сейчас живет сервис X» через реестр (registry), куда каждый инстанс регистрируется при старте и периодически шлет heartbeat.

*   **Eureka (Netflix):** Реестр от Spring Cloud Netflix. Клиенты сами регистрируются и кэшируют копию реестра — поэтому Eureka продолжает работать даже при временной недоступности сервера (AP по CAP).
*   **Consul (HashiCorp):** Реестр + key-value хранилище + health checks. Данные согласованы через Raft (CP по CAP). Часто используется и как конфиг-сервер.

**Client-side discovery:** Клиент сам спрашивает у реестра список живых инстансов и сам выбирает, куда слать запрос (балансировка на клиенте). В Spring это `RestTemplate`/`WebClient`/`Feign` с `@LoadBalanced` + Spring Cloud LoadBalancer.

```java
@Bean
@LoadBalanced // "http://order-service" резолвится через реестр в реальный host:port
public RestTemplate restTemplate() {
    return new RestTemplate();
}
```

**Server-side discovery:** Клиент обращается к балансировщику/роутеру (например, AWS ALB, Kubernetes Service, API Gateway), а тот уже знает живые инстансы и перенаправляет запрос. Клиент про реестр ничего не знает. В Kubernetes это модель по умолчанию: DNS-имя Service + kube-proxy разруливают всё сами, и отдельная Eureka там обычно не нужна.

Сравнение: client-side дает меньше сетевых прыжков и гибкую балансировку, но привязывает клиента к реестру и требует библиотеки на каждом языке. Server-side проще для клиентов и полиглот-стека, но добавляет посредника, который надо делать отказоустойчивым.

### 15. Централизованная конфигурация: Spring Cloud Config, Consul и Vault

Когда сервисов десятки, держать `application.yml` в каждом репозитории и пересобирать образ ради смены фичефлага неудобно. Централизованная конфигурация выносит настройки во внешнее хранилище.

*   **Spring Cloud Config Server:** Конфиг-сервер, который отдает настройки из Git-репозитория (есть и другие бэкенды) по HTTP. Клиенты при старте забирают свой конфиг по имени приложения и профилю: `/{application}/{profile}` → `order-service-prod.yml`. Git дает версионирование конфигов и историю изменений из коробки.
*   **Consul / Vault:** Consul хранит конфигурацию в своем key-value хранилище. Vault — про секреты: пароли, токены, динамические креденшелы к БД с автоматической ротацией. На практике часто связка: обычные настройки в Config Server/Consul, секреты в Vault.

**Обновление без рестарта.** Ловушка в том, что просто поменять файл в Git мало — работающие инстансы его не перечитают. Варианты:

*   `@RefreshScope` на бине + вызов `POST /actuator/refresh` на каждом инстансе: Spring пересоздаст refresh-бины с новыми значениями.
*   Spring Cloud Bus: конфиг-сервер шлет событие `RefreshRemoteApplicationEvent` в брокер (Kafka/RabbitMQ), и все подписанные сервисы обновляются сами — не нужно ходить на каждый инстанс руками.

```java
@RefreshScope // бин перечитает @Value при /actuator/refresh
@RestController
public class FeatureController {

    @Value("${feature.new-checkout:false}")
    private boolean newCheckoutEnabled;
}
```

Ограничение: `@RefreshScope` обновляет только бины этого scope и перечитываемые `@ConfigurationProperties`. Значения, зашитые в бины singleton-scope при старте (например, пул соединений с БД), без рестарта не поменяешь.

### 16. Идемпотентность консьюмера Kafka: дедупликация и idempotent producer

Дефолтная и самая практичная семантика доставки — at-least-once: оффсет коммитится после обработки, значит при падении консьюмера после обработки, но до коммита сообщение будет прочитано повторно. Дубли неизбежны, и единственный надежный ответ — идемпотентный консьюмер: повторная обработка того же сообщения не меняет результат.

Основные подходы:

*   **Дедупликация по message id:** Продюсер кладет в сообщение бизнес-ключ (например, `orderId` + тип события или UUID). Консьюмер перед обработкой проверяет, не видел ли он уже этот id — в отдельной таблице `processed_messages`, в Redis с TTL или через unique constraint в целевой таблице. Важно: вставка записи о процессинге и бизнес-апдейт должны быть в одной транзакции БД, иначе между ними успеешь упасть.
*   **Естественная идемпотентность:** Операция сама по себе безопасна к повторам — `UPDATE account SET balance = 100 WHERE id = 1` (а не `balance = balance + 100`), upsert по ключу.

```java
@KafkaListener(topics = "orders", groupId = "billing")
@Transactional
public void handle(OrderEvent event) {
    if (processedRepository.existsById(event.getEventId())) {
        return; // дубль, уже обработали
    }
    billingService.apply(event);
    processedRepository.save(new ProcessedMessage(event.getEventId()));
}
```

**Idempotent producer** — отдельная вещь, не путать с консьюмером. Настройка `enable.idempotence=true` (по умолчанию включена с Kafka 3.0) заставляет брокер отбрасывать дубли, которые возникают при ретраях продюсера: продюсер получает PID и нумерует сообщения sequence number'ами, брокер записывает каждую пару (PID, seq) один раз. Это убирает дубли *внутри лога Kafka*, но не спасает от дублей при повторной обработке на консьюмере — для этого нужна дедупликация выше. Поверх идемпотентности строятся транзакции Kafka (`transactional.id`) для exactly-once между несколькими партициями.

Частый follow-up: «почему нельзя просто включить exactly-once и забыть про дубли?» — exactly-once покрывает только связку Kafka→Kafka (read-process-write через транзакции). Как только в обработчике есть запись во внешнюю БД или вызов API, транзакция Kafka её не контролирует, и без идемпотентного консьюмера дубли вернутся.

### 17. Паттерн Transactional Outbox и Inbox

Задача: сервис должен в одной операции обновить свою БД и опубликовать событие в Kafka. Распределенной транзакции (2PC) между БД и брокером нет. Если писать сначала в БД, а потом в Kafka — сервис может упасть между двумя вызовами, и событие потеряно. Если наоборот — событие уйдет, а транзакция в БД откатится, и консьюмеры узнают о том, чего не было.

**Transactional Outbox:** В одной локальной транзакции БД пишем и бизнес-сущность, и запись в таблицу `outbox` в той же базе. Отдельный ретранслятор читает outbox и публикует события в Kafka, помечая их отправленными. Атомарность обеспечивает транзакция БД, доставку — ретранслятор с ретраями.

```java
@Transactional
public void createOrder(CreateOrderCommand cmd) {
    Order order = orderRepository.save(new Order(cmd));
    outboxRepository.save(new OutboxEvent(   // та же транзакция
        "orders", order.getId().toString(),
        objectMapper.writeValueAsString(new OrderCreatedEvent(order))));
}
```

Ретранслятор делают двумя способами:
*   **Polling publisher:** Планировщик периодически выбирает неотправленные записи (`SELECT ... WHERE sent = false FOR UPDATE SKIP LOCKED`). Просто, но добавляет задержку и нагрузку на БД.
*   **CDC (Change Data Capture):** Debezium читает WAL/бинлог базы и стримит новые строки outbox-таблицы прямо в Kafka. Меньше задержка, нет поллинга, но плюс один инфраструктурный компонент.

**Inbox** — зеркальный паттерн на стороне консьюмера: входящее сообщение сначала сохраняется в inbox-таблицу (по сути, та же дедупликация по message id из вопроса 16), и обработчик работает с ней как с очередью задач в своей транзакции.

Цена паттерна — eventual consistency: между записью в БД и публикацией события есть окно, и консьюмер увидит изменение не мгновенно. Плюс outbox-таблицу надо чистить от старых отправленных записей.

### 18. Распределенная трассировка: traceId, spanId, Micrometer Tracing, Jaeger и Zipkin

Когда запрос проходит через пять сервисов, по логам одного сервиса причину тормозов не найти. Распределенная трассировка склеивает путь запроса через все сервисы в одну картину.

*   **traceId:** Общий идентификатор всего запроса. Генерируется на входе (обычно на API Gateway) и передается дальше в HTTP-заголовках (`traceparent` по стандарту W3C Trace Context, раньше — `X-B3-*`) или в хедерах Kafka-сообщений.
*   **spanId:** Идентификатор одной операции внутри трейса — один вызов сервиса, один запрос в БД. Спаны образуют дерево: у каждого есть parent span. По длительности спанов видно, где именно застряло время.
*   **Micrometer Tracing:** Стандарт в Spring Boot 3 (пришел на смену Spring Cloud Sleuth, который больше не развивается). Сам по себе только создает спаны и кладет traceId/spanId в MDC логов; экспорт — через OpenTelemetry или Brave.
*   **Jaeger / Zipkin:** Бэкенды, куда спаны отправляются и где по ним можно искать и смотреть waterfall-диаграмму запроса. Сейчас чаще всего встречается связка OpenTelemetry Collector + Jaeger/Tempo.

```yaml
management:
  tracing:
    sampling:
      probability: 0.1 # сэмплируем 10% запросов, на проде 100% дорого
logging:
  pattern:
    level: "%5p [${spring.application.name:},%X{traceId:-},%X{spanId:-}]"
```

Трейсы — один из трех столпов наблюдаемости (observability):
*   **Логи** — что произошло (детали, стектрейсы). Централизуются в ELK/Loki, traceId в MDC позволяет отфильтровать логи одного запроса по всем сервисам.
*   **Метрики** — агрегаты: RPS, latency, error rate (Micrometer + Prometheus + Grafana). Отвечают на вопрос «есть ли проблема вообще».
*   **Трейсы** — где именно в цепочке вызовов проблема. Метрики говорят «медленно», трейс показывает, какой спан тормозит.

### 19. Версионирование API и Consumer-Driven Contracts

**Версионирование API.** Публичное API меняется, а клиенты обновляются не сразу — старые версии приходится поддерживать. Основные способы:

*   **URI versioning:** `/api/v1/users`, `/api/v2/users`. Самый простой и наглядный, легко кэшируется и маршрутизируется на gateway. Минус — версия «зашита» в адрес ресурса, что пуристы считают нарушением REST.
*   **Header versioning:** Версия в кастомном заголовке (`X-API-Version: 2`) или в Accept: `application/vnd.company.v2+json` (content negotiation). URI остается чистым, но API сложнее тестировать в браузере и кэшировать.
*   **Query-параметр:** `/users?version=2`. Редко, обычно считается наименее удачным вариантом.

На практике чаще всего URI versioning: просто, явно, понятно в логах и на gateway. Важнее само правило: ломающие изменения (удаление поля, смена типа) — только новая версия; обратно совместимые (новое необязательное поле) — можно в текущую.

**Consumer-Driven Contracts (CDC).** В микросервисах провайдер меняет API, не зная всех своих потребителей, и ломает их молча. Идея CDC: контракт пишет потребитель — «я вызываю `GET /users/1` и жду JSON с полями id, name, email». Провайдер в CI прогоняет эти контракты как тесты, и если его изменение ломает ожидания хотя бы одного потребителя — сборка падает до выкатки.

Реализация в Spring-стеке — **Spring Cloud Contract**: контракт описывается на Groovy DSL или YAML, из него генерируются автотесты для провайдера и stub для потребителя (WireMock), чтобы потребитель мог тестироваться без живого провайдера.

```groovy
Contract.make {
    request {
        method GET()
        url("/users/1")
    }
    response {
        status OK()
        body(id: 1, name: "Ivan", email: "ivan@example.com")
        headers { contentType(applicationJson()) }
    }
}
```

Альтернатива из другого стека — Pact, идея та же, контракты хранятся в Pact Broker.

### 20. Rebalance консьюмер-групп в Kafka: причины, последствия, static membership

Rebalance — это перераспределение партиций между консьюмерами группы. Запускает его координатор группы (один из брокеров). Пока идет rebalance, вся группа останавливается и ничего не читает — это stop-the-world пауза.

Причины:
*   Консьюмер присоединился к группе или штатно вышел (деплой, масштабирование).
*   Консьюмер упал или «завис»: перестал слать heartbeat дольше `session.timeout.ms` (по умолчанию 45 с).
*   **Медленная обработка:** консьюмер не вызывал `poll()` дольше `max.poll.interval.ms` (по умолчанию 5 мин). Координатор считает его зависшим и выгоняет из группы. Классическая причина — тяжелая обработка батча из `max.poll.records` сообщений в том же потоке, что и poll.
*   Изменилась подписка или число партиций в топике.

Последствия:
*   Пауза в обработке на время ребаланса. Частые ребалансы («flapping») могут почти остановить группу.
*   **Дубли:** консьюмер, чьи партиции отобрали, мог обработать сообщения, но не успеть закоммитить оффсет — новый владелец партиции прочитает их повторно. Еще один аргумент за идемпотентный консьюмер (вопрос 16).

Что делать:
*   Следить, чтобы обработка батча укладывалась в `max.poll.interval.ms`: уменьшить `max.poll.records`, увеличить интервал или вынести обработку в отдельный пул потоков (с паузой poll).
*   **Static membership:** задать консьюмеру постоянный `group.instance.id`. Тогда при перезапуске (деплой, рестарт пода) консьюмер возвращается с тем же идентификатором, координатор узнает его и не запускает rebalance — партиции остаются за ним. Заметно удешевляет rolling deploy.
*   Назначение партиций через `CooperativeStickyAssignor` (incremental cooperative rebalance): перераспределяются только затронутые партиции, а не вся группа целиком, как при старом eager-протоколе.

### 21. Ключ партиционирования и гарантии порядка в Kafka

**Порядок гарантируется только внутри одной партиции.** Между партициями никакого порядка нет: сообщения из партиции 0 и партиции 1 читаются независимо и конкурентно. Это фундаментальное следствие параллелизма Kafka, и на собеседовании это один из самых частых вопросов.

Ключ сообщения — механизм управления порядком. Если ключ задан, дефолтный партиционер кладет сообщение в партицию `hash(key) % numPartitions` — все сообщения с одним ключом всегда попадают в одну партицию и читаются одним консьюмером строго по порядку. Типичный пример: ключ `orderId` — все события заказа (`created → paid → shipped`) обрабатываются в правильной последовательности, а разные заказы параллелятся.

Ловушки:

*   **Добавление партиций ломает маршрутизацию:** формула зависит от `numPartitions`. Увеличили партиции с 6 до 12 — старые и новые сообщения одного ключа окажутся в разных партициях. Поэтому число партиций закладывают с запасом заранее.
*   **Горячие партиции:** если распределение ключей перекошено (один «крупный клиент» генерирует 50% трафика; null-ключи; монотонный ключ типа timestamp), одна партиция получает львиную долю нагрузки, а остальные простаивают. Партиционирование перестает масштабировать. Решения: составной ключ (`customerId + date`), salting — добавление случайного суффикса к ключу с последующей сборкой на консьюмере, либо кастомный `Partitioner`.
*   Сообщения **без ключа** распределяются равномерно (sticky partitioner: батчами прилипают к случайной партиции) — порядка для них нет вообще.
*   Даже внутри партиции порядок может нарушиться на продюсере, если `max.in.flight.requests.per.connection > 1` при включенных ретраях и выключенной идемпотентности: неудачный батч, переотправленный позже успешного, встанет в лог не на свое место. `enable.idempotence=true` эту проблему снимает.

### 22. Event-Driven против Request-Response: когда события, когда синхронный вызов

Два базовых способа связи сервисов, и зрелый ответ на собеседовании — не «Kafka лучше», а «зависит от природы взаимодействия».

**Request-Response (REST, gRPC):** Сервис А синхронно вызывает сервис Б и ждет ответ.
*   Подходит, когда вызывающему нужен ответ прямо сейчас, чтобы продолжить: проверка баланса перед списанием, получение данных для отображения пользователю, валидация.
*   Плюсы: просто, понятный flow, ошибку видно сразу, легко дебажить.
*   Минусы: временная связанность — если Б лежит или тормозит, страдает и А (каскадные сбои, отсюда Circuit Breaker и таймауты из вопроса 13). Сервисы жестко связаны по доступности.

**Event-Driven (Kafka, RabbitMQ):** Сервис А публикует событие («заказ создан»), заинтересованные сервисы подписаны и реагируют асинхронно.
*   Подходит для фактов, уже случившихся в системе: нотификации, обновление поискового индекса, аналитика, запуск следующих шагов процесса. Особенно когда подписчиков несколько или их число будет расти — новый консьюмер добавляется без изменений в продюсере.
*   Плюсы: слабая связанность, продюсеру плевать, жив ли консьюмер — сообщение дождется его в топике; естественная буферизация пиков нагрузки; replay истории событий.
*   Минусы: сложнее отладка (нужна трассировка, вопрос 18), нет мгновенного ответа, приходится думать про дубли (вопрос 16), порядок (вопрос 21) и DLQ — dead-letter topic, отдельный топик, куда укладываются сообщения, которые консьюмер не смог обработать после N попыток (например, poison pill с битым форматом), чтобы они не блокировали партицию вечными ретраями. DLQ потом разбирают руками или отдельным процессом.

Цена событий — **eventual consistency**: в момент после публикации события разные сервисы видят разное состояние, согласованность наступает «в конечном счете». Пользователь оформил заказ, а письмо-подтверждение придет через секунду — это нормально для такого дизайна, но бизнес и UI должны быть готовы (статусы вида «обрабатывается», компенсации через Saga).

Эвристика выбора: вопрос («дай данные», «можно ли?») — синхронный вызов; факт («случилось то-то») — событие. На практике системы почти всегда гибридные: REST/gRPC на критичном синхронном пути запроса пользователя, Kafka для всего, что может подождать.

### 23. CQRS и Event Sourcing: разделение команд и запросов

**CQRS (Command Query Responsibility Segregation)** — разделение модели данных на две: **командную** (запись, изменение состояния) и **запросную** (чтение). Команды (`CreateOrder`, `CancelOrder`) меняют состояние и ничего не возвращают; запросы читают и не меняют ничего.

Уровни применения, от простого к сложному:

1. **Логический CQRS** — одна БД, но разные модели: для чтения пишутся прямые запросы/DTO-проекции, минуя слой доменных сущностей (не гонять Hibernate-граф ради таблицы на экране). Это дёшево и полезно почти всегда.
2. **Физический CQRS** — отдельные хранилища: запись в PostgreSQL, чтение из денормализованного представления (Elasticsearch, Redis, материализованная read-модель), синхронизация через события. Можно независимо масштабировать чтение и запись и оптимизировать схему под каждую нагрузку.

Цена: eventual consistency между write- и read-моделью (запись есть, в выдаче появится через миллисекунды-секунды), вторая инфраструктура, консистентность проекций при сбоях. CQRS оправдан при сильно асимметричной нагрузке (чтений в 100 раз больше записей) и сложных отчётных запросах по горячей транзакционной базе. Для обычного CRUD это переусложнение — на собеседовании это стоит сказать прямо.

**Event Sourcing** — частый спутник CQRS: состояние сущности не хранится как строка в таблице, а восстанавливается из последовательности событий (`OrderCreated`, `OrderPaid`, `OrderShipped`). Текущее состояние — левая свёртка событий. Даёт бесплатный аудит-лог и возможность «отмотать время», но требует снапшотов для длинных историй, версионирования событий и меняет привычную модель мышления. На практике полный Event Sourcing встречается редко (финансы, биллинг), а вот связку «события → read-проекции» из физического CQRS — часто.

Частый follow-up: «чем событие в Event Sourcing отличается от события в Kafka?» В ES события — **источник истины** и единственное хранилище состояния; в event-driven интеграции события — сообщения между сервисами, а истина живёт в БД каждого сервиса.

### 24. Graceful Degradation и fallback-стратегии

**Graceful degradation (корректная деградация)** — система при отказе части компонентов продолжает работать с урезанной функциональностью вместо полного падения. Упавшие рекомендации не должны ронять страницу товара; отключение поиска не должно мешать оформить заказ.

Набор приёмов (по нарастанию «жёсткости»):

- **Fallback на кэш/дефолт:** при недоступности сервиса отдать закэшированный или статический ответ. Лента новостей часовой давности лучше, чем 500-ка.
- **Деградация функции:** некритичный блок отключается, критичный работает. На странице товара скрываем «похожие товары» и отзывы, но цена и кнопка «купить» живы.
- **Feature flags / kill switches:** заранее предусмотренные выключатели тяжёлых функций на время инцидента или пика нагрузки (на распродаже отключают персонализацию).
- **Load shedding:** отбрасывание части нагрузки осознанно — вернуть 503 быстро, чем утонуть в очередях (связано с Rate Limiter из вопроса 13).

Связь с уже разобранными паттернами: fallback — это «действие при разомкнутом Circuit Breaker» (вопросы 12–13); Bulkhead не даёт одному умирающему сервису съесть все потоки и тем самым сохраняет остальную функциональность. То есть graceful degradation — не отдельная библиотека, а проектное решение: для каждой внешней зависимости заранее ответить на вопрос «что покажем пользователю, когда она лежит?».

Два требования, без которых деградация не работает: критичные и некритичные функции должны быть **разведены по разным путям** (если рекомендации и заказ идут через один общий сервис/БД, деградировать нечем), и fallback-ответы должны быть **честными** (заглушка «0 товаров» вместо ошибки — это не деградация, а обман, который маскирует инцидент).

Частый follow-up: «как тестировать деградацию?» — fault injection: гасить зависимость (Chaos Monkey, Toxiproxy, tc netem) и проверять, что пользовательский сценарий выживает в урезанном виде, а не падает целиком.
